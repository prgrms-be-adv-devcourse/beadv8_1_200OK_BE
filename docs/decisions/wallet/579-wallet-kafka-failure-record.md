## 배경

팀은 모듈 간 생성·수정을 메시지 브로커로 옮기고 Spring 이벤트를 없애기로 했다. 정산은 지갑 전환을 기다리며 같은 정산을 Kafka와 Spring 이벤트 두 길로 보내고 있었다(#339).
Spring 이벤트는 리스너가 실패하면 `event_publication`에 미완료로 남아 다시 처리되지만, Kafka 기본 오류 처리는 간격 없이 10번 시도한 뒤 로그만 남기고 건너뛴다. Spring 리스너를 지우는 순간부터 DB가 몇 초 끊기기만 해도 정산금 입금 메시지가 사라질 수 있었다.
범위: 정산금 확정 수신, 지갑 전용 실패 처리, Spring 리스너 삭제. 범위 밖: 환불 반환 수신(#34, 이 실패 처리를 씀), 주문 생성·결제 결과(주문 쪽 Kafka 전환 뒤 따로 이슈), 실패 기록 자동 재처리·알림, 보내는 쪽 전달 보장.

## 버린 대안

- **팀 공통 실패 처리를 먼저 만들기(#382·#388과 함께):** 시점이 지갑 전환보다 늦고, 공통 DLT 방식은 위 "실패를 두는 곳"의 이유로 고르지 않았다. 감수하는 것은 지갑만 다른 실패 보관 방식을 쓴다는 점. `[WALLET_MESSAGE_FAILED]` 로그로 흐름 로깅(#375)과 알림이 지갑 실패를 찾게 한다.
- **실패 기록 표에 받은 바이트 그대로 보관:** 리스너가 DTO 대신 원본 레코드를 받아야 해서 받는 코드가 길어진다. 감수하는 것은 원문의 띄어쓰기·필드 순서가 받은 것과 다를 수 있고, 지갑 DTO에 없는 필드(정산이 나중에 더한 필드 등)는 읽을 때 버려져 기록에서 빠진다는 점. 다시 JSON으로 쓰지 못하면 값의 문자열로 남겨 기록이 막히지 않게 한다.
- **입력 어댑터에서 서비스 대신 저장소 직접 호출:** 구조 규칙(입력 어댑터는 유스케이스 포트만 안다)에 어긋나 입력 포트 `MessageFailureUseCase`를 두었다.

## 건드릴 때 주의

- 새 `@KafkaListener`에는 `groupId = WalletKafkaTopics.CONSUMER_GROUP`과 `containerFactory = WalletKafkaConsumerConfig.LISTENER_CONTAINER_FACTORY`를 꼭 적는다. 빠뜨려도 동작은 해서 오류 없이 메시지를 나눠 갖거나 실패를 건너뛴다.
- 지갑 수신 설정의 빈 이름을 기본 이름(`kafkaListenerContainerFactory`)으로 바꾸면 수신 설정을 고르지 않은 다른 모듈 리스너가 지갑 설정을 쓰게 된다. `PayoutKafkaListenerIntegrationTest`가 막는다.
- 리스너의 값 검사는 서비스를 부르기 전에 끝낸다. 트랜잭션 안에서 실패하면 롤백되어 지갑이 남지 않지만 실패 이유가 값 오류가 아닌 것으로 기록된다.
- 새 그룹은 토픽의 처음부터 읽는다. 정산 확정은 11-03 이후 메시지가 다시 오지만 지갑을 잠근 뒤 `PAYOUT:{payoutId}` 원장으로 막아 한 번만 입금된다. 새 토픽을 받을 때도 처음부터 다시 와도 안전한지 먼저 본다.
- 실패 기록은 잔액과 관계가 없어 `WalletTestDataCleaner`가 지우지 않는다. 이 표를 쓰는 시험은 따로 지운다.
- 배포 전 지운 Spring 리스너 앞으로 남은 미완료 이벤트를 확인한다(`event_publication`에서 `listener_id`가 `com.ok.wallet.adapter.in.event.PayoutEventListener`로 시작하고 `completion_date`가 빈 행). 리스너가 없어지면 받을 곳이 없다.

## 후속 (2026-11-16)

- 위 "다시 시도: 1·2·4초 3번"에 예외를 하나 더했다(#638). 처리 뒤 결과를 Kafka로 보내다 잠깐 실패하면 1초부터 두 배씩, 최대 1분 간격으로 간격 합 30분까지 다시 시도한 뒤 기록한다. 결과를 보내는 수신부(환불 반환 #34, 입금 확인 #613, 주문 결제 #614)가 늘어, 브로커가 1분만 불안정해도 돈은 움직였는데 결과가 나가지 않은 채 기록으로 넘어갔기 때문이다. DB 장애 때 막혀 있는 것을 의도한 동작으로 본 것(#637)처럼, Kafka가 없으면 결과를 보낼 수 없으니 돌아올 때까지 기다린다.
- "잠깐 실패"는 원인을 끝까지 따라가 Kafka가 다시 하면 될 수 있다고 표시한 오류(`RetriableException`)와 저장 확인 시간 초과(`java.util.concurrent.TimeoutException`)로 가린다. 보내는 쪽에 전용 예외를 두지 않은 이유는 받는 쪽(`adapter.in`)이 보내는 쪽(`adapter.out`) 패키지를 쓰지 않는 구조 규칙 때문이고, 보내기 예외가 브로커가 준 원인을 그대로 담아(#669) 원인만 보면 된다. 메시지 크기 초과 같은 영구 실패는 30분 붙잡으면 같은 파티션의 뒤 메시지가 모두 멈춰 1·2·4초 규칙을 그대로 쓴다.
- 30분까지인 이유: 그 뒤에는 주문이 결제 만료를 요청해 지갑이 처음 결과를 다시 보낸다. 최대 1분인 이유: 오류 처리기는 소비자 스레드에서 간격만큼 잠들어(spring-kafka 4.1.1), 간격과 한 번 보내는 데 걸리는 시간의 합이 `max.poll.interval.ms`(5분)를 넘으면 소비자가 그룹에서 빠졌다 다시 들어와 같은 메시지를 다시 처리한다. 한 번 보내기는 토픽 정보를 모르면 저장 확인(10초)을 기다리기 전에 토픽마다 `max.block.ms`(1분)까지 멈춘다. 앱을 띄운 뒤 그 토픽에 처음 보낼 때 브로커가 없으면 생기고, Kafka를 일시 정지한 로컬 확인에서 60초 멈춤을 봤다. 두 토픽에 보내는 동안 합은 1분 + 1분 × 2 + 10초 = 약 3분이다. `max.block.ms`는 모든 모듈이 같이 쓰는 설정(`common-kafka.yaml`)이라 줄이지 않았다.
- 30분은 간격의 합으로 센다. 시도마다 보내기에 걸린 시간이 더해져 끝내 실패하면 실제로는 30분보다 더 걸린다. 시도마다 `[WALLET_SEND_RETRY]` WARN 로그를 남기고, 끝내 실패하면 지금처럼 실패 기록과 `[WALLET_MESSAGE_FAILED]` ERROR 로그가 남는다.
- 간격 규칙은 한 메시지가 처음 실패할 때 고르고, 같은 종류의 예외로 다시 실패하는 동안 이어 쓴다. 지갑은 보내기 실패와 다른 오류 일부를 같은 `IllegalStateException`으로 올려, 처음에 보내기 실패였다가 다음 시도에 다른 오류가 나도 긴 간격이 이어질 수 있다. 이때도 메시지를 잃지 않고 30분 뒤 기록된다.
- 건드릴 때 주의: 기본 간격을 "다시 시도 없음"으로 바꾸면 오류 처리기가 간격을 고르지 않고 바로 기록해 긴 간격이 쓰이지 않는다. 보내기 대기(`WalletKafkaSender.SEND_TIMEOUT`)를 늘리거나 한 메시지를 보내는 토픽 수가 바뀌면(옛 이름 발행을 지우면 1개) `WalletKafkaConsumerConfigTest`에 적은 값도 함께 고친다.

## 후속 (2026-11-17)

- 위 "건드릴 때 주의"의 `groupId = WalletKafkaTopics.CONSUMER_GROUP` 안내를 바꾼다(#669). 그룹 `wallet` 하나를 리스너마다 나눴다(#648 규칙 `<모듈>.<용도>`). 새 `@KafkaListener`는 `WalletKafkaTopics`에 자기 그룹 상수를 더해 `groupId`에 적고, `containerFactory`는 그대로 지갑 수신 설정을 적는다. 받는 토픽 이름은 `.v1`이다.
- 그룹을 나눈 이유: 한 그룹을 함께 쓰면 한 리스너만 다시 읽거나 밀린 메시지를 리스너별로 볼 수 없다.
- 그룹을 새로 만들면 그 토픽을 처음부터 읽는다(위 "새 그룹은 토픽의 처음부터 읽는다"와 같음). 이번 새 그룹 3개도 옛 그룹이 처리한 메시지를 다시 받지만, 정산금은 `PAYOUT:{payoutId}` 원장, 환불 반환은 `refundId`로 한 번만 반영되고 입금 확인은 읽기만 한다. 배포 전 옛 그룹 `wallet`의 밀린 메시지가 0인지 확인한다.
- 옛 이름 발행을 지웠다(#669 PR 3). 지갑이 보내는 토픽은 모두 `.v1` 하나라, 위 후속(2026-11-16)의 "두 토픽에 보내는 동안 합은 약 3분"은 토픽 하나 기준 약 2분 10초(간격 1분 + 토픽 정보 대기 1분 + 저장 확인 10초)가 됐다. 한 메시지를 여러 토픽에 보내게 되면 토픽 수만큼 토픽 정보 대기가 늘어나니 `WalletKafkaConsumerConfigTest`의 계산도 함께 고친다.

## 후속 (2026-11-20)

- 위 "실패를 두는 곳"의 이유 중 "같은 토픽을 받는 다른 모듈에 중복이 가지 않는다"는 원래 토픽으로 다시 보내거나 그룹 구분 없는 실패 토픽(`<토픽>.DLT`)에 견준 이유다. 그룹별 실패 토픽(`<토픽>.<그룹>.DLT`)도 다른 모듈에 가지 않아, DB 표를 고른 이유가 되지 못한다(11-15 멘토 리뷰 지적). "버린 대안"에서 공통 DLT를 이 이유들로 고르지 않았다고 적은 것도 그룹별 DLT에는 이 이유가 해당하지 않는다.
- 그룹별 DLT와 견줘도 남는 이유는 둘이다.
  - SQL로 바로 찾고, 처리 기록(`wallet_order_payment`, `wallet_order_refund`, `wallet_order_refund_revert`)·원장과 이어 붙여 이미 풀린 기록을 거른다. 거르는 SQL은 `docs/DEVELOPMENT.md` 지갑 절 "실패 기록 처리 순서"에 있다.
  - Kafka 장애와 분리된다. 결과를 Kafka로 보내다 실패해 기록하는 경우(#638)는 Kafka가 문제라 DLT로 보내기도 실패한다.
- 그룹별 DLT로 바꾸자는 #637은 보류했다. 그 이슈가 걱정한 "DB 장애 때는 같은 DB에 기록하지 못한다"는 DLT로 바꿔도 남는다. DB가 없으면 지갑은 어차피 처리할 수 없고, 기록마저 실패하면 오프셋을 옮기지 않아 메시지를 잃지 않는다(위 "기록마저 실패", `WalletKafkaConsumerConfigTest`). DB가 살아나면 이어서 처리되거나 기록된다.
