## 배경

팀은 모듈 간 생성·수정을 메시지 브로커로 옮기고 Spring 이벤트를 없애기로 했다. 정산은 지갑 전환을 기다리며 같은 정산을 Kafka와 Spring 이벤트 두 길로 보내고 있었다(#339).
Spring 이벤트는 리스너가 실패하면 `event_publication`에 미완료로 남아 다시 처리되지만, Kafka 기본 오류 처리는 간격 없이 10번 시도한 뒤 로그만 남기고 건너뛴다. Spring 리스너를 지우는 순간부터 DB가 몇 초 끊기기만 해도 정산금 입금 메시지가 사라질 수 있었다.
범위: 정산금 확정 수신, 지갑 전용 실패 처리, Spring 리스너 삭제. 범위 밖: 환불 반환 수신(#34, 이 실패 처리를 씀), 주문 생성·결제 결과(주문 쪽 Kafka 전환 뒤 따로 이슈), 실패 기록 자동 재처리·알림, 보내는 쪽 전달 보장.

| 실패를 두는 곳 | 지갑 DB `wallet_message_failure` 표 (실패 토픽 아님) | Kafka가 멈춰도 남고, 원래 토픽으로 다시 보내지 않아 같은 토픽을 받는 다른 모듈에 중복이 가지 않으며, SQL로 바로 찾는다 (사용자 결정) |

| 기록마저 실패 | 예외를 던져 오프셋을 옮기지 않음 | 오류 처리기는 기록 단계가 예외를 던지면 같은 위치로 되돌린다. DB가 살아나면 다시 처리되거나 기록된다 |
| 같은 메시지 두 번 기록 | 토픽·파티션·오프셋 유니크, 있으면 넘김. 원문이 다르면 원문을 담은 `[WALLET_MESSAGE_FAILED]` ERROR 로그 | 기록 뒤 오프셋을 옮기기 전에 멈추면 같은 메시지가 다시 실패해 온다. 한 파티션은 한 곳에서만 처리하므로 확인과 넣기 사이에 끼어들지 않는다. 토픽을 새로 만들거나 Kafka 볼륨만 지우면 오프셋이 다시 매겨져 다른 메시지가 같은 위치에 올 수 있어, 그때는 묻히지 않게 로그로 남긴다(자동 리뷰 반영) |

| 실패 이유 | 가장 안쪽 원인의 예외 이름과 메시지 | 겉포장(리스너 실패)만 남으면 원인을 알 수 없다 |
| 값이 틀린 정산 | 입금하지 않고 원문과 함께 기록 (예전에는 로그만 남기고 건너뜀) | 건너뛴 정산은 지갑 원장에 흔적이 없어 로그를 뒤져야 했다 |
| 상태 값 | `PENDING`, `RESOLVED`만 | 지금은 사람이 처리하고 해결로 바꾼다. 재처리 횟수 칸과 사람 확인 상태는 자동 재처리를 만들 때 더한다 |
| 그룹 | `wallet`을 리스너에 직접 적음 | 공통 설정의 기본 그룹은 앱 이름이라 monolith에서 모듈끼리 메시지를 나눠 갖는다 |
| 리스너 이름 | `PayoutKafkaListener` | Spring 리스너와 한 커밋 동안 함께 있어야 해서 구분했다. 정산·환불 모듈의 `*KafkaListener`와 같다 |

## 버린 대안

- **팀 공통 실패 처리를 먼저 만들기(#382·#388과 함께):** 시점이 지갑 전환보다 늦고, 공통 DLT 방식은 위 "실패를 두는 곳"의 이유로 고르지 않았다. 감수하는 것은 지갑만 다른 실패 보관 방식을 쓴다는 점. `[WALLET_MESSAGE_FAILED]` 로그로 흐름 로깅(#375)과 알림이 지갑 실패를 찾게 한다.
- **실패 기록 표에 받은 바이트 그대로 보관:** 리스너가 DTO 대신 원본 레코드를 받아야 해서 받는 코드가 길어진다. 감수하는 것은 원문의 띄어쓰기·필드 순서가 받은 것과 다를 수 있고, 지갑 DTO에 없는 필드(정산이 나중에 더한 필드 등)는 읽을 때 버려져 기록에서 빠진다는 점. 다시 JSON으로 쓰지 못하면 값의 문자열로 남겨 기록이 막히지 않게 한다.
- **입력 어댑터에서 서비스 대신 저장소 직접 호출:** 구조 규칙(입력 어댑터는 유스케이스 포트만 안다)에 어긋나 입력 포트 `MessageFailureUseCase`를 두었다.

## 건드릴 때 주의

- 새 `@KafkaListener`에는 `groupId = WalletKafkaTopics.CONSUMER_GROUP`과 `containerFactory = WalletKafkaConsumerConfig.LISTENER_CONTAINER_FACTORY`를 꼭 적는다. 빠뜨려도 동작은 해서 오류 없이 메시지를 나눠 갖거나 실패를 건너뛴다.
- 지갑 수신 설정의 빈 이름을 기본 이름(`kafkaListenerContainerFactory`)으로 바꾸면 수신 설정을 고르지 않은 다른 모듈 리스너가 지갑 설정을 쓰게 된다. `PayoutKafkaListenerIntegrationTest`가 막는다.
- 리스너의 값 검사는 서비스를 부르기 전에 끝낸다. 트랜잭션 안에서 실패하면 롤백되어 지갑이 남지 않지만 실패 이유가 값 오류가 아닌 것으로 기록된다.
- 새 그룹은 토픽의 처음부터 읽는다. 정산 확정은 11-03 이후 메시지가 다시 오지만 지갑을 잠근 뒤 `PAYOUT:{payoutId}` 원장으로 막아 한 번만 입금된다. 새 토픽을 받을 때도 처음부터 다시 와도 안전한지 먼저 본다.
- 실패 기록은 잔액과 관계가 없어 `WalletTestDataCleaner`가 지우지 않는다. 이 표를 쓰는 시험은 따로 지운다.
- 배포 전 지운 Spring 리스너 앞으로 남은 미완료 이벤트를 확인한다(`event_publication`에서 `listener_id`가 `com.ok.wallet.adapter.in.event.PayoutEventListener`로 시작하고 `completion_date`가 빈 행). 리스너가 없어지면 받을 곳이 없다.
