> 이 문서는 #613 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

정산은 매일 "이 정산들이 지갑에 입금됐는지"를 `payout.payout-deposit-check-requested`로 묶어(최대 500건) 묻는다. 정산은 모듈 경계 때문에 지갑 표를 직접 읽을 수 없다. 지갑은 판매자 원장에서 `PAYOUT:{payoutId}`를 찾아 `wallet.payout-deposit-checked`로 답한다. 메시지 모양은 정산 대사 문서(PR #548 4절)와 정산 구현(#619)에 맞췄다.

범위 밖: 판정·다시 묻기·관리자 확인(정산 #619), 정산이 모르는 `PAYOUT` 입금 찾기(11/15 합의로 뺌), 환불·주문·토스 대사.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 지갑의 역할 | 원장을 읽기만 하고 판정하지 않음 | 판정 기준(판매자·금액 비교, 횟수)은 정산이 가진다. 읽기만 하면 같은 묶음이 다시 와도 같은 답이 가고 잔액이 바뀌지 않는다 |
| 원장 조회 | 근거 키 목록으로 원장과 지갑 회원 ID를 한 번에 읽고 500건씩 나눔 | 항목마다 조회하면 묶음 하나에 500번 조회한다. 500건보다 많이 와도 거절하지 않고 나눠 읽어 조회 조건이 한없이 길어지지 않게 한다 |
| 서비스 트랜잭션 | `@Transactional` 없음 | 답을 보내며 저장 확인을 기다리는 동안 DB 연결을 붙잡지 않는다. 원장은 추가만 되므로 나눠 읽어도 이미 읽은 사실이 바뀌지 않는다 |
| 답 보내기 | 읽음 처리 전에 보내고 저장 확인까지 기다림, 실패하면 예외로 다시 받음 | #34 환불 결과와 같은 방식이다. 답은 원장을 읽은 사실이라 두 번 가도 정산 판정이 달라지지 않아 outbox가 필요 없다 |
| 보내기 코드 | 환불 결과 보내기에서 저장 확인 대기·시간 초과·예외 바꾸기를 `WalletKafkaSender`로 빼서 함께 씀 (사용자 승인) | 두 곳에 같은 25줄을 두면 대기 시간이나 예외 처리를 바꿀 때 한쪽만 고쳐 어긋난다 |
| 틀린 묶음 | 묶음 번호 없음, 항목 없음·0건은 답하지 않고 실패 기록 표(#584)에 남김 | 묶음 번호가 없으면 어디에 답할지 모른다. 정산은 빈 묶음을 보내지 않는다(#619 코드 확인) |
| 틀린 항목 | 정산 ID 없는 항목만 로그를 남기고 답에서 뺌 | 항목 하나 때문에 묶음 전체를 실패로 보내면 나머지 정산도 답을 못 받는다. 정산은 답 없는 정산을 다음 날 다시 묻는다 |
| 로그 | 정산이 기대하는 판매자·금액은 뺀 항목에만 남김 | 모든 항목을 남기면 묶음마다 500줄이 된다 |
| 같은 정산이 묶음에 두 번 | 한 번만 조회하고 묻는 대로 각각 답함, 요청 순서 유지 | 정산이 보낸 모양 그대로 돌려줘야 정산이 맞춰 보기 쉽다 |
| 이름 | 리스너·서비스에 `Wallet`을 붙이고 토픽 생성 빈은 `walletOutboundPayoutDepositCheckedTopic` | 정산 #619에 같은 이름의 리스너·서비스·토픽 빈이 있어, 모든 모듈을 함께 띄우는 앱이 빈 이름 충돌로 시작되지 않았다(monolith 시험으로 확인). 팀 규칙대로 빈 이름에 모듈 이름을 붙였다 |
| 연결 시험 | monolith에서 정산이 묻고 지갑이 답해 "일치"가 되는지 시험 추가 (사용자 결정) | 두 모듈이 각자 JSON 모양만 시험하면 이름 충돌이나 실제 왕복 문제를 못 잡는다. 지갑이 금액을 틀리게 보내면 이 시험이 실패하는 것을 확인했다 |

## 버린 대안

- **보내기 코드 복사:** 정산 답 보내기에 환불 결과의 코드를 그대로 두는 방법은 같은 대기·예외 처리가 두 곳에 생겨 버렸다. 감수하는 것은 환불 결과 보내기 시험이 만드는 줄 하나 바뀐 것뿐이다.
- **틀린 항목이 있으면 묶음 전체 실패:** 단순하지만 나머지 정산까지 하루씩 늦어져 버렸다.
- **"없음" 경우의 monolith 시험:** 입금이 Kafka로 자동으로 되어, "없음"을 만들려면 지갑 원장을 억지로 지워 잔액과 원장이 어긋난다. "없음" 판정은 정산 쪽 시험이 본다.

## 건드릴 때 주의

- 답 메시지(`PayoutDepositCheckedMessage`)의 필드 이름·타입은 정산과의 약속이다. 정산은 `found`가 true인데 판매자·금액이 비면 그 항목을 버리므로, 원장을 읽는 조회에서 지갑 회원 ID를 빼면 안 된다.
- 입금 시각은 원장 `created_at`이고 오프셋 없는 시각 글자로 나간다. 모양은 `WalletPayoutDepositCheckServiceIntegrationTest`가 글자 그대로 본다.
- `WalletKafkaSender`의 10초 시간 초과는 받는 쪽이 같은 메시지를 여러 번 받아도 한 번만 반영하는 메시지에만 쓴다. 시간 초과 뒤 실제로는 저장됐을 수 있어 다시 보내면 두 번 가기 때문이다.
- 지갑 Kafka 빈·클래스를 새로 만들면 정산·환불에 같은 이름이 있는지 확인한다. 모듈 단독 시험에서는 드러나지 않고 monolith 시험에서만 드러난다.
- 입금 시각을 정하려고 원장을 SQL로 넣는 시험은 잔액과 맞지 않아 끝난 뒤 `deleteAll()`로 지운다(`verifyAndDeleteAll()` 아님).
