## 배경

환불 반환(#34)과 되돌리기(#611)는 잔액과 원장을 바꾸지만, 이용 내역은 세미 때 정한 대로 충전·결제만 보여 줘 내역이 잔액과 맞지 않았다. 환불 담당께 "이용 내역에 환불과 주문 번호를 표시한다"고 약속했다(11/04). 상품 이름은 주문 Kafka 전환 때 결제 요청에 주문 요약을 함께 보내기로 정했고, 주문은 #680부터 보낸다.

범위: 반환·되돌리기 줄 표시, 세 줄(결제·반환·되돌리기)의 주문 번호와 주문 요약, 요약 저장. 범위 밖: 판매자 이용 내역, 프런트 화면.

작업 순서는 #611을 먼저 머지하고 #609를 했다. #609를 먼저 하면 #611 머지 뒤 반환(+)만 보이고 되돌리기(−)는 숨는 시기가 생긴다(사용자 결정).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 되돌리기 줄 표시 | #609에서 반환 줄과 함께 보임 | 하나만 보이면 다시 가져간 환불이 내역에서 잔액과 맞지 않는다. #611 본문은 "따로"였으나 순서를 바꾸며 이 이슈로 옮겼다(사용자 결정) |
| 주문 요약 출처 | 주문이 결제 요청에 담은 값을 결제 처리 기록(`wallet_order_payment.order_summary`)에 저장 | 주문 시점 이름이 남고 조회 때 다른 모듈을 부르지 않는다(#614 협의, 주문 #680) |
| 반환·되돌리기 줄의 요약 | 반환 처리 기록에 따로 두지 않고 주문 번호로 결제 처리 기록을 찾음 | 같은 주문이면 요약이 같고, 저장 곳을 하나로 둔다 |
| 요약이 비었거나 120자를 넘을 때 | 비면 NULL, 넘으면 글자 수(코드 포인트)로 잘라 저장하고 결제는 그대로 | 보여 주기용 값이라 결제를 막지 않는다. 글자 수로 세야 이모지가 반으로 잘리지 않는다 |
| 조회 방식 | 한 페이지 분을 반환 처리 기록 한 번, 결제 처리 기록 한 번으로 읽음 | 줄마다 조회하면 페이지 크기만큼 조회가 는다 |
| 기록이 없거나 근거 키가 틀린 줄 | 그 값만 비우고 WARN 로그 | 한 줄 때문에 목록 전체를 못 보게 하지 않는다. 결제 줄의 기존 방식과 같다 |

## 버린 대안

- **되돌리기 줄을 나중에 따로 표시:** #611 본문의 원래 계획. 그 사이 내역이 잔액과 어긋나 버렸다.
- **긴 요약을 DB에 맡김:** 기록 넣기가 `INSERT IGNORE`라 긴 값도 DB가 잘라 넣지만 경고로만 남는 동작이라 기대지 않았다.
- **긴 요약이면 결제 거절:** 보여 주기용 값 때문에 결제가 실패하면 안 된다(이슈 완료 조건).
- **기록이 없으면 목록 조회 실패:** 이슈 완료 조건에 따라 버렸다. 감수하는 것은 주문 번호·요약이 빈 줄이 조용히 보일 수 있다는 점이고, WARN 로그로 찾는다.

## 건드릴 때 주의

- 줄과 주문 번호는 근거 키로 짝짓는다. 한 환불의 반환(`REFUND:{refundId}`)과 되돌리기(`REFUND_REVERT:{refundId}`)는 환불 ID가 같아, 환불 ID로 짝지으면 같은 페이지에서 한쪽이 덮인다. 원장 근거 키가 전체에서 하나뿐이라는 전제(유니크 제약)에 기댄다.
- 원장 유형을 새로 만들면 `WalletLedgerService`의 보여 주는 유형, API 문서(`LedgerHistoryRequest`·`LedgerHistoryResponse`), 잔액 검사 SQL을 함께 정한다. switch 문이 유형을 모두 다뤄 빠뜨리면 컴파일이 막힌다.
- 주문 요약은 결제 처리 기록의 구매자가 지갑 주인과 같을 때만 붙인다. 지금은 반환이 결제한 구매자에게만 돌려줘(`BuyerWalletService.refundForOrder`) 늘 같지만, 그 규칙에 기대지 않으려는 확인이다(PR 리뷰 반영). 반환 규칙을 바꿔도 이 확인은 지우지 않는다.
- 결제 처리 기록 넣기는 네이티브 SQL이라 칸을 더하면 `WalletOrderPaymentJpaRepository.insertIfAbsent`도 고친다. 만료로 먼저 남기는 기록은 요약을 넣지 않는다.
