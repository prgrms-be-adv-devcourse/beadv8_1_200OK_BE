## 배경

처음에는 모든 회원이 가입한 순간부터 지갑을 갖게 했다. 지갑이 늘 있다고 믿을 수 있으면 조회·충전·결제가 지갑이 없는 경우를 다루지 않아도 되기 때문이다. 가입 처리에서 지갑을 직접 만들면 회원 모듈이 지갑 모듈에 기대게 되므로, 회원은 가입·판매자 승인 사실만 알리고 지갑이 이벤트를 받아 만들게 했다.

가입이 확정된 뒤 받는 이벤트는 바로가 아니라 조금 뒤에 처리되어, 그 사이에 온 조회가 실패했다. 그래서 조회는 지갑이 없으면 0원·빈 목록으로 답하고, 돈이 움직이는 곳은 지갑이 없으면 만들게(`getOrCreate`) 바꿨다. 그 결과 회원 이벤트로 미리 만드는 길은 없어도 결과가 같아졌다.

범위는 지갑 쪽 수신부와 입력 포트를 지우는 것까지다. 회원 쪽 이벤트 발행, API, DB는 그대로다. 판매자 승인 이벤트 발행을 지울지는 회원 담당이 정한다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 지갑을 만드는 때 | 돈이 처음 움직일 때 `getOrCreate`로만 만듦 (사용자 결정) | 실제로 처음 만드는 곳은 두 곳이다. 구매자 지갑은 충전 승인을 시작할 때(토스에 승인을 요청하기 전), 판매자 지갑은 첫 정산금 입금 때다(코드에서 확인). 만드는 길이 둘이면 "가입했으면 지갑이 있겠지"라는 전제가 새 코드에 다시 생길 여지가 남는다. 처음 조회가 실패한 원인이 바로 그 전제였다. 서비스를 나누면 회원 이벤트는 두 서비스가 함께 지켜야 하는 약속이 되는데, 지갑은 이 이벤트 없이도 같은 결과를 낸다 |
| 입력 포트 `createIfAbsent` | 구매자·판매자 모두 지움 (#450의 결정을 바꿈) | 부르던 곳이 회원 이벤트 리스너뿐이었다 |
| 회원 ID 확인 | `getOrCreate`에서 null이면 `IllegalArgumentException` | 그대로 두면 DB의 NOT NULL 제약 오류로 끝나 호출하는 쪽의 잘못인지 DB 문제인지 알기 어렵다(고치기 전 시험으로 확인) |
| 넣기 메서드 | `getOrCreate` 안으로 합침 | 따로 둔 이유가 "만드는 길 둘을 하나로 모은다"였는데 부르는 곳이 하나만 남았다 |
| 새 기능의 저장 위치 | 지갑이 없어도 뜻이 있는 정보는 회원 ID로 따로 저장. 지갑 자체의 상태를 바꾸는 기능만 `getOrCreate`를 거침 | 약관 동의가 이미 이 방식이다(회원 ID로 저장하고 충전 요청 때 회원 ID로 확인). "지갑이 먼저 있어야 하는 기능"이 지갑을 바꾸는 입구 하나로 모여 만들기를 빠뜨릴 곳이 없어진다 |
| 판매자 승인 확인 | 판매자 `getOrCreate`에 넣지 않음 | 지금은 정산금 입금에서만 부르고, 정산은 승인된 판매자에게만 온다 |

## 버린 대안

- **회원 이벤트를 보완 길과 함께 남기기:** 결과가 같은데 위의 전제와 서비스 사이 약속만 남아 버렸다. 감수하는 것은 지갑이 돈을 움직인 회원에게만 생겨 지갑 수가 가입자 수와 같지 않은 것이다. 가입자 수는 회원 쪽에서 센다.
- **"한도 초과로 승인 시작이 실패하면 지갑이 남지 않는다"를 이유로 이벤트 남기기:** 실패하면 돈이 움직이지 않아 지갑이 필요 없다(잔액 0원, 빈 목록, 다음 충전에서 생김). 지갑 없는 회원은 잔액 0원이고 처리 중 충전도 없어, 승인 시작의 한도 확인은 충전 요청 단계의 같은 기준을 이미 통과한 금액만 받는다.
- **동시 첫 요청 대비 코드 추가:** "중복이면 무시" 넣기와 잠금 조회로 이미 한 줄로 처리된다. 구매자는 기존 동시 생성 시험이, 판매자는 이번에 더한 동시 입금 시험이 지킨다. 판매자 시험은 "중복이면 무시"를 빼면 실패하는 것을 확인했다.

## 건드릴 때 주의

- 지갑 행에 상태를 다는 새 기능(지갑 정지 등)은 `getOrCreate`로 지갑을 가져온다. 잠금 조회를 바로 쓰면 지갑이 아직 없는 회원에게서 실패한다.
- 결제가 지갑 없이 오지 않는 것은 주문 쪽의 주문 전 잔액 확인(`OrderFacade`) 덕분이다. `payForOrder` 자체는 약관 동의를 확인하지 않고 지갑을 만든다. 주문 쪽 확인이 바뀌면 약관에 동의하지 않은 회원에게도 0원 지갑이 생길 수 있다.
- 판매자 승인 이벤트는 지금 받는 곳이 없다. 출금이나 판매자 권한 회수를 만들 때, 승인·회수 이벤트를 받아 판매자 상태를 지갑이 따로 보관하는 방법을 고르면 승인 이벤트도 다시 받아야 한다(회수만으로는 "지금 판매자인가"를 알 수 없다). 그래서 회원 쪽에 발행을 지우지 말아 달라고 전한다. 출금할 때마다 회원 쪽에 묻는 방법을 고르면 필요 없다.
- 판매자 잔액 조회는 로그인 토큰의 판매자 권한만 본다. 출금도 이 방식만 쓰면 권한이 회수돼도 이미 받은 토큰이 만료될 때까지 출금할 수 있다.
- 지갑의 회원 이벤트 리스너가 없어졌으므로, 배포 전에 그 리스너 앞으로 남은 미완료 이벤트(`event_publication`)가 없는지 본다. 운영은 재시작 때 미완료 이벤트를 다시 보내므로 남아 있으면 받을 곳이 없는 기록이 된다.
