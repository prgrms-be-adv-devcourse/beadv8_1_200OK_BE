## 배경

주문은 결제를 요청하고 30분이 지나면 혼자 주문을 취소했다. 그 뒤 지갑이 결제하면(결과 보내기 실패 후 다시 받음 등) 구매자는 상품 없이 예치금을 잃는다. 돈이 움직였는지는 지갑만 알므로, 주문은 취소 대신 결제 만료를 요청하고 결과는 지갑이 정하기로 주문 담당과 합의했다(#656, 11/16).
범위: 만료 요청 수신, 처리 기록 상태 `EXPIRED`와 실패 사유 `PAYMENT_EXPIRED`, 만료된 주문의 늦은 결제 요청 막기. 범위 밖: 주문의 만료 요청 발행(#684), 늦게 온 결제 돌려주기(#612, 이 방식으로 필요 없어짐).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 처음 보는 주문 | 만료(`EXPIRED`)로 처리 기록을 먼저 넣고 결제 실패 `PAYMENT_EXPIRED`를 보냄 | 기록이 있어야 늦게 온 결제 요청을 처리 기록 넣기가 걸러 차감하지 않는다. "취소·실패된 주문에 결제 완료"가 생기지 않는다 (주문 담당 합의) |
| 이미 처리한 주문 | 아무것도 바꾸지 않고 처음 결과(결제 완료·잔액 부족·만료)를 다시 보냄 | 결제 요청과 같은 규칙(#614). 결제됐으면 주문은 30분이 지났어도 결제 완료로 끝낸다 |
| 만료 기록 금액 | 요청의 `totalAmount`(주문 생성과 같은 값) | 처리 기록 표는 금액이 필수이고 0보다 커야 한다. 금액을 받아 표를 바꾸지 않았다 (주문 PR #684에 요청해 더함) |
| 실패 사유 | 표에 사유 칸 없이 상태로 정함(`EXPIRED` → `PAYMENT_EXPIRED`) | 상태마다 사유가 하나다. `failureReason()`이 상태별 `switch`라 상태가 늘면 컴파일 오류로 드러난다 |
| 동시 요청 | 결제와 같은 순서로 구매자 지갑을 잠근 뒤 기록을 넣음 | 먼저 잠근 쪽 결과 하나만 남고, 잠그는 순서가 같아 서로 막혀 멈추지 않는다. 처리 기록의 주문 유니크 제약이 마지막 안전장치다 |
| 결과 보내는 때 | 기록을 커밋한 뒤, `Propagation.NEVER` | 결제 요청과 같은 이유(#614). 보내기 실패는 다시 받아 처음 결과를 다시 보낸다 |
| 받는 그룹 | `wallet.payment-expire` | #648 규칙(`<모듈>.<용도>`), 리스너마다 하나(#669) |
| 받는 토픽 생성 | 지갑도 앱 시작 때 만듦 | 지갑이 주문(#684)보다 먼저 머지되어 토픽이 없으면 리스너가 경고를 계속 찍는다. 주문이 결제 결과 토픽을 미리 만든 것과 같은 방식 |
| 상태 칸 | 타입·제약은 그대로, 설명만 마이그레이션 | `VARCHAR(20)`에 값 제약이 없어 `EXPIRED`를 그대로 넣을 수 있다 |

## 버린 대안

- **처음 보는 주문이면 기록 없이 실패만 보내기:** 늦게 온 결제 요청이 그대로 차감되어, 주문은 만료 실패로 끝났는데 돈이 빠진다.
- **실패 사유 칸을 표에 더하기:** 상태마다 사유가 하나라 칸이 필요 없다. 사유가 상태와 갈리면 그때 더한다.
- **지갑 잠금 없이 유니크 제약만으로 가르기:** 결과는 같지만, 결제와 다른 순서로 잡으면 잠금 순서를 따지기 어렵다. 결제와 같은 길로 맞췄다. 감수하는 것은 지갑이 없는 구매자의 만료 요청에도 빈 지갑이 생기는 점(처음 쓸 때 만드는 규칙과 같다).

## 건드릴 때 주의

- 머지 순서는 #640 → 이 PR → 주문 #684다. #684가 먼저 들어가면 주문이 취소하지 않고 만료만 요청하는데 받는 쪽이 없어 주문이 결제 대기에 묶인다.
- 처리 기록 상태를 더하면 `failureReason()`과 잔액·원장 검사 SQL(차감하지 않은 기록에 결제 원장이 붙었는지)도 함께 본다.
- 만료 처리에서 처리 기록 넣기 전에 잔액이나 원장을 바꾸지 않는다. 만료는 돈을 움직이지 않는다.
