> 이 문서는 #135 작업(PR 1, 복구)의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

토스 승인 응답을 받지 못하거나(시간 초과, 토스 오류, 그 사이 서버가 꺼짐) 반영에 실패한 충전 건은 처리 중으로 남는다. 승인됐는지 모르는 채 실패로 바꾸면 돈은 빠졌는데 잔액이 늘지 않으므로 일부러 남겨 두지만, 지금까지는 이 건을 끝내는 곳이 없었다. 토스가 승인했으면 잔액이 영영 늘지 않고, 승인하지 않았으면 처리 중 금액이 보유 한도 계산에 계속 들어간다.
범위: 토스 결제 조회, 복구 대상 칸, 완료·실패 처리의 선점, 복구 서비스, 스케줄러. 범위 밖: 승인됐지만 반영하지 못한 결제의 토스 취소(PR 2), 대기 건 만료, 토스 호출량 보호(후속).

## 버린 대안

- **ShedLock으로 한 서버만 돌리기:** 잠금 표와 잠금 시간 계산이 늘고, 그래도 승인 응답과 복구가 겹치는 경우는 막지 못해 건 단위 선점이 따로 필요하다. 건마다 맡으면 두 경우를 같은 칸으로 다룬다. 감수하는 것은 서버마다 같은 목록을 한 번씩 읽는 일이다.
- **완료·실패도 조건부 UPDATE로:** 상태 규칙이 JPQL과 엔티티 두 곳에 나뉜다. 엔티티 메서드(`complete`, `fail`)를 그대로 쓰려고 잠금 조회를 골랐다.
- **멈춤 상태나 칸을 따로 두기:** 처리 중이 아닌 새 상태를 만들면 한도 합계·검사 SQL·상태 전이를 모두 고쳐야 한다. 다음 확인 시각을 비우는 것으로 충분했다.
- **마이그레이션에서 기존 처리 중 건의 확인 시각 채우기:** 배포와 함께 개수를 모르는 운영 데이터가 바뀌고, 배포 직후 그 건들을 한꺼번에 토스에 묻는다.
- **다시 확인을 다음 회차(1분 뒤)에:** 10번 상한을 15분 안에 다 써, 결제 없음 1시간 기준 전에 사람에게 넘긴다.

## 건드릴 때 주의

- 완료 처리는 승인 시작과 같은 순서(지갑 → 충전 건)로 잠근다. 반대로 하면 같은 건의 승인 요청이 겹칠 때 교착이 난다(시험으로 확인).
- 잠그기 전에 같은 트랜잭션에서 충전 건을 읽지 않는다. 먼저 읽으면 잠금 조회가 영속성 컨텍스트의 옛 상태를 돌려줘, 이미 실패한 건을 완료로 덮어쓴다(시험으로 확인). 그래서 완료 처리는 소유자를 잠근 뒤에 확인한다. 부르는 곳은 승인 흐름(승인 시작에서 소유자 확인)과 복구(충전 건에 적힌 회원)뿐이다.
- 맡기 조건(`next_check_at <= now`)을 바꾸면 두 서버가 같은 건을 함께 맡을 수 있다. 처리 중이 될 때의 첫 확인 지연(5분)은 승인 응답 대기(30초)보다 넉넉해야 한다.
- 결제 없음을 실패로 보는 1시간과 다시 확인 간격 10분·상한 10번은 함께 움직인다. 하나를 바꾸면 "상한을 다 쓰기 전에 1시간을 넘기는지"를 다시 계산한다.
- 배포 뒤: 배포 전부터 처리 중이던 건은 `docs/DEPLOY.md`의 절차로 개수를 확인한 뒤 확인 대상으로 바꾼다. 바꾸면 1분마다 50건씩 토스에 묻는다.
- 배포 뒤: `[CHARGE_RECOVERY_HOLD]`, `[CHARGE_RECOVERY_APPLY_FAILED]`, `[CHARGE_LONG_IN_PROGRESS]` 로그를 확인한다. 멈춘 건은 사람이 토스 결제를 확인해 처리하고, 처리 뒤 상태를 바꾼다.
