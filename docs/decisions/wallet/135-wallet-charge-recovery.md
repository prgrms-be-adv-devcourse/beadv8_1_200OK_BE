## 배경

토스 승인 응답을 받지 못하거나(시간 초과, 토스 오류, 그 사이 서버가 꺼짐) 반영에 실패한 충전 건은 처리 중으로 남는다. 승인됐는지 모르는 채 실패로 바꾸면 돈은 빠졌는데 잔액이 늘지 않으므로 일부러 남겨 두지만, 지금까지는 이 건을 끝내는 곳이 없었다. 토스가 승인했으면 잔액이 영영 늘지 않고, 승인하지 않았으면 처리 중 금액이 보유 한도 계산에 계속 들어간다.
범위: 토스 결제 조회, 복구 대상 칸, 완료·실패 처리의 선점, 복구 서비스, 스케줄러. 범위 밖: 승인됐지만 반영하지 못한 결제의 토스 취소(PR 2), 대기 건 만료, 토스 호출량 보호(후속).

## 버린 대안

- **ShedLock으로 한 서버만 돌리기:** 잠금 표와 잠금 시간 계산이 늘고, 그래도 승인 응답과 복구가 겹치는 경우는 막지 못해 건 단위 선점이 따로 필요하다. 건마다 맡으면 두 경우를 같은 칸으로 다룬다. 감수하는 것은 서버마다 같은 목록을 한 번씩 읽는 일이다.
- **완료·실패도 조건부 UPDATE로:** 상태 규칙이 JPQL과 엔티티 두 곳에 나뉜다. 엔티티 메서드(`complete`, `fail`)를 그대로 쓰려고 잠금 조회를 골랐다.
- **멈춤 상태나 칸을 따로 두기:** 처리 중이 아닌 새 상태를 만들면 한도 합계·검사 SQL·상태 전이를 모두 고쳐야 한다. 다음 확인 시각을 비우는 것으로 충분했다.
- **마이그레이션에서 기존 처리 중 건의 확인 시각 채우기:** 배포와 함께 개수를 모르는 운영 데이터가 바뀌고, 배포 직후 그 건들을 한꺼번에 토스에 묻는다.
- **다시 확인을 다음 회차(1분 뒤)에:** 10번 상한을 15분 안에 다 써, 결제 없음 1시간 기준 전에 사람에게 넘긴다.

## 건드릴 때 주의

- 완료 처리는 승인 시작과 같은 순서(지갑 → 충전 건)로 잠근다. 반대로 하면 같은 건의 승인 요청이 겹칠 때 교착이 난다(시험으로 확인).
- 잠그기 전에 같은 트랜잭션에서 충전 건을 읽지 않는다. 먼저 읽으면 잠금 조회가 영속성 컨텍스트의 옛 상태를 돌려줘, 이미 실패한 건을 완료로 덮어쓴다(시험으로 확인). 그래서 완료 처리는 소유자를 잠근 뒤에 확인한다. 부르는 곳은 승인 흐름(승인 시작에서 소유자 확인)과 복구(충전 건에 적힌 회원)뿐이다.
- 맡기 조건(`next_check_at <= now`)을 바꾸면 두 서버가 같은 건을 함께 맡을 수 있다. 처리 중이 될 때의 첫 확인 지연(5분)은 승인 응답 대기(30초)보다 넉넉해야 한다.
- 결제 없음을 실패로 보는 1시간과 다시 확인 간격 10분·상한 10번은 함께 움직인다. 하나를 바꾸면 "상한을 다 쓰기 전에 1시간을 넘기는지"를 다시 계산한다.
- 배포 뒤: 배포 전부터 처리 중이던 건은 `docs/DEPLOY.md`의 절차로 개수를 확인한 뒤 확인 대상으로 바꾼다. 바꾸면 1분마다 50건씩 토스에 묻는다.
- 배포 뒤: `[CHARGE_RECOVERY_HOLD]`, `[CHARGE_RECOVERY_APPLY_FAILED]`, `[CHARGE_LONG_IN_PROGRESS]` 로그를 확인한다. 멈춘 건은 사람이 토스 결제를 확인해 처리하고, 처리 뒤 상태를 바꾼다.

## 후속 (2026-11-18)

PR 2: 복구가 끝내지 못한 충전 건(멈춘 건, 승인 뒤 실패한 건)을 관리자가 처리하는 기능. 이슈 범위를 자동 취소에서 관리자 처리로 바꿨다(사용자 결정).

| 결정 | 선택 | 이유 |
|---|---|---|
| 자동 취소 | 하지 않음. 관리자가 토스 상태를 보고 반영·실패·결제 취소 중 고름 | 이슈가 든 자동 취소 예(같은 결제 키가 다른 지갑에 이미 있음)는 결제 키 유일 제약으로 사실상 생기지 않는다. 취소는 되돌릴 수 없어, 드문 건을 위해 자동 판단 코드를 키우지 않는다 |
| 처리 방법 | 관리자 API가 토스 취소와 충전 건 변경을 함께 함 | 토스 상점관리자에서 취소하고 SQL로 상태를 바꾸면 두 곳이 어긋날 수 있다 |
| 잘못된 선택 막기 | 처리 직전에 토스에 다시 묻고, 상태와 맞지 않으면 거부 | 승인된 결제를 실패로 끝내면 돈은 빠졌는데 잔액이 늘지 않는다. 실패는 결제 없음·승인 실패·만료·취소됨일 때만, 반영·취소는 같은 금액으로 승인(DONE)됐을 때만 |
| 취소한 건의 상태 | 실패(`FAILED`) 그대로, 결제 취소 시각(`payment_canceled_at`) 기록 | 새 상태를 두면 상태 규칙·한도 합계·검사 SQL을 다 고쳐야 한다. 실패 코드에 적으면 승인 뒤 실패한 건의 원래 실패 사유를 잃는다 |
| 승인 뒤 실패한 건 찾기 | 늦은 승인 응답이 실패한 건을 만나면 `approved_after_failure_at`에 남김 | 실패 건은 DB만 봐서는 승인 여부를 알 수 없고, 로그(`[CHARGE_APPROVED_BUT_FAILED]`)만으로는 놓칠 수 있다 |
| 취소 순서 | 토스 취소(트랜잭션 밖) → 확인되면 충전 건 기록 | 반대 순서면 "기록은 환불, 실제는 미환불"이 생긴다(회원 손해) |
| 취소 중 겹침 | 멈춘 건은 토스를 부르기 전에 잠그고 취소 요청 시각(`payment_cancel_requested_at`)을 남김. 표시가 있는 처리 중 건은 완료·실패로 바꾸지 않음. 거절이면 다시 조회해 취소됐으면 기록함. 표시는 코드로 지우지 않고, 거절로 남은 표시는 사람이 토스를 확인한 뒤 지움 | 리뷰 지적. 토스 취소를 기다리는 사이 다른 관리자의 반영이나 늦은 승인 응답이 완료하면 환불과 잔액 증가가 함께 일어난다(시험으로 재현). 먼저 실패로 바꾸는 방법은 새 칸이 없지만, 토스가 거절하면 실패 → 완료가 막혀 반영으로 되돌릴 수 없어 버림 |
| 취소 결과가 애매할 때 | 알 수 없음·이미 취소됨이면 충전 번호로 다시 조회해 `CANCELED`일 때만 기록 | 토스 문서는 500·시간 초과 뒤 취소됐는지 알려 주지 않는다 |
| 멱등 키 | 시도마다 새로 만듦(`CANCEL-{충전 번호}-{시각}`) | 같은 키는 첫 응답을 그대로 돌려줘, 첫 응답이 일시 오류면 다시 시도해도 같은 오류만 받을 수 있다. 전액 취소는 토스에서 한 번만 돼(테스트 키로 다른 키 재요청이 `ALREADY_CANCELED_PAYMENT`로 오는 것 확인) 키를 바꿔도 두 번 환불되지 않는다 |
| 취소 결과 분류 | 취소되지 않았음이 분명한 코드만 거절, 나머지(일시 오류·처리 중·요청 제한·키 오류)는 알 수 없음 | 알 수 없음은 기록하지 않고 조회로 확인하므로, 잘못 분류해도 돈이 틀어지지 않는 쪽이다 |
| 부분 취소 | 처리 거부 | 충전에서 부분 취소는 우리가 하지 않는 일이라 사람이 토스에서 직접 본다 |

확인한 사실(테스트 키): 승인된 결제를 금액 없이 취소하면 `CANCELED`·취소 내역 `DONE`, 같은 멱등 키로 다시 보내면 같은 성공 응답, 다른 키나 키 없이 보내면 `ALREADY_CANCELED_PAYMENT`, 승인 안 된 결제는 `NOT_CANCELABLE_PAYMENT`. 카드 취소 기한은 문서에 "없지만 1년을 넘기면 안 될 수 있음"으로 나온다.

버린 대안:
- **토스 상점관리자 + SQL:** 코드는 없지만 토스와 DB를 따로 고치다 어긋난다.
- **고정 멱등 키:** 토스가 오류 응답도 저장한다면 다시 시도가 소용없다(저장 여부는 문서에 없음).
- **취소용 새 상태 `CANCELED`:** 위 "취소한 건의 상태" 이유.

건드릴 때 주의:
- 관리자 처리 대상은 멈춘 처리 중 건(`next_check_at` 비움)과 승인 뒤 실패해 아직 취소하지 않은 건뿐이다. 복구가 확인 중인 처리 중 건을 열면 복구와 겹친다.
- 취소 요청 표시는 완료 처리(`ChargeTransactionService.complete`)와 실패 처리(`failApproval`)가 잠근 뒤 확인해야 한다. 관리자 서비스의 사전 확인만으로는 늦게 온 승인 응답을 막지 못한다.
- 표시를 코드로 지우지 않는다. 거절을 받은 요청은 다른 관리자의 취소가 토스에서 아직 진행 중인지 알 수 없고, 그때 조회는 승인 상태로 보일 수 있다. 지운 사이 늦은 승인 응답이 완료하면 환불과 잔액 증가가 함께 일어난다(리뷰 지적, 두 관리자 동시 취소 시험으로 재현). 거절 때 자동으로 지우는 방법(요청 시각으로 가리기, 처음 남긴 요청만 지우기)은 리뷰마다 틈이 나와 버렸다. 충전 결제의 취소 거절은 환불 기한이 지났거나 휴면 회원처럼 드물어, 사람이 토스를 확인하고 SQL로 지운다(`docs/DEVELOPMENT.md`).
- `[CHARGE_CANCELED_BUT_COMPLETED]`: 취소를 기록할 때 이미 완료된 경우로, 환불도 되고 잔액도 늘었다. 취소 요청 표시로 막아 생기지 않아야 하지만 생기면 사람이 잔액을 회수한다.
- 처리 절차는 `docs/DEVELOPMENT.md` 지갑 절의 "충전 관리자 처리"에 있다.
