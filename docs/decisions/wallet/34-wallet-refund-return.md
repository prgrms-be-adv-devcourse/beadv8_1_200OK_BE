## 배경

출고 전 취소를 환불 모듈이 맡으면서(#323) 지갑은 주문 취소 이벤트가 아니라 환불의 `refund.refund-approved`를 받아 돈을 돌려주게 됐다. 환불은 이미 이 메시지를 보내고 있었고(#512), 지갑 결과를 받아야 완료하도록 바뀌었다(#544, PR #555). 지갑에 받는 곳이 없어 돌려줄 돈이 있는 환불이 모두 처리 중에 멈춰 있었다.
범위: 반환 처리 기록, 반환 처리, 결과 발행, Kafka 수신. 범위 밖: 이용 내역에 반환 줄 표시(#609), 상품명 표시, 돌려준 돈 다시 가져오기(#546 쪽 요청, 별도 이슈), 주문이 기한 지나 취소한 뒤 온 결제의 반환(#402).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 결과 메시지 | 보냄. `wallet.wallet-refund-completed` / `-failed`, 키 `orderId`, 필드 `refundId`·`orderId`·`buyerId`·`amount`(+`reason`) | 11/11에는 결과를 보내지 않기로 했지만 환불이 결과를 받아야 완료하도록 바뀌었다(PR #555). 모양은 환불 받는 쪽에 맞춘다 (사용자 결정) |
| 같은 환불이 다시 옴 | 돈은 다시 주지 않고 처음 결과(금액 포함)를 다시 보냄 | 환불이 멈춘 단계를 같은 `refundId`로 다시 보낸다(#545). 금액이 달라도 처음 금액을 보내야 환불이 비교해 `RESULT_MISMATCH`로 잡는다 |
| 거절 사유 | `PAYMENT_NOT_FOUND`, `REFUND_TOTAL_EXCEEDED` 두 개 | 환불은 지갑 거절을 받으면 주문 취소를 되돌린다(#546). 돈이 확실히 안 나갔고 다시 해도 같은 경우만 거절로 보낸다. 11/12에 알린 네 개에서 줄였고 환불 담당께 알림 (사용자 결정) |
| 같은 환불 다른 금액 | 거절(`AMOUNT_MISMATCH`)이 아니라 처음 결과 | 이미 돌려준 뒤라 거절을 보내면 돈은 구매자에게 있는데 주문만 되돌아간다 |
| 0원 이하·빈 ID | 결과 없이 지갑 실패 기록 표(#579) | 환불이 보내지 않는 값이고, 환불 받는 쪽도 금액이 1 이상이 아니면 거절해 결과가 닿지 않는다 |
| 처리 기록 | 새 표 `wallet_order_refund`(환불 ID 유니크, 결과·사유), 결제처럼 먼저 넣어 보고 판단(#360) | 결제 처리 기록은 주문당 한 줄이라 한 주문의 여러 환불을 담지 못한다. 넣기는 스냅샷이 아니라 유니크 제약으로 중복을 막는다 |
| 근거 키 | `REFUND:{refundId}` | 같은 주문 상품을 나눠 환불하면 주문 상품 ID로는 두 번째 반환이 막힌다 (환불 요청서 #413) |
| 결제 확인 | 그 주문·그 구매자의 성공한 결제, 잠그지 않고 읽음 | 다른 사람 지갑에 돈이 가지 않게 한다. 결제 기록은 바뀌지 않고, 없을 수 있는 행을 잠그면 빈 구간까지 잠긴다 |
| 합계 상한 | 결제 금액(주문이 보낸 `totalAmount`, 배송비 포함) | 돌려줄 금액 계산은 환불이 한다. 지갑은 낸 돈보다 많이 나가는 것만 막는다. 배송비를 빼든 돌려주든 합계는 결제 금액 안이다 |
| 합계 읽기 | 지갑을 잠근 뒤 잠금 조회 | 일반 조회는 잠금을 기다리기 전의 스냅샷을 봐서 방금 끝난 반환을 빼고 센다. 이미 열린 트랜잭션 안에서 잠금을 빼 보면 35,000원 결제에 50,000원이 나갔다 |
| 격리 수준 | 반환 트랜잭션만 READ COMMITTED | 정확성이 아니라 교착을 피하려는 것이다. 기본 격리 수준에서 이웃한 주문의 첫 반환 10건을 동시에 보내면 빈 구간 잠금끼리 부딪혀 매번 교착이 났다 |
| 결과 보내는 때 | 반환 커밋 뒤, 오프셋 커밋 전, 브로커 저장 확인까지 기다림 | 커밋 전에 보내면 돌려주지 않은 돈을 돌려줬다고 알릴 수 있다. 보내기가 실패하면 예외로 같은 요청을 다시 받아 처음 결과를 다시 보낸다 |
| 발행 포트 | 결제 결과(`WalletEventPublisher`)와 나눈 `WalletRefundResultPublisher` | 결제 결과는 아직 Spring 이벤트, 반환 결과는 처음부터 Kafka라 보내는 방식과 실패 처리가 다르다 |
| 보유 한도·판매자 지갑 | 보지 않음, 건드리지 않음 | 돌려줄 돈이라 한도로 막지 않는다. 출고 전 취소라 판매자에게 간 돈이 없다 |
| 이용 내역 표시 | #609로 분리 | 화면·API가 바뀌어 프런트 확인이 필요하고, 환불을 먼저 풀어야 한다. 돈은 #34로 맞다 (사용자 결정) |

## 버린 대안

- **outbox로 결과 보내기:** 처리 기록이 곧 "보낼 결과"라 다시 받으면 같은 결과를 다시 만들 수 있다. 감수하는 것은 다시 시도를 다 써서 실패 기록 표에 남으면 환불이 다시 요청할 때(#545)까지 결과가 가지 않는다는 점.
- **합계를 SQL `SUM ... FOR SHARE`로 바로 구하기:** 잠금은 `@Lock`으로만 적는다는 구조 규칙(`ArchitectureTest`)에 걸린다. 완료 기록을 잠금 조회해 어댑터에서 더한다. 한 주문의 환불은 상품 수만큼이라 행이 적다.
- **결제 처리 기록에 누적 반환 금액 칸 두기:** 결제 행 하나만 잠그면 돼 빈 구간 잠금이 없지만, 한 번 남으면 바뀌지 않는다는 결제 기록의 전제를 깨고 결제 넣기 쿼리도 바꿔야 한다.
- **READ COMMITTED만 믿고 일반 조회:** #360처럼 이미 열린 트랜잭션에 합류하면 격리 수준이 오류 없이 무시된다. 잠금 조회를 함께 둬 그때도 합계가 맞게 한다.
- **잘못된 값에도 실패 메시지 보내기:** 환불이 받지 못하고, 주문 되돌리기 근거가 될 수 있다.

## 건드릴 때 주의

- 주문 반환(#402)을 더하면 같은 결제 금액 상한을 함께 쓴다. 같은 구매자 지갑 잠금을 먼저 잡고, 반환 합계에 주문 반환 금액도 더해야 한다.
- 거절 사유는 환불 실패 처리(#546)가 주문 되돌리기를 결정하는 근거다. 사유를 더하거나 뜻을 바꾸면 환불 담당과 먼저 맞춘다. 일시적 오류를 거절로 바꾸지 않는다.
- `refundForOrder`를 트랜잭션 안에서 부르게 바꾸면 READ COMMITTED가 무시돼 교착이 다시 날 수 있다. 바깥 서비스(`OrderRefundService`)는 트랜잭션을 열지 않는다.
- 정합성 검사 SQL(`sql/wallet-balance-check.sql`)은 반환 기록과 `REFUND:` 원장의 짝을 양쪽에서 본다. 반환 원장을 만드는 새 길은 처리 기록도 함께 남겨야 한다.
- 받는 메시지(`RefundApprovedMessage`)와 보내는 메시지(`WalletRefund*Message`)의 필드는 환불과의 약속이다. 바꾸면 환불 쪽 DTO도 같이 바꾼다.
