# 설계 결정 기록 (ADR)

설계 결정과 그 이유를 작업(이슈) 단위로 남기는 곳이다. ADR(Architecture Decision Record, 아키텍처 결정 기록) 방식을 따른다. 코드는 결과만 보여 주므로 "왜 그렇게 정했는지, 어떤 대안을 버렸는지"를 여기에 둔다. 신입이나 오랜만에 복귀한 사람, 그리고 이전 작업의 흐름을 모르는 AI가 PR만으로 알기 어려운 맥락을 찾는 용도다.

PR 본문은 핵심 변경과 이유만 짧게 쓰고, 결정의 이유와 버린 대안 같은 세부는 이 문서에 쓴 뒤 PR에서 링크한다.

## 위치와 이름

```
docs/decisions/<모듈>/<이슈번호>-<slug>.md      예: docs/decisions/delivery/330-delivery-hexagonal.md
```

- `<모듈>`은 `settings.gradle.kts`의 모듈명(`common`, `delivery`, `media`, `member`, `monolith`, `order`, `payout`, `product`, `refund`, `wallet`)이다.
- `common` 폴더에는 `common` 모듈의 결정과, 어느 한 모듈에 속하지 않는 구조·규칙·공통 결정을 함께 둔다. 인프라·배포는 `infra`에 둔다.
- 여러 모듈에 걸친 결정은 주도한 모듈 한 곳에만 둔다. 같은 문서를 두 곳에 두지 않는다. 영향받는 다른 모듈의 문서를 찾을 때는 `paths` 겹침으로 찾는다.
- `<이슈번호>`는 브랜치 이름(`<유형>/<이슈번호>`)의 번호다. PR 번호는 문서를 쓸 때 아직 없을 수 있어 파일 이름에 쓰지 않는다.
- `<slug>`는 영문 소문자·숫자·하이픈 2~4단어다.

## 무엇을 남기나

한 문서는 이슈(작업) 하나이고, 그 작업의 핵심 결정 여러 개를 표로 담는다. 아래처럼 되돌리기 어렵거나 이유가 코드에 안 보이는 결정이 있을 때 쓴다.

- 모듈 경계, 패키지 구조, 의존 방향
- 외부 연동 방식, 이벤트 형식, API 계약의 큰 선택
- 트랜잭션·락·멱등성 같은 동작 정책
- 후보가 여럿이었고 하나를 골라 다른 것을 버린 경우

이름 변경, 단순 버그 수정, 이슈 본문에 이유가 이미 충분한 작업은 쓰지 않는다.

## 언제 쓰나

결정이 오간 대화가 살아 있는 동안 쓴다. 대화가 없으면 코드와 git 기록으로 알 수 있는 것만 남아 PR 본문을 다시 정리하는 수준이 된다. PR을 올리기 전이나 직후, `/clear`나 `/compact` 전에 `session-summary` 스킬로 초안을 만들고 사람이 확인한다. 문서는 작업 브랜치에 커밋해 PR과 함께 리뷰한다.

## 쓰는 법

[`TEMPLATE.md`](TEMPLATE.md)를 복사해 쓴다. 본문은 네 섹션이다.

| 섹션 | 내용 |
|---|---|
| 배경 | 해결하려는 문제와 범위, 범위 밖으로 둔 것 |
| 결정과 이유 | 고른 것과 고른 이유 |
| 버린 대안 | 버린 방법과 버린 이유, 감수하는 트레이드오프 |
| 건드릴 때 주의 | 고칠 때 깨지기 쉬운 것, 자동으로 로드되지 않는 규칙, 지켜야 할 전제 |

아래는 이 문서에 쓰지 않는다. 쉽게 낡거나 다른 곳이 더 정확하다.

- 남은 작업, 확인이 필요한 후속 결정: 후속 이슈 본문에 쓴다.
- 테스트 건수와 실행 결과 같은 검증: PR 본문에 쓴다.
- 구현 중 겪은 문제와 고친 과정: 커밋 메시지와 코드 주석에 쓴다. 고칠 때 다시 깨질 전제만 "건드릴 때 주의"에 남긴다.

머리말 필드는 아래와 같다.

| 필드 | 내용 |
|---|---|
| `issue` | 이슈 번호. `#` 없이 숫자만 쓴다 |
| `module` | 결정을 주도한 모듈 하나 |
| `summary` | 무엇을 왜 했는지 한 줄. 색인에 그대로 실린다 |
| `status` | `확정`, `진행 중`, `대체됨(이슈번호)` 중 하나. `확정`은 이 문서의 결정을 따른다는 뜻이고 PR을 올릴 때 보통 이 값이다. `진행 중`은 결정이 남아 후속 작업에서 정해질 때만 쓴다 |
| `date` | 작성한 날(YYYY-MM-DD) |
| `paths` | 이 결정이 걸린 대표 코드 경로. `[a, b]` 한 줄 목록으로 쓰고 경로에 쉼표를 넣지 않는다. 여러 줄 목록은 읽지 못한다. 문서가 낡았는지 확인하는 기준이다 |
| `related` | 같은 기능의 이전·이후 이슈 번호들. `#` 없이 숫자만 쓴다(`[331, 332]`). YAML에서 `#`은 주석이다 |

## 규칙

- 코드·테스트로 확인하지 못한 주장은 문장 앞에 `(미확인)`을 붙인다. 읽거나 돌려 본 것만 "확인했다"고 쓴다.
- PR 본문, 코드, 커밋 메시지에 이미 있는 내용은 되풀이하지 않고 "왜"만 쓴다.
- 전체 100줄 안쪽으로 쓴다. 같은 내용을 섹션마다 되풀이하지 않는다. 안 쓸 섹션은 지우지 말고 "해당 없음" 한 줄만 둔다.
- **민감정보를 쓰지 않는다.** 비밀번호, 토큰, API 키, 환경변수 값, IP, 이메일, 내부 URL, 개인정보는 적지 않는다. 코드는 파일 경로와 이름으로 가리키고 설정값은 옮기지 않는다. 문서는 코드 저장소 이력에 남으므로 한 번 머지되면 지우기 어렵다. Write·Edit로 문서를 쓸 때는 `.claude/hooks/scan-adr-before-write.sh` 훅이 쓰기 전에 자동으로 점검하고, 걸리면 쓰기를 막는다(`jq`가 없으면 검사하지 못하고 통과한다). Bash나 IDE로 직접 쓴 문서는 훅이 막지 못하므로 `.claude/skills/session-summary/scan-sensitive.sh <파일>`로 직접 점검하고, 리뷰어도 PR에서 문서를 함께 확인한다. 스크립트는 자주 나오는 꼴만 잡으므로 통과해도 안전하다는 뜻이 아니다. 사람이 문서를 읽어 확인한다. 오탐이면 값을 일반화해서 고친다(버전은 `25.0.1`처럼 줄이거나 "버전 25.0.1.2"처럼 앞에 "버전"을 붙인다). 특정 줄을 건너뛰는 주석은 우회로가 되어 두지 않는다.
- 머지된 문서는 고치지 않는다. 틀린 내용이나 바뀐 사실은 끝에 `## 후속 (YYYY-MM-DD)`를 덧붙인다. 결정이 통째로 바뀌면 이전 문서의 `status`만 `대체됨(이슈번호)`로 바꾸고, 새 문서의 `related`에서 이전 문서를 가리킨다. 이 둘이 머지된 문서를 고칠 수 있는 유일한 경우다. 머지 전에는 같은 PR 안에서 자유롭게 고친다.
- 문서는 작성일 기준이다. 코드가 바뀌었으면 코드가 우선이고, 이 문서는 이유를 되짚는 용도다.

## 민감정보 점검표

문서를 저장하기 전에 `scan-sensitive.sh`를 돌리고, 스크립트가 못 잡는 것은 사람이 읽어 확인한다.

**스크립트가 잡는 것**

- AWS 액세스 키 ID, 라벨이 없는 시크릿 키 추정, 계정 ID와 ARN, ECR·RDS·ELB·EC2·S3 주소, `sg-`·`vpc-`·`i-` 같은 리소스 ID
- 비밀번호·토큰·키 대입(`이름: 값`, JSON 키, 표, 한글 이름), JWT, Bearer·Basic 인증, 개인 키, GitHub·Slack·Google·Stripe·토스페이먼츠 같은 서비스 키
- 자격증명이 든 URL, URL 쿼리의 토큰, DB 접속 주소(도메인이 있는 것), 내부 호스트, IP, 이메일
- 주민등록번호, 휴대전화 번호, 카드 번호

**사람이 확인하는 것**

- 실제 고객·판매자·주문 데이터(이름, 주소, 계좌, 금액)와 로그·스택 트레이스에서 복사한 값
- 정산·결제 같은 내부 정책의 구체적인 수치, 내부 시스템의 이름과 주소
- 인증·인가를 우회하는 방법이나 아직 고치지 않은 취약점
- 문장 속에 풀어 쓴 비밀값, 영문자로만 된 비밀번호, 압축형 IPv6, 비공개 계약 내용
- 꺾쇠로 감싼 값(`<...>`, 80자 이하, `=`·`:`·따옴표 없음)과 `${변수}` 참조: 스크립트가 자리표시자로 보고 지운 뒤 검사하므로 통과한다. 실제 값을 꺾쇠로 감싸 쓰지 않는다

## 민감정보가 머지된 뒤에 발견했을 때

1. **값을 먼저 폐기하고 교체한다.** 비밀번호, 토큰, 키는 즉시 폐기하고 새로 발급한다. 이것이 실제 해결이다. AWS 키는 IAM에서 바로 비활성화하고 삭제한 뒤 새 키로 바꾸고, CloudTrail에서 그 키의 사용 이력을 확인한다.
2. 문서에서 해당 내용을 지우는 수정을 새 PR로 올린다.
3. 이력에서도 지워야 하면 `git filter-repo`로 정리하고 팀원에게 다시 clone하라고 알린다. `git push -f`로 덮어써도 이미 받아 간 복제본과 GitHub의 캐시에는 남고, 닫힌 PR 참조에서 커밋이 계속 보일 수 있다. 완전히 지우려면 GitHub 지원에 요청해야 한다. 그래서 이력 정리는 노출을 줄이는 보조 수단이고 1번을 대신하지 못한다.
4. `main`과 `dev`의 강제 푸시 금지 설정은 이력 정리를 할 때만 관리자가 잠시 푼다.

자동 검사(CI)는 아직 도입하지 않았다. 쓰기 전 훅, 저장 전 스크립트, PR 리뷰로 막는다. 팀이 필요하다고 정하면 별도 이슈로 CI에서 `scan-sensitive.sh`를 돌린다.

## PR에서 연결하기

PR 본문의 `💬 참고 사항`에 이 문서 링크를 한 줄 넣는다. 머지 전에는 상대 경로가 열리지 않으므로 브랜치 기준 전체 주소를 쓴다. 브랜치를 지우면 이 주소가 열리지 않으니, 머지된 뒤에도 필요하면 `blob/dev/...` 주소로 바꾼다.

```
- 설계 기록(ADR): https://github.com/<소유자>/<레포>/blob/<브랜치>/docs/decisions/<모듈>/<이슈번호>-<slug>.md
```

ADR이 없는 PR은 이 줄을 생략한다.

## 이전 결정 불러오기

`session-context` 스킬이 이 폴더에서 관련 문서를 찾아 현재 대화에 불러온다. 인수로 모듈 이름, 이슈 번호, 키워드를 준다. 사람은 IDE 프로젝트 트리에서 `docs/decisions/<모듈>/`을 열면 된다.

## 쌓이는 문서 관리

문서가 늘수록 읽히지 않는 문제를 줄이려고 세 가지를 둔다.

1. **오래 지킬 결정은 규칙으로 승격한다.** 작업을 마칠 때 "이 결정이 앞으로 모든 작업에 적용되는가?"를 묻는다. 그렇다면 ADR에만 두지 않고 자동으로 로드되는 곳에 올린다. 코드 규칙은 `docs/CONVENTION.md` 원문을 먼저 고치고 `.claude/rules/`에 반영한다(CLAUDE.md의 규칙). 올린 뒤에는 ADR 끝에 `## 후속`으로 "규칙으로 올렸다: 위치"를 남긴다. ADR에는 그 작업의 맥락과 버린 대안이 남는다.
2. **지금 따르지 않는 문서는 색인에서 뺀다.** `status`가 `대체됨`인 문서는 `build-index.sh`가 기본으로 빼고, 이력이 필요하면 `-a`로 포함한다.
3. **낡은 문서는 정리 후보로 표시한다.** 색인의 "겹침 / 이후 변경" 칸에 `[정리 후보: …]`가 붙는다. `paths`가 모두 사라졌거나 문서를 마지막으로 바꾼 뒤 `paths`에서 5건 이상 커밋이 있을 때다. 후보는 사람이 읽고 `대체됨`으로 바꾸거나 `## 후속`으로 고친다.

분기마다 한 번 `bash .claude/skills/session-summary/build-index.sh -a`로 정리 후보와 오래 `진행 중`인 문서를 점검한다. 기록 단위는 이슈 하나로 유지한다. 에픽처럼 여러 이슈로 나뉜 작업도 에픽 단위로 키우거나 통합하지 않고, 이슈마다 그 작업을 끝낸 시점에 ADR을 쓰고 `related`로 잇는다.
