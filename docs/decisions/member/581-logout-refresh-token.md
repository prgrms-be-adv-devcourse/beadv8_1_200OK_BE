## 배경

로그아웃 API가 없어 클라이언트가 토큰을 버려도 서버의 Refresh Token 행이 남았고, 그 토큰을 가진 쪽은 만료(14일)까지 재발급을 받을 수 있었다. #83에서 행 하나가 로그인 세션 하나가 되었으므로, 받은 토큰의 행만 지우면 그 기기의 세션만 끝난다.

범위 밖으로 둔 것:
- 이미 발급된 Access Token(30분) 즉시 무효화, 모든 기기 로그아웃(#561 토큰 버전 뒤)
- 재사용 탐지와 이전 해시 저장(#562)

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 없는·만료된·이미 로그아웃한 토큰 | 모두 204 (사용자 결정) | 멱등. 응답으로 토큰 유효 여부를 드러내지 않는다. 로그아웃의 목적(세션이 끝난 상태)은 이미 이뤄져 있다 |
| Access Token 요구 | 요구하지 않는다. `PUBLIC_ENDPOINTS`에 `TokenUse.IGNORED`로 등록 (사용자 결정) | Access Token이 만료돼도 로그아웃할 수 있어야 한다. Refresh Token을 가진 쪽은 재발급까지 할 수 있으므로 세션 종료는 더 작은 권한이다. `reissue`와 같은 구조 |
| 형식 오류 응답 | 422 (사용자 결정) | 처음에는 400으로 정했으나, 프로젝트의 요청 검증 실패가 `VALIDATION_FAILED`(422)이고 `reissue`도 422라 맞췄다 |
| 삭제 방법 | 해시로 만료되지 않은 행의 id만 잠금 없이 찾고(`findUnexpiredIdByTokenHash`), id로 벌크 삭제(`deleteDirectlyById`) | 해시로 바로 DELETE하면 없는 해시에서 인덱스 구간이 잠겨 로그인·재발급 저장을 막는다(`rotate`와 같은 이유, #83). id로 지우면 재발급이 해시를 바꾼 뒤 커밋해도 같은 행이 지워진다 |
| 재발급과 겹칠 때 | 잠금을 얻은 뒤 해시를 다시 비교하지 않고 지운다 | 커밋 전 스냅숏에서 id를 찾았다는 것이 그 토큰이 방금까지 이 세션에서 유효했다는 증거다. 재발급 응답으로 나간 새 토큰도 함께 무효가 되는 것이 로그아웃의 의도에 맞다 |
| 만료된 행 | 지우지 않고 정리 스케줄러에 맡긴다 (코드 리뷰 반영, 사용자 결정) | (미확인) 정리는 `expires_at` 인덱스 → 기본 키, id 삭제는 기본 키 → 인덱스 순서로 잠가 같은 만료 행을 함께 지우면 교착될 수 있고, 로그아웃이 지면 500이 된다. 만료 행은 재발급에 쓸 수 없어 남겨도 세션이 살아나지 않는다. 처음 결정은 "만료됐어도 지운다"였다 |
| 클라이언트 안내 | 진행 중인 재발급이 있으면 그 응답을 기다려 받은 새 토큰으로 로그아웃, 재발급이 실패하면 가진 토큰으로 (사용자 결정) | 재발급이 서버에서 먼저 커밋되면 옛 토큰으로는 행을 찾지 못한다. 동시에 보내면 이 경우가 가장 흔하다(id 삭제가 막는 구간은 재발급 트랜잭션 길이뿐). 처음 안내였던 "재발급 응답을 버린다"는 서버의 새 세션을 끝내지 못해 바꿨다 |
| 회원 상태 확인 | 하지 않는다 | 정지·탈퇴 회원이어도 세션 종료를 막을 이유가 없고, 회원을 조회하지 않아야 응답이 토큰 유효 여부와 무관하다 |

## 버린 대안

- **잠근 뒤 해시 재비교(재발급과 같은 방식):** 재발급이 먼저 해시를 바꾸면 로그아웃이 지우지 않아 새 토큰의 세션이 남는다. 로그아웃은 "방금까지 유효했던 세션을 끝낸다"가 맞아 버렸다.
- **해시로 바로 DELETE:** 위의 구간 잠금 문제와, 재발급이 커밋된 뒤 0건 삭제가 되는 문제가 있다.
- **만료 행도 지우고 교착 시 재시도·204 처리:** 예외가 트랜잭션 안에서 나서 처리 위치가 까다롭고 코드가 늘어난다. 만료 행을 남겨도 보안상 차이가 없어 버렸다.
- **이전 해시(`prev_token_hash`) 저장으로 옛 토큰 로그아웃도 처리:** 마이그레이션과 엔티티 변경이 필요하고 같은 컬럼이 재사용 탐지에도 쓰여 #562로 미뤘다. 감수하는 것은 재발급 응답이 유실돼 클라이언트가 새 토큰을 모르는 경우 그 세션이 만료까지 남는 것.
- **Spring Data 기본 `deleteById`:** 엔티티를 먼저 읽고 지우며 반환형(`void`)이 포트 선언과 겹쳐 이름을 `deleteDirectlyById`로 따로 두었다.

## 건드릴 때 주의

- `AuthService` 클래스 기본값이 `@Transactional(readOnly = true)`다. `logout`의 `@Transactional`을 빼면 `RefreshTokenService.revoke`가 읽기 전용 트랜잭션에 참여해 DELETE가 실패한다.
- 만료 기준은 `RefreshToken.isExpired`와 같아야 한다(만료 일시와 같은 순간부터 만료, 쿼리는 `expiresAt > now`). 어긋나면 재발급에서 거절되는 행을 로그아웃이 지우거나 그 반대가 된다.
- `deleteDirectlyById`는 벌크 DELETE라 영속성 컨텍스트를 거치지 않는다. 같은 트랜잭션에서 그 엔티티를 먼저 읽는 흐름(전체 로그아웃, 탈퇴 등)에서 쓰면 관리 중인 엔티티가 낡는다. `clearAutomatically`는 호출한 쪽의 다른 엔티티까지 분리해 넣지 않았다.
- `RefreshTokenSessionIntegrationTest`의 동시 요청 테스트는 1초 대기로 순서를 맞춘다. 테스트 DB 계정에 PROCESS 권한이 없어 `INNODB_TRX`로 잠금 대기를 확인할 수 없어서다. "로그아웃이 먼저" 테스트는 순서와 관계없이 결과가 같아 잠금 대기 경로를 보장하지 않는다.
- 클라이언트 안내 문구는 `AuthControllerSpec`과 `docs/DEVELOPMENT.md` 로그아웃 절 두 곳에 있다. 바꾸면 함께 고친다.
- 만료 행을 남겨도 정리와의 교착이 완전히 사라지지는 않는다. 로그아웃은 요청 시각, 정리는 시작할 때 정한 시각으로 만료를 판단해, 두 시각 사이에 만료된 행은 양쪽이 함께 지우려 할 수 있다(PR 리뷰 지적). 삭제 쿼리에 같은 시각으로 `expiresAt` 조건을 더해도 조회에서 이미 통과한 조건이라 막히지 않는다. 확률이 매우 낮고 InnoDB가 감지해 한쪽을 롤백해 데이터는 안전해 그대로 두었다. 재발급↔정리에도 같은 틈이 있으며, 정리를 기본 키부터 잠그게 바꾸면 둘 다 없어진다(#562에서 다룬다).
