## 배경

주문이 재고 해제를 부르는 곳은 세 곳이다(주문 생성 중 실패 보상, 지갑 결제 실패, 결제 대기 정리). 어느 곳도 해제가 실패하면 다시 부르지 않아, 상품 재시작이나 응답 지연 한 번으로 취소·결제 실패된 주문이 재고를 계속 붙잡았다.

결제 실패 경로는 문제가 하나 더 있었다. 리스너가 `@ApplicationModuleListener`라 트랜잭션 안에서 결제 실패와 재고 해제 HTTP가 함께 돌았다. 해제가 실패하면 결제 실패까지 롤백되어 주문이 결제 대기로 돌아가고, 30분 뒤 결제 대기 정리가 취소로 바꿔 주문 목록에서 사라졌다. 해제를 기다리는 동안 주문 행 잠금과 DB 커넥션도 쥐었다.

상품의 해제는 #605 이후 순서·횟수와 관계없이 같은 결과를 내므로 다시 불러도 안전하다.

범위 밖: 결제를 요청한 주문의 결제 만료 판정(#656), 상품 쪽 재고 배정 트랜잭션 시간 상한.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 다시 풀 대상 찾기 | `orders.stock_released_at`(해제 확인 시각) 칸. 취소·결제 실패인데 비어 있으면 대상 (사용자 결정) | 대상을 주문 상태에서 다시 고르므로 "실패를 따로 등록"하는 단계가 없어, 등록이 실패해 대상이 빠지는 일이 없다. 칸 하나와 인덱스로 끝난다 |
| 해제 순서 | 세 경로 모두 상태를 먼저 커밋하고 트랜잭션 밖에서 해제, 성공하면 해제 시각 기록 | 해제 확인은 취소·결제 실패된 주문에만 기록할 수 있다. 해제를 기다리는 동안 잠금과 커넥션을 쥐지 않는다 |
| 생성 실패 보상 | "해제 → 취소"에서 "취소 → 해제"로. 취소하지 못하면(예외 또는 결제 대기가 아님) 해제하지 않음 | 취소하지 못한 주문의 재고를 풀면 결제될 주문의 재고가 풀린다. 결제 대기로 남은 주문은 5분 뒤 결제 대기 정리가 취소하고 해제한다 |
| 해제 실패 처리 | 예외를 던지지 않고 WARN, 해제 시각은 비워 둠 | 주문 생성 실패 경로에서는 원래 실패를 그대로 응답해야 하고, 결제 실패 경로에서는 결제 실패가 남아야 한다. 다시 해제는 정리 스케줄러가 맡는다 |
| 결제 실패 리스너 | `@Async @TransactionalEventListener` (사용자 결정) | `@ApplicationModuleListener`에서 트랜잭션만 뺀 형태라 비동기·커밋 뒤 수신·Modulith 처리 기록은 그대로다. 결제 실패는 서비스가 자기 트랜잭션으로 먼저 커밋한다 |
| 재처리 주기 | 결제 대기 정리 스케줄러(5분)에 별도 단계로 붙임. 정리 대상이 없어도 돈다 (사용자 결정) | 상품 배포·재시작 같은 잠깐의 장애를 넘기는 용도라 결제 대기 정리와 같은 주기면 충분하다. 스케줄러를 하나 더 두면 같은 스케줄 스레드를 더 자주 쓴다 |
| 재처리 대상 | 상태가 바뀐 지(`updated_at`) 1분 지난 주문, 한 번에 100건, 오래된 주문부터 | 원래 경로가 막 해제 중일 수 있어 겹침을 줄인다(겹쳐도 결과는 같다). 스케줄 스레드를 다른 정기 작업과 같이 써서 한 번의 HTTP 호출 수를 제한한다 |
| 사람 확인 | 1시간 넘게 해제를 확인하지 못한 주문을 `[ORDER_STOCK_RELEASE_STUCK]` ERROR로 남김. 다시 시도는 계속함 (사용자 결정) | 배포·재시작은 거르고 진짜 문제는 그날 안에 보이게 한다. 해제 칸만 두어 시도 횟수가 없으므로 시간으로 판단한다 |

## 버린 대안

- **대상 찾기:** 별도 표(시도 횟수·다음 시도 시각·마지막 오류)는 횟수로 멈추고 실패 이유를 남길 수 있지만 표·엔티티·상태 전이가 새로 생겨 코드가 크게 는다. 기록 없이 취소·결제 실패 주문 전체를 매번 다시 해제하는 방법은 대상이 계속 늘어 5분마다 HTTP를 수천 번 부른다.
- **리스너:** 리스너는 두고 해제만 `TransactionSynchronization.afterCommit`으로 미루는 방법은 어노테이션을 안 바꾸지만 동기화 코드가 섞이고, Kafka로 옮길 때 다시 바꿔야 한다. Kafka 전환(#602) 때 함께 고치는 방법은 그때까지 결제 실패가 롤백되는 문제가 남는다.
- **주기:** 새 스케줄러(1분)는 복구가 빠르지만 클래스가 하나 늘고 공용 스케줄 스레드를 더 자주 쓴다.
- **사람 확인 기준:** 30분은 상품 배포 중에도 울릴 수 있고, 하루는 그동안 재고가 묶여 판매 기회를 놓친다.

## 건드릴 때 주의

- 결제 실패 리스너에 `@Transactional`을 붙이지 않는다(Kafka 컨슈머로 옮길 때도 같다). 붙이면 결제 실패와 해제 HTTP가 다시 한 트랜잭션에 묶여 해제를 기다리는 동안 잠금과 커넥션을 쥔다. 모듈 테스트 `결제_실패는_재고_해제를_부르기_전에_커밋된다`가 잡는다.
- 재처리 대상은 `updated_at`으로 고른다. 취소·결제 실패는 더 바뀌지 않는 상태라 상태가 바뀐 시각과 같다고 본다. 취소·결제 실패 주문을 바꾸는 쓰기를 더하면 재처리와 사람 확인 시점이 밀린다.
- 정리 스케줄러의 `run()`은 결제 대기 정리와 재고 해제 재처리를 따로 부른다. 결제 대기 정리가 대상이 없어 일찍 끝나도 재처리가 돌아야 한다(통합 테스트 `정리할_결제_대기_주문이_없어도_스케줄러가_재고_해제를_다시_부른다`).
- 배포 직후에는 이미 취소·결제 실패된 주문의 해제 칸이 비어 있어, 처음 몇 번의 실행이 한 번씩 다시 해제한다(5분에 100건). 상품의 해제가 같은 결과를 내서 문제는 없고, 지난 해제 실패분도 이때 정리된다.
- #656(결제 만료 요청)은 같은 정리 스케줄러와 `cancelStalePaymentPending`을 고친다. 결제를 요청한 주문을 취소하지 않게 바꿀 때도 취소한 주문은 이 문서의 순서(취소 커밋 → 해제 → 기록)를 따른다.
