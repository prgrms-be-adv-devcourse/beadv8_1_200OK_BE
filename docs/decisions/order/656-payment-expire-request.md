## 배경

정리 스케줄러(#402)는 결제를 요청하고 30분이 지나도 결과가 없는 주문을 지갑에 알리지 않고 취소하고 재고를 풀었다. 지갑이 그 뒤에 결제하면(결과 보내기 지연, 재처리 등) 구매자는 상품 없이 예치금을 잃고, 주문은 `[ORDER_PAID_AFTER_CANCELED]` ERROR 로그만 남겼다. 돈이 움직였는지는 지갑만 안다.

주문 생성 중 보상 취소도 같은 문제가 있었다. 결제 요청(`publishCreated`)을 커밋한 뒤 예외가 나면 결제 요청 시각을 보지 않고 취소했다.

11/16 지갑 담당과 합의했다(#614). 주문은 결제 만료를 요청하고, 지갑은 처리 기록에 실패(`PAYMENT_EXPIRED`)를 먼저 넣어 본 뒤 결과를 보낸다. 이미 결제했으면 결제 완료를 다시 보낸다. 그래서 "취소·실패된 주문에 결제 완료"가 생기지 않아 #517(늦게 온 결제 돌려주기)과 지갑 #612(반환 요청)를 대신한다.

범위 밖: 지갑의 만료 요청 수신(지갑 이슈), 지갑 Spring 길 삭제(#602 후속).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 결제를 요청한 주문의 정리 | 취소하지 않고 결제 대기로 둔 채 `order.order-payment-expire-requested.v1`(키 `orderId`, 값 `orderId`·`buyerId`·`totalAmount`)을 보낸다 | 결론은 돈을 움직인 쪽(지갑)이 낸다. 주문은 지갑이 보낸 결제 완료·실패로만 끝나고, 기존 `completePayment`·`failPayment`를 그대로 쓴다 |
| 다시 요청 | 결과가 올 때까지 정리 스케줄러(5분)가 돌 때마다 다시 보낸다. 컬럼 추가 없음 (11/16 결정) | 요청이 사라져도 저절로 다시 시도된다. 지갑은 같은 요청에 처음 결과를 다시 보낸다 |
| 결제 요청 전 주문 | 지금처럼 5분 지나면 취소하고 재고 해제 | 지갑이 모르는 주문이라 돈이 오가지 않는다 |
| 금액 포함 | 만료 요청에 결제 요청 금액(`totalAmount`)을 담는다 (지갑 리뷰) | 지갑은 처음 보는 주문이면 처리 기록에 만료 실패를 먼저 넣는데, 그 표는 금액이 필수이고 0보다 커야 한다. 늦게 온 주문 생성과 금액이 같아 비교 경고도 나지 않는다 |
| 전달 수단 | Kafka만(#666 outbox). Spring 이벤트로는 보내지 않음 | 지갑이 Kafka로 받기로 했다(#614). 새 메시지라 옮길 Spring 길이 없다 |
| 요청 시 잠금 | 결제 완료·실패와 같은 주문 잠금 후 다시 확인 | 조회 뒤 결과가 먼저 커밋됐으면 요청하지 않는다. 보내도 지갑이 처음 결과를 다시 보내 안전하지만 쓸데없는 메시지다 |
| 보상 취소 | 결제 요청 시각이 있으면 취소하지 않고 `false` (사용자 결정) | 지갑이 이미 결제했을 수 있다. 결제 대기로 남기면 30분 뒤 만료 요청으로 지갑의 결론을 받는다 |
| 답 없는 주문 알림 | 넣지 않음 (사용자 결정) | 지갑의 결과 지연은 지갑 쪽 로그(`[WALLET_SEND_RETRY]`, 실패 기록)로 본다. 요청마다 `[ORDER_PAYMENT_EXPIRE_REQUESTED]` WARN이 남는다 |
| 머지 순서 | 지갑의 만료 요청 수신(#693)이 먼저 머지된 뒤 머지 (사용자 결정, CONVENTION 11.4) | 주문이 먼저 머지하면 결제를 요청한 주문이 취소되지도 답을 받지도 못해 결제 대기로 남고 재고가 묶인다 |

## 버린 대안

- **만료 요청을 한 번만 보내고 시각 칸(`payment_expire_requested_at`)을 둠:** 요청 횟수는 줄지만 칸과 마이그레이션이 늘고, 요청이 사라지면 다시 보낼 기준이 따로 필요하다.
- **오래 답이 없으면(예: 2시간) 지금처럼 취소:** 지갑이 늦어도 재고는 풀리지만, 그 뒤 결제 완료가 오면 지금 문제가 그대로 남는다.
- **보상 취소는 따로 고치기:** 같은 원인(결제 요청 뒤 주문 혼자 취소)이고 고칠 곳이 몇 줄이라 함께 고친다.

## 건드릴 때 주의

- `PAYMENT_TIMEOUT`(30분)은 지갑이 결과 보내기를 다시 시도하는 시간(최대 30분)과 맞춘 값이다. 줄이면 지갑이 아직 다시 보내는 중인 주문에도 만료 요청이 가지만, 지갑이 처음 결과를 다시 보내므로 결과는 같다.
- 결제를 요청한 주문은 결제 완료·실패로만 끝난다. 지갑이 계속 답하지 않으면 결제 대기로 남고 재고도 묶인다. 이때는 지갑 쪽 실패 기록을 본다.
- `[ORDER_PAID_AFTER_FAILED]`, `[ORDER_PAID_AFTER_CANCELED]` ERROR 로그는 안전장치로 남긴다. 이 변경 뒤에는 결제를 요청한 주문이 주문 혼자 끝나지 않아 나오지 않아야 한다.
- 만료 요청은 주문 생성과 토픽이 달라 둘 사이 순서는 지켜지지 않는다. 만료 요청이 먼저 도착해도 지갑이 만료 실패를 먼저 기록해 늦게 온 주문 생성은 차감하지 않는다.
- 결제 만료 실패(`PAYMENT_EXPIRED`)는 다른 결제 실패와 같이 처리한다(결제 실패 커밋 → 재고 해제, #657).
