> 이 문서는 #794 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

주문 outbox 즉시 발송 실행기의 스레드 수(2)와 대기열(1000), 재발송의 주기(30초)와 한 번에 보낼 줄 수(100)는 측정 근거 없는 값이었다. 배송 outbox에서 같은 설정을 부하테스트로 쟀고(#793, 기록은 docs/decisions/delivery/793-outbox-send-drop-when-full.md), 그 값을 주문에 옮긴다.

주문 outbox는 따로 재지 않았다. 발송 작업 하나가 하는 일(줄 읽기, Kafka 전송과 저장 확인, 보냄 기록)이 배송과 같아 같은 값을 쓴다. 이 값들이 주문에서도 맞다는 것은 추론이다.

범위 밖: `min-age`(10초 그대로), 브로커 장애 때 전송이 오래 막히는 문제(배송 #810).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 스레드 수 | 2 → 4 | 배송 측정에서 포화 처리량이 초당 94→159건. 2배가 안 되는 것은 커넥션 풀(10개)이 한계라서로 봤다. 평소 부하에서 버림이 1812→273건으로 줄었고, 과부하 때 API p95는 26→36ms로 조금 늘었다 |
| 대기열 | 1000 → 20 | 과부하에서 대기열 크기는 처리량을 바꾸지 않고 지연만 늘린다. 평소 부하에서 20칸으로도 거의 다 즉시 보냈다. 브로커가 느릴 때(발송 1~2초) 스레드 4·대기열 20은 stale 0, 겹침 0이었고 100칸부터 stale이 1000건 넘게 났다 |
| 재발송 한 번에 보낼 줄 수 | 100 → 300 | 재발송은 한 스레드가 차례로 보내 초당 약 120줄이다. 300줄은 약 2.5초라 주기 안에 끝난다 |
| 재발송 주기 | 30초 → 5초 | 예전 값(초당 3.3줄)이면 과부하 3분 뒤 쌓인 약 4만 줄을 비우는 데 약 3.5시간, 새 값이면 약 12분(추론) |
| ERROR로 올리는 실패 횟수 | 10 → 60 | 주기가 5초로 짧아져, "약 5분 실패하면 사람이 본다"는 뜻을 지키려고 횟수를 늘렸다 |

대기열과 `min-age`의 관계:

- 대기열에서 기다리는 시간은 대략 대기열 크기 / 처리량이다. 배송 측정에서 생성→발송 시간과 맞았다.
- 이 대기가 `min-age`를 넘으면 꺼낼 때 stale로 버려 재발송에 맡긴다.
- stale 확인은 꺼낼 때만 하므로, 꺼낸 뒤 보내는 사이 `min-age`를 넘기면 재발송이 같은 줄을 함께 보낸다(겹침). 그래서 지킬 조건은 대기 + 발송 시간 < `min-age`다. 20칸은 브로커가 느릴 때도 이를 지켰다.

## 버린 대안

- **주문을 따로 측정:** 발송 작업 모양이 같아 결과가 크게 다르지 않을 것으로 보고 하지 않았다. 감수하는 것은 주문 쪽 수치가 추론이라는 점이다.
- **한 번에 1000줄:** 한 번 실행이 약 8초라 5초·10초 주기를 넘겨 cron이 회차를 건너뛰었다.

## 건드릴 때 주의

- 대기열이나 스레드 수를 바꾸면 대기열 크기 / 처리량 + 발송 시간이 `min-age`보다 짧은지 다시 본다. 대기열을 키우면 처리량은 그대로이고 stale·겹침만 는다.
- 재발송 주기를 바꾸면 한 번 실행 시간(줄 수 / 약 120줄)이 주기보다 짧은지, `ESCALATE_ATTEMPT_COUNT`가 약 5분이 되는지 함께 맞춘다.
- (미확인) 측정은 배송 앱 단독, 커넥션 풀 10개 기준이다. monolith에서는 모듈들이 풀을 나눠 써서 스레드 4개의 부담이 더 클 수 있다. 재발송 스케줄러 스레드도 다른 `@Scheduled` 작업과 나눠 쓴다.
