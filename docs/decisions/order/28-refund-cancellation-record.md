## 배경

환불 #513이 판매자 승인 직후 주문의 취소 반영 API(요청서 ②)를 HTTP로 부르는데 주문에 받는 곳이 없었고, 구매확정 이벤트 금액이 환불분을 빼지 않아 부분 환불 뒤 판매자에게 초과 정산될 수 있었다. 범위는 ② 취소 반영과 ③ 구매확정 금액 반영이다.

범위 밖: ① 환불용 조회(#449), 실패 시 되돌리기(#516), 주문 상세에 환불 수량 보여 주기(FE와 따로), 2단계(배송 후 반품)의 구매확정 보류.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 기록 시점 | ②를 받는 즉시(환불 승인 직후) | 환불은 처리 중이 되면 되돌리지 않는다(#413). 완료까지 기다리면 그사이 구매확정이 나서 정산이 초과 지급된다 |
| 주문 상품 상태 | 바꾸지 않음 | 환불 담당과 합의(11/05). 상태를 바꾸면 환불이 멈출 때 주문 상태도 멈춘다. 1단계 환불은 출고 전(PREPARING)만 대상이고 구매확정은 배송 완료(DELIVERED)만 대상이라 겹치지 않는다 |
| 저장 방식 | `order_item_refund` 표, 환불 한 건 = 한 줄, `refund_id` 유니크 | 며칠 뒤 구매확정에서 다시 쓰고, 같은 refundId 재요청을 막으려면 받은 환불 ID를 기억해야 한다. 환불마다 뺀 배송비가 다르다. #516 되돌리기에서 refundId로 기록을 찾는다 |
| 출고된 상품 | 409로 거절 (사용자 결정) | 배송 잠금이 없어(11/04 결정) 승인 뒤 출고를 알아챌 수 있는 곳이 주문뿐이다. 조용히 기록하면 판매자가 그 상품 대금을 못 받고 아무도 모른다. 실패로 드러나야 관리자가 처리한다(멘토 리뷰 변경 제안 3번) |
| 같은 refundId 재요청 | 같은 내용이면 204(다시 기록 안 함), 수량·뺀 배송비가 다르면 409 | 환불 #513 계약. 성공 코드는 주문이 정하기로 되어 있어 204로 정했다 |
| 판단 위치 | `OrderItem.recordRefund`(도메인) | 중복·출고·수량 합계 규칙을 누가 불러도 지키게 한다 |
| 동시 요청 | 주문 비관적 락 + READ COMMITTED | 같은 주문 상품에 환불 두 건이 동시에 와도 합계가 주문 수량을 넘지 않게 한다. 아래 "건드릴 때 주의" 참고 |
| 구매확정 상품 금액 | 판매가 × (산 수량 − 환불 수량) | 환불된 개수는 판매자 몫이 아니다 |
| 구매확정 판매자 배송비 | 묶음 배송비 + 그 묶음 환불에서 뺀 배송비 합계 | 무료배송 묶음이 일부 환불로 기준 아래가 되면 환불이 구매자 환불 금액에서 기본 배송비를 뺀다(`RefundShippingFeePolicy`). 이 돈은 남은 상품의 택배비라 판매자 몫이다 |
| 모두 환불된 상품 | 구매확정 이벤트를 보내지 않음 (사용자 결정) | 같은 묶음이 출고되면 함께 배송 완료가 되어 구매확정 대상이 되지만 정산할 금액이 0이다. 0원 정산 후보를 만들지 않는다 |

## 버린 대안

- **기록 시점:** 환불 완료 알림을 받고 기록하는 처음 합의안은, 그사이 구매확정이 나면 초과 정산된다. 환불이 승인 직후 부르도록 바뀌어(#513) 버렸다.
- **저장 방식:** 주문 상품에 `refunded_quantity` 칸만 두는 방법은 같은 refundId가 다시 왔는지 알 수 없어 수량이 두 번 더해진다. 구매확정 때 환불 모듈에 물어보는 방법은 새벽 배치가 환불 모듈 가용성에 묶이고 모듈 결합이 커진다.
- **상태 변경:** 주문 상품을 `REFUNDED` 등으로 바꾸는 방법은 합의에 어긋나고, 부분 환불(3개 중 1개)을 상태 하나로 표현하지 못한다. 감수하는 것은 모두 환불된 상품도 묶음 출고 때 배송 중·배송 완료로 보이는 점이다.
- **출고된 상품:** 상태를 확인하지 않고 기록하는 방법은 환불 쪽 확인만 믿는 것인데, 승인과 ② 사이의 출고를 놓친다.
- **동시성:** 잠금만 거는 방법은 REPEATABLE READ에서 합계가 넘는다(아래). 주문 ID를 다른 트랜잭션에서 먼저 찾고 잠금 조회를 첫 문장으로 두는 방법도 되지만, 호출이 둘로 나뉜다.

## 건드릴 때 주의

- `recordRefund`는 반드시 READ COMMITTED로 연다. 잠금 쿼리(`findByOrderItemIdForUpdate`)의 하위 쿼리가 일반 조회라 REPEATABLE READ에서는 잠금을 기다리기 전에 스냅샷이 고정되고, 잠금을 얻은 뒤에도 앞 요청이 커밋한 환불 기록이 보이지 않아 합계가 넘는다. 동시성 통합 테스트(`OrderItemRefundApiIntegrationTest`)가 이를 잡는다.
- 이 격리 수준은 내부 API 컨트롤러가 트랜잭션 없이 부를 때만 적용된다. 다른 트랜잭션 안에서 부르면 무시된다(Kafka 컨슈머 등으로 옮길 때 확인).
- `OrderItem.status` 값 이름은 환불이 문자열로 비교한다(①의 `status`). 바꿀 때는 환불 담당과 먼저 협의한다.
- 구매확정 금액 계산(`publishConfirmed`)은 환불 기록이 모두 들어온 뒤에 일어난다는 전제다. 1단계 환불은 출고 전에만 일어나고 묶음은 함께 출고되어 성립한다. 2단계(배송 후 반품)를 넣으면 이 전제가 깨지므로 구매확정 보류를 함께 설계한다.
- #516 되돌리기를 만들 때는 기록을 지우지 않고 되돌림을 표시해, 구매확정 금액 계산에서 빼도록 한다(이 세션의 제안, PR #537 댓글).
