## 배경

배송 완료는 앱 안 이벤트(`CarrierDeliveredEvent`)와 주기적인 조회로만 알 수 있어 택배사가 호출할 HTTP 입구가 없었다. 추적을 요청할 때 택배사에 알림 받을 주소를 등록하고, 택배사가 상태가 바뀔 때마다 보내는 알림을 받는 API를 추가했다. 알림 본문은 택배사 코드와 송장 번호뿐이다.

알림 형식은 가짜 택배사(#559)가 흉내 내는 Delivery Tracker 형식이다. (미확인) 실제 Delivery Tracker가 같은 방식으로 알림을 보내고 재전송하는지는 공식 문서와 대조하지 않았다.

범위 밖: 알림이 한꺼번에 몰릴 때의 처리 한계, 수신 즉시 응답하고 비동기로 처리하는 방식, `track` 응답 필드 확장, 운영 프록시의 경로 전달 설정.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 완료 판정 | 알림을 받으면 택배사에 `track`을 다시 조회하고, `DELIVERED`일 때만 반영한다 | 알림은 상태가 바뀔 때마다 오는데 본문에 상태가 없다. 본문을 믿지 않고 택배사가 확인해 준 상태만 반영하므로 위조된 알림이 와도 영향이 없다 |
| 응답 | 모르는 송장, 이미 완료, 아직 완료가 아님, 조회 오류까지 모두 2XX로 답한다. 비밀값이 틀릴 때만 403 | 택배사는 2XX가 오지 않으면 재전송한다(가짜 택배사 기준 1초 안에 못 받으면 1, 2, 4초 간격으로 최대 5분). 재전송해도 결과가 같은 경우는 받은 것으로 끝낸다 |
| 인증 | 알림 주소의 끝 경로에 비밀값을 둔다. 상수 시간으로 비교하고, 비밀값이 비어 있으면 모든 알림을 거절한다 | 택배사가 인증 헤더를 보내지 않는다(가짜 택배사 기준). 경로나 쿼리에 비밀값을 넣는 방식이 남는다 |
| 기동 검사 | 알림 주소를 넣으면 비밀값이 있어야 하고, 32자 이상이며 주소 끝 경로와 같아야 한다. 어긋나면 앱이 시작되지 않는다 | 어긋나면 알림이 모두 403으로 거절되는데 조회 덕에 겉으로는 정상처럼 보인다(#674 리뷰) |
| 외부 호출 | `track` 조회는 트랜잭션 밖에서 하고, `DELIVERED`가 확인된 뒤에만 행을 잠그고 반영한다 | 외부 호출을 DB 트랜잭션 안에서 하지 않는다. 같은 알림이 동시에 오면 뒤따르는 쪽은 잠금을 기다렸다가 이미 완료된 상태를 만나 그대로 끝난다 |
| 중복 처리 | 인박스 테이블 없이 배송 상태로 멱등하게 처리한다 | 완료 반영이 상태로 멱등하고, 알림에 고유 ID가 없어 거를 키가 없다. 유실은 폴링이 메운다 |
| 폴링 | 레거시로 유지한다 (사용자 결정) | 알림 유실, 등록 실패, 알림 뒤 조회 실패를 메운다 |
| 알림 등록 | 추적을 요청할 때 조회용 스레드에서 비동기로 등록하고, 실패해도 출고를 막지 않는다. 앱이 시작할 때 배송 중인 건을 다시 요청해 등록도 함께 복구한다 | 등록은 외부 호출이라 요청 스레드를 붙잡지 않게 한다. 재시작으로 사라진 추적 요청을 복구하는 기존 경로를 그대로 쓴다 |
| 등록 유효기간 | 기본 48시간이고 만료 전에 다시 등록하지 않는다 | 가짜 택배사가 자체 등록에 쓰는 값에 맞췄다. 만료 뒤는 폴링이 맡는다. (미확인) 실제 택배사의 권장 기간은 확인하지 못했다 |
| 공개 경로 | `common`의 `SecurityConfig` 공개 경로에 알림 경로 하나만 추가한다 | 택배사는 로그인할 수 없다. 하위 경로까지 열리지 않도록 경로를 하나씩 지정하는 기존 방식을 따랐다 |

## 버린 대안

- **인증:** shipment마다 다른 주소와 서명 토큰을 쓰는 방식(리뷰 제안)은 이번에 하지 않았다. 알림 주소는 등록할 때마다 정할 수 있어 가능한 방식이지만, 지금은 비밀값 하나를 모든 shipment가 공유한다. 감수하는 것은 한 번 새면 전체가 노출되고, 교체 중에 옛 값과 새 값을 함께 받는 기간이 없다는 점이다. (미확인) 실제 택배사가 shipment마다 다른 주소를 받아 주는지는 확인하지 못했다.
- **처리:** 받은 알림을 DB에 저장하고 비동기로 처리하는 인박스(리뷰 제안)는 쓰지 않았다. 감수하는 것은 알림을 받은 뒤 `track` 조회가 실패하면 그 알림이 사라진다는 점이다. 택배사는 2XX를 받아 재전송하지 않으므로 다음 알림이나 폴링이 돌 때까지(운영 폴링 기본 5분) 완료가 늦어진다.

## 건드릴 때 주의

- 폴링을 없애려면 먼저 받은 알림을 저장하고 재시도하는 장치가 있어야 한다. 지금은 알림 뒤 조회 실패와 만료 뒤 알림 중단을 폴링만 메운다.
- 알림 주소의 끝 경로가 비밀값이라 앞단 프록시의 접근 로그에 남을 수 있다. 운영에서 택배사가 닿으려면 nginx와 프론트 BFF가 이 경로를 delivery로 넘겨야 한다. (미확인) 운영 프록시 설정은 확인하지 않았다.
- 알림 등록이 조회와 같은 스레드 하나에서 돈다. 기동 복구 때 배송 중인 건이 많으면 등록이 쌓여 조회가 밀릴 수 있다.
- `CarrierNotificationFacade.deliver`는 `RestApiException` 전체를 "이미 반영됨"으로 삼킨다. 다른 비즈니스 예외도 같은 로그로 묻힐 수 있다.
- 택배사 종류가 `mock`이면 알림 경로는 동작하지 않고 알림은 무시된다. 의도한 동작이다.
- 설정 이름이 monolith와 모듈 단독 실행에서 다르다. monolith가 없어지면 `TrackerProperties`의 등록 유효기간 기본값 처리도 정리할 수 있다.
