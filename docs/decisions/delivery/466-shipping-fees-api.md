> 이 문서는 #466 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

주문은 이미 `POST /internal/v1/delivery/shipping-fees`를 부르는데(#342) 배송에는 이 경로가 없어, 같은 프로세스로 띄우면 주문 생성이 전부 실패했다. 배송 생성은 `charged_shipping_fee`를 저장하지 않아 항상 0이었고, 무료배송 기준이 없는 판매자는 결제 완료 이벤트가 만들어지거나 처리될 때 실패할 수 있었다.

범위 밖으로 둔 것은 둘이다. 주문의 실제 클라이언트와 배송 엔드포인트의 정식 연동 테스트는 #492로 분리했다. 이벤트에 주문이 받은 배송비를 실어 배송이 계산한 값과 대조하는 장치는 이 작업에 넣지 않았다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 계산 정책 | 견적과 같은 `ShippingFeePolicy.calculate`를 재사용 | 같은 입력이면 같은 금액이어야 견적에서 보여 준 금액과 결제 금액이 어긋나지 않는다 |
| 응답 의미 | `baseShippingFee`는 판매자 설정 값, `shippingFee`는 무료배송 적용 후 값, 기준이 없으면 `freeShippingThreshold`는 null | 주문이 설정 값을 결제 이벤트에 그대로 담고 배송이 그 값으로 다시 계산하는 계약이다. 견적 응답의 `baseShippingFee`와 뜻이 다르지만 주문 쪽 이름 때문에 바꾸지 못해 문서로 구분했다 |
| 판매자 응답 | 요청한 모든 판매자를 요청 순서대로 응답. 설정이 없는 판매자는 기본 설정, 미등록 우편번호는 일반 지역 | `getSettings`가 모든 판매자를 채워 주고, 주문이 판매자 ID로 응답을 맞춘다 |
| 요청 검증 | 견적의 요청 DTO를 함께 사용. 중복 판매자와 우편번호 오류는 422로 거절 | 검증 규칙을 한곳에 둔다. 422는 견적 API와 프로젝트 검증 실패 응답이 쓰는 코드라 따랐다(구현 때 정했고 리뷰에서 바꿀 수 있다) |
| 부과 배송비 | 배송 생성 때 결제 시점 이벤트 값(기본 배송비, 무료배송 기준, 추가 운임)과 품목 단가×수량 합계로 계산해 저장 | 판매자 설정을 다시 읽으면 결제 뒤 설정이 바뀐 경우 결제 금액과 달라진다 |
| 무료배송 기준 null | `PaidSellerOrder`에서 이 필드만 null 허용(음수는 거부), 배송은 null을 그대로 저장 | DB 컬럼과 주문 도메인은 이미 null을 허용한다. null은 "무료배송 없음", 0은 "항상 무료"라 의미가 다르다 |
| `remote-area-fee` | 삭제 | 주문이 더 이상 부르지 않고 저장소에 호출처가 없다 |

## 버린 대안

- **부과 배송비:** 배송 생성 때 판매자 설정을 다시 조회해 계산하는 방법은 결제 뒤 설정이 바뀌면 결제 금액과 어긋나 버렸다. 감수하는 것은 이벤트 값이 틀려도 배송이 알아채지 못한다는 점이다.
- **null 처리:** 무료배송 기준이 없을 때 0이나 큰 값을 넣는 방법은 "항상 무료"나 임의 기준과 구분되지 않아 버렸다.
- **요청 DTO:** 내부 API 전용 요청 DTO를 따로 만들면 우편번호 정규식, 판매자 수 제한, 중복 검사가 복붙된다. 감수하는 것은 견적 DTO를 고치면 이 API도 함께 바뀐다는 점이다.
- **`remote-area-fee` 유지:** 호출처가 없는 경로를 남기면 주문 계약이 둘로 보여 버렸다.

## 건드릴 때 주의

- 배송의 부과액은 주문의 상품 금액 정의(품목 단가×수량의 합)와 같아야 한다. 이벤트에 주문이 받은 배송비가 없어 둘이 어긋나도 배송은 알 수 없다. 주문의 금액 정의를 바꾸면 `ShipmentService`의 부과 배송비 계산도 함께 바꾼다.
- `SellerShippingSetting`은 마감 시간이 필수라, 결제 시점 값으로 설정 객체를 만들 때 현재 설정의 마감 시간을 넘긴다. 이 값은 배송비 계산에 쓰이지 않는다.
- 이 경로는 인증이 없고 내부 호출용이다. 앱이 같은 컨테이너에서 온 요청만 받고 nginx가 막는 전제에 기대므로, 이 전제를 바꾸면 이 API도 함께 다시 본다.
- (미확인) 모듈별 서버 배포로 바뀌면 신버전 주문이 아직 없는 `shipping-fees`를 부를 수 있으므로 배송을 먼저 배포해야 한다. 지금은 운영 앱이 하나이고 내부 호출이 같은 컨테이너 안에서 끝나 해당하지 않는다.
- 요청 DTO는 견적과 공유한다. 견적에 구매자용 제약이 생기면 이 API가 영향을 받으니 그때 DTO를 나눈다.
