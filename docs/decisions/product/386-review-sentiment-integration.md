## 배경

#385에서 고른 Jev로 상품 리뷰의 전체 감성과 여섯 분석 항목 감성을 분석해 판매자에게 보여 준다. #386은 작업을 티켓 네 개로 나눴다. 01은 분석 요청, 작업자, 결과 저장, 판매자 감성 집계 API, 기존 리뷰 백필이다. 02는 실제 Jev 연동, 03은 수정·삭제·내용 없는 리뷰 반영, 04는 백오프 재시도와 최종 실패 기록이다. 이 문서는 01까지의 결정을 담고, 나머지 티켓을 마치면서 덧붙인다. 티켓 계획은 이 세션 전에 정해졌고, 이 세션에서는 계획을 다시 설계하지 않았다.

## 버린 대안

- **백필을 표 생성 파일에 함께 넣기:** 이슈 01의 문구는 이쪽이었다. 버린 이유는 백필 SQL만 따로 실행해 테스트할 수 없어서다. 감수하는 것은 마이그레이션 파일이 하나 늘어나는 점이다.
- **분석기 계약을 `review/service`에 두기:** 패키지 순환 규칙에 걸려 버렸다.
- **표 이름에 `product_` 접두사:** 제약 이름 길이 한도 때문에 버렸다. 감수하는 것은 모듈의 다른 표(`product_review` 등)와 이름 규칙이 어긋나는 점이다.
- **작업자 간 잠금(행 잠금으로 꺼내기 등):** 간헐적인 중복이라 넣지 않았다. 감수하는 것은 겹친 요청의 분석기 호출 비용이 두 번 드는 점이다.
- **모델명 칼럼 늘리기:** 주석만 남기기로 했다.

## 건드릴 때 주의

- `criteria.json`의 질문 키나 선택지를 바꾸면 앱이 뜨지 않는다. 의도한 동작이다. `ReviewAspect`, `Sentiment`, `AspectSentiment`를 함께 고치고, 기준을 바꿀 때 지킬 절차는 #385 문서의 "건드릴 때 주의"를 따른다.
- 모델명이 50자를 넘으면 결과를 저장하지 못한다. 요청이 대기로 남아 5초마다 다시 분석되고 ERROR 로그가 쌓인다.
- 실제 분석기를 추가하면 임시 분석기(`UnconnectedReviewSentimentAnalyzer`)를 지운다. 둘 다 남으면 같은 인터페이스의 빈이 둘이 되어 주입이 모호해진다.
- 분석 요청과 결과 표가 `product_review`를 FK로 가리킨다. 테스트에서 리뷰 행을 지우려면 분석 요청과 결과를 먼저 지운다.
- 통합 테스트는 스케줄러를 켜지 않고 `ReviewSentimentAnalysisFacade.analyzePending()`을 직접 부른다. Fake 분석기는 `testsupport`에 한 번만 등록되어 있다.
