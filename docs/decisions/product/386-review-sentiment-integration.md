> 이 문서는 #386 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

#385에서 고른 Jev로 상품 리뷰의 전체 감성과 여섯 분석 항목 감성을 분석해 판매자에게 보여 준다. 작업은 티켓 네 개로 나눴다. 01은 분석 요청, 작업자, 결과 저장, 판매자 감성 집계 API, 기존 리뷰 백필이다. 02는 실제 Jev 연동, 03은 수정·삭제·내용 없는 리뷰 반영, 04는 백오프 재시도와 최종 실패 기록이다. 티켓 계획은 구현 전에 정해졌고, 구현 중에는 다시 설계하지 않았다. 02와 03·04는 별도 에이전트 세션이 동시에 구현했다. 그 티켓들의 결정 이유는 각 세션이 남긴 메모에서 옮겼다. 구매자 키워드 분석은 범위 밖이다.

## 버린 대안

- **백필을 표 생성 파일에 함께 넣기:** 백필 SQL만 따로 실행해 테스트할 수 없다. 감수하는 것은 마이그레이션 파일이 하나 늘어나는 점이다.
- **표 이름에 `product_` 접두사:** 제약 이름 길이 한도 때문에 버렸다. 감수하는 것은 `product_review` 등과 이름 규칙이 어긋나는 점이다.
- **#385 실험의 섞기 함수(FNV-1a + mulberry32)를 Java로 옮기기:** 이슈는 "리뷰 ID를 시드로"만 요구한다. 감수하는 것은 같은 리뷰라도 실험과 서비스의 선택지 순서가 다른 점이다.
- **Jev 빈을 작업자 켜기 설정에 걸기:** 작업자가 꺼진 로컬에서 분석기 빈이 없어 앱이 뜨지 않는다.
- **응답의 남는 답 키를 최종 실패로 보기(#385 실험 방식):** 이슈에 없는 실패 조건이라 무시한다.
- **결과 행을 지우고 새로 넣기:** 엔티티 규칙이 `repository.delete(...)`를 막는다.
- **ShedLock으로 작업자를 한 대에서만 돌리기:** 라이브러리와 잠금 표가 늘고, 앱을 늘려도 처리량이 그대로다. 임대는 기존 `next_attempt_at` 칼럼만 쓴다. 감수하는 것은 작업자가 도중에 멈추면 꺼낸 요청이 최대 10분 늦게 다시 처리되는 점이다.
- **서비스가 예외 타입을 보고 재시도 여부를 정하기:** "분류 못 한 예외는 최종 실패" 규칙이 두 곳으로 흩어진다.
- **재시도 5회 소진 통합 테스트:** 통합 테스트의 Clock이 시스템 시계라 시간을 넘길 수 없다. 도메인 테스트가 고정 시각으로 확인한다.

## 건드릴 때 주의

- `criteria.json`의 질문 키나 선택지를 바꾸면 앱이 뜨지 않는다. 의도한 동작이다. enum을 함께 고치고 #385 문서의 "건드릴 때 주의"를 따른다. 선택지 순서나 개수를 바꾸면 같은 리뷰 ID라도 섞인 순서가 달라진다.
- 리뷰 행을 바꾸는 새 경로를 만들면 그 경로도 분석 요청을 되돌려야 한다. 아니면 리뷰가 집계에서 빠진 채 다시 분석되지 않는다.
- 무엇을 재시도할지는 분석기 구현이 정한다. 분석기가 `RestClientException` 등을 감싸지 않고 던지면 첫 시도에 최종 실패가 된다.
- 모델명이 50자를 넘거나 결과 저장이 실패하면 시도 횟수에 들지 않고 임대 시간(10분)마다 다시 꺼내져 Jev를 다시 부르고 ERROR 로그가 쌓인다. 따로 막지 않기로 했다(사용자 결정).
- 최종 실패 ERROR 로그는 원인 예외를 스택 트레이스째 남겨 Jev 응답 본문이 찍힌다. 로컬에서 401로 확인했다. 정리는 #426이다.
- 한 번 실행이 임대 시간(10분)보다 길어지면 아직 처리 중인 요청을 다른 작업자가 다시 꺼낸다. 배치 크기, Jev 시간 초과, 임대 시간 중 하나를 바꾸면 이 관계를 다시 맞춘다.
- ERROR 로그는 커밋 전에 남는다. 커밋이 실패하면 로그는 최종 실패인데 행은 대기로 남는다.
- monolith에는 `RestClient` 빈이 둘(토스, Jev) 있고 필드 이름으로 고른다. 필드 이름을 바꾸면 주입이 모호해진다.
- API 키 없이 작업자를 켜면 401로 최종 실패한다. 운영 compose는 막지만 jar를 직접 실행하면 막지 못한다.
- 분석 요청과 결과 표가 `product_review`를 FK로 가리킨다. 테스트에서 리뷰 행을 지우려면 둘을 먼저 지운다. 통합 테스트는 스케줄러를 켜지 않고 `analyzePending()`을 직접 부르고, Fake 분석기는 `testsupport`에 한 번만 등록되어 있다.
