> 이 문서는 #718 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

검색 품질은 저장소 밖 스크립트를 사람이 돌려야 보였다. 점수식이나 정규화를 바꾼 PR이 recall을 깎아도 CI는 통과했다. 이어지는 #719(가공품 감점), #720(오타 제안)이 점수와 응답을 바꾸므로, 그 전에 측정 장치를 저장소 안에 두었다. 하한값 자체(1.0)는 #659에서 정했고 이 작업은 그 값을 바꾸지 않는다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 평가셋 위치 | 테스트 리소스(`search-eval/`)에 통째로 둔다 (사용자 결정) | 저장소 밖 경로를 읽으면 CI와 다른 사람 환경에서 돌지 않는다. 합성 데이터라 운영 정보가 없다. 생성 스크립트는 밖에 있어 파일을 손으로 고치지 않고 통째로 바꾼다 |
| 검색 경로 | 서비스가 아니라 `BuyerProductQueryJdbcRepository`를 운영 하한 1.0으로 직접 호출 | 테스트 설정(`module-test.yml`)의 하한은 상품 10개 안팎인 다른 테스트에 맞춘 0.5다. 서비스를 거치면 운영과 다른 하한으로 재게 된다. 0.5로 재면 typo recall이 0.818, 1.0이면 0.798로 달랐다 |
| 지표 | recall@10과 MRR(상위 10개 안 첫 정답의 역순위) | recall@10은 정답이 10개보다 적으면 상위 10개 안의 순서 변화를 보지 못한다. #719의 개선이 recall로는 보이지 않아 MRR을 더했다 |
| recall 정의 | `상위 10개 중 정답 수 / min(10, 정답 수)`의 검색어 평균 | 탐색 실험(E0~E3)과 같은 정의여야 기존 수치와 비교할 수 있다 |
| 하한 | 이 브랜치에서 잰 값을 소수 둘째 자리에서 버린 값 | 시드와 검색어가 고정이라 결과도 고정이다. 0.01 이상 떨어지면 실패하게 해 작은 회귀도 PR에서 드러나게 한다 |
| 격리 | 시작과 끝에 `product_search`를 `TRUNCATE`하고 상품을 지운다 | FULLTEXT 점수는 전체 문서 수(IDF)에 따라 달라진다. 앞서 돈 테스트의 잔여 행이나 DELETE 흔적이 있으면 숫자가 실행 순서에 따라 바뀐다 |

## 버린 대안

- **서비스 경로로 측정:** 실제 사용자 경로와 가장 가깝지만 테스트 설정 하한을 쓰게 된다. 감수하는 것은 서비스의 정렬 결정(`ProductSort.resolve`)을 거치지 않는 점이다. 테스트는 정확도순을 직접 넘긴다.
- **넉넉한 하한(예: PRD 목표 0.85·0.90):** 목표를 넘는 한 회귀가 나도 통과해 장치 구실을 못 한다.

## 건드릴 때 주의

- 점수식·정규화·품목 사전을 바꾸면 이 테스트의 숫자가 바뀐다. 오르면 하한을 올리고, 내리면 PR에서 이유를 밝힌 뒤 내린다.
- 운영 하한(`application-product.yaml`, monolith `application.yaml`)을 바꾸면 테스트의 `PRODUCTION_MIN_SCORE`도 함께 바꾼다. 자동으로 따라가지 않는다.
- 상품 300개 기준 숫자다. 상품 수가 다른 데이터(예: 로컬 5,000개)에서 잰 recall과 비교하지 않는다.
- (미확인) 리뷰 테이블에 다른 테스트가 행을 남기면 FK 때문에 상품 삭제가 실패한다. 지금은 리뷰 테스트가 스스로 비운다.
