## 배경

출시 후 구매자가 무엇을 검색했는데 못 찾았는지 알 방법이 없다. 0건 검색어 조회(#745), 태그·동의어 보강, 막연한 검색어 비율 확인이 모두 이 로그를 입력으로 쓴다. 범위는 구매자 키워드 검색의 기록과 보존 기간 정리다. 집계 화면과 판매자 검색은 범위 밖이다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 남기는 검색 | 검색어가 있는 첫 페이지(`page=0`)만. 정렬·필터만 바꾼 첫 페이지 재조회는 다시 남는다 | 다음 페이지마다 남기면 같은 검색이 여러 번 세어져 0건 비율이 틀어진다. 서버는 재조회와 새 검색을 구분할 수 없다 |
| 남기는 값 | 원문, 정규화 후 공백을 없앤 검색어(`compact`), 전체 결과 수, 지연, 제안 여부, 검색 시각 | 띄어쓰기만 다른 검색어를 #745에서 한 항목으로 묶는다. 결과 수는 페이지 개수가 아니라 전체 수여야 0건 판정에 페이지 크기가 섞이지 않는다 |
| 지연 범위 | 검색 SQL과 상품 조회만. 오타 제안과 로그 저장은 빠진다 | 검색 품질·성능을 보는 값이라 검색 경로만 잰다 |
| 남기지 않는 값 | 회원 ID, IP. 실패 WARN 로그에도 원문을 넣지 않는다 | 구매자가 검색창에 개인정보를 넣을 수 있다. 집계에는 사람을 알 필요가 없다 |
| 실행기 | 공통 `AsyncExecutorFactory`가 아니라 전용 `ThreadPoolTaskExecutor`(스레드 2, 대기열 1000). 가득 차면 거절하고 기록하는 쪽이 버린다 | 공통 실행기는 가득 차면 넘기는 스레드가 기다려 구매자 검색 응답이 로그 저장에 묶인다. 스레드는 DB 커넥션을 하나씩 잡아 적게 둔다 |
| 실패 처리 | 저장 실패도 버리고 WARN만 남긴다. 재시도하지 않는다 | 로그 한 행보다 검색 응답이 중요하다(이슈 완료 조건) |
| 서비스 경계 | 검색과 오타 제안을 `searchVisibleProducts` 한 번으로 합치고 `ProductSearchResult`로 돌려준다. #720 ADR의 "별도 메서드" 결정을 바꾼다 | 로그가 결과 수와 제안 여부를 함께 알아야 한다. #720 ADR이 이 경우 경계를 다시 본다고 남겨 두었다 |
| 보존 기간 | 기본 90일, `product.search.log.retention`으로 바꾼다. 날마다 04:30에 날짜 단위로 자른다 | PRD 7.3에서 아직 미결이라 바꿀 수 있게 둔다. 날짜로 자르는 것은 #745가 기간을 날짜로 받아, 마지막 날의 로그가 시각에 따라 일부만 남지 않게 하려는 것이다 |
| 지우는 방식 | soft delete가 아니라 행을 지우고, 한 문장 `delete`로 지운다 | 보관할 이유가 없는 로그다. 파생 delete는 행마다 읽고 지운다 |

## 버린 대안

- **공통 비동기 실행기 사용:** 설정이 한 곳에 모이지만, 가득 찼을 때 검색 스레드가 기다린다. 감수하는 것은 실행기 설정이 `app.async.executors`가 아니라 `product.search.log.*`에 따로 있다는 점이다.
- **(미확인) 회원 ID 저장:** 개인화 분석에는 쓸 수 있지만, 이슈와 PRD가 처음부터 남기지 않기로 했다. 비교 검토 기록은 없다.

## 건드릴 때 주의

- 실행기 설정 키는 `application-product.yaml`과 monolith `application.yaml` 두 곳에 같은 값으로 있다. 하나만 바꾸면 모듈 단독 실행과 운영 값이 달라진다.
- 테스트 설정은 스레드를 1로 둔다. 로그가 들어온 순서대로 저장돼야 테스트가 나중 검색의 행을 보고 앞선 저장이 끝났다고 판단한다.
- `searched_at`은 검색 시각이고 `created_at`은 저장 시각이다. 저장이 비동기라 둘이 다르다. 집계는 `searched_at`으로 한다.
- 보존 기간을 줄이면 #745의 조회 가능 시작일도 함께 당겨진다.
- 시간 초과로 실패한 검색은 남지 않는다. 결과 수를 모르고, 기존 WARN 로그가 이미 있다.
