## 배경

정산 데이터는 쌓기만 하므로, 다른 모듈이 금액을 잘못 보내면 고칠 수단이 관리자 조정(차액만큼 후보를 한 줄 더 넣음)뿐이다. 조정 API는 501로 막혀 있었다.
#552부터 금액 검사가 조정을 모두 빼서, 조정을 넣어도 금액 불일치 주문이 풀리지 않았다.
범위 밖: 배송비 조정(요청 모양으로 가리킬 수 없음), 양수 조정 상한(#388 M7), 보류 판매자 관리자 화면, TODO(#67).

## 결정과 이유

| 결정 | 선택 | 이유 |

| 조정 정산 시점 | 원래 후보를 따라감. 원래가 대기 중이면 같이 기다리고, 이미 정산됐으면 다음 배치에 바로 | 조정만 먼저 정산되면 받지도 않은 돈에서 빠지거나, 원래가 먼저 나가고 음수만 남아 회수가 어려움 (사용자 결정) |

## 버린 대안

- **미리 넣은 조정:** 확인 조건의 하한(실패 뒤)을 없애면 실패 전에 다른 이유로 넣은 조정이 해결만으로 초과 청구를 가림. 감수하는 것은 실패 전에 미리 넣은 관리자가 한 번 더 넣으면 두 번 빠지는 것(예: 29,100 대신 19,400). 안내문 순서("실패 → 조정 → 다시 처리")를 어긴 관리자 실수로 보고, 반대 금액 조정으로 상쇄함 (사용자 결정)
- **보류 창:** "어제 하루 draft"는 배치가 하루 멈추면 사슬이 끊겨 보류 후보를 기록 없이 영영 놓침. "오늘 − 30일"은 30일 연속 멈추면 놓침
- **수수료 짝 "원래 짝이 맞으면 통과":** 대금만 −10,000이면 판매자 300원 덜 받음을 아무도 못 잡음
- **시스템 몫 보류:** 보류 조회가 판매자 draft에서만 출발해 시스템 후보를 다시 찾을 길이 없음. 감수하는 것은 큰 음수 수수료 조정이면 시스템 정산이 음수 줄로 남는 것(지갑·대사로 가지 않음)
- **보류 판매자 화면:** 새 API라 범위 밖. 로그 한 줄로 찾게 함

## 건드릴 때 주의

- 금액 검사 세 조회(초과 청구 합계·근거, 수수료 짝)는 `checkedCandidate` 하나를 씀. 범위를 따로 바꾸면 검사한 돈과 지급하는 돈이 어긋남
- 확인한 조정의 시각 비교는 세 표의 `created_at`(JPA Auditing, 같은 JVM 시계, DATETIME(6))에 기댐. 서버를 나누면 시계 차를 다시 볼 것
- 확인하지 않은 조정도 스냅샷에는 들어가 지급됨. 양수 조정은 검사 없이 나감(상한은 #388 M7)
- 판매자 보류를 draft 단계로 옮기지 말 것: verify가 "draft에 없는 스냅샷 후보"를 누락으로 보고 주문을 잠금
- `HELD_LOOKBACK_DAYS`를 하한(대기 + 여유)보다 좁히면 보류 후보를 놓칠 수 있음
