## 버린 대안

- **미리·해결 뒤 넣은 조정:** 확인 조건의 하한(실패 뒤)을 없애면 실패 전에 다른 이유로 넣은 조정이 해결만으로 초과 청구를 가림. 감수하는 것은 실패 전에 미리 넣었거나 해결 뒤에 넣은 조정은 다시 해결해도 안 세어, 한 번 더 넣으면 두 번 빠지는 것(예: 29,100 대신 19,400). 순서를 어긴 관리자 실수로 보고, 멈춘 뒤 맞는 조정 → 해결 → **해결한 뒤에** 먼저 넣은 조정의 반대 금액 조정으로 상쇄 (사용자 결정, Spec에 안내). 반대 조정을 해결 전에 넣으면 그것도 확인한 조정이 되어 다시 막히고, 그때 한 번 더 넣으면 판매자가 덜 받음(11/18 바로잡음, 테스트 `미리_넣은_조정은_해결한_뒤_반대_조정을_넣어_상쇄하면_합계가_맞는_금액이_된다`)
- **틀린 항목에 넣은 조정 막기:** 초과 청구는 주문 단위 판정이라 어느 상품이 틀렸는지 코드가 모름. 근거의 "넘게 만든 주문상품"도 틀린 항목이라는 뜻이 아님. 같은 주문 다른 항목에 넣으면 검사는 통과하고 판매자끼리 돈이 잘못 나뉨 → 관리자 실수로 보고 Spec 안내, 반대 금액 조정으로 상쇄 (검토자 4명 일치)
- **보류 창:** "어제 하루 draft"는 배치가 하루 멈추면 사슬이 끊겨 보류 후보를 기록 없이 영영 놓침. "오늘 − 30일"은 30일 연속 멈추면 놓침. draft amount ≤ 0으로 좁히기는 결과 검증으로 항목을 뺀 뒤 보류된 판매자를 놓침
- **수수료 짝 "원래 짝이 맞으면 통과":** 대금만 −10,000이면 판매자 300원 덜 받음을 아무도 못 잡음
- **시스템 몫 보류:** 보류 조회가 판매자 draft에서만 출발해 시스템 후보를 다시 찾을 길이 없음. 감수하는 것은 큰 음수 수수료 조정이면 시스템 정산이 음수 줄로 남는 것(지갑·대사로 가지 않음)
- **원래 없는 조정을 실패로 기록:** #549 횟수에 들어 주문 전체가 멈추고, 반대 조정도 원래가 없어 422라 관리자가 풀 수 없음

## 건드릴 때 주의

- 금액 검사 세 조회(초과 청구 합계·근거, 수수료 짝)는 `checkedCandidate` 하나를 씀. 범위를 따로 바꾸면 검사한 돈과 지급하는 돈이 어긋남. 예외: 판매자 보류(commit)는 검사 뒤라, 보류된 음수는 검사에 들고 이번 지급에서 빠짐
- 확인한 조정의 시각 비교는 세 표의 `created_at`(JPA Auditing, 같은 JVM 시계, DATETIME(6))에 기댐. 서버를 나누면 시계 차를 다시 볼 것
- 확인하지 않은 조정도 스냅샷에는 들어가 지급됨. 양수 조정은 검사 없이 나감(상한은 #388 M7)
- 판매자 보류를 draft 단계로 옮기지 말 것: verify가 "draft에 없는 스냅샷 후보"를 누락으로 보고 주문을 잠금
- `HELD_LOOKBACK_DAYS`를 하한(대기 + 여유)보다 좁히면 보류 후보를 놓칠 수 있음
- 정산 상세 수수료의 짝 기준을 대금 조정으로 넓히지 말 것: 대금 조정은 원래가 정산된 뒤 다른 정산에 들어가, 같은 수수료가 두 상세에 붙음
- 조정 조회는 정산이 끝난 조정까지 지금까지 넣은 조정을 모두 읽음(쌓이는 속도가 느려 알고 감). 보류 조회는 창 안 판매자 draft 전부를 읽음. 대량에서의 시간은 #304
