## 배경

#568 해결 API는 해결한 순간의 결과만 돌려주고, #569 관리자 목록은 해결된 주문을 뺀다. 그래서 "누가·언제·왜 풀었나"를 나중에 볼 곳이 없었다. 판매자 문의("막혀 있던 정산이 왜 오늘 나갔나요?")에 답할 근거가 필요하다.

구현 전에 이슈를 규칙 대조·정산 흐름·반박 세 갈래로 점검했고, 그 결과로 이슈의 조회 조건과 응답 모양을 바꿨다.

범위 밖: 판매자 ID·기간으로 찾기(해결 기록 표에 판매자 칸·인덱스가 없음), 해결 뒤 다시 검사한 결과 보여 주기(정산 항목 조회로 확인).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 찾는 조건 | 주문 ID 하나 (처음 이슈의 "주문 ID 또는 주문상품 ID"에서 바꿈, 사용자 결정) | 막고 푸는 단위가 주문이다(잠금·멈춤 모두 order_id 기준). 주문상품 ID로 찾으면 배송비 줄(주문상품 ID 없음)과, 주문이 막힌 뒤 들어와 실패 기록 없이 빠졌던 상품이 빈 결과로 나와 "해결 안 됨"으로 오해한다. 판매자 정산 응답에 주문 ID가 늘 함께 있어 주문 ID를 모르는 경우가 없다 |
| 보기 | 1줄씩(실패 기록 1건 = 1줄)과 묶음(해결 요청 1번 = 1줄) 둘 다, 프런트가 고름 (사용자 결정) | 해결 1번에 실패 기록 수만큼 줄이 생긴다. 예) 상품 2개 + 배송비 주문이 3번 실패하면 15줄이 같은 관리자·메모로 나온다. 어느 실패를 풀었는지는 1줄씩, 누가 언제 왜는 묶음이 보기 쉽다 |
| 묶는 기준 | 해결 기록에 해결 요청 번호 칸을 더하고 요청마다 서비스가 UUID 하나를 만들어 모든 줄에 넣음 (사용자 결정) | 해결 시각은 줄마다 따로 찍혀(`@CreatedDate`, 마이크로초) 같은 요청도 다를 수 있다. 시각으로 묶으면 한 요청이 쪼개진다 |
| 요청 번호 값 | UUID 문자열, VARCHAR(36) | DB에 번호를 먼저 받으러 가지 않고(별도 표·시퀀스 없음) 동시에 다른 주문을 해결해도 겹치지 않는다. 레포에 CHAR 선례가 없어 VARCHAR |
| URL | `/orders/{orderId}/resolutions`, 묶음은 `/orders/{orderId}/resolution-requests` | api.md "리소스는 복수형 명사". "해결 요청"은 관리자가 한 번 누른 실제 단위라 리소스로 이름 붙인다 |
| 1줄씩 칸 | 해결 기록 + 실패 기록(사유·범주·상세·판매자·실패 시각) + 실패한 정산후보(종류·금액), 16칸 | 같은 주문상품의 대금·수수료 줄은 종류 칸이 없으면 구별할 수 없다(사용자 결정). 상세·판매자는 판매자 문의에 답하는 근거다 |
| 묶음 칸 | 요청 번호·주문·방법·관리자·해결 시각·메모·해결한 실패 기록 수 | 사유별 개수·상세는 1줄씩 보기에서 같은 요청 번호로 찾는다 |
| 범주 | 이 API가 처음 내보냄, enum 이름 문자열. #569는 이 모양을 따름 | 순서가 #571 → #569라 먼저 하는 쪽이 모양을 정한다 |
| 해결 기록이 없는 주문 | 200 빈 목록 | 정산은 주문 표가 없어 없는 주문을 구별할 수 없다 (#568과 같은 이유) |

## 버린 대안

- **주문상품 ID로도 찾기:** 위 "찾는 조건"의 오해 때문에 버렸다. "둘 다 없으면 오류", "둘 다 주면 둘 다 맞는 것" 규칙과 주문상품 ID 인덱스도 함께 필요 없어졌다. 감수하는 것은 상품 하나만 서버에서 거르지 못한다는 점(줄마다 주문상품 ID가 있어 프런트에서 거른다).
- **1줄씩만 주고 Swagger에 설명:** 가장 작지만 같은 메모가 반복되어 보기 불편하다.
- **조회할 때 주문·관리자·시각으로 묶기:** 표는 안 바뀌지만 시각이 줄마다 달라 한 요청이 쪼개질 수 있다.
- **해결 요청 표를 따로 두기, 첫 해결 기록 ID를 번호로 쓰기:** 앞은 표와 저장 단계가 늘고, 뒤는 저장 뒤 고쳐야 하는데 해결 기록은 고치지 않는 표(@Immutable)다.
- **`/resolutions/grouped`:** grouped는 형용사라 api.md 리소스 이름 규칙에 맞지 않는다.

## 건드릴 때 주의

- 묶음 조회는 요청 번호와 함께 주문·방법·관리자·메모를 GROUP BY에 둔다. 같은 요청의 이 값들은 같다는 전제다(서비스가 한 요청에서 같은 값으로 저장). 요청 안에서 값이 달라질 수 있게 바꾸면 한 요청이 여러 줄로 갈라진다.
- 묶음의 해결 시각은 그 요청에서 가장 이른 줄, 같으면 id가 큰 요청이 먼저다. 1줄씩은 해결 시각·id 역순이다. 줄마다 시각이 거의 같아 id가 없으면 페이지를 넘길 때 순서가 흔들린다.
- 해결 기록이 실패 기록을 외래키로 가리킨다. 실패 기록을 지우는 테스트 정리 코드는 해결 기록을 먼저 지워야 한다. 새 통합 테스트도 같다.
- 1줄씩 조회는 해결 기록 → 실패 기록 → 정산후보를 ID로 조인한다. 실패 기록 ID는 해결 기록에서 유니크, 정산후보 ID는 실패 기록에서 하나라 줄이 늘지 않는다는 전제로 개수를 해결 기록 표만으로 센다.
