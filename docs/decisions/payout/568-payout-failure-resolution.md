## 배경

수수료 불일치·결과 검증 불일치로 잠긴 주문(#552)과 #549에서 3번 실패해 멈춘 주문은 푸는 길이 없어 실패 기록을 DB에서 직접 지워야 했다. 늦게 지우면 조회 기간 밖이라 다시 잡히지도 않았다. #301(Epic)을 #568(해결)·#571(해결 기록 조회)·#569(관리자 목록)·#570(초과 청구 근거)으로 나눴고, 이 문서는 #568이다.

범위 밖: 해결 기록 조회(#571), 관리자 목록(#569), 정산 안 함·조정과 함께 해결(#291).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 해결의 뜻 | "다시 검사해도 된다"는 표시. 돈을 바로 내보내지 않고 다음 배치가 금액 검사·결과 검증부터 다시 거침 | 고치지 않고 해결해도 다시 걸러져 돈이 잘못 나가지 않는다 |
| 기록 방식 | 실패 기록은 그대로 두고 해결 기록(`payout_failure_resolution`)을 실패 기록마다 1건(실패 기록 ID 유니크) | 기록은 쌓기만 한다. 해결 뒤 새로 생긴 실패에는 해결 기록이 없어 다시 잠기거나 처음부터 센다 |
| 해결 대상 | 그 주문의 해결 안 된 실패 기록 **전부** (사유·실행 성공 여부·정산 여부로 거르지 않음) | #549 횟수는 사유를 가리지 않고 센다. 예) 초과 청구 2번 + 결과 검증 1번 = 3번. 잠그는 사유에만 달면 계속 멈춰 있다 |
| 해결을 반영하는 곳 | 잠금 조건과 #549 실패 횟수(여러 스냅샷에 걸친 조건)에만. 한 실행 안의 제외(draft 대상, 확정 제외)에는 넣지 않음 | 배치가 도는 중에 해결해도 그날 실패한 후보가 그 실행에서 정산되면 안 된다 |
| 기간 밖 해결 주문 | 해결 기록이 있고 횟수가 0인 주문(새 실패가 없는 주문)의 상한 전 미정산 후보를 #549 "기간 밖 다시 넣기" 자리에 더함 | 해결하면 횟수가 0이 되어 #549의 1~2번 실패 목록에 들지 않는다. 다시 3번 실패해 멈춘 주문은 빼야 4·5·6번 반복이 없다 |
| 해결할 것이 있는지 | 잠김(해결 안 된 잠그는 사유) 또는 멈춤(성공한 실행 기준 3번 이상). 1~2번 실패는 저절로 다시 검사되므로 대상 아님 | 스냅샷이 주문을 빼는 두 조건과 같은 기준이어야 해결과 실제 동작이 어긋나지 않는다 |
| 해결할 것이 없을 때 | 이미 해결·동시 두 번 요청·잘못된 주문 ID 모두 `NOTHING_TO_RESOLVE` 409 하나 (사용자 결정) | 관리자에게는 같은 뜻이고, 정산은 주문 테이블이 없어 없는 주문을 구별할 수 없다 |
| 동시 두 번 요청 | 실패 기록 ID 순서로 저장, 해결 기록 유니크 위반만 409로 바꿔 다시 던짐 | 같은 순서면 서로 기다리는 데드락 대신 유니크 위반이 난다. 다른 DB 오류를 409로 가리지 않는다 |
| 되돌리기 | 만들지 않음 (사용자 결정) | 기록은 쌓기만 하고, 잘못 해결하면 다시 검사에서 생긴 새 실패 기록이 그 해결을 상쇄한다 |
| 해결 기록 보기 | 해결 API 응답으로 방금 저장한 해결 기록을 돌려주고, 나중에 보는 조회는 #571 (사용자 결정) | 오늘 범위를 지키면서 기록은 남긴다 |
| 메모 형식 오류 | 422 (이슈에는 400으로 적었음) | 팀 규칙(api.md)과 기존 관리자 API가 형식 오류를 422로 쓴다 |

## 버린 대안

- **잠그는 사유의 실패 기록에만 해결 기록:** 섞인 사유의 횟수가 남아 해결해도 멈춰 있다.
- **해결 기록을 주문 ID로 잇기:** 해결 뒤 새로 생긴 실패까지 해결된 것으로 보여 다시 잠기지도 멈추지도 않는다. 실패 기록 ID로 잇는다.
- **실패 기록을 지우거나 상태를 바꿈:** 기록이 사라지고 "스냅샷 = draft + 실패" 등식이 깨진다.
- **해결 취소 기능:** 상쇄는 새 실패 기록이 맡아 필요 없다.

## 건드릴 때 주의

- 해결 조건을 draft 대상(`notFailedInSnapshot`)·확정 제외(`findFailureRows`)에 넣지 않는다. 넣으면 배치 도중 해결한 주문의 실패 후보가 그 실행에서 정산된다.
- `countFailedRunsByOrder`(네이티브 SQL)와 `unresolvedFailure()`(Querydsl)는 같은 조건을 따로 쓴다. 하나를 바꾸면 다른 하나도 바꾼다. SQL에는 `PayoutSchema.NAME`을 붙인다.
- 해결 방법은 지금 REPROCESS 하나라 다시 넣기 조회가 방법을 거르지 않는다. "정산 안 함" 같은 방법을 더하면 REPROCESS만 다시 넣어야 한다.
- 해결 기록이 있고 횟수 0인 주문은 기간과 상관없이 매 실행 다시 들어간다. 실패가 FAILED로 끝난 실행에만 생기면 횟수가 오르지 않아 멈추지 않는다(#549 FAILED 미집계와 같은 한계).
- 다른 통합 테스트의 정리 코드는 `payout_failure`를 지우는데, 해결 기록이 외래키로 가리키므로 해결 기록을 만드는 테스트는 해결 기록부터 지워야 한다.
