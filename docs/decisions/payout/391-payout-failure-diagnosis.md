## 배경

멘토링에서 "관리자 알림은 최후의 보루, 실패를 분류해 왜 실패했는지 분석까지 내놓아야 한다"는 지적을 받았다. 그때까지 초과 청구 실패의 상세는 "어느 주문상품이 틀렸는지 판별 불가"였고, 수수료 불일치와 초과 청구가 같은 사유(`AMOUNT_MISMATCH`)를 썼으며, 지갑이 같은 주문을 다른 금액으로 다시 보내면 흔적 없이 버렸다.

이 작업은 실패 기록을 알아보기 쉽게 만드는 데까지다. 누가 얼마를 언제 받는지(판정 공식, 주문 잠금)는 바꾸지 않는다. 금액 불일치 주문을 잠그지 않고 다시 검사하는 일은 #549로 나눴다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 시스템이 맡을 일 | 돈을 고치지 않고 원인을 진단해 남김 | 자동으로 금액을 고치는 방법 세 가지는 틀린 값을 만들거나 다른 판매자가 떠안았다(#391 본문의 시도 표). 돈의 최종 판단은 사람이 한다 (사용자 결정) |
| 이슈 범위 | 진단(#391)과 다시 검사(#549)를 이슈 두 개로 나눔 | 돈 흐름이 안 바뀌는 변경과 바뀌는 변경을 따로 리뷰받으려고 (사용자 결정) |
| 수수료 불일치 사유 | `AMOUNT_MISMATCH`에서 `FEE_MISMATCH`로 분리, 잠금은 그대로 | 초과 청구는 받은 값이 틀린 것이고 수수료는 정산이 직접 계산해 틀리면 우리 코드·정책 문제라 확인할 곳이 다르다. 잠금을 다르게 다루는 것은 #549 범위 |
| 범주 저장 방식 | DB 칸 없이 사유 enum이 값을 가짐 (`locksOrder`와 같은 방식) | 사유마다 정해진 값이라 저장할 정보가 늘지 않는다. 마이그레이션이 필요 없다 |
| 함께 보류의 범주 | `ORDER_HELD`는 시스템 문제로 고정 | 이 사유는 수수료 불일치 때만 생긴다. 초과 청구는 주문 후보 전부를 `AMOUNT_MISMATCH`로 기록한다 |
| 함께 보류 이름 | `ORDER_LOCKED` → `ORDER_HELD`, 저장된 행은 UPDATE 마이그레이션 | 옛 이름은 "이 후보가 주문을 잠갔다"로 읽히는데 실제로는 잠그지 않는 사유다. 사유는 글자로 저장돼 옛 이름이 남으면 읽을 때 enum 변환이 실패한다 |
| 초과 청구 근거 저장 | 실패 상세 글 한 줄(255자)에 모아 적음 | 표를 바꾸지 않아도 되고, 근거는 DB에서 다시 계산할 수 있다 |
| 근거 계산 범위 | 판정 합계와 같은 범위(그 주문의 후보 전체, 조정 포함) | 판정과 범위가 다르면 "넘친 금액"과 누적합이 서로 맞지 않는다. 조정을 빼는 것은 #549에서 판정과 함께 바꾼다 |
| 지갑 금액 충돌 | 저장된 금액은 유지하고 충돌만 별도 표에 기록 | 어느 금액이 맞는지 정산은 알 수 없다. 먼저 온 값으로 검사해 왔으므로 기준을 바꾸지 않는다 |
| 수수료 불일치 로그 등급 | 처리를 계속하지만 `ERROR`, 메시지 앞머리 고정 | 사람이 할 일이 코드 수정뿐이라 개발자가 바로 알아야 한다. 알림(#302)이 이 모양을 찾는다. 팀 로그 규칙과 달라 `payout/CLAUDE.md`에 예외로 적었다 (사용자 결정) |
| 잠금 경고의 원인 고르기 | 사유 이름 대신 `isLocksOrder()` | 이름으로 고르면 사유를 나눌 때마다 놓쳐 로그의 사유가 비게 된다 |

## 버린 대안

- **자동 정정:** 수수료를 정책대로 보정하기, 주문·지갑에 다시 묻기, 결제 금액만큼 먼저 지급하고 차액만 보류하기는 모두 버렸다. 결과는 #391 본문에 있다. 감수하는 것은 금액이 틀린 주문은 사람이 볼 때까지 정산되지 않는다는 점이다.
- **근거를 칸으로 나눠 저장:** 실패 당시 값이 그대로 남고 조건으로 찾을 수 있지만 표 변경이 필요해 이번에는 하지 않았다. 감수하는 것은 근거가 글 안에 섞여 있어 조건 조회·정렬이 안 된다는 점이다. 관리자 목록(#301)에서 다시 정한다.
- **충돌 시 금액 덮어쓰기:** 나중에 온 값이 맞다는 근거가 없어 버렸다.
- **옛 수수료 불일치 기록 옮기기:** 분리 전에 `AMOUNT_MISMATCH`로 저장된 수수료 불일치 행은 그대로 뒀다. 지금은 둘 다 주문을 잠가 결과가 같다.
- **근거를 항상 조회:** 초과 청구에 걸린 주문이 있을 때만 조회한다. 걸린 주문이 없는 날의 조회 수는 전과 같다.

## 건드릴 때 주의

- `locksOrder`와 범주는 DB에 저장하지 않는다. enum 값을 바꾸면 이미 저장된 실패 기록의 해석도 함께 바뀐다. 잠금 값을 `false`로 바꾸면 그동안 잠긴 주문이 다음 실행에서 한꺼번에 검사 대상이 된다.
- 초과 청구 판정 공식은 `PayoutAmountValidator.isOvercharged` 한 곳이다. 서비스가 근거를 조회할 주문을 고를 때도 같은 것을 쓴다. 한쪽만 바꾸면 근거 없는 실패가 생긴다.
- 근거 조회와 합계 조회의 범위가 어긋나면 상세가 "판별 불가"로 남는다. 두 조회는 같은 트랜잭션에서 같은 시점의 데이터를 본다는 전제(REPEATABLE READ)에 기댄다.
- 상세의 "넘게 만든 주문상품"은 누적합이 처음 결제 금액을 넘긴 후보일 뿐 원인이라는 뜻이 아니다. 먼저 들어온 틀린 금액이 원인일 수 있다.
- 잠금 경고 로그는 잠그는 사유의 상세를 원인으로 쓴다. 금액 불일치의 잠금을 없애면(#549) 이 로그의 사유가 비고 문구도 맞지 않게 된다.
- 수수료 불일치 `ERROR` 로그의 메시지 모양을 바꾸면 알림(#302)이 찾지 못한다. 등급은 통합 테스트가 확인한다.
- 이름 변경 마이그레이션은 추가만 하는 실패 표를 한 번 고친다. 코드와 같은 배포에 들어가야 하고, 되돌리려면 반대 방향 UPDATE가 필요하다.
- 금액 검사의 로그는 실패 기록이 커밋되기 전에 찍힌다. (미확인) 커밋이 실패하면 로그만 남고 기록은 없을 수 있다.

## 후속 (2026-11-13)

- 다시 검사를 이슈 두 개로 다시 나눴다. #549는 실패 횟수 세기·3번 멈춤·기간 밖 다시 넣기이고, #552는 금액 불일치 잠금 없애기·수수료 불일치를 횟수에서 빼기·조정을 초과 청구 합계에서 빼기다. 잠금을 먼저 없애면 3번에서 멈추는 장치가 없어 #549를 먼저 한다.
- 그래서 위 본문의 다음 내용은 #549가 아니라 #552에서 한다: 금액 불일치 주문을 잠그지 않고 다시 검사(배경), 잠금을 다르게 다루는 것(수수료 불일치 사유 줄), 조정을 빼는 것(근거 계산 범위 줄), 잠금 경고 로그의 사유가 비는 문제(고칠 때 주의할 점). "이슈 범위" 줄의 다시 검사(#549)는 #549와 #552를 합친 것이다.

## 후속 (2026-11-14)

- #552에서 수수료 불일치는 다시 검사해도 풀리지 않아 잠금 유지로 정했다(ADR 552). 그래서 위 후속(2026-11-13)의 #552 범위 중 "수수료 불일치를 횟수에서 빼기"와 "잠금을 다르게 다루는 것(수수료 불일치 사유 줄)"은 하지 않았고, #552는 초과 청구 잠금 없애기·조정을 초과 청구 합계에서 빼기만 했다. 수수료 불일치 사유 줄의 "잠금은 그대로"는 #552 뒤에도 맞다.
- 같은 후속의 "금액 불일치 주문을 잠그지 않고 다시 검사"는 초과 청구(`AMOUNT_MISMATCH`)에만 해당한다.
- 잠금 경고 로그의 사유가 비는 문제는 #552에서 원인 고르기를 `!= ORDER_HELD`로, 문구를 "정산 금액 검사로 주문 제외"로 바꿔 풀었다.
- 옛 `AMOUNT_MISMATCH`로 저장된 수수료 불일치 행은 #552부터 한 번 다시 검사된 뒤 `FEE_MISMATCH`로 잠긴다. 그래서 본문의 "결과가 같다"는 그 뒤로 맞다.
