## 배경

잠그지 않는 실패(결제 기록 없음 `DEDUCTION_MISSING`, 판매자 처리 중 예외 `UNEXPECTED_ERROR`)는 조회 기간 안에 있는 동안 매 실행 다시 검사됐다. 원인이 남으면 실행마다 같은 실패가 쌓였고, 하한이 올라가 기간 밖으로 밀리면 기록 없이 묻혀 해결된 것처럼 보였다. 멘토링에서 "관리자 알림은 최후의 보루, 사람의 개입은 최소화"라는 지적을 받았다.

이 작업은 실패 횟수 세기, 3번에서 멈추기, 기간 밖 다시 넣기까지다. 범위 밖: 초과 청구 잠금 없애기·조정을 초과 청구 합계에서 빼기(#552, 수수료 불일치는 잠금 유지로 정함), 멈춘 주문 목록·해결(#301), 알림(#302), 판매자 저장 실패 시 주문별 다시 시도(#534), 두 조회의 대량 속도(#304).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 세는 단위 | 주문. 한 실행에서 그 주문의 미정산 후보에 실패 기록이 남으면 1번(사유·건수 무관) | 같은 주문의 상품은 함께 빠지고 함께 다시 들어가야 일부만 정산되지 않는다 (사용자 결정) |
| 세는 실행 | Job이 `COMPLETED`로 끝난 실행만, 실행 종류(정기·수동·대기 건너뛰기)는 가리지 않음 | `FAILED`로 끝난 실행의 실패는 주문 탓이 아닐 수 있다. 하루에 손으로 여러 번 돌리면 그날 3번이 찰 수 있음을 알고 감 (사용자 결정) |
| 멈추는 횟수 | 기간 안팎을 합쳐 3번, `PayoutPolicy.MAX_FAILED_RUNS` | 매일 실행이면 기간 안 기회가 이미 4번이라 "기간 밖에서 3번 더"(11/01·11/03 결정)는 사람에게 가는 날만 늦춘다. 대가로 저절로 풀릴 기회가 1번 줄어든다 |
| 기간 밖 다시 넣기 | 1~2번 실패한 주문의 미정산 후보를 하한 없이 상한 전까지 다시 넣음, 잠긴 주문은 넣지 않음 | 배치를 쉰 날이 있으면 3번을 못 채우고 밀린 주문이 생긴다(사전 점검에서 실행으로 확인) |
| 고르는 방식 | 기간 안 조회와 실패 주문 조회를 따로 해서 자바에서 합치고 ID 순 정렬 | 한 조회에 "또는"으로 붙이면 느려진다(버린 대안) |
| 멈춤 알림 | 스냅샷을 만들 때 멈춘 주문 수를 WARN 한 줄로, 0이면 남기지 않음 | 실패를 저장하는 순간에는 그 실행이 성공으로 끝날지 몰라 3번째가 확정되지 않는다. 멈춘 주문이 풀릴 때까지 스냅샷마다 같은 수가 반복되는 것은 감수 (사용자 결정) |
| WARN 세는 범위 | 3번 이상·잠기지 않음·상한 전 미정산 후보가 남은 주문, 기간 하한과 무관 | 기간 안 후보만 세면 기간 밖에서 3번째로 실패해 멈춘 주문이 경고 없이 빠진다 |
| 실패 횟수 조회 | 네이티브 SQL 유지(`countFailedRunsByOrder`) | "성공한 실행"은 JPA 엔티티가 없는 Spring Batch 표에만 있다. DB 안에서 걸러 주문별로 세면 주문 수만큼만 받는다 (사용자 결정, 규칙은 `payout/CLAUDE.md`) |
| 이슈 순서 | #549를 먼저, 잠금 없애기(#552)를 나중에 | 잠금을 먼저 없애면 멈추는 장치가 없어 금액이 틀린 주문을 끝없이 다시 검사한다 |

## 버린 대안

- **한 조회에 "기간 안 또는 실패 주문":** 날짜 인덱스를 못 써서 후보 20만 건에서 0~1ms → 약 750ms가 됐다(사전 점검 시제품). 감수하는 것은 조회가 둘이 되고 합친 뒤 다시 정렬해야 한다는 점이다.
- **실패를 저장할 때 "3번째"로 경고:** 그 실행이 나중에 `FAILED`로 끝나면 세지 않는 실패라 틀린 경고가 된다.
- **횟수를 칸에 저장:** 실행이 끝나야 셀지 말지가 정해져 저장 시점에 값을 확정할 수 없다. 실패 기록·스냅샷·Batch 실행 기록을 이어 매번 센다.
- **Spring Batch에 실행마다 상태를 물어 자바에서 세기:** 실패 기록이 쌓일수록 DB에서 옮기는 줄이 늘어난다(예: 실패 주문 1,000개 × 실행 30번이면 최대 30,000줄).
- **Batch 실행 표를 읽기 전용 엔티티로 만들기:** 조회 속도는 같지만 Spring Batch 버전이 바뀌면 표 모양이 달라져 앱이 뜨지 않을 수 있다.

## 건드릴 때 주의

- `countFailedRunsByOrder`는 Spring Batch 표 이름·열(`BATCH_JOB_EXECUTION`, `STATUS`)과 `payout_snapshot.job_execution_id`에 기댄다. 표 이름 앞에 `PayoutSchema.NAME`을 붙이지 않으면 로컬 테스트는 통과해도 운영에서만 실패한다.
- Batch 실행 기록이 지워진 실행의 실패는 세지 않아 그 주문이 0번으로 보인다(운영 전이라 지금 영향 없음).
- 잠긴 주문도 실패가 1번 남아 "다시 넣을 주문" 목록에 계속 들어간다. 결과는 잠금 조건이 걸러 맞지만 목록이 길어진다(대량 측정 #304에서 본다).
- #552에서 초과 청구 잠금을 없애면 그 실패도 이 횟수로 세어져 3번에서 멈춘다. 이 문서의 세는 기준이 #552의 전제다.
- 주문 단위로 멈춰도 이미 정산된 후보는 그대로 둔다. 일부 상품만 정산된 주문이 멈추면 정산된 몫과 남은 미정산 후보가 갈라진 채 남는다(의도한 동작, 남은 후보는 #301에서 처리). 세는 조회와 고르는 조회가 모두 미정산 후보만 보기 때문이다.
- 멈춘 주문 WARN은 상한(`to`) 전 후보만 센다. 대기 건너뛰기 실행(스위치 기본 꺼짐)으로 3번이 찬 주문은 정기 실행에서 경고가 최대 약 15일 늦다. 빠지는 동작은 상한을 보지 않아 맞다.
- 다시 넣은 후보는 스냅샷의 `period_from`보다 앞설 수 있다. 정산 상세의 "정산 대상 기간"과 항목 날짜가 어긋날 수 있다(`PayoutDetailResult` 주석).
