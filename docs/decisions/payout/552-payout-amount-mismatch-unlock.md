## 배경

#195·#290부터 금액 검사에 걸린 주문(초과 청구, 수수료 불일치)과 결과 검증 불일치 주문은 잠겨, 원인이 사라져도 사람이 실패 기록을 지워야 정산됐다. 멘토링에서 "관리자 알림은 최후의 보루, 사람 개입은 최소화"라는 지적을 받았다. #549가 실패 횟수를 세어 3번이면 멈추는 장치를 만들었으므로, 이 작업에서 잠금을 다시 검사로 바꿀 수 있는 사유를 골라 바꿨다.

범위 밖: 멈춘·잠긴 주문의 관리자 목록·해결(#301), 조정으로 금액 불일치를 바로잡는 흐름(#291), 후보에 그때 쓴 수수료율 저장.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 초과 청구 `AMOUNT_MISMATCH` | 잠그지 않고 다음 실행에서 다시 검사, #549 횟수에 세어 3번이면 멈춤 | 사람 개입을 줄이려는 것이다(사용자 결정). 사람이 틀린 데이터를 바로잡으면 실패 기록을 지우지 않아도 다음 실행에서 정산된다(3번 안). 입력이 그대로면 매번 같은 검사에 걸려 돈이 나가지 않는다. 다만 지금은 저절로 풀리는 정상 경로가 없다(차감액은 처음 값 유지, 후보 불변, 조정 제외) |
| 수수료 불일치 `FEE_MISMATCH` | 잠금 유지 (사용자 결정, #391 때의 "세지 않고 매번 다시 검사"를 바꿈) | 수수료 검사는 같은 주문상품의 원래(조정 아닌) 대금·수수료 후보끼리 비교하고 두 후보는 한 번 들어오면 바뀌지 않는다. 다시 검사해도 결과가 같아 풀리는 길은 개발자의 코드·정책 수정뿐이다 |
| 결과 검증 불일치 `VERIFY_MISMATCH` | 잠금 유지 | 코드 버그다. 잠그지 않으면 정산할 다른 주문이 없는 날 "전부 걸림"으로 Job이 기록 없이 실패하는 일이 반복된다 |
| 초과 청구 합계와 근거 범위 | 조정 후보(`adjustment_id ≠ 0`)를 뺌 | 잠금이 사라지면 −조정이 초과 청구를 가려 틀린 금액이 통과된다(예: 결제 9,000, 후보 9,700, 조정 −700). 근거 행(#391)도 같은 범위여야 누적합이 합계와 맞는다 |
| 금액 검사 경고 로그 | "정산 주문 잠금" → "정산 금액 검사로 주문 제외", 원인은 `ORDER_HELD`만 빼고 고름 | 초과 청구가 잠그지 않게 되어 "잠금"이라는 말과 `locksOrder`로 원인을 고르는 방법이 모두 맞지 않게 됐다 |
| #391 전 `AMOUNT_MISMATCH`로 저장된 수수료 불일치 기록 | 옮기지 않음 | 아직 운영 전이라 영향이 없다. 옮기지 않으면 그 기록은 잠그지 않아 한 번 다시 검사되고, 초과 청구가 아니므로 수수료 검사에서 `FEE_MISMATCH`로 새로 기록되어 그때부터 잠긴다 |
| 잠금 여부 저장 | DB 칸 없이 enum 값 그대로 | 값을 바꾸면 과거 기록의 잠금도 함께 풀리지만, 운영 전이고 풀린 주문도 금액 검사를 다시 거친다 |

## 버린 대안

- **수수료 불일치를 세지 않고 매번 다시 검사(#391 때 결정, 처음 구현):** 검사식이 틀렸을 때는 고쳐 배포하면 저절로 정산되지만, 후보를 만들 때부터 틀렸으면 배포로도 안 풀려 끝없이 다시 검사하고 #301에도 가지 않는다(구현 리뷰에서 발견). 감수하는 것은 검사 코드를 고쳐 배포한 경우에도 사람이 #301에서 한 번 풀어 줘야 한다는 점이다.
- **수수료 불일치에 큰 상한(예: 30번)이나 3번 세기:** 상한은 "배포까지 기다려 주는 기간"일 뿐이고, 데이터가 바뀌어 풀릴 길이 없어 그사이 쌓이는 실패 기록만 늘어난다.
- **모든 금액 불일치 잠금 유지(#552 전):** 초과 청구는 입력이 바뀌면 풀릴 수 있는데 사람이 손으로 지워야 정산된다.
- **초과 청구가 계속 나면 주문·지갑에 금액을 다시 묻기:** 구매확정 금액과 지갑 차감액이 같은 주문 DB 값에서 나와 다시 물어도 같은 값이 온다(#391 사전 점검). 기준값(주문상품별 금액)을 미리 받아 두는 방향은 #391에서 다음 단계로 남겼다.

## 건드릴 때 주의

- `locksOrder`를 바꾸면 이미 남은 실패 기록의 잠금도 함께 바뀐다. 운영 중에 바꿀 일이 생기면 기록 시점의 값을 저장하는 칸이 필요하다.
- 합계에서 조정을 빼므로, 원래 후보 없이 조정만 있는 주문은 합계가 없다. 꺼내기만 하면 NPE로 Job 전체가 FAILED가 되므로, 이 주문은 "초과 청구 판정 불가"로 금액 불일치 처리해 빼고 3번이면 멈추게 했다(검사할 기준 없는 돈을 내보내지 않으려고). 조정 API가 막혀 있어 지금은 생기지 않고, 올바른 검사 방법은 #291에서 정한다(`TODO(#291)`).
- +조정은 이제 결제 금액 상한 검사를 받지 않는다(예: 결제 10,000, 원래 후보 10,000, 조정 +5,000 → 통과). 조정 API를 열 때(#291) 함께 정한다.
- 초과 청구 실패가 `FAILED`로 끝난 실행에만 남으면 횟수가 0이라, 후보가 조회 기간 밖으로 밀리면 다시 검사도 멈춤도 없이 빠진다. 결제 기록 없음과 같은 #549의 한계이고 돈은 나가지 않는다.
- 금액 검사 경고 로그의 원인은 `ORDER_HELD`만 빼고 고른다. 금액 검사가 원인이 아닌 사유를 새로 만들면 여기도 빼야 한다.
- 결과 검증 불일치·수수료 불일치의 임시 해제(실패 기록 행 수동 삭제)와 그 한계는 `PayoutFailureReason`의 `VERIFY_MISMATCH` 주석에 있다.

## 후속 (2026-11-14)

- 위 "건드릴 때 주의"의 임시 해제(실패 기록 행 수동 삭제)는 #568에서 해결 API("다시 처리")로 바뀌었다. `VERIFY_MISMATCH` 주석도 해결 API 기준으로 고쳤다. 실패 기록은 지우지 않고 해결 기록을 남기며, 조회 기간 밖으로 밀린 주문도 다시 들어간다(ADR 568).
