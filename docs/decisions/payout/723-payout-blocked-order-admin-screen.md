## 배경

해결 전에는 순서대로 맞게 넣은 조정도 "지금" 근거에 안 보여, 관리자가 같은 조정을 사유만 바꿔 또 넣으면 판매자가 두 번 덜 받는다(#291 조정 API를 연 뒤 생긴 빈틈). 11/19 배포 사이트 화면 점검에서 프런트가 AI로 Swagger를 읽고 관리자 화면을 만든다는 점이 확인되어, 화면에 필요한 조회 조건과 처리 흐름 설명까지 이 이슈에 모았다.
범위 밖: 해결 요청에 기대 합계를 넣어 409로 막기, 검사 밖 조정 합계 칸, 해결 기록 머리 표, 1~2번 실패한 주문 조회 API, Swagger 공통 표기(nullable·minLength·페이지 응답 설명).

## 버린 대안

- **대기 조정:** 합계 한 칸은 수수료 불일치를 맞게 고치면 0이 됨. 합계 + 건수는 금액이 맞는지 모름. "지금" 합계에 바로 더하면 #570 약속이 깨짐. 미확인 조정 줄 목록은 응답이 커지고 관리자가 직접 더해야 함(누가 넣었는지는 정산후보 조회의 조정 정보로 봄).
- **원인 줄에 후보 금액 칸:** 대기 중이라 원인에 없는 상품이 여전히 안 보이고 집계 표 칸·마이그레이션이 늘어남.
- **해결 기록:** 실패 1건 = 1줄은 같은 주문·시각·메모가 반복됨. 기간을 선택 사항으로 두면 기간 없이 부를 때 쌓인 기록을 전부 읽음(payout/CLAUDE.md 규모 전제). `(admin_id, created_at)` 인덱스는 관리자로 거르는 일이 드물다고 보고 두지 않음. 감수하는 것은 관리자로 거를 때 기간 안 줄을 표에서 다시 읽는 것(위 가정이면 1년에 수십만 줄).
- **서버가 순서 강제(조정 없으면 해결 거절):** 사람이 원본을 직접 고친 경우 조정 없이 풀어야 하고 #568 "해결 = 다시 검사 표시"와 어긋남.

## 건드릴 때 주의

- 대기 합계는 "해결 시점에 확인한 조정이 될 집합"이지 다음 실행 검사에 반드시 드는 집합이 아님. 실행 중(스냅샷 뒤)에 넣고 해결한 조정은 그 실행 검사에서 빠질 수 있음(`checkedCandidate` 주석).
- 확인한 조정 사유를 바꿀 때는 `ADJUSTMENT_CONFIRMING_REASONS` 하나만 고침. 대기 조건과 확인한 조정이 같이 따라감. 금액 검사 경로이므로 정산 테스트 전체로 확인.
- 막힌 주문 표를 읽는 새 조건에도 `notPendingBlockedOrder()`를 늘 같이 검(#570).
- 정산후보 조회의 공용 조건(`candidateSearchCondition`)은 기간이 null이면 걸지 않음. 판매자 조회는 요청 DTO가 기간을 필수로 막아 null이 오지 않음. 판매자 요청에 같은 예외를 두지 말 것.
- 정산후보 요청의 기간 검증은 다른 관리자 목록과 "함께 바꿈" 사이인데, 이 요청만 주문 ID 예외가 있음. 해결 기록 전체 목록 요청이 같은 검증의 5번째 복사본임(TODO(논의 필요)).
- ADR 571이 범위 밖으로 둔 "기간으로 찾기"를 이번에 엶. 판매자로 찾기는 여전히 범위 밖(해결 기록 표에 판매자 칸이 없음).
- (미확인) 실행 계획(EXPLAIN)은 대량 데이터로 본 적 없음. 해결 기록 전체 목록의 규모 가정(하루 100건)이 크게 바뀌면 해결 요청 머리 표나 SQL 페이지 나누기를 다시 볼 것.
- 해결 기록 두 번째 조회의 시각 범위는 "한 요청의 줄은 한 트랜잭션에서 1분 안에 저장됨"에 기댐. 해결 저장 방식을 바꾸면 이 범위도 다시 볼 것.
- 정산후보 조회에서 주문 ID도 기간도 없을 때 422 오류 목록의 path가 `from`·`to` 둘에서 `periodPresentWithoutOrderId` 하나로 바뀜(클래스 단위 검사). 입력칸별로 오류를 붙이는 화면은 이 이름을 씀.
- 대기 합계는 주문 단위라, 판매자가 여럿인 주문에서 다른 판매자 상품에 넣은 조정을 가리지 못함. 조정마다 검사 상태·판매자를 보여 주는 일은 후속 이슈로 둠 (사용자 결정).

버린 대안 (서버에서 막기, 11/20 설계 검토 7명)
- 해결됐던 주문은 확인 표시 없으면 409: 화면이 늘 표시를 켜면 효과가 없고 요청 형식이 바뀜
- 해결 뒤 조정은 다음 해결 전까지 지급 보류: 보류된 조정은 검사 밖이라 주문이 다시 막히지 않아 보류를 풀 길이 없음
- 검사 밖 조정 합이 0을 넘으면 거절: 결제를 넘는 정당한 보상까지 막음
- 양수 조정은 확인 여부와 상관없이 늘 금액 검사에 넣기: 미리 넣은 −X를 해결 뒤 +X로 상쇄하는 안내 절차가 다시 막힘

건드릴 때 주의
- 막지 않으므로 응답을 무시하면 남는 위험: 확인한 조정을 해결 뒤 반대 금액으로 상쇄하면 돈이 더 나감(예: 결제 30,000, 원래 40,000, −10,000 확인 → 해결 뒤 +10,000 → 검사 30,000 통과·지급 40,000). 같은 조정 또 넣기, 다른 판매자 상품에 넣기도 그대로
- 판정은 주문 단위: 다른 판매자 상품이나 같은 판매자의 다른 상품에 넣은 조정도 확인됨·해결 대기로 나옴
- 생성 응답의 `CONFIRMED`는 해결 시각 > 조정 시각이어야 해서 서버 시계 차이 같은 예외가 아니면 나오지 않음
