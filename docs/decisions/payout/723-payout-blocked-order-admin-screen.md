## 배경

해결 전에는 순서대로 맞게 넣은 조정도 "지금" 근거에 안 보여, 관리자가 같은 조정을 사유만 바꿔 또 넣으면 판매자가 두 번 덜 받는다(#291 조정 API를 연 뒤 생긴 빈틈). 11/19 배포 사이트 화면 점검에서 프런트가 AI로 Swagger를 읽고 관리자 화면을 만든다는 점이 확인되어, 화면에 필요한 조회 조건과 처리 흐름 설명까지 이 이슈에 모았다.
범위 밖: 해결 요청에 기대 합계를 넣어 409로 막기, 검사 밖 조정 합계 칸, 해결 기록 머리 표, 1~2번 실패한 주문 조회 API, Swagger 공통 표기(nullable·minLength·페이지 응답 설명).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 대기 조정 합계 | 판매 대금·수수료 두 칸, 없으면 0. "지금" 근거 합계에는 섞지 않음 | 수수료 불일치를 맞게 고치면(+700/−700) 한 칸으로는 0이라 들어간 것이 안 보임. 수수료 검사도 따로 더함(#291 결정 5번). 섞으면 #570 "지금 근거 = 검사 범위" 약속이 깨짐 (사용자 결정) |
| 대기 조정 조건 | 해결 안 된 금액·수수료 불일치 실패 f ≤ 조정, 아직 확인한 조정 아님 | 해결은 그 주문의 해결 안 된 실패를 모두 풀고 해결 시각은 늘 조정 뒤라, 이 조건 = 지금 해결하면 확인한 조정이 되는 것 |
| 조건 공유 | 사유 목록·"f ≤ 조정"을 `amountFailureBeforeAdjustment()`로 빼서 확인한 조정과 함께 씀 | 따로 쓰면 사유를 더할 때 한쪽만 바뀌어 화면 합계와 해결 뒤 검사가 어긋남 |
| 막힌 주문 하나 보기 | 개별 조회 API 대신 목록에 주문 ID 조건 | 원인·근거·합계가 다 목록 줄에 있어 같은 응답으로 충분 (사용자 결정) |
| 상태 조건 | LOCKED·STOPPED·RESOLVED 여러 값, 대문자만, PENDING은 422. 문자열로 받아 서비스가 바꿈 | 보통 안 푼 것만 봄. 기존 `(status, last_failed_at)` 인덱스를 씀. 컨트롤러·DTO는 domain 타입을 쓰지 않음(api.md) (사용자 결정) |
| 막힌 주문 기간 조건 | 두지 않음 | 오래 막힌 주문이 바로 찾아야 할 대상 (사용자 결정, #569와 같은 이유) |
| 정산후보 주문 ID | 관리자 조회만, 주면 기간 없이. 기간과 함께 주면 둘 다 적용 | 조정 금액을 정하려면 대기 중 상품까지 상품별 금액이 필요(대기 중 상품은 원인에 없음). 한 주문 몇 줄은 order_id로 시작하는 유니크 인덱스로 읽음. 함께 줄 때 기간을 몰래 무시하지 않으려고 (사용자 결정, #236 기간 필수의 예외) |
| 해결 기록 전체 목록 | 요청 1번 = 1줄, 기간 필수(최대 1년), 관리자 선택 | 해결됨 줄은 다음 실행 뒤 목록에서 빠지고 해결 기록은 주문 번호로만 봤음. 관리자가 누른 단위가 요청이고 주문별 묶음 보기와 같은 모양 (사용자 결정) |
| 기간 판정 | 요청의 가장 이른 해결 줄 시각, 앞뒤 1분 더 읽음 | 줄마다 판정하면 경계에 걸친 요청이 두 기간으로 갈라져 푼 실패 수가 덜 셈. 한 요청의 줄은 한 트랜잭션에서 저장되어 시각 차이가 아주 작음 |
| 정렬 | 해결 시각 최신순, 같으면 `max(id) desc` | 요청 번호는 UUID라 순서 뜻이 없음. 주문별 묶음 보기와 같게 |
| 인덱스 | `(created_at, resolution_request_id)` 하나 | 기간 안 요청 번호를 표를 다시 읽지 않고 고름. 관리자 ID까지 넣으면 이름 규칙(칸 이름 줄이지 않음)으로 64자를 넘음 |
| 개수·페이지 | 기간 안 요청(번호·시각·ID)을 다 가져와 자바에서 셈, 상세는 페이지의 요청만 두 번째 조회 | Querydsl이 묶은 결과 개수를 바로 못 셈. 가정: 하루 100건 해결이면 1년 36,500줄을 인덱스로 한 번 읽음 |
| Swagger 확인 공식 | "예상 합계가 결제 금액보다 크면 아직 넘침, 같거나 작다고 맞은 것은 아님. 결제 금액에 맞추려고 더 넣지 말 것" | 검사는 넘칠 때만 막음(`PayoutAmountValidator`). 결제 금액에는 다른 상품·배송비가 섞일 수 있어 "같게 맞추라"면 틀린 조정을 유도 |
| Swagger 태그 설명 | 관리자 정산·대기 건너뛰기 Spec이 상수 하나를 함께 씀 | 같은 태그 이름에 설명이 둘이면 어느 쪽이 보일지 정해져 있지 않음 |

## 버린 대안

- **대기 조정:** 합계 한 칸은 수수료 불일치를 맞게 고치면 0이 됨. 합계 + 건수는 금액이 맞는지 모름. "지금" 합계에 바로 더하면 #570 약속이 깨짐. 미확인 조정 줄 목록은 응답이 커지고 관리자가 직접 더해야 함(누가 넣었는지는 정산후보 조회의 조정 정보로 봄).
- **원인 줄에 후보 금액 칸:** 대기 중이라 원인에 없는 상품이 여전히 안 보이고 집계 표 칸·마이그레이션이 늘어남.
- **해결 기록:** 실패 1건 = 1줄은 같은 주문·시각·메모가 반복됨. 기간 선택은 쌓인 기록을 전부 읽음(payout/CLAUDE.md 규모 전제). `(admin_id, created_at)` 인덱스 추가는 기록이 빨리 쌓이지 않아 저장 비용만 늚. 감수하는 것은 관리자로 거를 때 기간 안 줄을 표에서 읽는 것.
- **서버가 순서 강제(조정 없으면 해결 거절):** 사람이 원본을 직접 고친 경우 조정 없이 풀어야 하고 #568 "해결 = 다시 검사 표시"와 어긋남.

## 건드릴 때 주의

- 대기 합계는 "해결 시점에 확인한 조정이 될 집합"이지 다음 실행 검사에 반드시 드는 집합이 아님. 실행 중(스냅샷 뒤)에 넣고 해결한 조정은 그 실행 검사에서 빠질 수 있음(`checkedCandidate` 주석).
- 확인한 조정 사유를 바꿀 때는 `ADJUSTMENT_CONFIRMING_REASONS` 하나만 고침. 대기 조건과 확인한 조정이 같이 따라감. 금액 검사 경로이므로 정산 테스트 전체로 확인.
- 막힌 주문 표를 읽는 새 조건에도 `notPendingBlockedOrder()`를 늘 같이 검(#570).
- 정산후보 조회의 공용 조건(`candidateSearchCondition`)은 기간이 null이면 걸지 않음. 판매자 조회는 요청 DTO가 기간을 필수로 막아 null이 오지 않음. 판매자 요청에 같은 예외를 두지 말 것.
- 정산후보 요청의 기간 검증은 다른 관리자 목록과 "함께 바꿈" 사이인데, 이 요청만 주문 ID 예외가 있음. 해결 기록 전체 목록 요청이 같은 검증의 5번째 복사본임(TODO(논의 필요)).
- ADR 571이 범위 밖으로 둔 "기간으로 찾기"를 이번에 엶. 판매자로 찾기는 여전히 범위 밖(해결 기록 표에 판매자 칸이 없음).
- 해결 기록 전체 목록의 규모 가정(하루 100건)이 크게 바뀌면 해결 요청 머리 표나 커버링 인덱스를 다시 볼 것. 실행 계획(EXPLAIN)은 대량 데이터로 본 적 없음(미확인).
