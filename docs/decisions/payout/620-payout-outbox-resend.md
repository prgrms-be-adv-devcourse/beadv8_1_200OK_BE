## 배경

- #309는 outbox 줄을 정산 Job 발행 단계만 보내게 했다. 그때는 지갑이 Spring 이벤트로 이미 입금해서 Kafka가 늦어도 입금과 상관없었다(309 문서의 "별도 스케줄러가 필요 없다").
- #584·#588 뒤로 지갑은 Kafka 메시지로만 입금한다. 발행 단계에서 못 보낸 정산은 다음 날 정산 Job까지 입금이 늦어진다. 309 문서의 그 전제가 사라졌다.
- #619 대사는 지갑이 "입금 없음"으로 답한 정산의 입금 메시지를 답 처리 중에 바로 보냈다. 건마다 Kafka 저장 확인을 기다려(최대 120초) 답 처리가 Kafka 기본 `max.poll.interval`(5분)을 넘을 수 있었다.
- 범위 밖: 스케줄 스레드 수, 테스트 설정에서 재발송 끄기(설정 파일이라 따로 다룸).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 재발송 간격 | 설정 값 `payout.outbox-resend.fixed-delay`, 기본 5분, `fixedDelay`(앞 실행이 끝난 뒤부터 셈) | Kafka가 살아난 뒤 최대 5분 안에 나간다. 대부분은 "보낼 것 없음"이라 PENDING 조회 1번(인덱스)으로 끝난다. 한 번이 길어져도 실행이 겹쳐 쌓이지 않는다 (사용자 결정) |
| 첫 실행 | 앱 시작 5분 뒤(`initialDelay` = 간격) | 앱이 뜨는 중 Kafka 연결을 서두르지 않고, 통합 테스트가 컨텍스트를 띄우자마자 끼어들지 않게 (사용자 확인) |
| 겹침 막기 | 새 ShedLock 잠금 `payoutOutboxSend`를 발행 단계와 재발송이 같이 씀. 잠금은 입구(`adapter.in.batch`의 `PayoutOutboxSendLock`)에서 잡음 | 실제로 겹치는 곳은 발행 단계뿐이라 그 구간만 잠근다. 잠금 줄은 ShedLock이 처음 잠글 때 스스로 넣어 마이그레이션이 필요 없다 (사용자 결정) |
| 잠금을 못 잡은 쪽 | 기다리지 않고 이번에는 안 보냄. 발행 단계는 0건, Job은 COMPLETED | 남은 줄은 PENDING이라 다음 재발송이 보낸다. 늦어도 보통 몇 분이다. 기다리면 Kafka 장애 날 정산 Job이 재발송 한 번(최대 약 6분)만큼 묶인다 (사용자 결정) |
| 잠금 시간 | 최대 10분(실행 중 자동 연장), 끝난 뒤 유지 0 | 끝나자마자 발행 단계가 와도 잠금이 남아 그날 발송을 건너뛰지 않게. 정해진 시각 실행이 아니라 서버마다 같은 시각에 또 도는 문제가 없다 |
| 잠금 표 DB 오류 | 발행 단계는 WARN 후 0건, Job은 실패시키지 않음 | 확정은 이미 끝났고 줄은 PENDING이라 재발송이 보낸다. "발송 단계 문제로 Job을 FAILED로 만들지 않는다"(#309)를 지킨다 (사용자 확인) |
| 대사 "입금 없음" | 답 반영과 같은 트랜잭션에서 그 정산의 outbox 줄을 SENT → PENDING으로 되돌림. 재발송이 보냄 | 답 처리가 DB만 고치고 끝나 `max.poll.interval`을 넘지 않는다. 함께 커밋되므로 커밋 직후 서버가 죽어도 재발송이 사라지지 않는다 (#619 리뷰 결정, 사용자 결정) |
| 되돌릴 때 값 | `sentAt`은 비움, `attemptCount`는 그대로 | PENDING인데 보낸 시각이 남으면 헷갈린다. 시도 횟수는 실패 기록이고 보내는 순서(덜 시도한 줄부터)에만 쓰여 남겨도 해가 없다 (사용자 확인) |
| outbox 줄이 없을 때 | `[정산-시스템문제]` ERROR 남기고 나머지 정산은 계속 되돌림 | 예외로 멈추면 같은 답 묶음(최대 500건)의 멀쩡한 정산까지 롤백된다. 그 정산은 다시 안 보내져 3번째 "없음" 뒤 관리자 확인으로 드러난다 (사용자 결정) |
| 빈 실행 로그 | 0건이어도 "보낸 수=0" INFO를 남김 | 재발송이 5분마다 돌고 있다는 흔적을 남긴다. 하루 최대 288줄 (사용자 결정) |

## 버린 대안

- **겹침 막기:** 잠금 없이 두기는 완료 조건("같은 줄을 동시에 보내지 않음")을 못 지킨다. 정산 Job 잠금 `payoutJob`을 같이 쓰면 재발송이 잠근 순간 관리자·정기 정산 실행이 거절된다. 정산 Job이 도는 내내 재발송을 쉬게 하기는 실제 충돌이 발행 단계뿐이라 범위가 지나치다.
- **잠금을 못 잡은 발행 단계:** 잠금이 풀릴 때까지 기다렸다 보내면 그 회차 정산이 몇 분 일찍 나간다. 대가로 Kafka 장애 날 정산 Job이 묶이고 기다리는 코드가 는다.
- **대사 "입금 없음":** 답 처리 중 바로 보내기(#619 방식)는 위 `max.poll.interval` 문제로 버렸다. outbox 줄이 없을 때 새 줄을 만들어 보내기는 버그 상태를 코드가 덮어 원인을 가린다.
- **빈 실행 로그:** 0건이면 로그를 생략하는 방식은 로그 양은 줄지만 재발송이 돌았다는 흔적이 사라진다.

## 건드릴 때 주의

- 잠금은 `publishPending`이 아니라 부르는 쪽(`PayoutOutboxSendLock`)에서 잡는다. 새 곳에서 `publishPending`을 부르면 반드시 이 클래스를 거쳐야 겹치지 않는다.
- `publishPending`은 시작할 때 PENDING 목록을 한 번만 읽는다. 재발송이 정산 commit보다 먼저 목록을 읽었다면 그 회차에 만든 줄은 다음 재발송이 보낸다.
- 같은 스레드에서 같은 이름의 잠금을 다시 잡으면 ShedLock은 이미 잡은 잠금으로 보고 실행을 허락한다. 겹침 테스트는 잠금을 다른 스레드에서 잡아야 한다(`PayoutOutboxResendIntegrationTest`).
- 재발송은 Spring 기본 스케줄 스레드를 같이 쓴다. (미확인) Kafka가 멈추면 한 번에 최대 약 6분 걸려 그동안 다른 모듈의 `@Scheduled`가 밀릴 수 있다.
- (미확인) 통합 테스트는 컨텍스트 하나를 공유해 5분이 지나면 재발송이 테스트 도중 돌 수 있다. 테스트 설정에서 간격을 늘리지 않은 상태다.
- 대사 줄과 outbox 줄은 정산 확정 때 같은 조건(시스템 몫·0원 이하 제외)으로 함께 만든다. 한쪽 조건만 바꾸면 "outbox 줄 없음" ERROR가 난다.
