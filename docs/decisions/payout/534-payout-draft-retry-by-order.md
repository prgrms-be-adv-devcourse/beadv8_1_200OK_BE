## 배경

#90부터 draftStep은 판매자 1명 몫을 한 트랜잭션으로 저장해, 예외가 나면 어느 주문 때문인지 몰라 그 판매자 후보 전부를 `UNEXPECTED_ERROR`로 기록했다. 판매자 A의 주문 100(오류)과 주문 200(정상)이 같은 날 들어오면 200도 실패하고, #549의 실패 횟수도 함께 쌓였다.

범위 밖: 일부 주문 실패를 배치 실행 기록·알림에 드러내기(#302), 계속 실패하는 주문 하나만 있는 날 Job이 매일 FAILED로 끝나 #549 횟수가 오르지 않는 문제(별도 이슈).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 다시 시도 방식 | 판매자 저장이 실패하면 주문마다 시험 저장(REQUIRES_NEW에서 저장·flush 뒤 `setRollbackOnly`) → 통과한 주문을 모아 `saveDraft` 1번 | 판매자 draft는 스냅샷당 판매자 1건(UK `snapshot_id, seller_id`)이고 `@Immutable`이라 합계를 나중에 고칠 수 없어, 주문마다 진짜로 저장할 수 없다 |
| 평소 경로 | 그대로 판매자 1번 저장 | 실패한 판매자에만 주문 수 + 1번 트랜잭션이 더 든다 |
| 다시 시도 상한 | 두지 않음, 주문마다 시험 1번 (사용자 결정) | 오류 주문을 정확히 가려낸다. 판매자 draft 표는 INSERT만 받고 Job은 하나만 돌아(#223) 오래 기다릴 잠금 상대가 거의 없다. DB 연결이 끊기면 첫 실패 기록 저장에서 예외가 나가 Job이 멈춘다(기존과 같음) |
| 주문이 1개인 판매자 | 시험 없이 바로 후보 전체 실패 기록 | 다시 해도 같은 저장이다. 일시 오류였다면 다음 실행에서 다시 시도된다 |
| 합친 저장도 실패할 때 | 통과했던 주문도 그 예외로 기록 | 주문 하나씩은 되는데 합치면 안 되는 경우(커밋 때만 나는 오류 등)라 어느 주문 탓인지 가릴 수 없다 |
| 실패 판매자 수 | 저장된 주문이 하나도 없을 때만 실패로 셈 | 그날 정산이 나가므로 "전원 실패"(Job FAILED)로 보지 않는다 |
| 출력 포트 `flush()` | 둠 | 롤백으로 끝나는 트랜잭션은 커밋 때 flush하지 않는다. 지금은 IDENTITY라 저장 즉시 INSERT가 나가 없어도 같지만, 쓰기를 모아 보내는 방식으로 바뀌면 시험이 늘 통과해 오류 주문이 합친 저장에 섞인다. 정산 모듈 규칙은 서비스가 JPA 타입을 쓰는 것을 막을 뿐이고, delivery·member 포트에도 같은 `flush()`가 있다 |

## 버린 대안

- **첫 주문으로 draft를 만들고 다음 주문 항목을 덧붙임:** `@Immutable`이라 합계를 못 고친다. 엔티티를 바꾸면 verify가 기대는 "draft는 바뀌지 않는다"는 전제가 깨진다.
- **주문마다 판매자 draft를 따로 저장 / 처음부터 주문 단위 저장:** UK 위반이고 commitStep이 판매자당 payout을 여러 건 만든다. 평소 커밋 수도 판매자 수에서 주문 수로 는다.
- **후보 단위로 다시 시도:** validate·verify가 주문 단위로 빼고 보류하는데, 한 주문의 일부만 정산될 수 있다.
- **연속 2번 실패면 중단·판매자당 N개만:** 정상 주문도 함께 실패할 수 있다(사용자가 상한 없음을 고름).
- **일시 오류(연결·잠금 대기)만 골라 다시 시도:** 버그를 낸 주문을 가려낼 수 없어 이 이슈의 목적과 다르다.
- **이분 탐색(반씩 나눠 시험):** 시험 횟수는 줄지만 지금 규모에서 이득이 작고 구현이 복잡하다.

## 건드릴 때 주의

- 시험 저장(`trySaveDraft`)은 다른 빈에서 REQUIRES_NEW로 불러야 한다. 같은 클래스에서 부르면 바깥 Step 트랜잭션에 참여해 `setRollbackOnly`가 Step 전체를 롤백 표시하고 Job이 FAILED가 된다(미확인).
- 시험 저장 안에서 예외를 잡아 결과로 돌려주지 않는다. flush 예외 뒤 트랜잭션에 롤백 표시가 남아 원래 원인이 사라진다.
- 주문은 `orderId`로 묶는다. 주문상품 단위로 묶으면 한 주문이 이틀에 나뉘어 정산된다.
- 일부 주문만 실패한 판매자는 write skip count와 전원 실패 판정에 잡히지 않는다(로그·`payout_failure`로만 보임, 알림은 #302).
- #549 실패 횟수는 COMPLETED 실행만 센다. 계속 실패하는 주문 하나만 있고 그날 다른 판매자가 없으면 Job이 매일 FAILED로 끝나 멈추지 않는다(이 변경 전에는 정상 주문까지 실패해 더 나빴다).
