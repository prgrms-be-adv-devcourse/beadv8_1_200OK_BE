## 배경

관리자 목록(#569)을 만들려고 이슈를 점검하니, 잠김 판정이 `lockedOrder`(스냅샷)·`isOrderLocked`(해결 API)에, 멈춤 기준 "3번 이상"이 `PayoutService`·`PayoutFailureResolutionService`에 따로 적혀 있었다. 목록을 원본에서 바로 계산하면 세 벌째가 되고, 규칙을 바꿀 때 한 곳을 빠뜨리면 같은 주문에 서로 다른 답을 낸다(#568 때 세 곳을 따로 고쳤다). 그래서 #569·#570 전에 "막힌 주문"을 한곳에서 계산해 적어 두는 표를 먼저 만들기로 했다.

이 작업 중 정산 설계 전제를 "하루 최소 10만 명 이용"으로 정해 `payout/CLAUDE.md`에 적었다.

범위 밖: 목록 API(#569), 초과 청구 근거(#570), 범위를 정해 원본과 맞추기(#583), 스냅샷의 실패 기록 전체 조회(#304).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 표의 성격 | 원본(실패·해결 기록)에서 계산한 조회용 사본. 정산 표 중 예외로 수정·삭제 허용 (사용자 결정) | 원본은 고치지 않는 원칙(#388 M3)을 지키면서 "지금 상태"를 한 줄로 둘 곳이 필요. 틀리면 원본에서 다시 계산할 수 있음 |
| 스냅샷 판정 | 계속 원본으로 | 표가 낡아도 돈이 잘못 나가지 않게. 표는 보기용 |
| 표 모양 | 막힌 주문(주문 1줄) + 원인(하위 표) + 갱신 상태(1줄) (사용자 결정) | JSON 칸보다 DB가 칸 모양을 지키고, 원본과 같은 방식이라 Querydsl·JPA로 다룸. #570 근거 칸을 더하기 쉬움 |
| 갱신 시점 | 정산 Job 끝(COMPLETED·FAILED 모두, afterJob) | 실패 기록은 Job에서만 생김. FAILED 실행의 실패도 주문을 잠금. Spring Batch 6.0은 실행 상태를 저장한 뒤 afterJob을 불러 이번 실행까지 횟수에 셈(라이브러리 원본 확인) |
| 다시 볼 주문 | 표에 있는 주문 ∪ 반영 표시 뒤에 생긴 실패 기록의 주문 | 잠긴·멈춘 주문은 다음 스냅샷에 안 들어가 "이번 스냅샷"만 보면 한 번 놓친 주문을 영영 못 잡음. 표에 있는 주문은 해결로 풀렸으면 지워야 함 |
| 반영 표시 | 한 줄짜리 갱신 상태 표에 "반영한 마지막 실패 기록 ID". 다 끝나야 올림 | 막힌 주문 줄 안에 두면 0개일 때 사라지고, 스냅샷 표는 @Immutable. 중간 실패 시 다음 갱신이 같은 범위를 다시 판정(결과가 같음) |
| 전체 다시 계산 | 하지 않음 (사용자 결정) | 실패 기록은 지우지 않아 운영 기간만큼 커짐. 하루 10만 명 규모에서 매번 전체를 읽지 않음 |
| 해결 API | 그 줄을 RESOLVED로. 지우기는 다음 Job 끝 (사용자 결정) | 해결 직후 목록에 계속 "잠김"으로 보여 다시 해결하다 409를 받는 혼란을 없앰 |
| 판정 기준 | 잠김 = `lockingFailure()`, 멈춤 = `PayoutPolicy.isStopped`. 스냅샷·해결 API와 같은 메서드 | 판정을 한곳에 모아 어긋나지 않게 (이번에 두 벌을 한 벌로 합침) |
| 원인 | 해결 안 된 실패 중 함께 보류(ORDER_HELD, "[함께 보류]" 상세)를 빼고 (주문상품·종류·사유·상세)가 같으면 1번만 | 멈춘 주문은 같은 실패가 실행마다 쌓임. 함께 보류만 남으면 그 기록이라도 보여 줌 |
| 묶음 | 1,000개씩 트랜잭션 | 막힌 주문이 많을 때 하나의 긴 트랜잭션을 피함 |
| 판정 실패 | 판정(메모리 계산)에서 예외가 난 주문만 `[정산-시스템문제]`로 남기고 건너뜀. 저장 중 DB 오류는 묶음 전체 실패 (PR #585 리뷰, 사용자 결정) | 코드 버그 하나로 묶음 전체가 롤백되면 버그를 고칠 때까지 모든 갱신이 같은 곳에서 멈춤. 저장 오류는 트랜잭션이 이미 롤백 표시라 주문 하나만 뺄 수 없음 |
| 갱신·해결 겹침 | 그대로 둠 (사용자 결정) | `@Version`은 해결 API가 지면 관리자에게 500. 겹침은 하루 1번 Job과 관리자 조작이 같은 순간일 때뿐이고 다음 갱신에 바로잡힘 |
| 처음 배포 | 반영 표시 0, 첫 Job이 따라잡음 | 운영 데이터 없음 |

## 버린 대안

- **#569 목록을 네이티브 SQL 하나로(잠김∪멈춤 정렬·페이지):** 판정 조건이 SQL 문자열로 세 벌째가 됨.
- **Job 끝에 표 전체를 다시 계산:** 단순하고 저절로 회복되지만 실패 기록 전체를 매번 읽음.
- **"이번 스냅샷의 실패"만 다시 판정:** 갱신을 한 번 놓치면 잠긴 주문을 영영 못 잡음.
- **범위 맞추기 API를 이 이슈에:** 커서 #583으로 나눔. 그동안 표가 틀리면(코드 버그, 규칙 변경, DB 직접 수정) 바로잡을 수단이 없음.

## 건드릴 때 주의

- 반영 표시는 뒤로 가지 않는다. 가장 큰 실패 기록 ID가 표시보다 작으면(최근 기록을 사람이 지운 경우) 표시를 그대로 둔다. 되돌리려다 예외가 나면 그 뒤 모든 Job 갱신이 매번 실패한다(테스트에서 실제로 났음).
- 갱신 실패는 리스너가 잡아 `[정산-시스템문제]` ERROR만 남기고 Job 결과는 바꾸지 않는다. 그래서 테스트가 통과해도 갱신이 실패했을 수 있다. 테스트 출력의 "막힌 주문 표 갱신 실패" 로그를 확인한다.
- 판정 조건을 바꾸면 `lockingFailure()`·`PayoutPolicy.isStopped`·`FAILED_RUNS_BY_ORDER_SELECT`를 고친다. 표·스냅샷·해결 API가 같이 따른다. 이미 표에 들어간 줄은 다음 갱신에 표에 있는 주문으로 다시 판정된다(반영 표시 앞이어도 표에 있으면 다시 봄).
- 갱신이 원본을 읽은 뒤 커밋 전에 해결 API가 RESOLVED로 바꾸면 예전 상태로 덮일 수 있다. 다음 갱신에 바로잡힌다(잠금을 두지 않은 이유: 하루 1번 Job과 관리자 조작이 겹치는 드문 경우).
- 판정에 실패해 건너뛴 주문이 표에 없던 새 주문이면 반영 표시가 지나가 다시 보지 않는다. 버그를 고친 뒤 범위 맞추기(#583)로 바로잡는다. 판정에 쓰는 세 조회(잠김, 실패 횟수, 해결 안 된 실패)는 한 트랜잭션이고 MySQL 기본 격리 수준(REPEATABLE READ)이라 같은 시점을 본다. 격리 수준을 READ COMMITTED로 바꾸면 사이에 커밋된 해결 때문에 판정이 어긋날 수 있다.
- 반영 표시는 "실패 기록은 정산 Job 안에서만 생긴다"는 전제에 기댄다. 실패 기록을 Job 밖에서 만들면 AUTO_INCREMENT 순서와 커밋 순서가 달라, 아직 커밋 안 된 작은 번호를 표시가 지나쳐 영영 못 볼 수 있다(PR #585 리뷰).
- `PayoutBlockedOrder`는 ID를 직접 넣어 `Persistable`로 새 줄인지 알려 준다. 빼면 저장마다 SELECT가 먼저 나간다.
