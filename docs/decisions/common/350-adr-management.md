> 이 문서는 #350 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR #351이 정확하고, 코드가 바뀌었으면 코드가 우선이다. 아래 실험 수치는 별도 개인 노트(저장소 밖)에 있던 것을 옮긴 것이라 이 문서가 유일한 저장소 내 기록이다.

## 배경

AI와 장기 작업을 이어서 하면 세션이 끝나거나 담당자가 바뀐 뒤 설계 결정의 이유가 사라진다. 이유는 대화에만 있고 커밋과 PR에는 결과만 남는다. 그래서 AI가 이미 버린 방법을 다시 제안하거나 결정을 뒤집을 수 있고, 신입이나 복귀자는 PR만으로 맥락을 찾기 어렵다. 이 작업은 결정과 이유를 남기고 불러오는 체계를 만든다.

세 문서가 역할을 나눈다. PR은 "무엇이 바뀌었나", ADR은 "왜 그렇게 했나", 규칙(`.claude/rules`, `docs/DEVELOPMENT.md`)은 "앞으로 항상 지킬 것"이다.

- 범위: 폴더 구조, README(기록 기준과 규칙), 템플릿, 세션 요약 스킬 2개의 경로·절차 변경, PR 연결(pr 스킬, PR 템플릿, CLAUDE.md), 민감정보 검사 스크립트, 예시 ADR 1건(#330).
- 범위 밖: 훅과 settings.json, CI 자동 검사, docs/CONVENTION.md 반영, 이미 머지된 PR의 소급 작성.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 쓰는 범위 | 계획·설계 질문에서 쓰고, 이슈가 이미 자세한 구현은 필수로 두지 않는다 | 실험에서 계획 품질은 올랐지만(아래) 구현 코드 품질은 같았다. 효과가 코드와 문서에 이유가 남지 않은 결정에 몰렸다 |
| 저장 위치 | 프로젝트 안 docs/decisions (사용자 결정) | 결정이 바뀌면 코드와 같은 PR에서 고치고 함께 리뷰하고, IDE에서 바로 열고, 새 worktree마다 초기화할 필요가 없다 |
| 폴더 구조 | docs/decisions/모듈/이슈번호-slug.md (사용자 결정) | 모듈 폴더는 Gradle 모듈명과 같게 해 IDE에서 모듈별로 찾고 후보를 좁힌다. PR 번호는 문서를 쓸 때 없을 수 있어 이슈 번호를 쓴다 |
| 문서 단위 | 이슈(작업) 하나에 핵심 결정 여러 개를 표로. 에픽 단위로 키우거나 통합하지 않는다 (사용자 결정) | 표준 ADR(결정 하나당 한 문서)보다 PR과 대응되고 쓰는 부담이 적다. 표준과 다른 점은 감수한다 |
| 본문 구성 | 배경, 결정과 이유, 버린 대안, 건드릴 때 주의 네 섹션. 머리말도 PR 번호·제목·영향 모듈은 빼고 일곱 필드만 둔다 (PR 리뷰 피드백 반영) | 남은 작업·검증은 이슈와 PR이 더 정확하고 쉽게 낡는다. 설계 의도·구현 이력은 결정 표, 코드, 커밋과 겹쳐 읽는 사람에게 같은 말을 반복했다. PR 번호는 PR을 올린 뒤 채우는 커밋이 따로 필요했고, 제목은 요약과 겹치고, 영향 모듈은 paths 겹침으로 찾을 수 있다 |
| PR 연결 | PR 본문은 핵심 변경만, 설계 세부는 ADR 링크 | PR 본문은 짧게 쓰는 방침과 맞다. 머지 전에는 상대 경로가 열리지 않아 브랜치 기준 전체 주소를 쓴다 |
| 낡음 판정 | 커밋 해시 대신 관련 코드 경로(paths)와 문서를 마지막으로 바꾼 커밋 이후 변경 수 | squash 머지에서는 브랜치 커밋 해시가 이력에 남지 않는다. 문서와 코드를 같은 PR에서 머지해도 그 커밋은 세지 않는다 |
| 후보 선택 | 모듈 폴더와 paths 겹침으로 스크립트가 좁히고, 색인은 파일로 저장하지 않는다 | AI 판단에만 맡기면 놓친다. 색인 파일을 커밋하면 PR마다 충돌한다 |
| 민감정보 | 유입을 막는다(작성 규칙, 저장 전 검사 스크립트, PR 리뷰). 유출되면 값 폐기를 먼저 한다 | 문서는 코드 저장소 이력에 남아 머지 뒤에는 지우기 어렵다. 강제 푸시로 덮어써도 복제본과 캐시에 남는다 |
| 상태 규칙 | 보통 확정으로 쓰고, 머지된 문서는 고치지 않는다. 바뀐 사실은 후속 절, 결정이 바뀌면 대체됨 | 머지 전에 진행 중으로만 쓰면 확정으로 바꿀 정상 경로가 없어진다 |
| 쌓이는 문서 | 오래 지킬 결정은 규칙으로 승격하고, 대체됨은 색인에서 기본으로 빼고, 낡은 문서는 정리 후보로 표시하고, 분기마다 점검한다 | 쌓기만 하면 문서가 늘수록 읽히지 않는다. 자동으로 로드되는 규칙이 "참고하길 기대하는" ADR보다 확실하다 |
| CI 자동 검사 | 이번에는 도입하지 않는다 | 팀 전체 설정을 바꾸는 일이라 팀이 정한 뒤 별도 이슈로 한다 |

- 계획 품질(8점 만점, 요청 7개 × 조건 2 × 3회, 조건을 가린 두 판정자의 교차 채점): 문서 없음 5.52, 사용 7.24. 이미 내린 결정과 이유를 아는가, 버린 대안을 근거 없이 되살리지 않는가 항목이 가장 크게 올랐다. 정답 기준이 같은 설계 내용에서 나와 "더 잘하는가"가 아니라 "결정을 아는가"를 잰 점수다.

- 낡은 문서를 현재 사실로 쓴 응답은 30개 중 0개였다. 문서 108건 규모(대부분 단순한 스텁)에서는 필요한 문서를 찾는 재현율이 1.00에서 0.90으로 떨어지고 호출당 비용과 시간이 약 2배가 됐다.

## 버린 대안

- **별도 문서 저장소와 git submodule:** 이력과 접근 범위를 분리하고 민감정보를 코드 이력에서 떼어 둘 수 있다. 그러나 버전 고정이라는 서브모듈의 장점을 쓰지 않고, worktree마다 초기화하고 포인터를 관리하고 CI에서 recurse 설정을 챙기는 마찰이 생긴다. 결정이 바뀔 때 코드와 같은 PR에서 고치기도 어렵다. 이력 분리 장점을 잃는 것은 감수하고 작성 규칙과 리뷰로 막는다.
- **레포 밖 고정 경로에 일반 clone하고 심볼릭 링크:** 심볼릭 링크는 IDE 설정이 필요하고 Windows에서 개발자 모드가 필요할 수 있다. (미확인) 팀에 Windows 사용자가 있는지는 확인하지 않았다.
- **레포 안에 clone하고 git에서 제외:** worktree마다 따로 받아야 하고 `git clean -fdx`에 지워질 수 있다.
- **외부 문서 도구(노션 등):** 비용이 들고 평문 노출 위험은 비슷하며, AI가 읽는 경로가 복잡해진다. 코드와 동기화되지 않는다.
- **강제 푸시로 이력의 민감정보 덮어쓰기:** 이미 받아 간 복제본과 GitHub 캐시에 남는다. 그래서 값 폐기를 우선하고 이력 정리는 보조로 둔다.
- **AI 판단만으로 후보 선택:** 108건에서 필요한 문서를 두 번 놓쳤다. 모듈 폴더와 경로 겹침으로 구조적으로 좁힌다.
- **본문에 남은 작업, 알려진 약점, 검증, 이어서 작업할 때를 두는 안:** 이슈와 PR, 코드가 더 정확하고 쉽게 낡는다. 그 대신 후속 작업을 막는 확인 사항은 후속 이슈 본문에 쓰는 습관이 필요하다.

## 건드릴 때 주의

- 머지된 ADR은 고치지 않는다. 바뀐 사실은 후속 절, 결정이 바뀌면 이전 문서의 status만 대체됨으로 바꾼다.
- 머리말의 이슈·관련 이슈 번호는 `#` 없이 숫자만 쓴다. YAML에서 `#`은 주석이라 값이 잘린다.
- 낡음 판정에서 문서와 같은 PR에 든 코드 커밋을 세면 "이후 변경"이 항상 1건 이상이 된다. 문서를 건드린 커밋은 세지 않아야 한다.
- 검사 스크립트(`scan-sensitive.sh`)는 awk에서 안쪽 `match()`가 `RSTART`·`RLENGTH`를 덮어써 한글 값 줄에서 무한 루프가 난 적이 있다. 바깥 값을 먼저 저장하는 순서를 유지한다. 자리표시자를 가리는 규칙은 안에 `=`, `:`, 따옴표가 없는 짧은 `<...>`만 지운다. 넓히면 그 안의 비밀값을 놓친다.
- 검사 스크립트는 자주 나오는 꼴만 잡는다. 문장에 풀어 쓴 값, 영문자로만 된 비밀번호, 실제 고객 데이터는 README의 점검표대로 사람이 읽어 확인한다.
- 기준 브랜치가 다른 작업 브랜치 위에 쌓인 경우 PR이 없으면 `session-summary`가 부모 기준을 묻는다. 스택으로 묶인 PR은 base를 바꾸기 전에 `gh stack unstack`으로 풀어야 한다.
- 예시 ADR(#330)은 draft인 PR #334의 구조를 설명한다. #334가 머지되기 전에는 문서와 코드가 다르다.
