> 이 문서는 #350 작업의 설계 의도와 결정의 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR #351이 정확하고, 코드가 바뀌었으면 코드가 우선이다. 아래 실험 수치는 별도 개인 노트(저장소 밖)에 있던 것을 옮긴 것이라 이 문서가 유일한 저장소 내 기록이다.

## 목적과 범위

AI와 장기 작업을 이어서 하면 세션이 끝나거나 담당자가 바뀐 뒤 설계 결정의 이유가 사라진다. 이유는 대화에만 있고 커밋과 PR에는 결과만 남는다. 그래서 AI가 이미 버린 방법을 다시 제안하거나 결정을 뒤집을 수 있고, 신입이나 복귀자는 PR만으로 맥락을 찾기 어렵다. 이 작업은 결정과 이유를 남기고 불러오는 체계를 만든다.

- 범위: 폴더 구조, README(기록 기준과 규칙), 템플릿, 세션 요약 스킬 2개의 경로·절차 변경, PR 연결(pr 스킬, PR 템플릿, CLAUDE.md), 민감정보 검사 스크립트, 예시 ADR 1건(#330).
- 범위 밖: 훅과 settings.json, CI 자동 검사, docs/CONVENTION.md 반영, 이미 머지된 PR의 소급 작성.

## 핵심 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 쓰는 범위 | 계획·설계 질문에서 쓰고, 이슈가 이미 자세한 구현은 필수로 두지 않는다 | 실험에서 계획 품질은 올랐지만(아래) 구현 코드 품질은 같았다. 효과가 코드와 문서에 이유가 남지 않은 결정에 몰렸다 |
| 저장 위치 | 프로젝트 안 docs/decisions (사용자 결정) | 결정이 바뀌면 코드와 같은 PR에서 고치고 함께 리뷰하고, IDE에서 바로 열고, 새 worktree마다 초기화할 필요가 없다. ADR은 관련 코드와 가까운 곳, 가능하면 같은 버전 관리에 두라는 일반적인 권장과도 맞다 |
| 폴더 구조 | docs/decisions/모듈/이슈번호-slug.md (사용자 결정) | 모듈 폴더는 Gradle 모듈명과 같게 해 IDE에서 모듈별로 찾고 후보를 좁힌다. PR 번호는 문서를 쓸 때 없을 수 있어 이슈 번호를 쓴다 |
| 문서 단위 | 이슈(작업) 하나에 핵심 결정 여러 개를 표로 | 표준 ADR(결정 하나당 한 문서)보다 PR과 대응되고 쓰는 부담이 적다. 표준과 다른 점은 감수한다 |
| PR 연결 | PR 본문은 핵심 변경만, 설계 세부는 ADR 링크 | PR 본문은 짧게 쓰는 방침과 맞고 PR 리뷰가 쉬워진다. 머지 전에는 상대 경로가 열리지 않아 브랜치 기준 전체 주소를 쓴다 |
| 낡음 판정 | 커밋 해시 대신 관련 코드 경로(paths)와 문서를 마지막으로 바꾼 커밋 이후 변경 수 | squash 머지에서는 브랜치 커밋 해시가 이력에 남지 않는다. 문서와 코드를 같은 PR에서 머지해도 그 커밋은 세지 않는다 |
| 후보 선택 | 모듈 폴더와 paths 겹침으로 스크립트가 좁히고, 색인은 파일로 저장하지 않는다 | AI 판단에만 맡기면 놓친다. 색인 파일을 커밋하면 PR마다 충돌한다 |
| 민감정보 | 유입을 막는다(작성 규칙, 저장 전 검사 스크립트, PR 리뷰). 유출되면 값 폐기를 먼저 한다 | 문서는 코드 저장소 이력에 남아 머지 뒤에는 지우기 어렵다. 강제 푸시로 덮어써도 복제본과 캐시에 남는다 |
| 상태 규칙 | 보통 확정으로 쓰고, 머지된 문서는 고치지 않는다. 바뀐 사실은 후속 절, 결정이 바뀌면 대체됨 | 머지 전에 진행 중으로만 쓰면 확정으로 바꿀 정상 경로가 없어진다 |
| 쌓이는 문서 | 오래 지킬 결정은 규칙으로 승격하고, 대체됨은 색인에서 기본으로 빼고, 낡은 문서는 정리 후보로 표시하고, 분기마다 점검한다 | 쌓기만 하면 문서가 늘수록 읽히지 않는다. 자동으로 로드되는 규칙이 "참고하길 기대하는" ADR보다 확실하다. 기록 단위를 에픽으로 키우는 안은 사용자 확인이 필요해 보류했다 |
| CI 자동 검사 | 이번에는 도입하지 않는다 | 팀 전체 설정을 바꾸는 일이라 팀이 정한 뒤 별도 이슈로 한다 |

근거가 된 실험(표본이 작아 방향을 확인한 수준이다).

- 계획 품질(8점 만점, 요청 7개 × 조건 2 × 3회 = 42회, 조건을 가리고 두 판정자가 교차 채점): 문서 없음 5.52, 사용 7.24. 결정·이유 인식과 버린 대안 처리 항목이 가장 크게 올랐다.
  - 점수 기준: 요청마다 AI가 낸 진행 계획을 네 항목(각 0~2점)으로 채점해 더한 값이 8점이다. 이미 내린 결정과 그 이유를 아는가, 이미 버린 대안을 근거 없이 되살리지 않는가, 변경의 범위와 순서를 짚는가, 사용자 확인이 필요한 지점을 짚는가를 본다.
  - 정답 기준은 요청별로 그 작업의 설계 문서에 적힌 결정에서 뽑았다. 판정자 두 명(Opus 서브에이전트, Codex)이 어느 조건의 응답인지 모른 채 채점했고, 응답별로 두 점수를 평균했다.
  - 한계: 정답 기준과 요약이 같은 설계 내용에서 나왔다. 그래서 이 점수는 "이미 내린 결정을 아는가"를 재는 것이고 "일을 더 잘하는가"를 재는 것은 아니다.
- 다른 모델(요청 4개 × 조건 2 × 2회): Haiku +0.87, Opus +1.00. 방향은 같았고 차이는 코드와 문서에 이유가 없는 결정에 몰렸다.
- 구현 코드 품질(35점 만점, 후보 3개씩): 28.83 대 28.83로 차이가 없었다. 의존 방향, 포트 설계, 기능·테스트 보존, 아키텍처 규칙, 단순성, 컨벤션, 변경의 안전성 7항목을 각 0~5점으로 채점해 더한 값이고, 이 실험도 두 판정자가 조건을 가린 채 채점해 평균했다.
- 낡은 문서를 현재 사실로 쓴 응답은 30개 중 0개였다. 문서 108건 규모에서는 필요한 문서를 찾는 재현율이 1.00에서 0.90으로 떨어지고 호출당 비용과 시간이 약 2배가 됐다.

## 검토한 대안과 버린 이유

- **별도 문서 저장소와 git submodule:** 이력과 접근 범위를 분리하고 민감정보를 코드 이력에서 떼어 둘 수 있다. 그러나 버전 고정이라는 서브모듈의 장점을 쓰지 않고, worktree마다 초기화하고 포인터를 관리하고 CI에서 recurse 설정을 챙기는 마찰이 생긴다. 결정이 바뀔 때 코드와 같은 PR에서 고치기도 어렵다. 이력 분리 장점을 잃는 것은 감수하고 작성 규칙과 리뷰로 막는다.
- **레포 밖 고정 경로에 일반 clone하고 심볼릭 링크:** 프론트·백엔드가 문서 저장소를 공유하기에 적합하다. 그러나 IDE에서 보려면 링크나 IDE 설정이 필요하고, 심볼릭 링크는 Windows에서 개발자 모드가 필요할 수 있다. (미확인) 팀에 Windows 사용자가 있는지는 확인하지 않았다.
- **레포 안에 clone하고 git에서 제외:** worktree마다 따로 받아야 하고 `git clean -fdx`에 지워질 수 있다.
- **외부 문서 도구(노션 등):** 비용이 들고 평문 노출 위험은 비슷하며, AI가 읽는 경로가 복잡해진다. 코드와 동기화되지 않는다.
- **강제 푸시로 이력의 민감정보를 덮어쓰기:** 이미 받아 간 복제본과 GitHub 캐시에 남고, 닫힌 PR 참조에서 커밋이 계속 보일 수 있다. 완전히 지우려면 GitHub 지원이 필요하다. 그래서 값 폐기를 우선하고 이력 정리는 보조로 둔다.
- **AI 판단만으로 후보 선택:** 108건에서 필요한 문서를 두 번 놓쳤다. 모듈 폴더와 경로 겹침으로 구조적으로 좁힌다.

## 설계 의도

세 문서가 역할을 나눈다. PR은 "무엇이 바뀌었나", ADR은 "왜 그렇게 했나", 규칙(.claude/rules, docs/DEVELOPMENT.md)은 "앞으로 항상 지킬 것"이다.

흐름은 이렇다. 작업 중 대화에서 결정이 나온다. PR을 올리기 전이나 직후 대화가 살아 있을 때 `session-summary`가 템플릿대로 ADR 초안을 만들고 사람이 확인한 뒤 작업 브랜치에 커밋한다. PR 본문은 핵심만 쓰고 ADR 링크를 넣는다. 다음 작업에서 `session-context`가 모듈 폴더와 paths 겹침으로 후보를 좁혀 보여주고 고른 문서만 대화에 불러온다. 대화 없이 쓴 요약은 정직하지만 쓸모가 낮았기 때문에 대화가 살아 있을 때 쓰는 것을 전제로 한다.

## 구현 중 부딪힌 것

- 예시 ADR의 머리말이 YAML로 읽히지 않았다. `related: [#331, ...]`에서 `#`이 주석으로 처리됐다. 이슈·PR·관련 이슈 번호를 `#` 없이 숫자로 쓰도록 규칙을 바꿨다.
- 상태 규칙이 서로 부딪혔다. 머지 전에는 진행 중으로 쓰고 머지된 문서는 고치지 않으면 확정으로 바꿀 길이 없다. 확정을 기본으로 하고 진행 중은 결정이 남은 경우로 한정했다.
- 검사 스크립트가 같은 줄의 예시 값(127.0.0.1 등) 때문에 다른 비밀값을 놓쳤고, 특수문자가 든 비밀번호와 새 키 형식을 못 잡았다. 값이 한글인 줄에서는 awk가 무한 루프에 빠졌다(안쪽 `match()`가 `RSTART`와 `RLENGTH`를 덮어씀). 예시 값은 그 값만 지우고 검사하도록 바꾸고 바깥 값을 먼저 저장했다.
- PR 리뷰에서 검사 스크립트의 빈틈이 지적됐다. 자리표시자를 가리는 규칙이 `<`와 `>` 사이를 통째로 지워 그 안의 비밀값을 놓쳤고, 따옴표 친 JSON 키, 표, 한글 이름, 마침표가 붙은 IP, Bearer 토큰을 못 잡았다. 자리표시자는 안에 `=`, `:`, 따옴표가 없는 짧은 `<...>`만 지우도록 좁히고 위 꼴을 규칙에 추가했다.
- AWS 키는 올라가면 안 되는데 검사가 액세스 키 ID와 라벨이 붙은 시크릿 키만 잡았다. 라벨 없는 시크릿 키, 계정 ID·ARN, ECR·EC2·S3 주소, 리소스 ID와 개인정보 형식(주민등록번호, 휴대전화, 카드)을 추가했다. 기존 문서로 스캔해 보니 `${DB_PASSWORD:password}` 같은 Spring 기본값 표기와 자바 코드 예시가 오탐이어서 `${변수}` 참조는 가리고 괄호가 있는 값은 코드로 보도록 했다.
- 스킬을 추가한 PR #347 위에 이 PR을 쌓았는데, 이 PR이 같은 스킬을 새 방식으로 거의 다시 썼다. #347이 먼저 머지되면 옛 설계(별도 문서 저장소, 서브모듈)가 `dev`에 잠깐 들어갔다 바뀌어서, #347을 닫고 base를 `dev`로 바꿔 한 PR로 합쳤다. 스택으로 묶인 PR은 base를 바꿀 수 없어 먼저 `gh stack unstack`으로 스택을 풀었다.
- "이후 변경"이 거의 항상 1건 이상으로 나왔다. 문서와 코드를 같은 PR에서 squash 머지하면 그 커밋이 paths를 바꾼 것으로 셌다. 문서를 건드린 커밋은 세지 않도록 바꿨다.

## 남은 과제와 주의할 점

**남은 작업**

- **쌓이는 문서.** 승격 기준, 색인에서 대체됨 제외, 정리 후보 표시, 분기 점검은 넣었다. 기록 단위를 이슈가 아니라 기능이나 에픽으로 키우고 끝나면 통합하는 안은 사용자 확인이 필요해 정하지 않았다. 승격이 실제로 이뤄지는지는 시범에서 확인한다.
- 신입·복귀자가 실제로 맥락을 빨리 찾는지는 시험하지 못했다. 팀 시범에서 사람 대상 이해 시험으로 확인한다.
- PR 직후 작성을 알리는 훅은 개인 설정에서 먼저 시험한다. 훅은 상기시키는 것까지만 가능하다고 문서 기준으로 확인했고 만들지 않았다.
- CI 자동 검사와 docs/CONVENTION.md 반영은 팀이 정한다.
- 예시 ADR(#330)은 draft인 PR #334의 구조를 설명한다. #334가 머지되기 전에는 문서와 코드가 다르다.

**알려진 약점**

- 실험은 AI 독자 중심이고 조건당 응답이 6~21개이며 Sonnet 위주다. 사람 독자 효과는 측정하지 못했다.
- 문서 108건 규모(대부분 단순한 스텁)에서 재현율이 0.90으로 떨어졌다. 승격과 색인 정리를 넣었지만 실제 문서가 많아진 상황은 검증하지 못했다.
- 검사 스크립트는 자주 나오는 꼴(AWS 키·계정 ID·주소·리소스 ID, 비밀값 대입, 서비스 키, 인증 헤더, 접속 주소, 주민등록번호·휴대전화·카드 번호 등)만 잡는다. 문장에 풀어 쓴 값, 영문자로만 된 비밀번호, 압축형 IPv6, 실제 고객 데이터, 내부 시스템의 구체적인 이름은 사람이 README의 점검표대로 읽어 확인해야 한다. AWS 문맥 단어가 없는 줄의 40자 시크릿 키는 git 해시와 구분할 수 없어 잡지 않는다.
- "이후 변경" 열은 커밋 수로 센 근사치다. 실제 squash 머지 이력에서의 값은 재현하지 못했다.

**건드릴 때 주의**

- 머지된 ADR은 고치지 않는다. 바뀐 사실은 후속 절, 결정이 바뀌면 이전 문서의 status만 대체됨으로 바꾼다.
- 머리말의 이슈·PR·관련 이슈 번호는 `#` 없이 숫자만 쓴다.
- `session-summary`는 사용자 승인 대화가 있는 절차라 끝까지 자동으로 시험하지 못했다.
- 기준 브랜치가 다른 작업 브랜치 위에 쌓인 경우 PR이 없으면 부모 기준을 확인한다.

## 검증

- 확인한 것: 검사 스크립트를 양성 51줄(모두 검출)과 음성 42줄(오탐 0)로, NUL·CRLF·한 줄 다중 값까지 시험하고 저장소의 마크다운 30개를 스캔해 걸리는 곳이 없는 것을 확인했다. 색인 스크립트를 임시 git 저장소에서 끝 슬래시, 따옴표와 공백 경로, 없는 기준 브랜치, 문서와 코드 동시 커밋으로 시험했다. 예시 ADR과 템플릿의 머리말이 YAML로 읽히는 것을 확인했다. 새 세션에서 `session-context`를 두 번 실행해 정상 동작을 확인했다. 독립 리뷰어가 문서와 스킬의 모순을 점검했고 지적을 반영했다.
- 확인하지 못한 것: `session-summary`의 전 과정, PR 본문에서 ADR로 연결되는 모습(이 PR에는 링크 줄을 넣지 않았다), 실제 squash 머지 이력에서의 낡음 값, 사람 독자의 이해도.
