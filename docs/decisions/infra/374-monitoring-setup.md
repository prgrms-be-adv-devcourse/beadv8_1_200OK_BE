## 배경

부하테스트와 병목 개선에는 지표가 먼저 필요한데 앱에는 헬스 체크만 있었다. 앱 지표, MySQL 지표, 컨테이너 지표를 Prometheus로 모으고 Grafana로 보게 했다. 모듈별 서버로 나뉘어도 대상만 더하면 되게 만드는 것이 조건이었다.
범위 밖: 도메인 지표(이벤트 적체, 정산 배치), 로그 수집(#381), 알림, Redis·Kafka 지표(#395, #396), CPU·메모리 상한 값(#424).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 지표 노출 위치 | 서비스 포트(8080)가 아니라 관리 포트 18080. `health`도 함께 이동 | 서비스 포트에 두면 `SecurityConfig`에서 경로를 열어야 해 외부로 샐 위험이 있다. 18080은 호스트에 열지 않고 nginx도 프록시하지 않아 구조로 막힌다. 모듈 단독 실행이 8081~8088을 써서 피했다 |
| 인스턴스 태그 | 앱은 `application` 태그만 달고 `instance`는 Prometheus가 대상 주소로 부여 | 같은 정보를 두 곳에서 만들지 않는다 |
| p95/p99 | `http.server.requests` 히스토그램(5ms~10s)을 켜고 Prometheus에서 계산 | 인스턴스를 합쳐 분위수를 구하려면 버킷이 필요하다. 범위를 줄여 uri별 시계열 폭증을 막았다 |
| 수집 대상 | `file_sd` 대상 파일로 분리. 잡은 `app*.yml`, `cadvisor*.yml`로 파일을 나눠 읽음 | 모듈별 서버로 나뉘면 대상 파일에 항목만 더한다. `*.yml` 하나로 읽으면 cAdvisor 대상을 앱 잡이 잘못된 경로로 긁는다 |
| 로컬 기본 대상 | 컨테이너 앱(`app:18080`). IDE·`bootRun` 사용자는 `host.docker.internal:18080`으로 바꿈 (사용자 결정) | 운영이 컨테이너라 같은 방식으로 맞춘다. 환경별 우회(`host.docker.internal`은 Linux에서 별도 설정 필요)를 기본에서 뺀다 |
| Grafana DB 계정 | MySQL 데이터소스를 만들지 않음 | MySQL 지표는 mysqld-exporter에서 Prometheus로 온다. Grafana가 DB 계정을 가질 이유가 없어 "조회 전용 분리"는 exporter 계정으로 충족한다 |
| exporter 계정 | 수동 스크립트(멱등)로 만든다. 조회 전용, 연결 3개 제한 | `initdb`는 빈 데이터 디렉터리에서만 돌아 이미 데이터가 있는 DB에는 적용되지 않는다 |
| 슬로우 쿼리 | 1초 이상을 로그 파일 이름을 고정해 남김 | 병목 쿼리를 찾는 용도라 더 낮추면 로그만 빨리 쌓인다. 이름을 고정하지 않으면 컨테이너 ID가 이름에 들어가 재생성마다 바뀐다 |
| 운영 접속 | Prometheus·Grafana는 서버의 loopback에만 열고 SSH 터널로 접속. nginx에는 연결하지 않음 | 인증이 약한 도구를 외부에 노출하지 않는다 |
| 대시보드 기준 | 주요 지표(구글 SRE의 네 가지 황금 신호(Golden Signals)인 트래픽·지연·에러·포화도)를 맨 위 행에 두고, 지표를 증상(지연·에러)과 원인(CPU·메모리·풀)으로 나눠 위에서 아래로 배치. 기준은 서버 모니터링 분석 가이드 글(kciter.so/posts/server-monitoring-analysis-guide) | 병목 분석은 "증상 확인 → 영향 범위(전체인지 일부 API인지) → 원인 후보" 순서라 화면 순서가 그 흐름과 같아야 한다 |
| 지연 | P50/P95/P99. 평균 지연 패널은 없앰. API별 p95 상위 10은 표로 보여 줌 | 평균은 분포를 지워 꼬리 지연을 숨긴다. 장애 전조는 P99에 먼저 나타난다. 전체가 느린지 특정 API만 느린지를 가르려면 API별 값이 필요하다 |
| 에러 | 4xx와 5xx를 나눠 비율로 표시 | 5xx만 보면 배포 직후 API 계약이 깨져 4xx가 늘어도 놓친다. 개수가 아니라 비율로 봐야 트래픽 변화와 섞이지 않는다 |
| 포화도 | CPU, 커넥션 풀 사용률, GC 후 살아 있는 힙 크기, 진행 중 요청 수. CPU는 P99와 한 그래프에 겹침 | CPU는 응답 시간과 같이 읽어야 의미가 있다(CPU가 낮은데 느리면 I/O·락·풀 대기). 힙은 GC 후 크기의 바닥이 오르는지로 누수를 본다. 동시 요청 수는 유입량×처리 시간(리틀의 법칙)이라 풀·스레드 고갈의 신호다 |
| 변화 표현 | 현재값 stat에 선택한 시간 범위 처음 대비 변화율을 붙이고, 그래프에 비교 구간(5분·15분·1시간) 전 값을 점선으로 겹침 (사용자 결정) | 숫자 하나로는 "전에 비해 어떻게 변해 문제인지"를 알 수 없다. 모양이 달라지는 시점이 변화가 생긴 때다 |
| 임계값 색 | CPU 70%/80%, 풀 사용률 70%/90%, 5xx 1%/5%, 4xx 10%/30%, 지연 500ms/1s는 시작값. 부하테스트 후 서비스 평소 값으로 조정 | CPU 80% 부근에서 대기 시간이 꺾인다는 글의 기준을 따랐다. 나머지는 이 서비스의 평소 값을 아직 모르므로 근거를 만들지 않고 시작값으로 표시했다 |
| 대시보드 수정 | JSON 파일로만 고친다 | 화면 수정은 저장되지 않게 해 파일과 어긋나지 않게 했다 |
| 컨테이너 지표 | cAdvisor로 CPU 스로틀링·메모리를 모음. 로컬 compose에는 메모리·CPU 상한을 걸지 않음 (사용자 결정) | 상한은 측정 후 #424에서 정한다. 이슈의 초기값(Prometheus 512m, Grafana 256m, exporter 64m)은 로컬 사용량과 맞지 않았다(Grafana가 256m의 약 84%). 운영 compose에는 이슈 초기값이 들어 있다 |
| 운영 배치 범위 | #374에 포함 (사용자 결정) | 처음에는 후속 이슈로 나누려다 같은 이슈에서 처리하기로 바꿨다 |
| MySQL 메모리 상한 | 걸지 않음 | 한도에 걸려 OOM kill로 DB가 죽는 쪽이 더 위험하다. 부하테스트 실측 후 정한다 |

## 버린 대안

- **로컬 대상 주소:** 두 주소를 한 파일에 병기하면 안 쓰는 쪽이 늘 down으로 보인다. 앱 컨테이너에 `host.docker.internal` 네트워크 별칭을 주면 한 주소로 자동 전환되는 것을 Mac에서 확인했지만, (미확인) Linux에서는 `extra_hosts` 때문에 동작하지 않을 가능성이 커서 쓰지 않았다.
- **exporter 계정 자동 생성:** `initdb`에 넣어 빈 DB에서 자동 생성하는 방식을 시도했으나 기존 DB에는 안 돌아 수동 스크립트와 두 갈래가 된다고 보고 제외했다. 감수하는 것은 처음 켤 때 스크립트를 한 번 실행해야 한다는 점이다.
- **키 경로 통일, 로컬 compose 키 마운트:** 이 작업과 별개라 #431에서 다룬다.
- **주요 지표 대안:** 네 신호를 신호등 한 칸씩으로 요약하는 방식은 임계값 근거가 없어 거짓 안심을 줄 수 있어 뺐다. "가장 많이 변한 지표 순위"와 평소 값 기준의 상대 임계값 색도 평소 값이 정해지지 않은 개발 환경에서는 오탐이 많아 뺐다.
- **Tomcat 스레드 풀 지표:** 포화도 후보였지만 Micrometer가 내려면 앱 설정(`mbeanregistry`)을 켜야 해서 이번에는 앱 설정 변경 없이 되는 진행 중 요청 수로 대신했다. 감수하는 것은 스레드 풀 사용량을 직접 보지 못한다는 점이다.
- **주간 비교(`offset 7d`):** Prometheus 보존이 7일이라 딱 일주일 전 값이 없을 수 있어 비교 구간을 5분~1시간으로 제한했다.
- **컨테이너 스로틀링 기본 활성화:** CPU limit이 없는 컨테이너는 스로틀 지표가 생기지 않아 패널이 비어 보인다. limit을 기본으로 거는 것은 값을 측정으로 정해야 해서 #424로 넘겼다.

## 건드릴 때 주의

- 관리 포트에도 Security 필터 체인이 적용된다. 새 actuator 경로를 쓰려면 `SecurityConfig`의 공개 경로에 따로 추가해야 한다. `MANAGEMENT_SERVER_PORT`를 빈 값으로 주면 포트 분리가 풀려 서비스 포트에 지표가 열린다(nginx가 막아 외부 영향은 없다).
- 18080을 호스트에 publish하거나 nginx에서 프록시하면 외부 비노출이 깨진다.
- 이 변경은 monolith에만 관리 포트를 적용한다. 모듈 yaml에는 `management` 설정이 없다. 모듈별 서버로 나눌 때 같은 설정이 필요하다.
- 수집 대상 파일의 `labels`에 `application`을 넣으면 앱이 다는 값과 충돌해 `exported_application`으로 밀린다. 대상 파일 이름은 `app*.yml`, `cadvisor*.yml`을 따라야 잡이 읽는다.
- 대시보드는 앱 지표 이름(예: `http_server_requests_active_seconds_gcount`, `jvm_gc_live_data_size_bytes`)에 의존한다. Spring Boot·Micrometer를 올리면 이름이 같은지 확인한다.
- 운영 앱 healthcheck가 18080을 본다. 관리 포트 분리 전 이미지로 롤백하면 healthcheck가 실패한다.
- 비율 stat(4xx·5xx)은 요청이 적으면 한두 건에 100%로 튀고 요청이 끝나면 값이 사라진다. 계산 구간을 늘리거나 최소 트래픽 조건을 두는 보완은 하지 않았다.
- 변화율은 선택한 시간 범위의 처음 값과 비교한다. 처음 값이 없거나 0이면 비어 보인다. 비율 stat에 붙은 변화율은 "비율 자체가 바뀐 정도"라 헷갈릴 수 있다.
- 지연·에러 임계값은 시작값이다. 값이 의미를 가지려면 평소 값이 정해진 뒤 조정해야 한다.
- (미확인) 운영 EC2에서 새 compose를 띄워 보지 않았다. `config` 검증까지만 했다. Linux에서의 cAdvisor 동작도 확인하지 않았다.
