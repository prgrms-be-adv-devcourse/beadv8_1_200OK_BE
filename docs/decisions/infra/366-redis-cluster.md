> 이 문서는 #366 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

#319의 단일 Redis는 죽으면 캐시·락·중복 방지가 모두 멈춘다. 노드는 자주 죽는다는 전제로, 노드가 죽어도 복제본이 마스터가 되고(장애 조치) 앱이 새 마스터를 스스로 찾아가게 한다. 범위는 로컬·운영 compose, 앱 접속 설정, 배포 스크립트, 테스트, 문서다. 캐시·락 사용 코드와 eviction 정책 재검토(#324)는 범위 밖이다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 구성 | 마스터 3 + 복제본 3, 총 6노드 | 장애 조치와 샤딩을 함께 얻는다. 노드가 죽는 것과 리더 변경이 요구사항이었다 (사용자 결정) |
| 배치 | 기존 EC2 1대에 6노드 | 자원이 빠듯해 서버를 늘리지 않는다 (사용자 결정). 노드 1대 고장과 리더 변경은 버티지만 EC2가 죽으면 6대가 함께 내려간다 |
| 영속성 | 노드별 볼륨에 `nodes.conf`와 가벼운 RDB만. AOF는 끔 | 볼륨 없이 재시작하면 노드 ID가 바뀌어 클러스터가 어긋난다. 사용처(캐시·락·중복 방지)의 정합성은 어차피 DB가 최종 방어선이고, AOF는 자원 부담이 확실하다 (사용자와 합의) |
| 앱 설정 | 토폴로지 주기 갱신(30초) + 복제본 우선 읽기 | 장애 조치 뒤 새 마스터를 찾게 한다 (사용자 결정). adaptive 갱신은 Boot 속성이 없고 Lettuce 7 기본값으로 켜져 있어, 값을 기대는 대신 테스트로 고정했다 |
| 로컬 접속 주소 | 노드 이름 `redis-N.localhost`, 포트 7001~7006 고정 | 노드는 알리는 주소로 앱이 다시 접속하게 하는데 Redis는 주소를 하나만 알린다. 호스트에서는 `*.localhost`가 loopback으로, 컨테이너에서는 네트워크 별칭으로 풀려 양쪽이 같은 값을 쓴다. 로컬 전용 Java 코드가 필요 없다 |
| 장애 감지 | `cluster-node-timeout 5000`, `cluster-require-full-coverage no` | 기본 15초는 감지가 느리다. 마스터 1대가 죽어도 나머지 슬롯은 서비스한다 |
| 클러스터 초기화 | 6대가 모두 새 노드일 때만 `create`, 이미 묶였으면 대기만, 그 밖은 실패 | 일부 볼륨만 사라진 상태에서 `create`를 다시 하면 기존 데이터와 슬롯 배치에 영향을 준다 |
| 배포 | 앱보다 먼저 노드를 1대씩, 복제본 먼저, 마스터는 복제본에 `CLUSTER FAILOVER`로 역할을 넘긴 뒤 재기동 | `docker compose up -d`는 바뀐 서비스를 동시에 다시 만들어 Redis 전체를 멈춘다. 마스터를 넘긴 뒤 내리면 쓰기가 끊기지 않는다 |
| 재기동 판정 | `docker compose --dry-run up`의 "Recreate"로 바뀐 노드만 처리 | 설정이 그대로인 마스터까지 장애 조치하면 앱 오류 구간만 늘어난다 |
| 무중단 기준 | 승격 직후 수 초의 일시 오류는 허용, 지속 중단은 불허 | 합의한 기준이다. 로컬 시험에서 정상 롤아웃 중 요청 약 1,130개 중 7개, 비정상 종료(SIGKILL) 중 약 1,040개 중 9개가 타임아웃이었고 이후 재시작 없이 복구했다 |
| 복제 버퍼 | `repl-backlog-size 4mb`, `client-output-buffer-limit replica 32mb 16mb 60` | 기본 상한(256mb)이 `mem_limit`(160m)보다 커서 데이터가 찬 마스터가 풀 싱크 중 메모리 제한에 걸릴 수 있다. 검토에서 지적받아 추가했다 |
| 메모리 | 노드당 `maxmemory 96mb`, `mem_limit 160m`(6대 합계 960m) | 예산 여유 안에 들게 잡은 시작값이다. (미확인) 운영 EC2 실측은 하지 않았다 |
| 통합 테스트 | 기본 Redis는 단일 노드 유지. 클러스터 모드 연결만 별도 테스트 1개 | 모든 통합 테스트가 Redis를 띄우므로 6노드로 바꾸면 기동 시간이 크게 는다 |

## 버린 대안

- **구성:** 마스터만 3대는 노드가 죽으면 그 슬롯이 멈추고 리더 변경이 없다. Sentinel은 샤딩이 안 되어 트래픽 분산에 맞지 않는다. 감수하는 것은 노드 6대의 메모리와, 마스터 과반(3대 중 2대)이 살아 있어야 자동 장애 조치가 된다는 제약이다.
- **로컬 주소:** `host.docker.internal`은 이 개발 환경의 hosts 파일에 없어 호스트 앱이 못 푼다. Lettuce 주소 매핑은 로컬 전용 Java 코드를 만들어 운영과 설정이 갈라진다. 감수하는 것은 `*.localhost`가 안 풀리는 환경에서의 hosts 파일 수정이다.
- **영속성:** AOF `everysec`는 EC2 재부팅 때 유실을 줄이지만 디스크 쓰기·재작성 메모리·CPU 크레딧 부담이 6대분이다. 감수하는 것은 비정상 종료 시 마지막 스냅샷 뒤 몇 분치 유실이다.
- **서버 분산:** 두 번째 EC2에 3 + 3을 나누면 서버 1대 장애까지 버티지만 이번에는 자원 때문에 하지 않았다.

## 건드릴 때 주의

- **포트 7001~7006과 이름 `redis-N.localhost`는 바꿀 수 없다.** 노드가 알리는 주소와 호스트에서 닿는 주소가 같아야 한다. `db-net`은 이름이 고정이라 같은 머신의 다른 compose 프로젝트와 네트워크를 공유한다.
- **노드 healthcheck가 `cluster_state:ok`라 클러스터를 만들기 전에는 healthy가 될 수 없다.** 그래서 초기화 서비스는 노드가 `service_started`이면 시작하고, 앱은 6대 healthy와 초기화 정상 종료를 기다린다. 이 의존을 바꾸면 기동이 교착한다.
- **`docker compose up -d`를 직접 실행하면 6대가 동시에 다시 만들어진다.** `deploy.sh`와 `redis-rollout.sh`를 쓴다. `needs_recreate`는 compose의 `--dry-run` 출력 형식에 기대며, 실패하면 모든 마스터를 장애 조치하는 안전한 쪽으로 기운다.
- **마스터가 3대라 마스터 2대가 동시에 죽으면 자동 장애 조치가 안 되고 클러스터 전체가 멈춘다.** 장애 판정과 승격은 마스터 과반(2대)의 동의가 필요하다. 로컬에서 마스터 2대를 동시에 죽여 승격 없이 `cluster_state:fail`이 되는 것과, 복제본에 `CLUSTER FAILOVER TAKEOVER`를 하면 복구되는 것을 확인했다. 이 한계는 서버 분산이나 마스터 수 증가로만 줄일 수 있다.
- 노드 6대는 같은 `REDIS_PASSWORD`를 써야 복제본이 마스터에 붙는다(`requirepass`와 `masterauth`).
- **복제는 비동기라 장애 조치 순간 마스터의 최신 쓰기가 사라질 수 있다.** Redis는 락과 중복 방지의 정합성을 보장하지 않으므로 DB 유니크 제약 같은 최종 방어선이 필요하다. 복제본 읽기는 오래된 값을 줄 수 있어 락·중복 방지는 `SET NX`나 Lua 같은 원자적 명령으로 한다. 여러 키 명령과 Lua는 해시 태그가 필요하다.
- 일부 노드의 볼륨만 지우면 초기화가 실패하는 것이 의도다. 6대를 모두 지워야 새로 시작한다.
- `read-from`이 있으면 단일 노드 접속도 복제 토폴로지 경로를 타며, 통합 테스트는 접속 정보 빈이 속성보다 우선하는 데 기댄다.
- (미확인) 컨테이너 안 앱(Lettuce)이 `redis-N.localhost`로 접속하는 것은 `redis-cli`로만 확인했다. (미확인) Linux·Windows에서 `*.localhost` 해석, 서버의 compose 버전이 `--dry-run`을 지원하는지, 운영 EC2 메모리 실측은 확인하지 못했다.
