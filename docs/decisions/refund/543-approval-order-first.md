## 배경

판매자가 승인한 뒤 환불은 지갑 반환 요청(Kafka) → 주문 취소 반영(HTTP) → 재고 복구(HTTP) 순서로 불렀다.
승인과 주문 반영 사이에 상품이 출고되면 주문이 409로 반영을 막는데, 그때는 지갑 반환 요청이 이미 나간 뒤라 되돌릴 수 없었다. 구매자는 상품과 돈을 둘 다 받고 환불은 처리 중에 멈췄다.
범위: 승인 뒤 순서, 주문 409 처리, 처리 중 → 거절 전이. 범위 밖: 실패 기록과 다시 시도(#545), 지갑 완료 메시지(#544), 되돌리기(#546).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 승인 뒤 순서 | 주문 → 지갑(0원이면 건너뜀) → 재고 → 완료 | 거절될 수 있는 단계를 앞에, 다시 하면 결국 되는 단계를 뒤에 둔다. 주문이 거절하면 아무것도 움직이지 않았으니 거절로 끝낼 수 있다 (11/12 멘토 리뷰, 사용자 결정) |
| 주문 409 처리 | 이유와 상관없이 처리 중 → 거절, 커밋 뒤 ERROR 로그 | 409 이유 이름은 ProblemDetail `type`에만 오는데, `PROBLEM_BASE_URI`가 기본값이면 `about:blank`라 환불이 이유를 구분할 수 없다. 세 이유(이미 출고, 수량 초과, 같은 refundId 다른 내용) 모두 다시 보내도 같은 답이다 (11/13 사용자 결정) |
| 거절 사유 | 승인 때 출고 자동 거절과 같은 문구 | 가장 흔한 원인이 승인 사이의 출고이고, 구매자에게는 "취소할 수 없다"면 충분하다. 주문의 설명 문장은 로그에만 남긴다 |
| 거절 구간의 잠금 | 새 트랜잭션에서 자기 환불 행만 잠금 | 완료로 바꿀 때와 같은 방식. 같은 묶음 배송비 한계는 아래 "주의" 참고 |
| 주문 결과 전달 | `OrderCancellationResult`(반영됨 / 거절됨)를 돌려주고, 응답 없음·그 밖의 오류는 예외(`ORDER_API_FAILED`, 503) | 다시 시도하면 낫는 실패와, 다시 보내도 같은 답인 거절을 서비스가 다르게 다루려고 나눴다 |
| 승인 뒤 거절에 빈 사유 | `IllegalArgumentException` | 사유는 판매자가 아니라 서비스 상수가 넣는다. 비면 버그라 표준 예외로 드러낸다(exception.md) |
| 주문 상태 `CANCELED` | 승인 때 자동 거절 목록에 넣음 | 주문 조회 응답(#533)에 있는 값인데 목록에 없어 모르는 값(500)으로 처리됐다 |

## 버린 대안

- **409를 이유별로 나누기:** 이미 출고만 거절, 수량 초과는 거절 + ERROR, refundId 충돌은 500으로 처리 중에 두기(11/12 결정). 이유 이름이 오지 않아 구현할 수 없었다. 주문 팀에 `PROBLEM_BASE_URI` 설정을 요청하는 길도 있었지만 요청하지 않기로 했다(주문의 409는 약속대로라 바꿀 것이 없음). 감수하는 것은 refundId 충돌도 거절로 끝나 주문의 취소 기록과 어긋날 수 있다는 점이다(환불 코드 버그나 환불 DB만 초기화했을 때만). ERROR 로그로 사람이 맞춘다.
- **같은 묶음 배송비를 이번에 맞추기:** 묶음 전체를 잠그고 드러내거나, 배송비를 다시 계산해 되돌리기. 금액을 맞추려면 되돌리기(#546)가 먼저 정의돼야 해서 이번에는 받아들였다 (사용자 결정).

## 건드릴 때 주의

- `RefundShippingFeePolicy.CANCELLING_STATUSES`는 처리 중과 완료를 "취소됨"으로 센다. #543부터 처리 중이 거절로도 갈 수 있다. 그래서 처리 중인 A를 세고 같은 묶음 B를 승인한 뒤 A가 거절되면, B의 배송비 판단이 틀린 채 남는다(예: 판매자 몫 기본 배송비 3,000원). `TODO(#516)` 참고.
- 주문 409의 `type`을 보고 분기하려면 먼저 `PROBLEM_BASE_URI`가 운영에서 설정돼 있는지 확인한다. 기본값이면 이름이 오지 않는다.
- 주문 어댑터는 `exchange()`를 쓴다. 응답 상태는 공통 클라이언트(`InternalRestClient`)의 인터셉터 밖에서 읽힌다. 그래서 응답을 읽다 끊기면 `ResourceAccessException`이 나고, 어댑터가 이를 잡아 503으로 바꾼다. 재고·조회 쪽은 아직 이 처리가 없어 500이 된다(#545).
- 지갑 발행이 실패하면 주문은 이미 취소를 기록한 상태다. 다시 시도는 같은 refundId로 주문부터 다시 불러도 된다. 주문은 같은 refundId·같은 내용이면 출고 여부보다 먼저 성공으로 답한다(#542).
