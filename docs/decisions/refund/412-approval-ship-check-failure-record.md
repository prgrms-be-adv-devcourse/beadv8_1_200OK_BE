> 이 문서는 #412 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

구매자가 요청할 때는 출고 전(`PREPARING`)이었어도, 판매자가 승인하기 전에 출고할 수 있다. 출고된 상품을 승인하면 구매자가 돈과 상품을 둘 다 받는다. 승인 때 주문 재조회는 #410이 이미 붙였고, 이 작업은 그 결과로 출고 여부를 판단한다.
또 승인 뒤 주문·재고 호출(#413·#414)이 실패해도 1단계에는 다시 처리하는 기능이 없어, 운영자가 어디서 멈췄는지 볼 표시가 필요하다. 이 작업은 그 표시를 남기는 틀까지 만든다.
범위 밖: 멈춘 환불을 다시 진행하는 방법(#413 설계 때 정함), 지갑 실패 기록(지갑은 Kafka라 #413), 재조회 뒤 완료까지 사이의 출고 막기.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 출고된 상품 승인 | 사유를 넣어 자동 거절(`REJECTED`, 200). 사유 "이미 출고됐거나 취소된 상품이라 취소할 수 없습니다." | 출고는 되돌아가지 않아 요청을 남겨 둘 이유가 없다. 409로 남기면 판매자가 거절할 때까지 요청이 쌓이고, 구매자는 이유를 모르며 같은 상품에 다시 요청도 못 한다. #410 배송비 모자람 자동 거절과 같은 방식 (사용자 결정, 처음 설계의 409를 함께 리뷰에서 바꿈) |
| 자동 거절할 상태 | 주문 상품 상태 중 `PREPARING`을 뺀 7개를 문자열로 나열 | 주문 모듈 enum을 import하지 않는다(모듈 경계). 결제 대기·결제 실패도 넣어 문구를 "출고됐거나 취소된"으로 넓혔다 (사용자 결정) |
| 주문 상태가 비었거나 모르는 값 | `IllegalStateException`(500), 요청됨 그대로 | 자동 거절이면 주문 쪽 버그만으로 구매자 요청이 끝나 버린다. 다른 모듈이 보낸 값의 오류는 버그로 드러낸다(`exception.md`) (사용자 결정) |
| 반품 안내 문구 | 넣지 않음 | 반품 기능(2단계)이 아직 없어 가리킬 곳이 없다 (사용자 결정) |
| 사유 문구 위치 | 서비스 상수 | 요청 때 409(`ORDER_ITEM_NOT_CANCELLABLE`)는 결제 대기 등에도 나가 출고 문구가 맞지 않는다 |
| 판단 순서 | 잠금 → 요청됨 확인 → 같은 주문 상품인지 확인 → 출고 판단 → 배송비 판단 | 끝난 요청은 출고와 상관없이 409가 진짜 이유다. 다른 상품 정보로 이 환불을 거절하면 안 된다. 거절할 환불에는 배송비를 판단하지 않는다 |
| 실패 기록 칸 | `failed_step`(멈춘 단계), `failure_code`(이유) 두 칸, NULL 허용 | 실패가 없는 것이 정상이라 채울 값이 없다. 빈 값으로 채우면 "실패했는데 이유 없음"과 구분되지 않는다 |
| 실패 이유 내용 | 에러 코드 이름, 없으면 예외 클래스 이름 | 예외 메시지에는 다른 모듈의 응답 내용이 섞일 수 있어 DB에 남기지 않는다 |
| 틀의 응답 | 원래 오류 그대로(잠깐 장애 503, 버그 500) | 버그까지 503(다시 시도)으로 감싸면 다시 눌러도 낫지 않는데 계속 누르게 된다. 이슈의 "503" 문구를 고쳤다 (사용자 결정) |
| 기록마저 실패하면 | 원래 오류로 응답, 기록 실패는 원래 예외에 붙이고(`addSuppressed`) ERROR 로그 | 기록 실패로 응답을 바꾸면 진짜 원인이 가려진다. 원래 예외가 `RestApiException`이면 공통 예외 처리기가 로그를 남기지 않아 이 로그가 유일한 흔적이다 (사용자 결정) |

| 기록 저장 | 별도 짧은 트랜잭션에서 그 행을 잠그고 처리 중일 때만 기록 | 같은 환불을 동시에 결정·기록하는 트랜잭션과 섞이지 않게 한다 |
| 틀 위치 | 별도 클래스 `RefundStepRunner` | 이 작업 안에서는 부르는 곳이 없어 Facade 안에 두면 테스트할 수 없다. #413·#414가 주입받아 쓴다 |

## 버린 대안

- **출고 처리:** 409를 내고 요청됨 그대로 두는 방법(처음 설계)은 요청이 남고 구매자가 이유를 모르게 돼서 제외했다. 감수하는 것은 자동 거절이 판매자 거절과 같은 `REJECTED`라 사유 문구로만 구분된다는 점.
- **모르는 주문 상태:** `PREPARING`이 아니면 모두 자동 거절하는 방법은 단순하지만, 주문 쪽 버그만으로 구매자 요청이 끝나 버려서 제외했다.
- **틀의 응답:** 모든 실패를 `*_API_FAILED`(503)로 감싸는 방법은 버그가 "잠시 후 다시 시도"로 가려져서 제외했다.
- **기록 실패:** 기록 실패 오류로 응답하는 방법은 진짜 원인이 가려져서, WARN만 남기는 방법은 기록 누락이 묻혀서 제외했다. 감수하는 것은 `service.md` 로그 표(보상 실패는 WARN)와 다르다는 점.
- **실패 이유:** 예외 메시지를 그대로 저장하는 방법은 다른 모듈 응답 내용이 DB에 남아서 제외했다.

## 건드릴 때 주의

- 주문 상태가 새로 생기면 `RefundableOrderItem`의 자동 거절 목록에 넣을지 정해야 한다. 넣지 않으면 그 상태의 승인은 500이 된다.
- 판단 순서를 바꾸지 않는다. 출고 판단을 같은 상품 확인 앞으로 옮기면 다른 상품의 상태로 이 환불이 거절된다(테스트가 잡는다).
- `RefundStepRunner`는 #411의 승인 트랜잭션 같은 트랜잭션 안에서 부르지 않는다. Facade에서만 부른다.
- 1단계에는 멈춘 환불을 다시 진행하는 기능이 없다. 기록이 남아도 그 환불은 처리 중에 머물고, 구매자는 철회도 다시 요청도 못 한다. 기록마저 실패하면 ERROR 로그만 남는다. 재처리는 #413 설계 때 정한다.
- 이름 없는 예외 클래스는 클래스 이름이 빈 값이라 이유 기록이 실패한다(ERROR 로그로만 남음). 다른 모듈 클라이언트는 이름 있는 예외를 던지게 한다.
