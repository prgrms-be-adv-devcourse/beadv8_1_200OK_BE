## 배경

#592가 승인 뒤 단계를 지휘자 `RefundSagaService` 한 곳으로 옮겼지만, 같은 상황을 경로마다 다르게 처리했다(단계 줄 없는 옛 환불, 다음 줄 무조건 새로 저장, 완료 메서드 둘, 처리 중이 아닐 때 예외·넘김이 섞임). 판단은 지휘자 안 if 문이었고, 알람(#576)이 부를 환불 번호 입구가 없었다. #575(정석 사가 지휘자)의 셋째 하위 이슈로 셋을 맞춘다.

범위 밖: 시도 중이 오래 멈춘 줄 다시 집기(#576), 결과 대기 시간 초과(#577), 되돌리기(#546·#622), 불일치 출처 구분(#572).

이 문서가 대체하는 부분: ADR 592의 "판단 객체를 만들지 않음", "완료 메서드 둘", "다음 단계 줄 무조건 새로 저장", "출고 거절 사유 상수 두 곳". ADR 544의 "거르는 위치(서비스 안)". ADR 574의 "옛 기록 옮기기" 이유 중 "#574 전 환불도 재고 실패 보호가 이어져야 한다"(옮긴 멈춤 줄만 있는 처리 중 환불은 이제 진행하지 않는다, 결정 "옛 환불"). 예전 문서는 고치지 않는다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 판단 입력 | 환불 + 단계 줄 + 방금 받은 답 + 지금 시각. 입구는 둘: 답이 있으면 `afterEvent`, 알람이면 `fromSteps` | 진행표만 보면 "불일치로 멈춘 지갑 줄 + 맞는 완료"(#544 결정 8)를 멈춤으로 잘못 정한다. 지금 시각은 #576·#577이 쓴다(지금은 받기만 함) (사용자 결정) |
| 옛 환불 | 단계 줄이 없거나 앞 단계 성공 뒤 다음 줄이 없으면 있을 수 없는 상태 → WARN, 진행 안 함 | 다음 줄은 앞 단계 성공과 같은 트랜잭션에서 만든다. 이유를 모르는 채 돈을 보내지 않는다. #574 전 처리 중 환불은 DB에 없다 (사용자 결정) |
| 다음 줄 준비 | 없음 → 만듦, 할 차례 → `begin`(횟수 +1), 시도 중·결과 대기 → 보내지 않음, 끝 상태 → 진행 안 함 | 무조건 새로 저장하면 다시 진행할 때 `(refund_id, step)` 유일 제약에 걸린다(통합 테스트로 재현). 모든 단계가 `begin`을 거쳐 #576 횟수 제한이 이 숫자를 쓴다 (사용자 결정) |
| 처리 중 아님 | 잠근 뒤 처리 중이 아니면 쓰지 않고, 예외 없이 지금 상태를 돌려주고 WARN(정상 중복은 INFO) | 경로마다 409·넘김·도메인 예외가 섞여 있었다. 0원 승인 경합 때 판매자 응답이 409에서 지금 상태로 바뀐다 (사용자 결정) |
| 환불 번호 입구 | `RefundSagaUseCase.resume(refundId)`. 예외는 그대로 올린다 | 다른 두 입구와 같은 계약. 환불마다 예외를 잡고 넘어가는 일은 알람(#576) 몫 (사용자 결정) |
| resume 실행 모양 | 계획에 한 번 묻고, 승인·지갑 완료와 같은 실행 메서드(`runOrderStep`·`publishWallet`·`releaseProduct`·`completeInRequest`)를 부른다 | 실행 코드가 한 벌이라 승인 때와 알람 때 동작이 어긋나지 않는다 (사용자 결정) |
| 잠근 뒤 줄 확인 위치 | 지휘자(`prepareStep`)에 둔다 | 잠금과 붙어 있어야 하는 실행이라 #575 결정 5(실행은 지휘자)를 따른다. 계획으로 옮겨도 잠근 뒤 다시 보기는 남는다 (사용자 결정) |
| 결정 8 뒤 알람 | 재고 줄이 있으면 지갑 줄 상태를 보지 않고 재고 줄로 이어 간다 | 재고 줄 = 지갑 완료를 받은 증거. `WalletResultPolicy`의 "지갑 성공 뒤" 기준과 같고, 같은 상태가 들어온 경로에 따라 다르게 끝나지 않게 한다 (사용자 결정) |
| 다음 할 일 답 | 주문·지갑·재고 부르기, 완료, 거절, 기다림, 멈춤 7종 | 되돌리기(#546)·시간 초과(#577)는 그 이슈에서 더한다 (사용자 결정) |
| 호출 값 출처 | 세 입구 모두 환불 행에서 꺼낸다 | 입구마다 값 출처가 달라 어긋날 수 있었다. 승인마다 읽기 한 번이 는다 (사용자 결정) |

## 버린 대안

- **진행표만으로 판단:** 입력이 단순하지만 결정 8 경로를 멈춤으로 바꿔 버렸다.
- **판단 객체가 답과 줄을 함께 받아 "넘김"까지 답하기:** 판단이 한 곳에 더 모이지만, 지휘자의 잠근 뒤 다시 보기가 남아 비슷한 확인이 두 곳인 것은 같고 코드만 는다. 감수하는 것은 단계를 더할 때(#546) 계획과 `prepareStep`을 같이 봐야 하는 것.
- **resume을 "계획 → 한 단계 → 계획" 반복으로:** 단계마다 트랜잭션 모양이 달라 반복문이 복잡하고, 실행 코드가 승인 쪽과 두 벌이 된다.
- **중간 줄이 없으면 만들어 진행:** 자동으로 끝나지만 버그·손댄 데이터일 때 돈이 잘못 나갈 수 있다.
- **시도 중 재고 줄이어도 지갑 완료가 다시 오면 재고 다시 부르기(예전 동작):** 상품은 refundId로 한 번만 풀지만 단계마다 규칙이 달라진다. 감수하는 것은 "재고 실패 + 실패 기록도 실패"가 겹친 환불이 #576 전까지 멈추는 것.
- **`now`를 지금 빼고 #576에서 넣기:** 쓰지 않는 값은 없어지지만 결정한 입력 목록과 어긋나고 바로 다음 이슈에서 다시 고친다.

## 건드릴 때 주의

- 단계 순서를 아는 곳은 `RefundSagaPlan`이다. 단계를 더하면 `afterEvent`·`fromSteps`와 지휘자의 `prepareStep` 결과 처리(BUSY·ENDED)를 함께 본다.
- `fromSteps`의 "재고 줄 있음 → 지갑 줄 안 봄"과 `WalletResultPolicy`의 "재고 줄 있음 = 지갑 성공 뒤"는 같은 기준이다. 한쪽만 바꾸면 결정 8 환불이 경로마다 다르게 끝난다.
- 진행표만으로는 "지갑 줄이 시도 중·할 차례 = 실제로 보냈는지"를 가를 수 없다. 다시 보내도 안전한 것은 지갑이 같은 refundId 중복을 막는다는 약속(PR #537·지갑 #611)에 기댄다.
- 시도 중·결과 대기 줄은 지금 어떤 경로로도 다시 보내지 않는다. 다시 집기는 새 도메인 전이로 #576·#577에서 더한다.
- `resume`은 트랜잭션 밖에서만 부른다(입구가 실행 중에 검사).
