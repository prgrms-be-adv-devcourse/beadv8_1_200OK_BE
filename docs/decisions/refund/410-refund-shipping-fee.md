## 배경

배송비와 도서산간 운임은 판매자 묶음(한 주문 안 같은 판매자 상품들, 한 상자) 단위로 낸다. 묶음을 나눠 취소하면 그중 한 요청만 배송비를 돌려받아야 하고, 무료배송 묶음을 일부만 취소해 기준 아래로 내려가면 판매자가 남은 상품의 택배비를 떠안는다.
이 작업은 환불 한 건의 배송비(돌려줄 배송비, 도서산간 운임, 뺀 배송비)를 정하고 저장하는 것까지다.
범위 밖: 같은 묶음 동시 승인(#411), 승인 때 출고 확인(#412), 지갑 전송과 0원 처리(#413), 완료 상태(#414), 묶음 한꺼번에 취소(#365).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 계산 시점 | 판매자 승인 때 | 나눠 요청하면 어느 요청이 "묶음 전부 취소"인지 승인 순서로만 알 수 있다. 요청 때 정하면 아무도 배송비를 못 받는 경우가 생긴다 (사용자 결정) |
| 승인 때 주문 값 | 주문을 다시 조회 | 요청 때 받은 값을 저장하려면 묶음 상품 목록을 담을 곳이 따로 필요하다. 출고 확인(#412)에 어차피 승인 때 조회가 필요해 앞당겼다 (사용자 결정) |
| 거절 때 조회 | 하지 않음 | 쓸 값이 없고, 주문이 느리거나 장애여도 거절은 막히지 않게 한다 (사용자 결정) |
| 전부 취소 판단 | 환불 테이블의 처리 중 수량을 직접 집계 | 주문의 `refundedQuantity`는 처리 중인 환불을 모른다 |
| 무료배송이 깨질 때 | 기본 배송비를 뺌. 처음 깨질 때 한 번만 | 판매자가 남은 상품 택배비를 떠안지 않게. 이슈와 주문 요청서가 "뺀다"로 합의 |
| 끝까지 전부 취소되면 | 앞에서 뺀 배송비도 마지막 환불에서 돌려줌 | 상자가 나가지 않으니 받을 근거가 없다. 나눠서 전부 취소한 합계 = 낸 돈 |
| 취소 금액 = 기본 배송비 | 0원 환불로 받음 | 손해 보는 사람이 없다 (사용자 결정) |
| 배송비가 모자랄 때 | 요청 때 409 `PARTIAL_CANCEL_NOT_ALLOWED`, 승인 때 사유를 넣어 자동 거절 | 승인 때 409로 두면 요청이 쌓이고 구매자가 이유를 모른다. 자동 거절은 판매자 거절과 같은 `REJECTED`이고 사유 문구로만 구분한다 (사용자 결정) |
| 배송비를 낸 묶음 | 단가 합이 기준 이상으로 보여도 빼지 않음 | 주문 쪽 계산이 달라져도 이미 낸 배송비를 두 번 빼지 않게, 낸 배송비를 기준 판단보다 먼저 믿는다 (리뷰 반영) |
| 저장 방식 | 세 칸을 따로 저장, 합계(`refundAmount`)는 응답 때 계산 | 합계까지 저장하면 어긋날 칸이 늘어난다. 화면에서 더하고 빼면 부호 실수가 생겨 서버가 계산해 준다 (사용자 결정) |
| 끝난 상태의 금액 | 거절·철회도 칸 값을 그대로 보여 줌 | 상태로 구분된다. #409 응답을 바꾸지 않는다 (사용자 결정) |
| 뺀 이유 칸 | 두지 않음 | 1단계에서는 이유가 하나뿐이다 (사용자 결정) |
| 승인 트랜잭션 | Facade: 읽기(잠금 없음) → 주문 조회(트랜잭션 밖) → 서비스 한 트랜잭션: 행 잠금 → 상태 확인 → 집계 → 판단 → 저장 | 주문 호출 동안 DB 연결과 행 잠금을 잡지 않는다. 그사이 철회되면 잠근 뒤 상태 확인이 409로 막는다 |
| 끝난 요청 승인 | 주문을 부르기 전에 409 | 주문 장애 때 409 대신 503이 나가지 않게 한다. 최종 확인은 잠근 뒤 다시 한다 |
| 요청 때 판단 순서 | 저장(`saveAndFlush`) 뒤 판단, 모자라면 예외로 되돌림 | 같은 상품에 처리 중 요청이 있으면 그 개수까지 더해져 판단이 "개수 초과"(500)로 깨진다. UNIQUE가 먼저 409로 막게 한다 |
| 주문이 보낸 값이 깨졌을 때 | 표준 예외(500). `sellerGroup` 없음, 음수, 빈 목록, 중복 상품, 묶음에 없는 상품 | `exception.md`: 다른 모듈이 보낸 값의 오류는 버그로 드러낸다. 503(다시 시도)으로는 낫지 않는다 |

## 버린 대안

- **계산 시점:** 요청 때 계산은 나눠 요청한 묶음에서 마지막 요청을 알 수 없어 버렸다.
- **승인 때 주문 값:** 요청 때 받아 저장은 묶음 목록 저장소가 필요해 버렸다. 감수하는 것은 승인 때 주문 호출 하나(실패하면 503, 요청됨 유지).
- **무료배송이 깨질 때 안 뺌(10/29 초안):** 판매자가 택배비를 떠안아 버렸다.
- **취소 금액 = 배송비도 막음(`<=`):** 손해가 없는데 막을 이유가 없어 버렸다.
- **승인 때 모자라면 409로 요청됨 유지:** 요청이 남고 구매자가 이유를 몰라 버렸다.
- **끝난 상태 금액 0:** #409 응답을 바꾸게 되어 버렸다.
- **합계 저장 / 프론트 계산:** 어긋날 칸이 늘거나 부호 실수가 생겨 버렸다.
- **주문 응답이 깨지면 503:** 다시 시도해도 낫지 않는 버그를 일시 장애처럼 보이게 해 버렸다(PR 리뷰 제안).
- **주문이 "무료배송 적용 여부"를 직접 보냄:** 지금 주문에는 할인·쿠폰이 없어 단가 합 판단이 배송 모듈과 같다. 할인이 생기면 다시 본다(PR 리뷰 제안).

## 건드릴 때 주의

- 같은 묶음의 다른 환불을 동시에 승인하면 서로의 처리 중 개수를 못 봐 배송비가 틀릴 수 있다. 행 잠금은 환불 한 건 단위다. #411이 묶음 단위로 줄 세우기 전까지 받아들인 위험이고, 지갑 전송(#413) 전이라 돈은 나가지 않는다.
- 집계 상태는 `PROCESSING`만이다(`RefundService.CANCELLING_STATUSES`). 완료 상태(#414)를 만들면 여기에 더해야 한다. 처리 중에서 되돌아가는 상태가 생기면 이미 저장한 뺀 배송비와 집계가 어긋나니 함께 정한다.
- 서비스 `approve`의 상태 확인은 배송비 판단보다 먼저여야 한다. 처리 중인 요청을 다시 판단하면 자기 개수가 집계에 들어가 500이 난다. 엔티티 `Refund.approve`도 상태를 보지만 판단 뒤라 이것만으로는 안 된다.
- 요청 때 판단을 저장 앞으로 옮기면 같은 상품 중복 요청이 409 대신 500이 된다.
- 배송비는 승인 때 한 번 정하고 다시 계산하지 않는다. 주문 조회와 잠금 사이의 변화는 반영하지 않는다(쓰는 값은 결제 뒤 바뀌지 않는 값).
- 무료배송 기준은 배송 모듈 `ShippingFeePolicy`와 같게 "남은 단가 합 >= 기준이면 무료"다. 배송 모듈 기준이 바뀌면 같이 바꾼다.
- 주문 팀의 환불용 조회 API는 아직 없다. `sellerGroup` 모양은 주문 요청서(PR #327)를 가정했다. (미확인) 실제 API 모양
