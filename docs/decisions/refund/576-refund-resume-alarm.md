## 배경

승인 뒤 단계가 실패하면 환불이 처리 중에 멈추고 다시 진행할 길이 없었다(다시 승인하면 409). #616이 환불 번호 입구(`resume`)를 만들었고, 이 이슈는 그 입구를 정해진 시간마다 부르는 알람과 다시 시도 규칙을 정한다. #545(정석 지휘자)의 하위 이슈다.

범위 밖: 결과 대기 시간 초과와 멈춘 환불 찾기·알림(#577), 되돌리기(#546), 관리자가 손으로 다시 실행하는 API.

이 문서가 대체하는 부분: ADR 616 결정 "다음 줄 준비"의 "시도 중 → 보내지 않음"과, "건드릴 때 주의"의 "시도 중·결과 대기 줄은 어떤 경로로도 다시 보내지 않는다" 중 시도 중 부분(둘 다 만료되면 다시 집음). 예전 문서는 고치지 않는다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 서버 여러 대일 때 잠금 | ShedLock으로 알람을 한 번에 한 서버만 돌린다. 잠금 표는 환불 DB `shedlock` | 서버가 늘어날 전제다. 알람이 집는 것은 실패해서 멈춘 환불뿐이라 한 서버로 충분하다. 돈이 두 번 나가지 않게 막는 것은 환불 행 잠금과 잠근 뒤 상태 확인이라 ShedLock은 헛일만 줄인다 (사용자 결정) |
| 잠금 실행기 | 빈으로 두지 않고 알람 안에서 만든다 | 정산이 `LockingTaskExecutor`를 타입으로 주입받아, 같은 타입 빈이 둘이면 한 앱(monolith)이 뜨지 않는다 |
| 시도 중 만료 | 2분 | 지갑 발행 최대 대기(주소 찾기 60초 + 저장 확인 10초, (미확인) 설정으로 계산한 약 70초)보다 길어야 아직 보내는 중인 줄을 다른 서버가 다시 보내지 않는다 (사용자 결정) |
| 만료 다시 집기 | 잠근 구간의 `prepareStep`에서 한다. 세 입구(승인·지갑 완료·resume) 모두 같다 | 어느 입구로 와도 같은 줄에 같은 판단을 한다. 다시 집을 때는 정상 겹침(INFO)과 구분해 WARN (사용자 결정) |
| 시도 횟수 | 5번. 실패 뒤 또는 만료가 반복될 때 다 쓰면 멈춤 | 다시 시도 간격(1분)과 알람 쉬는 시간(1분)이 겹쳐 약 4~8분 동안 다시 시도한다. 값은 상수 + `TODO(#577)`(#576이 닫혀 시간 값을 함께 정하는 #577로 옮김) (사용자 결정) |
| 다시 안 할 실패 | 상품 404·409·422만 `PRODUCT_RELEASE_REFUSED`로 바꿔 바로 멈춘다. 그 밖의 4xx·5xx·응답 없음은 다시 시도 | 409는 상품 API 문서가 "재시도해도 결과가 같음"으로 적었다. 404(배정 기록 없음)·422(요청 값 오류)는 문서에 없지만 다시 보내도 바뀌지 않는다고 판단했다. 422는 우리가 보낸 값이 틀린 것(우리 버그)이라 표준 예외로 나눌 수도 있지만, 되돌리기 범위와 함께 #546에서 다시 정한다. 이슈에 적힌 `ALLOCATION_IN_PROGRESS`는 상품 코드에 없다. 401·403(설정 실수)·429까지 멈추면 설정 하나로 돈을 돌려준 환불이 모두 멈춘다 (사용자 결정) |
| 0원 승인 중 상품 거절 응답 | 409 `PRODUCT_RELEASE_REFUSED`("관리자에게 문의") | 503 "잠시 후 다시"는 다시 눌러도 소용없는 이 경우에 틀린 안내다. 409는 `INVALID_REFUND_STATE`와 겹치지만 `type`으로 구분된다 (사용자 결정) |
| Kafka 오류 처리기와 알람 | 지갑 완료 뒤 재고 실패는 기록하고 예외를 삼킨다. Kafka 다시 시도(5번)는 그대로 둔다 | 던지면 31초에 5번 다시 시도하며 시도 횟수를 다 써 알람 전에 멈추고, 같은 파티션 뒤 메시지도 기다린다. Kafka 횟수를 줄이면 DB 순간 장애에 지갑 답을 잃는데 되살릴 길(#577·팀 DLT)이 아직 없다 (사용자 결정) |
| 다시 진행할 수 없는 환불 | 알람은 처리 중인 환불만 고른다. resume이 멈춤으로 판단한 처리 중 환불은 남은 할 차례·만료된 시도 중 줄을 멈춤(`BLOCKED_BY_STOPPED_STEP`)으로 바꾼다 | 그대로 두면 줄 시각이 바뀌지 않아 매 회차 맨 앞에 다시 뽑히고, 50건 쌓이면 다른 환불이 다시 시도되지 않는다(재검수에서 실행으로 확인). 처리 중이 아닌 환불은 줄에 쓰지 않으므로(#616 결정 15) 조회에서 뺀다 (사용자 결정) |
| 알람 잠금 위치 | ShedLock은 입구(`adapter/in/scheduler`)에서 잡고, 모듈 규칙 "입력 어댑터는 DB를 안 본다"에 이 표만 예외로 적는다 | 잠금은 "언제 돌릴지"의 문제라 입구 몫이다. 환불·단계 표는 입력 포트를 거친다 (사용자 결정) |
| 회차 시간 한도 | 30초가 지나면 새 환불을 집지 않고 다음 회차로 넘긴다 | 한 앱의 스케줄 작업은 스레드 1개를 함께 쓴다((미확인) 설정이 없어 Spring Boot 기본값). Kafka가 죽으면 한 회차가 약 58분(70초 × 50건)이 되어 다른 모듈 작업이 멈춘다. 한도로 최대 약 100초로 줄인다. 스레드를 나누는 일은 공통 설정이라 팀 회의 안건으로 둔다 (사용자 결정) |
| 알람 실행 | 1분 간격, 50건씩, 환불마다 예외를 잡음(다른 모듈 실패 WARN, 그 밖 ERROR). 테스트 프로필에서는 끔 | 하나가 실패해도 회차가 멈추지 않는다. 통합 테스트 중 알람이 줄을 집으면 결과가 흔들려 테스트는 유스케이스를 직접 부른다 |

## 버린 대안

- **잠금 없이 행 잠금에만 맡기기:** 서버가 한 대면 충분하지만 여러 대면 같은 목록을 함께 훑으며 같은 환불 행을 두고 서로 기다린다.
- **줄 단위 나눠 갖기(`SKIP LOCKED`):** 처리량이 늘지만 알람이 집는 양이 적어 얻는 것이 없고 직접 SQL로 복잡해진다.
- **만료 1분:** 서버가 죽었을 때 1분 빨리 다시 집지만, Kafka가 느릴 때마다 같은 반환 요청이 두 번 가서 지갑 중복 방지 약속에만 기대게 된다.
- **Kafka 다시 시도에 재고 실패도 맡기기:** 1초 만에 복구되지만 위 이유로 횟수를 다 쓴다. 감수하는 것은 잠깐 실패의 복구가 약 1분으로 늦어지는 것.
- **지갑 완료 입구는 만료 줄도 넘기기:** 알람만 다시 집게 하면 입구마다 규칙이 달라진다. 차이는 최대 1분.

## 건드릴 때 주의

- 같은 단계를 두 번 부르지 않는 근거는 `prepareStep`이 환불 행을 잠근 구간 안에서 `begin`·`restartExpired`를 판단하는 것이다. 이 판단을 잠금 밖으로 옮기면 ShedLock이 있어도 깨진다(잠금이 5분을 넘기면 회차가 겹친다).
- `ClockProvider.setClock`은 정산이 이미 부른다(JVM 전역). 환불에서 다시 부르지 않는다.
- 결과 대기 줄은 알람이 집지 않는다(조회 조건이 할 차례·시도 중). 시간 초과는 #577.
- 재고 거절로 멈춘 환불은 돈을 이미 돌려준 채 처리 중으로 남는다. 되돌리기(#546) 전까지 WARN 로그로만 드러난다.

## 후속 (2026-11-16)

- 상품 422는 #546에서 거절(`PRODUCT_RELEASE_REFUSED`)과 나눴다. 우리가 보낸 값의 오류라 표준 예외(`IllegalStateException`)로 던지고 다시 시도한 뒤 멈춘다. 거절과 섞으면 돈 다시 가져오기가 우리 버그 때문에 구매자 돈을 회수하게 된다. 바로 멈추려면 422 전용 이유 값이 필요해 두지 않았다(상품은 422에 아무것도 바꾸지 않고, 사람 알림은 1시간 찾기가 맡음).

## 후속 (2026-11-17)

- 상품 404도 거절(`PRODUCT_RELEASE_REFUSED`)과 나눴다(#546). `PRODUCT_STOCK_NOT_FOUND`로 받아 다시 시도하지 않고 바로 멈추는 것은 같지만, 돈 다시 가져오기는 하지 않는다. 404는 상품 문서에 뜻이 없고 주소 설정 오류·게이트웨이 404와 가를 수 없어 돈을 움직이는 근거로 쓰지 않는다(봇 리뷰, 사용자 결정). 위 결정 표의 "404·409·422 → `PRODUCT_RELEASE_REFUSED`"는 이제 409만 그렇다.

## 후속 (2026-11-18)

- 결정 표 "시도 중 만료"의 "(미확인) 설정"을 #578에서 확인했다. 주소 찾기 60초는 Kafka 기본값(`max.block.ms`)이다. 공통 producer 설정(`common-kafka.yaml`)과 다른 yaml 어디에도 이 값이 없다. 그래서 최대 대기 약 70초와 만료 2분은 그대로 둔다.
