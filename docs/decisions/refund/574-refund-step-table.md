> 이 문서는 #574 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

#545(다시 시도·멈춘 환불 찾기)를 환불이 지휘하는 정석 사가 지휘자 방식으로 바꾸기로 하고 하위 이슈로 나눴다(사용자 결정, 이유: "정석이 더 안전하다"). #574는 그 첫 단계로, 진행 상태를 저장하고 보내기 전에 먼저 기록해 명령을 잃지 않게 한다.
이전에는 진행 상태가 환불 행의 상태와 `failed_step`·`failure_code`뿐이라, 지갑 발행이 실패하면 주문만 취소된 채 무엇을 다시 보낼지 기록이 없었다.
범위 밖: 다음 단계를 지휘자 한 곳에서 정하기(#575), 지휘 작업·다시 시도(#576), 시간 초과·멈춘 환불 찾기(#577), 되돌리기(#546·#572). 승인 API 응답은 바꾸지 않는다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 표 모양 | 차례가 올 때 단계 줄을 하나씩 만든다. 단계는 ORDER·WALLET·PRODUCT, (환불, 단계) 유일 | 다음 단계를 정하는 것은 지휘자 일이라 줄을 만드는 것도 그때가 자연스럽다. 0원·주문 거절에 "건너뜀" 상태가 필요 없다 (사용자 결정) |
| 상태 | 할 차례·시도 중·결과 대기·성공·거절됨·멈춤. 끝 상태(성공·거절됨·멈춤)는 이유까지 다시 바뀌지 않는다. 규칙은 도메인(`RefundStep`) | 지갑 결과는 리스너 스레드에서 와 승인 스레드의 "결과 대기" 기록보다 먼저 올 수 있다. 뒤로 가지 않아야 성공이 덮이지 않는다 (사용자 결정) |
| 멈춘 줄의 이유 | 다른 이유의 실패가 와도 처음 이유를 둔다. 뒤 이유는 WARN 로그 | 결과 불일치(`RESULT_MISMATCH`)가 뒤에 온 보통 실패로 덮이면 되돌리기(#546)가 돈이 나갔는지 모르는 환불의 주문을 되돌릴 수 있다. #544의 "마지막 실패로 덮어쓴다"는 결정 없이 테스트로만 정해진 동작이었다 (사용자 결정) |
| 실패 기록 위치 | 환불 행의 `failed_step`·`failure_code`를 지우고 단계 줄로 옮긴다. 판단도 표 기준(재고 실패 보호 = 재고 줄이 있음, 같은 실패 = 지갑 줄 멈춤+같은 이유) | 기준이 하나라 어긋나지 않는다. 다시 시도 뒤 옛 값이 남아 찾기가 잘못 걸리는 일도 없다. API 응답에는 나가지 않던 칸이다 (사용자 결정) |
| 옛 기록 옮기기 | 실패 기록이 있는 모든 환불을 단계 줄(멈춤, 이유=옛 실패 코드)로 옮긴 뒤 칸을 지운다. 같은 줄이 있으면 건너뜀 | #574 전 환불도 재고 실패 보호가 이어져야 한다. 끝난 환불의 멈춤 줄은 이력이고, 멈춘 환불 찾기는 처리 중만 본다 |
| 잠금 | 단계 줄은 그 환불 행을 같은 트랜잭션에서 잠근 뒤에만 만들거나 고친다. 영속 어댑터가 실행 중에 검사한다 | 잠금 순서가 "환불 행 → 단계 줄" 하나라 승인 묶음 잠금과 교착이 없다 (사용자 결정) |
| 기록 시점 | 처리 중이 되면 승인 구간에서 주문 줄을 "시도 중"으로 만든다. 다음 단계 줄은 앞 단계 성공 구간에서 만들고 커밋한 뒤 보낸다. 단계 상태와 환불 상태(거절·완료)는 같은 구간에서 저장. 자동 거절은 기록하지 않음 | 보내다 실패해도 "할 차례"가 남는다(진행 표가 아웃박스 역할). 시도 중으로 바로 만들어 부르기 직전 구간을 하나 줄인다 (사용자 결정) |
| 다시 볼 시각 | 칸 하나(`next_check_at`)가 상태마다 뜻이 다르다: 할 차례=다시 시도 시각, 시도 중=시도 만료, 결과 대기=시간 초과. 값은 1분·1분·30분 임시 | 지휘 작업이 "다시 볼 시각이 지난 줄" 한 조건으로 찾는다. 마이그레이션을 한 번에 끝낸다 (사용자 결정) |
| 코드 위치 | 상태 규칙은 domain, 저장은 새 포트 `RefundStepPersistencePort`(기존 영속 어댑터가 함께 구현), 실패는 `RefundStepRunner`가 단계 줄에 기록. 두 서비스가 각자 부른다 | 서비스 패키지 규칙(`@Service`와 `RefundStepRunner`만)을 지금 바꾸지 않는다. 지휘자 자리와 규칙 변경은 #575에서 정한다 (사용자 결정) |
| 지갑 발행 뒤 기록 실패 | "결과 대기" 기록이 실패해도 WARN만 남기고 처리 중으로 응답한다 | 지갑에는 이미 요청이 갔다. 줄은 "시도 중"으로 남고 지갑 결과로 바로 성공·멈춤이 될 수 있다. 응답이 #574 전과 같다 |

## 버린 대안

- **표 모양:** 승인 때 세 줄을 한꺼번에 만드는 방법은 "건너뜀" 상태와 처리 코드가 늘어 버렸다. 감수하는 것은 표만으로는 앞으로 남은 단계를 알 수 없다는 점.
- **실패 기록:** 환불 행과 표 두 곳에 쓰는 방법은 두 기준이 어긋날 수 있어 버렸다.
- **잠금:** 단계 줄만 잠그는 방법은 길마다 잠금 순서가 달라 교착이 날 수 있어 버렸다. 감수하는 것은 한 환불의 일이 한 번에 하나씩만 된다는 점.
- **공용 기록 클래스:** 서비스 패키지에 두 서비스가 함께 쓰는 기록 클래스를 두는 방법은 #575의 지휘자와 겹쳐 두 번 손댈 수 있어 지금은 쓰지 않았다. 감수하는 것은 #575 전까지 두 서비스에 비슷한 흐름 코드가 있다는 점.

## 건드릴 때 주의

- 끝 상태는 도메인이 막는다. 멈춘 줄을 다시 진행하려면(관리자 다시 실행) 별도 길을 열어야 한다(#576에서 정함).
- 단계 줄 저장 전에 같은 트랜잭션에서 그 환불의 `findByIdForUpdate`를 먼저 불러야 한다. 다른 환불을 잠근 것으로는 통과하지 않는다.
- "재고 줄이 있음"은 "지갑 완료가 이미 반영됐거나, 지갑을 거치지 않는 0원 환불"이라는 뜻이다. 두 경우 모두 지갑 결과는 기록하지 않는다. 재고 줄을 이 두 곳 밖에서 만들면 지갑 실패 보호가 깨진다.
- `V202611141632`는 칸을 지우는 마이그레이션이라 배포 뒤 코드만 이전 버전으로 되돌릴 수 없다.
- ADR 412·544의 `failed_step`·`failure_code` 설명은 이 문서로 대체된 사실이다.
- `refund/CLAUDE.md` 5절이 이 결정의 규칙 문구다.
