## 배경

지갑 반환 요청은 Kafka로 보내고 결과도 메시지로 받는다(#544). 결과 메시지가 늦거나 버려지면 지갑 줄은 결과 대기로 남고, 다시 진행 알람(#576)은 결과 대기 줄을 집지 않아 아무도 몰랐다. 멈춘 줄도 멈추는 순간 WARN만 남아 사람이 찾아볼 방법이 없었다.
범위: 결과 대기 시간 초과 다시 요청, 사람이 봐야 하는 환불 찾기. 범위 밖: 되돌리기를 시작한 환불에는 다시 요청하지 않기(#546), 외부 알림(슬랙 등), 다시 시도 값의 설정 파일 이전(`TODO(#577)`로 남김).

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 결과 기다리는 시간 | 30분 → 5분 | 정상 답이 늦게 오는 최대 시간(발행 약 70초 + 환불 받기 다시 시도 약 31초 + 지갑 받기 다시 시도 약 7초 + 지갑 결과 보내기 최대 약 40초, 약 148초)보다 길면 된다 (사용자 결정 11/15) |
| 시간이 지나면 | 같은 refundId로 다시 보냄(결과 대기 → 시도 중). 시도 횟수에 넣지 않고 멈추지 않음 | 멈추면 끝 상태라 뒤늦은 진짜 지갑 답(잔액 부족 등)을 기록하지 못해 되돌리기(#546)가 "지갑이 거절함"과 "돈이 나갔는지 모름"을 못 가른다. 지갑이 같은 refundId를 한 번만 처리한다 (사용자 결정 11/15) |

## 버린 대안

- **시간 초과 처리:** 시간이 지나면 멈춤으로 바꾸기는 위 기록 문제 때문에 버렸다. 감수하는 것은 지갑이 영영 답하지 않으면 5분마다 계속 보낸다는 점이고, 30분 찾기가 사람에게 알린다.
- **30분 기준:** `created_at`만으로 재기는 첫 발행 실패로 보낸 몇 분이 섞여 버렸다. 감수하는 것은 칸 하나와 마이그레이션이다.
- **찾기 로그 ERROR:** 멘토·정산 방식과 맞지만 팀 규칙을 앞질러 가므로 #649에서 팀이 정하기로 했다.
- **다시 시도 간격 늘리기(멘토 2차 리뷰 제안 6번):** 이 작업 범위 밖이라 #649 R2에서 정한다.

## 건드릴 때 주의

- `awaiting_since`는 `awaitResult`가 처음 결과 대기가 될 때만 채운다. 이 값으로 "이미 보낸 줄"을 가르므로, 다른 곳에서 채우거나 지우면 다시 보내기 중 실패가 다시 멈추게 된다. 테스트 도우미에서 `restore`로 줄을 바꿀 때도 이 값을 넘겨야 한다.
- 결과 대기 5분과 시도 중 만료 2분은 Kafka 발행 대기(`max.block.ms` 기본 60초)를 전제로 계산했다. 팀이 `common-kafka.yaml`에 producer 상한을 두면(#649 C3) 다시 계산한다.
- "다음 줄 없음" 규칙은 `RefundSagaPlan.fromSteps`와 `RefundStepJpaRepository.findRefundIdsNeedingAttention` 두 곳에 있다. 한쪽을 고치면 대조 테스트(`RefundStepPersistenceAdapterIntegrationTest`)가 깨지는지 본다.
- 잠금 이름 `refundAttention`은 코드 상수와 마이그레이션 두 곳에 있다. 이름을 바꾸면 새 마이그레이션도 필요하다.
