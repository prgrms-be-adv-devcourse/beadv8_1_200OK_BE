## 배경

승인 뒤 단계가 끝내 실패하면(지갑이 반환에 실패, 또는 재고가 다시 해도 거절돼 회수가 성공) 주문에는 취소가 기록된 채 남는다. #546까지는 이 환불이 처리 중으로 남아 사람이 봤다. 이 작업은 PR #537 약속대로 주문에 취소 기록(수량·뺀 배송비)을 되돌려 달라고 하고, 되돌리면 환불을 실패로 끝낸다.
범위 밖: 주문 쪽 수신·결과 발행(#604), 상품이 "이미 통째로 풀림"을 다른 코드로 답하기(#709), 같은 묶음 다른 환불의 배송비 판단(#707), 지갑 완료 결과 불일치의 반환 취소(#572).

## 버린 대안

- **0원도 주문 되돌리기:** 처음 추천했으나 검토(에이전트 3명)에서 409가 "이미 풀림"일 수 있다는 점이 나와 버렸다. 감수하는 것은 0원 + 재고 409 환불이 처리 중으로 남아 관리자가 정리해야 한다는 점이다.
- **재고 409면 회수도 되돌리기도 하지 않음:** 409에 "이 환불 몫이 안 풀림"도 섞여 있어(코드 확인) 모두 멈추면 그 경우를 바로잡지 못한다. 약속과 멘토 의견(합의 유지 + 이미 풀림만 따로)과도 달라 버렸다.
- **실패 사유 새 칸 / 문구 둘:** 새 칸은 마이그레이션·엔티티·응답이 모두 바뀐다. 문구를 지갑 실패·재고 실패로 나누면 회수 줄을 보는 분기가 하나 는다. 감수하는 것은 돈이 들어왔다 나간 구매자도 같은 문구를 본다는 점이다.
- **찾기 쿼리에 되돌리기 결과 대기 조건 추가:** 되돌리기 중인 환불은 항상 멈춘 지갑·재고 줄이 있어 기존 조건으로 잡힌다(#546과 같은 판단). 감수하는 것은 정상 진행 중에도 목록에 뜬다는 점이다.
- ⚠️ **되돌리기를 HTTP로(멘토 #649 R4):** 멘토는 주문 되돌리기를 HTTP로 부르자고 했다. PR #537에서 주문 팀과 Kafka로 합의했고(되돌리기는 환불이 실패로 끝내기로 정한 뒤라 답을 기다려 다음을 정할 일이 없다, 약속 문서 83줄), 주문 #604가 Kafka로 받게 만들고 있어 Kafka로 했다. 감수하는 것은 결과가 비동기라 주문이 답하기 전까지 환불이 처리 중으로 남는다는 점이다.
- **"실패로 끝, 관리자 알림"(약속 문서 51·54줄):** 실패로 끝난 환불은 찾기 알람(처리 중만 봄)에 들지 않아, 지금은 WARN 로그 한 줄이 알림을 대신한다. 따로 알리는 수단(관리자 화면·알림)은 만들지 않았다.
- **발행 어댑터를 지갑 어댑터와 합침:** 보내는 코드 약 20줄이 겹치지만, 받는 모듈이 달라 이름과 맡은 일이 어긋나고 이미 테스트가 붙은 지갑 어댑터를 고쳐야 해 따로 뒀다.

## 건드릴 때 주의

- 되돌리기 시작은 지갑 실패(`recordWalletRefundFailure`)·회수 결과(`recordRevertResult`) 구간 안에 있다. 그 기록을 다른 곳으로 옮기면 되돌리기 줄이 빠진다.
- `fromSteps`에서 되돌리기 줄을 먼저 보는 순서를 바꾸면 되돌리기를 다시 보내지 못한다.
- `FAILED`는 `RefundShippingFeePolicy.CANCELLING_STATUSES`에 없다. 넣으면 되돌린 상품이 취소된 것으로 세어진다.
- 실패로 바꾸는 구간은 자기 행만 잠근다. 같은 묶음 다른 환불의 배송비 판단이 틀린 채 남을 수 있다(#707, 승인 뒤 거절과 같은 한계).
- 우리 쪽 발행이 시간 초과로 5번 이어져 회수·되돌리기 줄이 멈춘 뒤(메시지는 실제로 갔을 수 있음) 진짜 결과가 늦게 오면 끝난 줄이라 버린다(`ALREADY_FINISHED`). 환불은 처리 중으로 남아 찾기 알람에 잡힌다. 받아들이려면 회수·되돌리기 결과 정책 둘을 함께 고쳐야 해 감수했다(투표 4/4).
- `refund_step.step` 칼럼 설명은 아직 `ORDER, WALLET, PRODUCT`만 적혀 있다(동작 영향 없음).
