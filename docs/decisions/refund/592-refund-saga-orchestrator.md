> 이 문서는 #592 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

승인 뒤 다음 단계를 정하는 판단이 `DecideRefundService`(승인 뒤 주문·지갑·0원 재고)와 `HandleWalletRefundResultService`(지갑 결과 뒤 재고·완료) 두 곳에 나뉘어 있었다. #576 다시 시도, #577 시간 초과, #546 되돌리기가 붙으면 판단이 세 곳 이상으로 흩어진다. #575(정석 사가 지휘자)의 둘째 하위 이슈로, 동작을 바꾸지 않고 한 곳으로 옮기기만 한다(첫째 #591이 옮기기 전 동작을 통합 테스트로 고정).

범위 밖: 같은 상황을 경로마다 다르게 처리하던 것(단계 줄 없는 옛 환불, 다음 줄 무조건 새로 저장, 두 완료 메서드)을 맞추는 일, 판단을 domain 객체(가칭 `RefundSagaPlan`·`WalletResultPolicy`)로 빼는 일, 환불 번호로 시작하는 입구는 #616(#575 하위 셋째)으로 미뤘다.

이 문서가 대체하는 부분: ADR 574의 "코드 위치(두 서비스가 각자 `RefundStepRunner`를 부른다)", ADR 544의 "거르는 위치·재고 복구를 부르는 주체(서비스)", ADR 412의 "틀 위치(별도 클래스 `RefundStepRunner`)". 예전 문서는 고치지 않는다.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 지휘자 모양 | 입력 포트 `RefundSagaUseCase` + 구현 `RefundSagaService`. 입구는 승인 뒤 시작·지갑 완료·지갑 실패 셋 | 정석 지휘자 조건(순서는 한 곳, 답장은 지휘자가 직접 받음, 상태 저장 후 이어 감, 참가자는 지휘자만 부름)을 갖춘다. 승인 서비스와 Kafka 수신기가 같은 문으로 들어오고, #576 알람도 같은 문을 쓴다 (사용자 결정, #575 결정 1) |
| 481과의 관계 | 3절 "유스케이스 하나 = 서비스 하나"에 예외를 둔다. 승인 서비스는 승인 구간을 커밋한 뒤 지휘자를 시작만 한다 | 481이 막은 것은 트랜잭션 경계 때문에 한 요청의 흐름을 Facade·Service로 쪼개는 것이다. 승인 뒤 단계는 한 요청에서 끝나지 않는다(승인 → 몇 분 뒤 지갑 답 → 다시 시도). 여러 요청에 걸친 단계를 한 곳에 모으는 것이라 방향이 반대다 |
| 사가 단위 | 환불 하나. 진행표(refund_step)가 기억이고 지휘자는 기억이 없다 | 진행표가 환불 하나에 단계마다 한 줄이라(574) 그대로 사가 상태가 된다 |
| 지갑 결과 서비스 | `HandleWalletRefundResultUseCase/Service`를 지우고 지휘자에 합침. 수신기는 지휘자 포트를 부름 | 답장을 지휘자가 직접 받아야 다음 단계 판단이 두 곳으로 갈라지지 않는다. 토픽·메시지 모양은 그대로라 지갑 팀 영향 없음 |
| 실패 기록 틀 | `RefundStepRunner`를 지휘자 안 `runStep`·`recordFailure`로 합침 | 단계 실행·성공 기록·실패 기록을 지휘자 한 곳이 맡아 진행표에 쓰는 코드가 둘로 나뉘지 않는다 (사용자 결정, 진행자 추천은 "그대로 두기"였음) |
| 트랜잭션 밖 검사 | Runner의 검사만 지휘자 입구 세 곳으로 옮김. 승인 서비스의 `requireNoOuterTransaction`은 그대로 | 승인 서비스 검사는 승인 구간(READ COMMITTED 묶음 잠금)이 새 트랜잭션으로 시작하는지를 지킨다. 빼면 `RefundConcurrencyIntegrationTest` 2건이 실패하는 것을 실행으로 확인했다 |
| 시작 입력 | 승인 구간 결과 `RefundResult`를 그대로 받음 | 그대로 옮기기라 #591 테스트로 같은 동작임을 보이기 쉽다. 환불 번호 입구는 #616에서 길을 합칠 때 만든다 (사용자 결정, #575 결정 9) |
| 판단 객체 | 이번에 만들지 않음. 판단은 지휘자 안 if 문 그대로 | 지금 승인 경로는 진행표가 아니라 방금 받은 금액으로 다음 단계를 정한다. 동작을 그대로 두고 빼면 입력이 "입구+방금 값"이 되어 #576에서 다시 고치게 된다(추정). 처리를 맞춘 뒤 한 번에 만든다 (사용자 결정, #575 결정 8) |
| 구조 규칙 | `ArchitectureTest`: 서비스 패키지는 `@Service`만, 서비스가 부르는 다른 `*UseCase`는 `RefundSagaUseCase`뿐(자기 구현 제외) | 서비스가 다른 입력 포트로 흐름을 나누는 길을 지휘자 하나로만 연다. 두 규칙 모두 일부러 넣은 위반으로 실패하는 것을 실행으로 확인했다 |
| 승인 단위 테스트 | 지휘자를 Mockito로 대체하지 않고 같은 가짜 포트로 만든 진짜 지휘자를 넣음 | 옮기기 전 기대값 그대로 승인 → 주문 → 지갑·재고를 한 흐름으로 확인해 동작이 같다는 근거로 쓴다 (사용자 결정, 모듈 규칙 7절) |

## 버린 대안

- **Runner:** 별도 클래스로 두는 방법은 진행표에 쓰는 코드가 지휘자와 Runner 두 곳으로 나뉘어 버렸다. 감수하는 것은 지휘자 클래스가 커진 것(약 660줄).
- **판단 객체를 지금 만들기:** 결정 5대로 #592에서 만드는 방법은 경로마다 다른 처리를 남긴 채 판단을 굳히게 돼 버렸다. 감수하는 것은 #616까지 판단이 if 문으로 남는 것.
- **시작 입력을 환불 번호로:** 알람(#576)과 입구를 처음부터 하나로 할 수 있지만, 승인할 때마다 DB를 한 번 더 읽고 승인 시점 값 대신 다시 읽은 값으로 진행해 "그대로 옮기기"가 아니게 돼 버렸다. 감수하는 것은 #616 전까지 길이 둘인 것.
- **출고 거절 사유 상수를 domain으로:** 이번엔 옮기기만 해서 승인 서비스와 지휘자에 같은 상수를 두고 같은지 테스트로 지킨다.

## 건드릴 때 주의

- 지휘자 입구 셋은 트랜잭션 밖에서만 부른다(입구가 실행 중에 검사). `runStep`은 검사하지 않으므로 지휘자 안에서 `runStep`을 트랜잭션 구간 안에 넣지 않는다. 넣으면 실패 기록이 바깥과 함께 롤백된다.
- `runStep`·`recordFailure`는 테스트 때문에 패키지 안에서 열려 있다. 다른 서비스가 부르면 구조 규칙(서비스가 다른 서비스를 쓰지 않음)에 걸린다.
- 완료 메서드가 둘이다: 0원 승인 요청 안(`completeInApprovalRequest`, 처리 중이 아니면 도메인 예외)과 지갑 완료 뒤(`completeAfterWalletStock`, 넘김). 옮기기 전 동작 그대로이며 #616에서 맞춘다.
- `SHIPPED_REJECT_REASON`이 승인 서비스와 지휘자 두 곳에 있다. 한쪽만 바꾸면 테스트가 잡는다.
- 다음 단계 줄은 아직 무조건 새로 저장한다(`recordOrderSucceeded`). #576이 같은 단계를 다시 진행하기 전에 #616에서 고쳐야 유일 제약 위반이 나지 않는다.
