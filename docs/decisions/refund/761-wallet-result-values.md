> 이 문서는 #761 작업의 결정과 이유를 남긴 기록이다. 무엇이 바뀌었는지는 PR이 정확하고, 코드가 바뀌었으면 코드가 우선이다.

## 배경

지갑이 보낸 반환 결과의 주문·구매자·금액이 환불과 다르면 #544부터 지갑 줄을 `RESULT_MISMATCH`로 멈추고 환불은 처리 중으로 둔다. 하지만 DB에는 이유 글자만 남고, 지갑이 보낸 값과 실패 이유는 로그에만 있었다. 이미 멈춘 줄이나 넘기는 경우에는 로그에도 값이 없었다.
처음 #572는 이런 결과를 지갑에서 자동으로 다시 가져오려 했다. 이 문서는 그 범위를 "값을 남기고 사람이 맞춘다"로 바꾼 결정이다.
범위 밖: 자동 회수, 관리자 화면·API, 회수·주문 되돌리기 결과가 어긋난 경우의 값 저장.

## 결정과 이유

| 결정 | 선택 | 이유 |
|---|---|---|
| 되돌리는 방법 | 자동 회수 없이 값만 남김, 관리자가 지갑과 맞춤 | 정상 흐름에서는 생기지 않는다(같은 환불 번호에 지갑이 처음 결과를 다시 보냄, PR #537 합의). 지갑 버그나 환불 DB 초기화 때만 생긴다. 자동 회수는 지갑 #611이 있어야 돌고, 시험 구현이 17개 파일·+742줄로 드문 경우 하나에 비해 컸다 (사용자 결정) |
| 남기는 곳 | 로그만이 아니라 DB(`refund_step`의 `wallet_*` 칸 5개) | 로그는 보관 설정이 없어 사라질 수 있고 찾기 어렵다. 관리자는 SQL 한 번으로 환불 값과 나란히 본다 (사용자 결정) |
| 남기는 값 | 결과 종류(완료·실패)·주문·구매자·금액·실패 이유 | 실패 메시지면 이유 칸이 `RESULT_MISMATCH`라 지갑의 이유가 사라진다. 결과 종류로 돈이 나갔는지(완료) 아닌지(실패)를 가른다. #616이 미뤘던 "불일치가 완료에서 왔나 실패에서 왔나"도 이 칸이 대신한다 (사용자 결정) |
| 남기는 때 | 결과 불일치로 지갑 줄을 처음 멈출 때만. 이미 끝난 줄은 이유도 값도 그대로 | 처음 기록을 덮지 않으려는 것이다(`RefundStep.stop`과 같은 규칙). 멈추기와 값 남기기를 `stopForMismatch` 하나로 묶어 값만 덮는 길을 없앴다 |
| DB에 안 남는 경우 | 넘기는 모든 로그에 지갑 값. 이미 완료됐거나 회수 뒤 실패로 끝난 환불에 값이 다른 완료가 오면 WARN | 그 경우 로그가 유일한 흔적이다. 값이 다른 완료는 정상 중복이 아니라 돈이 한 번 더 나갔을 수 있다 (사용자 결정, 검토 반영) |
| 지갑 실패 경로의 어긋난 완료 | 주문 되돌리기 줄을 `WALLET_COMPLETED_LATE`로 멈춤(맞는 값의 늦은 완료와 같은 이유) | 멈추지 않으면 주문이 되돌린 뒤 실패로 끝나 찾기 알람에서 빠지고 DB에 흔적이 없다. 새 이유 값은 그 값을 보고 판단하는 곳을 늘려 두지 않았다 (사용자 결정) |
| 값 검사 | 앱(`WalletReport`)과 DB CHECK 4개가 같은 규칙: 네 칸 함께, 결과는 `COMPLETED`·`FAILED`만, 실패면 이유 있음·완료면 없음, 금액 > 0 | 손으로 넣은 이상한 행을 앱이 읽으면 예외가 나 그 환불의 지갑 메시지가 다시 시도 없이 버려진다. CHECK 이름이 64자 한도를 넘지 않게 둘로 나눴다 |

## 버린 대안

- **자동 회수(#572 시험 구현, 원격 `feature/572`):** 위 이유. 감수하는 것은 잘못 나간 돈을 사람이 맞춰야 한다는 점.
- **로그만 보강:** 마이그레이션 없이 작지만, 로그가 사라지면 값도 사라진다.
- **완료만 저장:** "값 있음 = 돈 나감"으로 단순하지만 어긋난 실패에서 지갑이 보낸 값을 잃는다.
- **이미 멈춘 줄에도 첫 지갑 값은 채우기:** 우리 쪽 사정(발행 소진·만료·막힘)으로 먼저 멈춘 줄에 온 지갑의 첫 답을 살리지만, "끝난 줄은 바뀌지 않는다" 규칙에 예외가 생긴다.

## 건드릴 때 주의

- `RefundStepJpaEntity.changeMutableState`에서 `wallet_*` 칸을 빼면 다른 칸을 고친 update가 값을 NULL로 지운다. CHECK는 다섯 칸이 함께 비는 것을 막지 않아 조용히 사라진다(영속 통합 테스트가 지킴).
- `WalletReport.Result`의 enum 이름이 그대로 DB 값이다. 바꾸면 저장된 행을 읽지 못하고, CHECK도 함께 바꿔야 한다.
- `wallet_*`가 NULL이어도 불일치였을 수 있다(이미 멈춘 줄에 뒤늦게 온 결과, 이 작업 전 기록). 그때는 로그를 본다.
- 지갑 실패 경로에서 멈춘 되돌리기 줄의 이유는 맞는 값의 늦은 완료와 같아 DB만으로는 둘을 가를 수 없다. 다른 값이었는지는 WARN 로그로 본다.
- 관리자 확인 SQL은 이슈 #761 본문에 있다. 환불에는 돌려줄 금액 칸이 없어 계산식으로 구한다.
