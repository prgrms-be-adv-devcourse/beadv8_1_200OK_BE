# Claude 작업 스킬 사용법

반복되는 작업은 `.claude/skills/`의 프로젝트 스킬로 정리해 두었다. Claude에게 해당 작업을 시키면 스킬의 절차를 따라 진행한다. 이 문서는 팀원이 스킬을 **언제, 어떻게 부르는지**를 설명한다.

이 문서는 레포에 포함된 스킬만 다룬다. 각자 설치한 개인 플러그인이나 전역 스킬은 팀 공통이 아니므로 여기에 적지 않는다. 컨벤션 원문은 [CONVENTION.md](CONVENTION.md)이고, 스킬은 그 규칙을 작업 절차로 옮긴 것이다. 규칙이 바뀌면 원문을 먼저 고치고 스킬에 반영한다.

## 스킬 한눈에 보기

| 스킬 | 언제 쓰나 | 부르는 법 | 원문 |
|---|---|---|---|
| [`commit`](#commit) | 변경사항을 커밋할 때 | `/commit` 또는 "커밋해 줘" | CONVENTION 11절 |
| [`pr`](#pr) | PR 제목·본문 초안이 필요할 때 | `/pr` 또는 "PR 초안 써 줘" | CONVENTION 11.2, 11.3 |
| [`migration`](#migration) | 테이블·컬럼·인덱스를 바꿀 때 | `/migration` 또는 "마이그레이션 만들어 줘" | CONVENTION 8절 |
| [`error-code`](#error-code) | 도메인 오류 응답을 새로 정의할 때 | `/error-code` 또는 "에러 코드 추가해 줘" | CONVENTION 6절 |
| [`stacked-pr`](#stacked-pr) | 서로 의존하는 PR을 스택으로 관리할 때 | `/stacked-pr` 또는 "스택 보여 줘" | CONVENTION 11절 |

## 부르는 방법

- **슬래시로 직접 부른다**: 프롬프트에 `/commit`처럼 입력한다. 뒤에 요구사항을 이어 쓸 수 있다(예: `/migration 장바구니 테이블 추가`).
- **말로 시킨다**: "마이그레이션 만들어 줘"처럼 요청하면 Claude가 해당 스킬을 골라 쓴다. 스킬이 자동으로 안 붙으면 `/스킬이름`으로 직접 부른다.
- 스킬은 이 레포를 연 Claude Code 세션에서만 보인다. 새 스킬을 받았다면 세션을 다시 연다.

## commit

변경사항을 컨벤션에 맞춰 커밋한다. **사용자가 승인하기 전에는 커밋하지 않는다.**

**진행**
1. 현재 브랜치와 변경 내용을 확인한다. `main` 또는 `dev`에서는 커밋하지 않고 알려 준다.
2. 성격이 다른 변경(문서, 기능, 테스트)은 커밋을 나눈다.
3. 메시지를 만든다. 형식은 `<Type>: <제목>`, 본문 한글, 끝에 `Ref: #이슈번호`다. 이슈 번호는 브랜치 이름(`<유형>/<이슈번호>`)에서 얻는다.
4. 커밋할 파일 목록, 제목, 본문을 보여 주고 **명시적 승인**을 받는다.
5. 승인 후 파일을 이름으로 지정해 커밋한다(`git add -A`는 쓰지 않는다).

**예시 요청**
```
/commit
```
```
방금 수정한 내용 커밋해 줘
```

**알아둘 점**
- 메시지와 PR 본문에 AI 표기(`Co-Authored-By: Claude`, `Generated with Claude Code` 등)를 넣지 않는다.
- `.env`, 비밀번호, 토큰, `.claude/settings.local.json` 같은 개인 설정은 커밋에서 제외한다.
- push와 PR 생성은 요청할 때만 한다. `--no-verify`, `--amend`, 강제 푸시는 임의로 쓰지 않는다.

## pr

현재 브랜치의 PR **초안**(제목과 본문)을 `.github/PULL_REQUEST_TEMPLATE.md` 형식으로 쓴다. PR 생성은 사용자가 명시적으로 요청할 때만 한다.

**진행**
1. 브랜치와 `dev` 대비 커밋·변경 범위를 확인하고, 브랜치 이름에서 이슈 번호를 얻는다.
2. `gh issue view`로 이슈를 읽어 작업 이유와 범위를 확인한다(읽기만 한다).
3. 전체 커밋 이력을 기준으로 제목(`<Type>: <제목>`)과 본문(개요, 작업 내용, 참고 사항, 관련 이슈, 완료 조건)을 쓴다.
4. 초안과 리뷰어 추천(변경과 연관된 도메인 담당자)을 보여 준다.
5. 생성을 요청하면 푸시 후 `dev`를 대상으로 PR을 만든다.

**예시 요청**
```
/pr
```
```
이 브랜치 PR 초안 써 줘. 만들지는 말고
```
```
PR 만들어 줘
```

**알아둘 점**
- 제목에 `(#N)`을 직접 쓰지 않는다. squash merge 때 GitHub이 붙인다.
- `gh`는 `env -u GITHUB_TOKEN gh ...` 형태로 호출한다.
- AI 봇 리뷰가 OK이면 squash merge로 병합한다.

## migration

Flyway 마이그레이션 SQL 파일을 컨벤션대로 새로 만든다. 엔티티를 추가·수정하면 대응하는 마이그레이션을 함께 추가해야 한다.

**진행**
1. 어느 모듈의 어떤 테이블·컬럼을 바꾸는지, 대응하는 엔티티가 무엇인지 확인한다(불분명하면 묻는다).
2. 이미 커밋된 마이그레이션은 고치지 않고 **항상 새 파일**을 추가한다.
3. 버전은 `date +%Y%m%d%H%M` 12자리이고, `main`과 현재 브랜치의 가장 큰 버전보다 뒤여야 한다.
4. 파일명은 `V{버전}__{모듈}__{동작_설명}.sql`(밑줄 두 개)이고 `<모듈>/src/main/resources/db/migration/<모듈>/`에 둔다.
5. 템플릿대로 SQL을 쓰고, 엔티티와 컬럼명·타입·nullable을 맞춘 뒤 통합 테스트로 검증한다.

**예시 요청**
```
/migration 장바구니 항목 테이블 추가 (cart_item)
```
```
주문 테이블에 취소 사유 컬럼 추가하는 마이그레이션 만들어 줘
```

**알아둘 점**
- 같은 모듈 안의 연관에는 외래키를 두고, 다른 모듈의 ID에는 외래키를 두지 않는다.
- 제약·인덱스 이름은 `{uk|ck|fk|idx}_{테이블}_{컬럼들}`이다.
- 상세 규칙은 `.claude/rules/migration.md`에 있다.

## error-code

모듈의 `*ErrorCode` enum에 에러 코드를 추가하고, `RestApiException`으로 던지는 코드까지 작성한다.

**진행**
1. 예외 종류를 **값의 출처**로 정한다. 사용자 입력이 닿는 값의 오류는 `RestApiException` + `*ErrorCode`, 다른 모듈·시스템이 넘긴 값의 오류는 표준 예외(`IllegalArgumentException` 등)이고 이 스킬 대상이 아니다.
2. 모듈의 `*ErrorCode`를 찾는다. 없으면 모듈의 `exception` 패키지에 만든다.
3. 같은 의미의 코드가 이미 있으면 재사용한다.
4. 항목을 추가한다. 이름은 `UPPER_SNAKE_CASE`, `title`은 영어 짧은 문장, 기본 메시지는 한국어, HTTP 상태는 400/422(입력), 404(없음), 409(충돌), 403(권한)이다.
5. 던지는 코드를 쓰고, 테스트는 메시지가 아니라 `isInstanceOfSatisfying`으로 확인한다.

**예시 요청**
```
/error-code 이미 결제된 주문이면 409로 응답하는 코드 추가
```

**알아둘 점**
- `OrderErrorCode`, `PayoutErrorCode`는 `slug()` 모듈 접두사 오버라이드가 없어 컨벤션과 다르다. 스킬은 임의로 고치지 않고 알려 준다.
- 상세 규칙은 `.claude/rules/exception.md`에 있다.

## stacked-pr

서로 의존하는 PR을 **스택**(브랜치를 부모-자식으로 쌓은 구조)으로 관리한다. 앞 작업의 리뷰를 기다리는 동안 그 위에서 이어서 작업해야 할 때 쓴다. `git`과 `gh`만 쓰며 외부 서비스나 GitHub 앱 설치가 필요 없다. 서로 독립인 작업은 스택으로 만들지 않고 각각 `dev`에서 시작한다.

```
dev ── feature/278 ── feature/279 ── feature/280
       (PR #282)      (PR #283)      (PR #284)
       base: dev      base: 278      base: 279
```

**기능**
| 기능 | 하는 일 | 변경 여부 |
|---|---|---|
| 스택 보기 | 부모-자식 트리와 PR 상태, 뒤처진 브랜치(`restack 필요`)를 보여 준다 | 읽기만 |
| 쌓기 | 현재 브랜치 위에 새 브랜치를 만들고 부모를 기록한다 | 로컬 브랜치 |
| restack | 앞 브랜치가 바뀐 뒤 뒤 브랜치를 새 부모 위로 옮긴다 | 로컬 rebase |
| 올리기 | 스택 브랜치를 push하고 **draft** PR을 만든다 | 요청할 때만 |
| sync | 앞 PR이 머지된 뒤 뒤 브랜치를 `dev` 위로 옮기고 PR base를 바꾼다 | 요청할 때만 |

**예시 요청**
```
/stacked-pr 스택 보여 줘
```
```
feature/278에 커밋 추가했어. 뒤 브랜치들 restack 해 줘
```
```
스택 PR 올려 줘
```
```
#282 머지됐어. 스택 정리해 줘
```

**꼭 지킬 것**
- **머지는 항상 맨 아래 PR부터** 한다. 위쪽 PR의 base가 `dev`로 잘못 잡힌 채 먼저 머지하면 아래 PR의 변경이 리뷰 없이 `dev`에 함께 들어간다.
- PR은 항상 draft로 만들고, ready 전환·머지는 사람이 한다.
- 이 프로젝트는 squash merge를 쓰므로 앞 PR이 머지되면 **sync로 정리**해야 한다(그냥 rebase하면 충돌한다).
- `dev`에는 직접 푸시하지 않고, 스택 브랜치에만 `--force-with-lease`로 푸시한다.
- 스택의 각 브랜치도 `<유형>/<이슈번호>` 이름과 자기 이슈 번호를 가진다.
- 스택 관계는 각자의 로컬 `.git/config`에 저장된다(커밋되지 않음). 다른 PC에서는 PR의 base 브랜치를 기준으로 스택을 파악한다.

## 스킬 추가·수정

- 새 스킬은 `.claude/skills/<이름>/SKILL.md`로 만든다. 맨 위에 `name`과 `description`(언제 쓰는지)을 쓴다.
- 스크립트가 필요하면 `.claude/skills/<이름>/scripts/`에 둔다. 스킬 본문에서는 `$(git rev-parse --show-toplevel)/.claude/skills/<이름>/...` 경로로 부르면 worktree에서도 동작한다.
- 컨벤션을 바꿀 때는 [CONVENTION.md](CONVENTION.md)를 먼저 고치고 스킬과 `.claude/rules/`에 반영한다. 두 곳이 어긋나면 원문이 기준이다.
- 스킬을 추가하면 이 문서의 표와 `CLAUDE.md`의 작업 스킬 표에도 한 줄 추가한다.
