# 정산·지갑 대사 (#308) — 지갑 담당과 이야기할 것

- 작성: 2026-11-12, 정산 담당
- 상대: 지갑 담당 (`hyunjeong222`)
- 관련: #308(이 일), #388 M5(상위), #106·#339(이벤트 약속), #309(outbox), #343(지갑 Kafka 수신 전환), #391(실패 범주), #532(지갑 내부 점검), #91
- 기준 코드: `dev` (cc5da8b1)

## 1. 한 줄 요약

정산이 매일 12시에 "이 정산들, 지갑에 입금됐나요?"를 Kafka로 묶어서 묻고, 지갑이 원장을 보고 답하면, 정산이 자기 대사 표에 결과를 고쳐 적는다. 없으면 입금 이벤트를 다시 보내고, 3번 확인해도 없거나 금액이 다르면 관리자 확인 목록으로 넘긴다. 지갑에는 **확인 요청을 받아 원장을 읽고 답하는 기능**을 요청한다.

## 2. 상황

- 정산은 판매자 몫을 확정하면 지갑에 입금 이벤트를 보낸다.
- 지갑은 그 이벤트를 받아 판매자 지갑 원장에 입금 기록을 남긴다.
- #308은 이 둘을 매일 맞춰 보는 일이다.

예시: 정산 15번이 판매자 5번 몫 9,700원으로 확정됨 → 지갑 원장에 `PAYOUT:15` +9,700원이 있어야 함.

찾을 것 세 가지:

1. 정산은 있는데 지갑 입금이 없음 → 판매자가 돈을 못 받음
2. 둘 다 있는데 금액이 다름
3. 지갑 입금은 있는데 정산이 없음 → 근거 없는 입금

## 3. 코드로 확인한 사실

| 사실 | 근거 |
|---|---|
| 지갑은 정산 입금을 **Spring 내부 이벤트**로 받는다. 지갑에는 Kafka 리스너가 없다 | `wallet/.../adapter/in/event/PayoutEventListener.java:25-39`, `docs/decisions/payout/309-payout-outbox.md:15` |
| 원장 참조 키는 `"PAYOUT:" + payoutId`이고 표 전체에서 유일하다. 같은 정산이 두 번 입금되는 것은 DB가 막는다 | `SellerWalletService.java:20,64`, `V202610151012__wallet__create_seller_wallet_ledger_table.sql:11` |
| 같은 정산 이벤트가 다시 오면 지갑은 이미 있는 키를 보고 입금하지 않고 넘어간다 | `SellerWalletService.java:69-71` |

| 원장에는 판매자 회원 ID가 없고 `seller_wallet_id`만 있다. 회원 ID는 `seller_wallet.member_id`에 있다 | 원장 마이그레이션 :1-14, `V202610131100__wallet__create_seller_wallet_table.sql:3,7` |

| 지갑이 입금을 건너뛰면(`payoutId`·`payeeId`·`amount`가 비었거나 `amount <= 0`) `[PAYOUT_DEPOSIT_SKIPPED]` ERROR 로그만 남는다. DB에는 흔적이 없다 | `PayoutEventListener.java:29-36, 43-54` |
| 지갑 처리가 실패하면 다시 처리되는 건 앱 재시작 때뿐이다(운영 설정) | `monolith/src/main/resources/application-prod.yml:22` |
| 원장 `created_at`은 지갑이 이벤트를 처리한 시각이다. 이벤트 안의 정산 확정 시각(`createdAt`)은 지갑이 쓰지 않는다 | `BaseTime.java:26-28`, `PayoutEventListener.java:38` |

| 정산 outbox의 "보냄(SENT)"은 Kafka 브로커가 받았다는 뜻일 뿐이다. 지갑 입금과는 관계가 없다 | `PayoutOutboxService.java:26-29`, 위 첫 줄 |
| 정산 Job은 매일 02:00에 돈다 | `PayoutJobScheduler.java:19` |

이미 합의된 것은 이벤트 약속뿐이다(필드 `payoutId, payeeId, amount, createdAt`, `payoutId`로 중복 방지, 0원 이하는 보내지 않음, Kafka 토픽·키, #106·#339). 대사는 아직 합의된 것이 없다.

## 4. 정산이 제안하는 방식: Kafka로 묶어서 묻고 답하기

정산은 지갑 표를 직접 조회할 수 없다(모듈 경계, 서버 분리 대비).

### 4-1. 흐름

정산 쪽에 **대사 표**를 새로 둔다. 확인할 정산마다 한 행이고, 상태와 시도 횟수를 고쳐 가며 쓴다. 지갑은 답만 하고, 표를 고치고 판정하는 건 정산이다.

예시: 정산 15번(판매자 5번, 9,700원)

| 때 | 일어나는 일 | 대사 표의 15번 행 |
|---|---|---|
| 1일차 02:00 | 정산 15번 확정, 지갑에 입금 이벤트 보냄 | 새 행: 확인 대기, 시도 0번 |
| 1일차 12:00 | 1번째 확인 → 지갑이 "없음" → 정산이 입금 이벤트를 다시 보냄 | 시도 1번, 확인 대기 |
| 2일차 12:00 | 2번째 확인 → 지갑이 "있음, 판매자 5번, 9,700원" | 일치, 끝(다시 묻지 않음) |

다른 경우:

| 경우 | 처리 |
|---|---|
| 3번 확인해도 "없음" | 관리자 확인 목록: "정산은 됐는데 지갑 입금 없음" |
| "있음"인데 금액이나 판매자가 다름 | 바로 관리자 확인 목록(기다려도 저절로 맞춰지지 않음) |
| 지갑이 답하지 않음 | 시도 횟수에 넣고 다음 날 다시 물음 |

- 매일 12:00에 확인한다. 배포 서버가 켜져 있는 시간(9시~18시) 안이고, 9시 재시작 때 지갑이 실패한 입금을 다시 처리한 뒤라서다.
- 3번 확인하는 동안 서버 재시작이 최소 2번 지나므로, "확정 후 며칠 기다리기"를 따로 두지 않는다.
- 다시 보내는 입금 이벤트는 같은 `payoutId`라, 이미 입금됐으면 지갑이 넘어간다(위 사실 3번째 줄).

### 4-2. 정산 → 지갑: 확인 요청 (제안)

토픽 `payout.payout-deposit-check-requested`. 한 메시지에 여러 정산을 묶어 보낸다. 한 묶음 최대 500건(제안).

```json
{
  "checkId": 3,
  "items": [
    { "payoutId": 15, "payeeId": 5, "amount": 9700 },
    { "payoutId": 16, "payeeId": 8, "amount": 12000 }
  ]
}
```

| 값 | 뜻 |
|---|---|
| `checkId` | 묶음 번호. 답에 그대로 돌려줌 |
| `items[].payoutId` | 확인할 정산 ID. 원장 키 `PAYOUT:{payoutId}`로 찾음 |
| `items[].payeeId` | 정산이 기대하는 판매자 회원 ID |
| `items[].amount` | 정산이 기대하는 금액(원). 항상 1 이상 |

`payeeId`·`amount`는 지갑이 답에 쓰지 않아도 된다. 지갑 로그에 남겨 두면 확인할 때 편하다.

### 4-3. 지갑 → 정산: 확인 답 (제안)

토픽 `wallet.payout-deposit-checked`. 요청 묶음 하나에 답 묶음 하나.

```json
{
  "checkId": 3,
  "items": [
    { "payoutId": 15, "found": true, "payeeId": 5, "amount": 9700, "depositedAt": "TODO(확인 필요)" },
    { "payoutId": 16, "found": false, "payeeId": null, "amount": null, "depositedAt": null }
  ]
}
```

| 값 | 뜻 |
|---|---|
| `checkId` | 요청의 묶음 번호 그대로 |
| `items[].payoutId` | 요청의 정산 ID 그대로 |
| `items[].found` | 원장에 `PAYOUT:{payoutId}`가 있으면 true |
| `items[].payeeId` | 그 원장 행이 속한 판매자 지갑의 회원 ID(`seller_wallet.member_id`). 없으면 null |
| `items[].amount` | 원장 행의 금액. 없으면 null |
| `items[].depositedAt` | 원장 행의 `created_at`. 없으면 null. 형식은 기존 `SellerPayoutCreatedMessage.createdAt`과 같은 방식으로 맞춘다 |

- 지갑은 사실만 답하고 판단하지 않는다. 같은 요청이 여러 번 와도 원장을 읽기만 하므로 답이 같다.
- 지갑은 확인 요청을 받아도 입금하지 않는다. 입금은 정산이 다시 보내는 입금 이벤트로만 한다.
- 묶음 안에서 읽을 수 없는 항목(`payoutId`가 없음 등)은 지갑이 로그를 남기고 그 항목만 답에서 뺀다. 정산은 답이 없는 정산을 다음 날 다시 묻는다.

### 4-4. 지갑에 새로 필요한 것

- Kafka 수신(지갑의 첫 Kafka 리스너)과 발행. 컨슈머 그룹은 지갑 전용으로 둔다(`payout/docs/kafka-switch-team-talk.md` 7-1).
- 원장 조회: 여러 키로 원장 행과 지갑 회원 ID를 한 번에 읽는 조회.
- 이 요청은 입금 경로를 바꾸지 않는다. 다만 지갑에 Kafka 수신 설정을 처음 만드는 일이 #343과 겹치므로 같은 설정을 쓸 수 있다.

### 4-5. 고르지 않은 방식

| 방식 | 고르지 않은 이유 |
|---|---|
| 지갑이 HTTP 조회 API를 열고 정산이 부름 | 정산 담당이 Kafka로 묻고 답하는 방식으로 정함 |
| 대사를 지갑이 통째로 맡음 | 정산 담당이 Kafka로 묻고 답하는 방식으로 정함 |

## 5. 이야기할 것

### 안건 1. 위 방식과 메시지 모양에 동의하는지

- 토픽 이름·필드 이름은 기존 `payout.seller-payout-created`, `wallet.wallet-payment-completed` 형식을 따른 제안이다. 지갑 규칙에 맞춰 바꿔도 된다.
- 묶음 크기 500건은 제안이다. Kafka 메시지 한 개의 기본 최대 크기(1MB) 안에 들어가게 정한다.
- 멘토 리뷰(11/12)는 "대사는 지갑 단계 4와 같은 일이니 지갑 담당과 하나로"라고 했다. 지갑 #532에는 "#308 대사와는 다르다. 지갑 안의 기록만 본다"고 적혀 있다.
- 물을 것: "지갑 단계 4"가 무엇인지 TODO(확인 필요), #532와 겹치는지.

### 안건 2. 입금 이벤트를 다시 보내는 길

- 지금 정산은 확정 때 두 길로 보낸다: Spring 이벤트(지갑이 받아 입금)와 Kafka `payout.seller-payout-created`(지갑이 아직 받지 않음) (`PayoutService.java:356-362`).
- 정산 제안: 지갑이 #343으로 Kafka 수신을 하고, 다시 보내는 입금 이벤트도 기존 토픽 `payout.seller-payout-created`로 보낸다. 같은 `payoutId`라 이미 입금됐으면 지갑이 넘어간다.
- 지갑이 Kafka로 받게 되면 정산은 Spring 이벤트 발행을 지운다(`PayoutModuleEventPublisher.java:7`의 `TODO(#343)`). 그 전까지는 같은 정산이 두 길로 오므로 지갑의 중복 방지가 두 길 모두에 걸려야 한다.
- 물을 것: #343 시점. 대사의 "다시 보내기"는 #343 뒤에야 지갑 입금으로 이어진다.

### 안건 3. 비교 기준

정산이 정할 내용이지만 지갑과 같은 문장으로 맞춰 둔다.

- 대상: 판매자 몫이면서 금액이 0원보다 큰 정산. 정산이 이벤트를 보내는 조건과 같다(`PayoutService.java:354`).
- 짝 맞추기: 시각이 아니라 `payoutId` ↔ 원장 `PAYOUT:{payoutId}`로 맞춘다. 원장 시각은 지갑이 처리한 시각이라 늦게 처리되면 날짜가 달라지기 때문이다.
- 비교: 판매자(`payeeId`)와 금액(`amount`)이 같아야 한다.
- "딱 1건" 검사는 하지 않는다. 원장 유니크 키가 이미 지킨다.

### 안건 4. 관리자 확인 목록에 넘어간 건의 처리

- 지갑 코드 주석은 "이 로그로 찾아 원인을 고친 뒤 수동으로 입금"이라고만 한다(`PayoutEventListener.java:31-32`).
- 정할 것: 관리자 확인 목록의 "입금 없음"·"금액 다름"을 누가, 어떤 방법으로 고치는지. 입금은 같은 키 `PAYOUT:{payoutId}`로 넣어 중복을 막는다.
- 정할 것: 로그 수준. 지갑은 `ERROR`, 정산은 비슷한 "건너뛰고 계속" 경우를 `WARN`으로 남긴다(#421). 알림 기준을 맞출지.

### 안건 5. 근거 없는 입금 (찾을 것 3번)

- 위 방식으로는 찾을 수 없다. 정산은 자기가 아는 정산만 묻기 때문이다.
- 선택지: 이번 범위에서 뺀다 / 지갑이 기간별 `PAYOUT` 입금 목록을 보내는 메시지를 더한다.
- 멘토 리뷰는 나중에 차감·환불(`REFUND:{refundId}`)까지 넓히라고 했다. 원장에 유형이 늘어날 계획이 있는지도 묻는다.

## 6. 지갑과 상의하지 않아도 되는 것 (정산 내부 일)

- 대사 표의 칸 모양(상태, 시도 횟수, 지갑이 답한 금액 등). 기존 `payout_failure`는 스냅샷·후보·주문 칸이 필수(NOT NULL, FK)이고 고칠 수 없는 표라 쓰지 않는다.
- 관리자 확인 목록을 보여 주는 관리자 API.
- 대사 작업 모양: 정산 Job과 따로 두는 작업, 잠금 이름 등.
- #391 실패 범주에 "대사 불일치" 사유를 붙이는 방식.
- 정산 Job 실행 시각: 지금 02:00이라 9시~18시에만 켜지는 배포 서버에서는 돌지 않는다. #308과 별개로 정한다.
