# 환불(refund) 모듈 규칙

환불 모듈은 포트·어댑터(헥사고날) 구조다. 이 파일은 `refund/` 아래 코드에서
`.claude/rules/structure.md`, `service.md`, `api.md`의 **패키지·레이어·트랜잭션 위치·이름 규칙보다 우선한다.**
그 밖의 레포 규칙(한국어 주석, 커밋·브랜치, 테스트 스타일 `testing.md`, 예외 `exception.md`,
마이그레이션 `migration.md`, 코드 포맷 `code-style.md`, API URL·DTO·Swagger 작성법 `api.md`)은 그대로 따른다.

## 모듈 소개
- 구매자의 출고 전 취소 요청을 받고, 판매자가 승인·거절, 구매자가 철회한다. 승인 때 배송비를 정하고, 승인 뒤 단계(주문 반영 #513 → 지갑 환불 요청 #512 → 지갑 완료 메시지 뒤 재고 복구 #414 → 완료 #544)는 지휘자(`RefundSagaService`)가 진행한다(#575). 0원은 지갑 없이 승인 요청 안에서 바로 완료한다. 주문이 이미 출고로 반영을 거절하면(409) 거절로 끝낸다(#543). 기록이 어긋났다는 422는 거절로 닫지 않고 주문 줄을 멈춘다(#554). 재고가 다시 해도 거절되면 돌려준 돈을 지갑에서 다시 가져온다(#546). 지갑이 반환에 실패하거나 회수가 성공하면 주문 취소 기록을 되돌리고 실패(`FAILED`)로 끝낸다(#622).
- 테스트: 레포 루트에서 `./gradlew :refund:test` (통합 테스트는 Testcontainers MySQL·Kafka. 발행은 실제 토픽을 읽어 JSON으로 확인한다)

## 1. 패키지
```
com.ok.refund
├── RefundSchema              모듈 DB 스키마 이름
├── domain/                     도메인 모델·정책. JPA·Spring을 모른다
├── exception/                  RefundErrorCode
├── config/                     모듈 전용 설정
├── application/
│   ├── port/in/                입력 포트(*UseCase)와 그 입출력 값(*Command, *Query, *Result)
│   ├── port/out/               출력 포트(*Port)와 그 값
│   └── service/                유스케이스 구현(*Service)만. 승인 뒤 단계 지휘자도 유스케이스(RefundSagaService)다
└── adapter/
    ├── in/web/                 컨트롤러, *Spec, 요청·응답 DTO(dto/)
    ├── in/event/               (#413~) 받은 메시지 → 값 검사 → 입력 포트. 받기용 Kafka 설정·토픽 상수도 여기(Kafka 타입은 이벤트 어댑터만 쓸 수 있어 config/에 못 둠)
    ├── in/scheduler/           (#576·#577) 정해진 시간마다 도는 입구(다시 진행 알람, 멈춘 환불 찾기 알람) → 입력 포트. ShedLock 잠금 표만 직접 쓴다
    ├── out/persistence/        JPA 엔티티, Spring Data 저장소, 변환, 영속 포트 구현
    ├── out/order/              주문 모듈 호출 포트 구현
    ├── out/product/            상품 모듈 호출 포트 구현 (재고 복구, #414)
    └── out/event/              (#413~) 이벤트 발행 포트 구현
```

## 2. 의존 방향
- `adapter.in → application.port.in → application.service → application.port.out ← adapter.out`
- `application`과 `adapter.out`은 `domain`을 쓴다. `domain`은 `application`·`adapter`와 JPA·Spring 같은 기술을 모른다.
  예외로 환불 에러 코드(`exception`), 공통 예외(`com.ok.common.exception`), lombok만 쓴다. 상태 규칙을 어기면 에러 코드로 알려야 하기 때문이다.
- 입력 어댑터는 입력 포트만 안다. 서비스·출력 포트·출력 어댑터를 직접 쓰지 않는다.
- 출력 어댑터는 출력 포트를 구현하고, 입력 포트·서비스·입력 어댑터를 모른다.
- 이 방향과 패키지·이름 규칙은 `ArchitectureTest`가 검사한다. 그 밖의 규칙은 아래처럼 지킨다.
  - 다른 모듈 타입 금지: `refund/build.gradle.kts`가 `:common`만 의존해서 컴파일이 안 된다
  - 잠근 행에만 `update`: 영속 어댑터가 실행 중에 검사한다
  - 같은 행을 한 트랜잭션에서 두 번 잠금 조회 금지: 영속 어댑터가 실행 중에 검사한다
  - 지휘자는 트랜잭션 밖에서만 부른다: `RefundSagaService` 입구가 실행 중에 검사한다(안에서 부르면 실패 기록이 바깥과 함께 롤백된다)

## 3. 유스케이스와 트랜잭션
- 입력 포트(유스케이스) 하나를 서비스 하나가 구현한다. 한 유스케이스의 흐름은 그 서비스 한 클래스에서 읽힌다. 바깥 조율 클래스와 안쪽 DB 클래스로 나누지 않는다.
- 예외: 승인 뒤 단계는 지휘자 유스케이스(`RefundSagaUseCase`)가 맡는다. 승인 서비스는 승인 구간을 커밋한 뒤 지휘자를 불러 시작만 한다.
  승인 뒤 단계는 한 요청 안에서 끝나지 않기 때문이다(승인 요청 → 몇 분 뒤 지갑 답 → #576 다시 시도).
  ADR 481이 막은 것은 트랜잭션 때문에 한 흐름을 쪼개는 것이고, 이것은 여러 요청에 걸친 단계를 한 곳에 모으는 것이다.
  서비스가 부를 수 있는 다른 입력 포트는 지휘자 포트뿐이다(`ArchitectureTest`).
- 여러 서비스가 함께 쓰는 코드는 서비스 패키지에 도우미로 두지 않는다. 업무 규칙이면 `domain`(정책)에,
  DB에서 꺼내는 방법(쪽 크기·정렬 등)이면 영속 어댑터에 둔다. 서비스에는 흐름(포트 호출 → 도메인 호출 → 저장)만 남긴다.
- 트랜잭션은 서비스 안에서 **DB 작업 구간만** 연다(`TransactionTemplate`). 다른 모듈 호출(주문·상품 HTTP, 지갑·주문 Kafka)은 그 구간 밖에서 한다. 느린 상대 때문에 DB 연결과 행 잠금을 오래 잡지 않으려고.
- 격리 수준처럼 구간마다 다른 설정이 필요하면 그 구간의 `TransactionTemplate`에 준다(예: 승인의 묶음 잠금은 READ COMMITTED).
- DB 작업만 하는 조회 유스케이스는 읽기 전용 구간 하나로 끝낸다.

## 4. 영속 (도메인과 JPA 분리)
- `domain`의 모델은 JPA·Hibernate·Spring 타입을 쓰지 않는다. 테이블 매핑은 `adapter/out/persistence`의 `*JpaEntity`가 맡고, 둘 사이 변환은 `*Mapper`가 한다.
- 저장은 명시적으로 한다. 서비스는 도메인 상태를 바꾼 뒤 영속 포트를 불러야 DB에 반영된다.
  서비스는 변경 감지(값을 바꾸면 저장하라는 말 없이 저장되는 JPA 기능)에 기대지 않는다.
  변경 감지는 영속 어댑터의 `update` 안에서만 쓴다(포트를 부르지 않으면 반영되지 않음).
  - 새 행: `saveNew`가 저장하고 ID·생성 시각이 채워진 도메인을 돌려준다.
  - 기존 행: `update`는 같은 트랜잭션에서 쓰기 잠금으로 불러온 행에만 쓴다(아니면 예외). `update`는 한 트랜잭션에서 여러 번 불러도 된다.
- 잠금 조회는 그 트랜잭션에서 그 행의 첫 조회여야 한다. 먼저 읽어 둔 값이 있으면 잠금은 걸려도 옛 값으로 판단한다.
- 잠금 조회는 한 트랜잭션에서 한 행에 한 번만 한다(두 번째는 예외). 두 번째 조회는 같은 행으로 새 도메인 객체를 만든다.
  그래서 처음 객체를 바꾼 뒤 두 번째 객체로 저장하면 앞의 변경이 사라진다. 다시 필요하면 처음 잠근 객체를 넘겨서 쓴다.
- 제약 이름·SQLState 같은 DB 지식(진행 중 중복, 교착 판별)은 영속 어댑터 안에 둔다.

## 5. 다른 모듈 연동
- 다른 모듈 호출은 모두 출력 포트 뒤에 둔다. `application`은 HTTP 클라이언트·Kafka 타입을 쓰지 않는다.
- 다른 모듈 타입(enum·DTO)을 import하지 않는다. 값(문자열·숫자)으로 받는다.
- 승인 뒤 단계(주문·지갑·재고)의 진행은 단계 진행 표에 남긴다. 환불 하나에 단계마다 한 줄이고, 차례가 오면 그 줄을 만든다(#574).
  - 다른 모듈은 트랜잭션 밖에서 부른다. 부르기 전에 그 단계를 같은 트랜잭션으로 먼저 기록한다. 보내다 실패해도 "할 차례"가 남게 하려는 것이다.
  - 단계 줄 상태는 할 차례·시도 중·결과 대기·성공·거절됨·멈춤이다. 끝 상태(성공·거절됨·멈춤)는 다시 바뀌지 않는다(도메인이 지킨다).
  - 단계 줄은 그 환불 행을 같은 트랜잭션에서 잠근 뒤에만 만들거나 고친다(영속 어댑터가 실행 중에 검사한다).
  - 단계 줄을 만들고 고치는 일(성공·실패 기록 포함)은 지휘자만 한다.
  - 다시 시도는 알람 한 곳이 맡는다(`RefundResumeScheduler` → `ResumeDueRefundsUseCase` → `resume`, #576). 1분마다 돌고 ShedLock으로 한 번에 한 서버만 돈다. 같은 단계를 두 번 부르지 않게 막는 것은 잠금이 아니라 환불 행 잠금과 잠근 뒤 상태 확인이다.
  - 한 단계는 5번까지 자동으로 시도하고, 다 쓰면 멈춘다. 다시 해도 같은 실패(`NON_RETRYABLE_FAILURES`, 상품 404 `PRODUCT_STOCK_NOT_FOUND`·409 `PRODUCT_RELEASE_REFUSED`, 주문 422 `ORDER_RECORD_CONFLICT`)는 바로 멈춘다. 상품 422는 환불이 보낸 값의 오류(우리 버그)라 표준 예외로 다시 시도한 뒤 멈추고, 돈 다시 가져오기 대상이 아니다(#546). 주문 422는 숫자만 같고 뜻이 다르다. 주문 기록과 어긋난 것(수량 합계 초과, 같은 refundId에 다른 내용, 이미 되돌린 환불)이라 주문 줄을 바로 멈춘다. 주문 반영은 첫 단계라 돈이 나가기 전이다(#554). 시도 중인 채로 2분이 지난 줄은 어느 입구든 잠근 뒤 다시 집는다.
  - 지갑 결과를 5분 기다려도 오지 않으면 같은 refundId로 다시 보낸다(#577). 회수 줄·주문 되돌리기 줄도 이 절의 규칙(5분, 24시간 한도, 늦은 결과 기다림)을 같이 쓴다(#546, #622). 시도 횟수에 넣지 않고 멈추지도 않는다. 이미 한 번 보내 결과를 기다린 적 있는 줄(`awaiting_since`가 있음)은 다시 보내다 발행이 실패하거나 시도 중으로 만료돼도 멈추지 않는다. 멈추면 늦게 온 진짜 지갑 답(잔액 부족 등)을 기록하지 못하기 때문이다. 지갑은 같은 refundId를 한 번만 처리한다. 다시 진행할 수 없는 환불에서도 이미 보낸 줄은 멈추지 않고 결과 대기로 두되 다시 볼 시각을 비운다(`RefundStep.holdForLateResult`, #546). 처음 기다린 지 24시간(`RefundStep.RESEND_LIMIT`)이 지나도 더 보내지 않고 같은 모양으로 늦은 결과만 기다린다(토픽에 같은 요청이 쌓이지 않게, #546). 결과 대기 시간 초과의 다시 보내기와 시도 중 만료 다시 집기 모두 이 한도를 본다.
  - 사람이 봐야 하는 처리 중 환불(멈춘 줄, 단계 줄 없음, 앞 단계 성공인데 다음 줄 없음, 지갑 결과를 처음 기다린 지 30분 넘음)은 찾기 알람(`RefundAttentionScheduler`, 1시간마다)이 `[환불-확인필요]` WARN 한 줄(건수, 앞 10개 번호)로 알린다. 다시 보낼 때마다 남기는 로그는 많아(24시간 동안 환불 1건에 최대 288줄) INFO다. "다음 줄 없음" 규칙은 계획(`RefundSagaPlan.fromSteps`)과 찾기 쿼리 두 곳에 있어 함께 고치고, 대조 테스트(`RefundStepPersistenceAdapterIntegrationTest`)로 확인한다. 되돌리기 중인 환불(회수·주문 되돌리기)은 앞의 멈춘 지갑·재고 줄 때문에 정상 진행 중에도 이 목록에 뜬다. 결과 대기 오래됨 조건을 되돌리기 줄에 따로 두지 않은 이유다(같은 것을 두 번 봄).
  - 회수(지갑 돈 다시 가져오기, #546): 재고가 다시 해도 같은 이유로 거절되고(상품 409 `PRODUCT_RELEASE_REFUSED`만. 404 `PRODUCT_STOCK_NOT_FOUND`는 주소 설정 오류와 가를 수 없어 멈추기만 한다) 돌려준 돈이 있으면, 재고 줄을 멈춘 같은 구간에서 회수 줄(`WALLET_REVERT`)을 시도 중으로 만들고 커밋 뒤 `runStep`이 바로 Kafka로 회수를 요청한다. 5번을 다 써 멈춘 재고, 상품 422, 0원 환불은 회수하지 않는다. 바로 보내기가 실패하면 회수 줄을 할 차례로 남겨 알람이 다시 보낸다. 회수 줄이 있으면 계획이 그 줄만 보고 앞으로 가지 않는다(지갑 반환을 다시 요청하지 않음). 회수 결과는 domain `WalletRevertResultPolicy`가 지갑 반환 결과와 같은 기준으로 거른다. 회수가 성공하면 이어서 주문을 되돌리고, 실패하면 주문은 되돌리지 않고 처리 중으로 남아 찾기 알람이 알린다. 지갑 반환 실패의 `REFUND_REVERTED`는 지갑 실패로 기록하지 않는다.
  - 주문 되돌리기(#622): 지갑 반환 실패로 지갑 줄을 처음 멈춘 구간, 또는 회수 성공을 기록한 구간에서 되돌리기 줄(`ORDER_REVERT`)을 시도 중으로 만들고 커밋 뒤 바로 Kafka로 주문에 취소 기록 되돌리기를 요청한다(되돌리는 순서는 지갑 먼저, 주문 다음, PR #537). 결과 불일치·이미 다른 이유로 멈춘 지갑 줄·회수 실패·0원 재고 거절은 되돌리지 않고 사람이 본다(0원: 상품 409에 "이미 풀림"이 섞여 주문만 되돌리면 재고가 한 번 더 팔릴 수 있음, #709). 계획은 되돌리기 줄을 가장 먼저 본다. 주문 결과는 domain `OrderRevertResultPolicy`가 잠근 뒤 한 번 거르고(주문·주문 상품 비교), 되돌림이면 되돌리기 줄 성공과 환불 실패(`FAILED`, 진행 중 칸 비움, 구매자에게 보일 사유는 `rejectReason`에 `Refund.FAILED_REASON`)를 한 구간에서 남긴다. 실패(예: `ALREADY_CONFIRMED`)면 되돌리기 줄만 멈추고 되돌리기를 또 되돌리지 않는다. 되돌리기 줄이 있는 환불에는 지갑 완료가 와도 재고·완료까지 가지 않는다(돈과 상품이 함께 나가지 않게). 재고 줄이 없으면(지갑 실패 경로) 값이 같든 다르든 약속 위반이라 되돌리기 줄을 `WALLET_COMPLETED_LATE`로 멈춰(값이 다른 완료는 #761, DB만으로는 둘을 가르지 못해 로그로 본다) 처리 중으로 남기고(찾기 알람이 알림), 재고 줄이 있으면(회수 경로) 같은 완료가 다시 온 정상 중복이라 넘긴다(값이 다른 완료면 WARN, #761)(지갑 줄은 앞선 불일치로 멈춘 채 회수 경로로 갈 수 있어 기준으로 쓰지 않는다). 실패는 배송비 집계에 들지 않지만 자기 행만 잠근다(승인 뒤 거절과 같은 한계, #707).
  - 다음에 할 일은 domain `RefundSagaPlan` 한 곳에서 정한다(방금 받은 답이면 `afterEvent`, 알람이 깨우면 `fromSteps`). 잠근 뒤 줄을 다시 보고 부를지 넘길지는 실행이라 지휘자가 한다. 앞 단계는 성공했는데 다음 줄이 없거나 단계 줄 자체가 없으면, 있을 수 없는 상태로 보고 진행하지 않는다(#616).
  - 환불 번호만으로 이어 가는 입구는 `RefundSagaUseCase.resume`이다. 예외는 그대로 올리고, 환불마다 잡는 일은 부르는 쪽(알람, #576)이 한다.
- 발행: 서비스는 발행 출력 포트만 부르고, `adapter/out/event`의 구현체가 그 포트를 구현한다. 토픽 이름과 메시지 클래스는 어댑터 안에만 둔다.
- 수신: `adapter/in/event`는 받은 값(빈 ID, 0원 이하, 빈 사유 등)만 검사한다. 입력 어댑터는 DB를 볼 수 없어서다(예외: 알람 `adapter/in/scheduler`는 서버 간 잠금을 위해 ShedLock 표만 직접 쓴다. 환불·단계 표는 입력 포트를 거친다).
  없는 환불, 끝난 환불, 금액·주문·구매자가 다른 메시지는 domain `WalletResultPolicy`가 거른다(회수 결과는 `WalletRevertResultPolicy`, 주문 되돌리기 결과는 `OrderRevertResultPolicy`가 잠근 뒤 한 번 거른다). 받음·불일치·넘김만 답하고 다음 단계는 정하지 않는다. 지휘자는 잠그기 전 먼저 읽은 값으로 한 번, 잠근 뒤 다시 읽은 값으로 한 번 부른다. 읽은 뒤 잠그기 전에 상태가 바뀔 수 있어서다. 결과 불일치로 지갑 줄을 처음 멈출 때는 지갑이 보낸 값(결과 종류·주문·구매자·금액·실패 이유)을 지갑 줄의 `wallet_*` 칸에 함께 남긴다(`RefundStep.stopForMismatch`, #761). 돈은 자동으로 되돌리지 않고 관리자가 맞춘다. 이미 끝난 줄은 이유도 값도 바꾸지 않고, DB에 남지 않는 경우(이미 멈춤, 넘김)는 로그에 지갑 값을 남긴다.
  걸러 넘길 때는 예외를 던지지 않는다. 던지면 Kafka 오류 처리기가 다시 시도해 뒤 메시지가 기다린다(#544).
  지갑 완료 뒤 재고 복구 실패도 재고 줄에 기록한 뒤 예외를 던지지 않는다. 오류 처리기가 다시 시도하면 시도 횟수를 다 써 알람보다 먼저 멈추기 때문이다(#576).

## 6. 이름
| 역할 | 이름 | 위치 |
|---|---|---|
| 입력 포트 | `*UseCase` | `application/port/in` |
| 입력 값 / 조회 조건 / 결과 | `*Command` / `*Query` / `*Result` | 그 값이 지나가는 포트 옆 |
| 유스케이스 구현 | `*Service` (입력 포트 하나당 하나) | `application/service` |
| 출력 포트 | `*Port` (예: `RefundPersistencePort`, `OrderQueryPort`) | `application/port/out` |
| 영속 어댑터 / JPA 엔티티 / Spring Data 저장소 / 변환 | `*PersistenceAdapter` / `*JpaEntity` / `*JpaRepository` / `*Mapper` | `adapter/out/persistence` |
| 다른 모듈 호출 어댑터 | `*Adapter` (예: `RefundOrderHttpAdapter`) | `adapter/out/<상대 모듈>` |
| 컨트롤러 / 문서 인터페이스 / 요청·응답 | `*Controller` / `*ControllerSpec` / `*Request`·`*Response` | `adapter/in/web` |
| 도메인 모델 | 접미사 없이 도메인 이름 (`Refund`) | `domain` |

- 스프링 빈으로 등록되는 클래스(서비스·어댑터·컨트롤러·Spring Data 저장소)는 이름에 `Refund`가 들어가게 짓는다. 모든 모듈이 한 앱(monolith)으로 뜰 때 다른 모듈의 같은 이름 클래스와 빈 이름이 겹치면 앱이 시작되지 않는다.

## 7. 테스트
- 도메인: 순수 단위 테스트
- 서비스: 출력 포트를 Mockito로 대체한다. 상태를 바꾸는 유스케이스는 영속 포트에 넘긴 값을 확인한다(저장 호출 자체가 요구사항)
  - 승인 서비스 단위 테스트는 같은 가짜 포트로 만든 진짜 지휘자를 넣어 승인 뒤 흐름까지 함께 본다. 지휘자의 지갑 결과 입구는 따로 테스트한다(#592)
- 영속 어댑터: 실제 DB로 직접 테스트한다(잠금·변환·중복 감지는 서비스 경로로 다 만들 수 없어서).
  실제 DB로 만들기 어려운 예외 경우(예: 알 수 없는 DB 오류를 그대로 던지는지)만 Mockito(가짜 객체를 만들어 주는 테스트 도구)로 추가로 확인한다.
- 웹·전체 흐름: 통합 테스트(`AbstractIntegrationTest` + 주문 Fake)
- 구조: `ArchitectureTest`
