# 환불 실패 처리(되돌리기) 제안과 팀별 요청 (의견 구함)

> 환불 #516 중 다른 팀과 맞춰야 하는 부분을 모은 제안서다. 정해진 것이 아니라 의견을 묻는 문서다.
> 의견은 해당 줄에 리뷰 댓글로 남겨 주세요. API 경로·메시지 이름·필드 이름은 받는 팀 편한 대로 바꿔도 된다.

## 0. 이 문서에서 쓰는 말

| 말 | 뜻 |
| --- | --- |
| 성공 처리 | 판매자 승인 뒤 단계를 끝까지 진행해 환불을 완료하는 것 |
| 다시 시도 | 잠깐의 문제(서버 재시작, DB 끊김)로 실패한 단계를 같은 `refundId`로 다시 해서 앞으로 진행하는 것 |
| 실패 처리 | 다시 해도 같은 결과인 실패가 났을 때, 앞에서 이미 한 단계를 되돌리는 것 |

## 1. 지금 모습 (#528 머지 기준)

판매자가 환불을 승인하면, 승인 요청 한 번 안에서 환불 모듈이 다른 모듈을 차례로 부른다.

| 순서 | 상대 | 방식 |
| --- | --- | --- |
| 1 | 지갑: 예치금 돌려주기 | Kafka `refund.refund-approved` 발행 (지갑이 처리했는지는 확인하지 않음) |
| 2 | 주문: 취소 수량 반영 (요청서 ②) | HTTP `POST /internal/v1/orders/items/{orderItemId}/refunds` (주문 PR #542 진행 중) |
| 3 | 상품: 재고 일부 되돌리기 | HTTP `POST /internal/v1/products/stock-allocations/{orderId}/partial-release` (#363) |
| 4 | 환불: 완료 | - |

중간에 실패하면 환불은 "처리 중"에 멈추고, 다시 진행하거나 되돌리는 길이 없다.

## 2. #516에서 환불이 바꾸는 것

### 2-1. 순서: 주문 → 지갑 → 재고
예시: 판매자가 감자 1개(10,000원) 취소를 승인했는데, 그 직후 출고 담당이 송장을 등록했다.
- 지금 순서(지갑 먼저)면 10,000원이 이미 나간 뒤에 주문이 출고를 알게 된다.
- 주문을 먼저 부르면 주문이 "이미 출고"라고 답하고, 돈·재고는 아직 안 움직였으니 환불은 거절로 끝난다.

그래서 거절될 수 있는 단계(주문)를 앞에, 다시 하면 결국 되는 단계(지갑·재고)를 뒤에 둔다.

### 2-2. 바뀐 성공 처리
1. 환불 → 주문: 취소 수량 반영 (HTTP, 지금과 같은 API)
2. 환불 → 지갑: 돌려줘 (Kafka `refund.refund-approved`, 지금과 같은 메시지)
3. 지갑 → 환불: 결과 메시지 (지갑 팀이 11/12에 제안한 모양)
4. 환불 → 상품: 재고 되돌리기 (HTTP, #363 그대로)
5. 환불: 완료

지갑의 결과를 받은 뒤에 완료로 바꾼다. 지금은 Kafka에 들어간 것만 보고 완료로 바꾸는데(임시), 이것을 없앤다.

### 2-3. 실패하면

| 실패한 단계 | 이미 한 것 | 하는 일 |
| --- | --- | --- |
| 주문 반영: "이미 출고"·"수량 초과" | 없음 | 환불은 거절로 끝 |
| 주문 반영: 응답 없음·5xx | 없음 | 다시 시도 |
| 지갑: 실패 메시지 (다시 해도 같은 결과) | 주문 반영 | **실패 처리: 주문의 취소 수량을 되돌린다** → 환불은 실패로 끝, 관리자 알림 |
| 지갑: 결과가 오래 안 옴 | 주문 반영 | 처리 중에 오래 머문 환불을 찾아 관리자 알림 |
| 재고: 응답 없음·5xx, `ALLOCATION_IN_PROGRESS`(409, "잠시 후 다시") | 주문 반영, 돈 돌려줌 | 다시 시도 |
| 재고: 다시 해도 실패 (`ALLOCATION_NOT_FOUND` 404, `RELEASE_QUANTITY_EXCEEDED`·`ALLOCATION_ALREADY_RELEASED`·`PARTIAL_RELEASE_MISMATCH` 409) | 주문 반영, 돈 돌려줌 | **실패 처리: 지갑이 돌려준 돈을 먼저 다시 가져오고, 성공하면 주문의 취소 수량을 되돌린다** → 환불은 실패로 끝, 관리자 알림 |
| 실패 처리(되돌리기)가 잠깐 실패 | - | 다시 시도 |
| 지갑 돈 다시 가져오기가 다시 해도 실패 (예: 잔액 부족) | 주문 반영, 돈 돌려줌 | 주문은 되돌리지 않고 멈춤, 관리자 알림. 돈은 구매자에게, 주문은 취소된 상태라 관리자가 재고만 맞추면 된다 |
| 주문 되돌리기: 이미 구매확정 (주문이 실패 결과를 보냄) | 주문 반영, (재고 실패면) 돈 돌려줌·다시 가져옴 | 멈추고 관리자 알림 |
| 주문 되돌리기: 그 밖에 다시 해도 실패 | - | 멈추고 관리자 알림 |

"다시 해도 실패"는 같은 요청을 다시 보내도 같은 답이 오는 경우다. 정상이라면 생기지 않고, 주문·상품·환불 기록 가운데 어딘가가 서로 어긋났을 때 난다.
예: 감자 1개 환불에서 주문 반영과 지갑 10,000원 반환까지 끝났는데, 상품이 `ALLOCATION_ALREADY_RELEASED`(그 주문의 재고가 이미 전부 해제됨)로 계속 거절한다.
이때 돈과 주문만 바뀌고 재고는 그대로인 상태로 두지 않으려고, 앞에서 한 지갑·주문을 되돌린다.

되돌리는 순서는 **지갑 먼저, 그다음 주문**이다. 지갑이 돈을 다시 가져오지 못했는데(구매자가 이미 씀) 주문을 먼저 되돌리면, "돈은 구매자에게 있는데 주문은 취소 안 됨"이 되어 판매자가 상품을 보내야 하는 상태가 된다.
되돌리기도 다시 해도 안 되면 거기서 멈추고 관리자에게 넘긴다. "되돌리기를 또 되돌리기"는 만들지 않는다.

환불이 지휘하는 사가다. 환불이 단계를 차례로 시키고, 실패하면 이미 한 단계에 되돌리기를 시킨다.
되돌리기가 끝까지 가도록 환불이 "되돌리기 남음"을 기록하고, 될 때까지 다시 시도한다.

## 3. 팀별 요청

### 주문
1. **취소 수량 반영(②)에 조건 추가** — PR #542에 반영됨
   - 출고 전일 때만 반영한다. 이미 출고됐으면 반영하지 않고 409로 답한다(`REFUND_NOT_ALLOWED_STATUS`). 수량 합계 초과는 `REFUND_QUANTITY_EXCEEDED`, 같은 `refundId`로 다른 내용은 `REFUND_ID_CONFLICT`.
   - 같은 `refundId`·같은 내용이 다시 오면 두 번 더하지 않고 성공으로 답한다(출고 여부보다 먼저 본다).
   - HTTP 동기로 둔다(주문 팀 합의). 409(이미 출고)를 받아야 지갑에 돈을 보내기 전에 멈출 수 있다.
2. **취소 기록 되돌리기 (새로, 실패 처리용, Kafka)** — 주문 팀 합의
   - 받는 메시지: `refund.refund-order-revert-requested` (필드 `refundId`, `orderId`, `orderItemId`, `quantity`, 키 `orderId`)
   - 그 `refundId`로 남긴 취소 기록(수량·뺀 배송비)을 되돌린다. 주문 상품 상태는 바꾸지 않는다(취소 반영도 상태를 바꾸지 않음).
   - 같은 `refundId`로 두 번 와도 한 번만 되돌린다. 반영한 적 없는 `refundId`면 아무것도 안 하고 성공으로 본다.
   - 결과 메시지: 되돌림 `order.order-refund-reverted` (필드 `refundId`, `orderId`, `orderItemId`) / 실패 `order.order-refund-revert-failed` (위 필드 + `reason`, 예: `ALREADY_CONFIRMED` 이미 구매확정)
   - 이미 구매확정된 뒤에 온 되돌리기는 실패 결과로 보내고, 환불은 멈추고 관리자에게 넘긴다(주문 팀 제안).
   - Kafka로 하는 이유: 되돌리기는 환불이 이미 "실패로 끝"을 정한 뒤라 답을 기다려 다음을 정할 일이 없다. 구매확정 전까지만 확실히 처리되면 된다(주문 팀).
   - 조건: 팀 공통 Kafka 오류 처리기·DLT(처리 못 한 메시지를 따로 모아 두는 곳)가 먼저 있어야 한다.
   - 언제 보내나: 지갑이 다시 해도 실패했을 때, 또는 재고가 다시 해도 실패해 지갑이 돈을 다시 가져온 뒤(2-3 표). 정상 운영에서는 거의 없어야 한다.
3. 구매확정 금액에서 환불된 개수를 뺀다(`OrderService` `TODO(#28)`, 요청서 ③). 빠지면 부분 환불 뒤 판매자에게 돈이 더 나간다.
   - 예: 감자 10,000원 x 3개 + 배송비 3,000원 = 33,000원 결제, 1개 환불 뒤 3개분을 보내면 판매자가 9,700원(29,100원 − 19,400원)을 더 받는다.
4. 환불용 조회(①)는 PR #533으로 머지됐고, 취소 수량 반영(②)과 구매확정 금액(③)은 PR #542에서 진행 중이다.

## 4. 되돌리기는 Kafka로 (주문 팀 합의)

지갑이 이미 Kafka로 주고받고, 주문 팀도 되돌리기를 Kafka로 원한다. 지갑의 돈 다시 가져오기도 같은 방식(Kafka)이 자연스럽다.

| 보내는 쪽 → 받는 쪽 | 토픽 (제안) | 필드 (제안) |
| --- | --- | --- |
| 환불 → 주문 | `refund.refund-order-revert-requested` | `refundId`, `orderId`, `orderItemId`, `quantity` |
| 주문 → 환불 | `order.order-refund-reverted` | `refundId`, `orderId`, `orderItemId` |
| 주문 → 환불 | `order.order-refund-revert-failed` | 위 필드 + `reason` |

토픽 이름은 받는 모듈마다 나눈다(지갑은 `refund.refund-wallet-revert-requested`, 주문은 `refund.refund-order-revert-requested`). 한 이름을 같이 쓰면, 주문만 되돌리면 되는 경우(지갑 실패)에도 지갑이 메시지를 받게 된다.

키는 모두 `orderId`다. 같은 주문의 메시지가 같은 파티션으로 가 순서가 지켜진다.

같은 이유로, 원하면 성공 처리의 주문·상품 호출도 Kafka로 바꿀 수 있다. 다만 이번 #516에서는 바꾸지 않는 것을 기본으로 한다.

## 5. 의견을 구할 것

1. 실패 처리(되돌리기)가 두 경우인 것이 맞는지: 지갑이 다시 해도 실패 → 주문 되돌리기 / 재고가 다시 해도 실패 → 지갑 돈 다시 가져오기 + 주문 되돌리기
2. 지갑: 돈을 다시 가져올 때 구매자 잔액이 모자라면 어떻게 할지
3. ~~주문 되돌리기 방식~~ → 주문 답: Kafka (팀 공통 DLT가 먼저)
4. 성공 처리의 주문·상품 호출도 Kafka로 바꾸기를 원하는지 → 주문 답: 취소 반영(②)은 HTTP 유지
5. API 경로·메시지 이름·필드 이름·실패 사유
6. 팀별 작업 일정
