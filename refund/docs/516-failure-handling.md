# 환불 실패 처리(되돌리기) 제안과 팀별 요청 (의견 구함)

> 환불 #516 중 다른 팀과 맞춰야 하는 부분을 모은 제안서다. 정해진 것이 아니라 의견을 묻는 문서다.
> 의견은 해당 줄에 리뷰 댓글로 남겨 주세요. API 경로·메시지 이름·필드 이름은 받는 팀 편한 대로 바꿔도 된다.

## 0. 이 문서에서 쓰는 말

| 말 | 뜻 |
| --- | --- |
| 성공 처리 | 판매자 승인 뒤 단계를 끝까지 진행해 환불을 완료하는 것 |
| 다시 시도 | 잠깐의 문제(서버 재시작, DB 끊김)로 실패한 단계를 같은 `refundId`로 다시 해서 앞으로 진행하는 것 |
| 실패 처리 | 다시 해도 같은 결과인 실패가 났을 때, 앞에서 이미 한 단계를 되돌리는 것 |

## 1. 지금 모습 (#528 머지 기준)

판매자가 환불을 승인하면, 승인 요청 한 번 안에서 환불 모듈이 다른 모듈을 차례로 부른다.

| 순서 | 상대 | 방식 |
| --- | --- | --- |
| 1 | 지갑: 예치금 돌려주기 | Kafka `refund.refund-approved` 발행 (지갑이 처리했는지는 확인하지 않음) |
| 2 | 주문: 취소 수량 반영 (요청서 ②) | HTTP `POST /internal/v1/orders/items/{orderItemId}/refunds` (주문 쪽 API 아직 없음) |
| 3 | 상품: 재고 일부 되돌리기 | HTTP `POST /internal/v1/products/stock-allocations/{orderId}/partial-release` (#363) |
| 4 | 환불: 완료 | - |

중간에 실패하면 환불은 "처리 중"에 멈추고, 다시 진행하거나 되돌리는 길이 없다.

## 2. #516에서 환불이 바꾸는 것

### 2-1. 순서: 주문 → 지갑 → 재고
예시: 판매자가 감자 1개(10,000원) 취소를 승인했는데, 그 직후 출고 담당이 송장을 등록했다.
- 지금 순서(지갑 먼저)면 10,000원이 이미 나간 뒤에 주문이 출고를 알게 된다.
- 주문을 먼저 부르면 주문이 "이미 출고"라고 답하고, 돈·재고는 아직 안 움직였으니 환불은 거절로 끝난다.

그래서 거절될 수 있는 단계(주문)를 앞에, 다시 하면 결국 되는 단계(지갑·재고)를 뒤에 둔다.

### 2-2. 바뀐 성공 처리
1. 환불 → 주문: 취소 수량 반영 (HTTP, 지금과 같은 API)
2. 환불 → 지갑: 돌려줘 (Kafka `refund.refund-approved`, 지금과 같은 메시지)
3. 지갑 → 환불: 결과 메시지 (지갑 팀이 11/12에 제안한 모양)
4. 환불 → 상품: 재고 되돌리기 (HTTP, #363 그대로)
5. 환불: 완료

지갑의 결과를 받은 뒤에 완료로 바꾼다. 지금은 Kafka에 들어간 것만 보고 완료로 바꾸는데(임시), 이것을 없앤다.

### 2-3. 실패하면

| 실패한 단계 | 이미 한 것 | 하는 일 |
| --- | --- | --- |
| 주문 반영: "이미 출고"·"수량 초과" | 없음 | 환불은 거절로 끝 |
| 주문 반영: 응답 없음·5xx | 없음 | 다시 시도 |
| 지갑: 실패 메시지 (다시 해도 같은 결과) | 주문 반영 | **실패 처리: 주문의 취소 수량을 되돌린다** → 환불은 실패로 끝, 관리자 알림 |
| 지갑: 결과가 오래 안 옴 | 주문 반영 | 처리 중에 오래 머문 환불을 찾아 관리자 알림 |
| 재고: 응답 없음·5xx | 주문 반영, 돈 돌려줌 | 다시 시도 |
| 재고: 다시 해도 실패 | 주문 반영, 돈 돌려줌 | 되돌리지 않고 관리자 처리 (아래 이유) |
| 실패 처리(주문 되돌리기)가 실패 | - | 다시 시도, 계속 실패하면 관리자 알림 |

재고 실패를 되돌리지 않는 이유: 되돌리려면 이미 구매자에게 돌려준 돈을 다시 가져와야 한다. 구매자가 그 돈을 이미 썼을 수 있다. 재고 숫자는 관리자가 맞추는 편이 낫다고 본다.

환불이 지휘하는 사가다. 환불이 단계를 차례로 시키고, 실패하면 이미 한 단계에 되돌리기를 시킨다.
되돌리기가 끝까지 가도록 환불이 "되돌리기 남음"을 기록하고, 될 때까지 다시 시도한다.

## 3. 팀별 요청

### 주문
1. **취소 수량 반영(②)에 조건 추가**
   - 출고 전일 때만 반영한다. 이미 출고됐으면 반영하지 않고 409로 답한다(사유를 알 수 있게).
   - 같은 `refundId`가 다시 오면 두 번 더하지 않는다.
2. **취소 수량 되돌리기 API (새로, 실패 처리용)**

   ```
   POST /internal/v1/orders/items/{orderItemId}/refunds/{refundId}/revert
   ```
   - 그 `refundId`로 더했던 취소 수량을 뺀다. 그 반영으로 바뀐 주문 상품 상태(예: 모두 취소되어 `REFUNDED`)도 되돌린다.
   - 같은 `refundId`로 두 번 와도 한 번만 뺀다(두 번째는 아무것도 안 하고 성공 응답).
   - 반영한 적 없는 `refundId`면 아무것도 안 하고 성공 응답. 환불이 다시 시도하다 보면 이런 요청이 갈 수 있다.
   - 언제 부르나: 지갑이 다시 해도 실패했을 때(2-3 표). 정상 운영에서는 거의 없어야 한다.
3. 구매확정 금액에서 환불된 개수를 뺀다(`OrderService` `TODO(#28)`, 요청서 ③). 빠지면 부분 환불 뒤 판매자에게 돈이 더 나간다.
   - 예: 감자 10,000원 x 3개 + 배송비 3,000원 = 33,000원 결제, 1개 환불 뒤 3개분을 보내면 판매자가 9,700원(29,100원 − 19,400원)을 더 받는다.
4. 환불용 조회(①)와 취소 수량 반영(②) API 일정을 알려 주세요. 지금 dev에 없어서 배포 앱에서는 환불이 동작하지 않는다.

### 지갑
1. 받는 메시지(`refund.refund-approved`)는 그대로다. 보내는 때만 "판매자 승인 직후"에서 "주문 반영 뒤"로 바뀐다.
2. **11/12에 주신 결과 메시지 모양 그대로 붙여 주세요.** 이름·필드·사유를 바꾸지 않고 그대로 받는다.
   - 완료 `wallet.wallet-refund-completed`, 실패 `wallet.wallet-refund-failed`, 키 `orderId`
   - 필드 `refundId`, `orderId`, `buyerId`, `amount`, 실패일 때만 `reason`
   - 실패 사유 `PAYMENT_NOT_FOUND`, `REFUND_TOTAL_EXCEEDED`, `AMOUNT_MISMATCH`, `INVALID_AMOUNT`
   - 같은 `refundId`가 다시 오면 돈은 다시 주지 않고 처음 결과를 다시 보냄
3. 지갑에 되돌리기(돌려준 돈 다시 가져오기)는 요청하지 않는다. 지갑 뒤 단계(재고)가 실패해도 돈은 되돌리지 않는다(2-3 표).
4. 반환 근거 키를 `refundId` 기준으로 둔다(예: `REFUND:{refundId}`). 같은 주문 상품을 나눠 환불하면 두 번째 반환이 막히지 않아야 한다.

### 상품
- 새로 할 일은 없다. 재고 일부 되돌리기(#363)를 지금처럼 부른다.
- 다시 시도 기준을 맞추고 싶다: 응답 없음·5xx는 환불이 다시 시도하고, 409·404는 다시 하지 않고 관리자 처리한다. 다른 의견이 있으면 알려 주세요.

## 4. 선택안: 되돌리기를 Kafka로

지갑이 이미 Kafka로 주고받으므로, 주문 되돌리기도 메시지로 할 수 있다. 원하는 팀이 있으면 이쪽으로 한다.

| 보내는 쪽 → 받는 쪽 | 토픽 (제안) | 필드 (제안) |
| --- | --- | --- |
| 환불 → 주문 | `refund.refund-revert-requested` | `refundId`, `orderId`, `orderItemId`, `quantity` |
| 주문 → 환불 | `order.order-refund-reverted` | `refundId`, `orderId`, `orderItemId` |

| | HTTP (기본안) | Kafka (선택안) |
| --- | --- | --- |
| 주문 팀이 만들 것 | API 하나 | 메시지 수신과 결과 발행 |
| 주문이 꺼져 있으면 | 환불이 기록해 두고 다시 시도 | 메시지가 남아 있다가 처리됨 |
| 다시 시도는 누가 | 환불 | Kafka와 주문 |

같은 이유로, 원하면 성공 처리의 주문·상품 호출도 Kafka로 바꿀 수 있다. 다만 이번 #516에서는 바꾸지 않는 것을 기본으로 한다.

## 5. 의견을 구할 것

1. 실패 처리(되돌리기)가 "지갑이 다시 해도 실패 → 주문 되돌리기" 한 경우뿐인 것이 맞는지
2. 재고가 다시 해도 실패하면 되돌리지 않고 관리자 처리로 두는 것이 괜찮은지
3. 주문 되돌리기를 HTTP(기본안)로 할지, Kafka(선택안)로 할지
4. 성공 처리의 주문·상품 호출도 Kafka로 바꾸기를 원하는지
5. API 경로·메시지 이름·필드 이름·실패 사유
