# 배송 팀 요청: 환불 취소 예약·확정 (#184 B9-3)

> 환불 1단계(#323) 요청서 중 배송 팀 부분이다. 전체 흐름과 공통 부탁은 [README.md](README.md)를 본다.
> 의견은 해당 줄에 리뷰 댓글로 남겨 주세요.

## 요청 요약

| API | 언제 부르나 | 하는 일 |
| --- | --- | --- |
| ① 취소 예약 | 판매자가 취소를 승인한 직후 (흐름 5번) | 그 상품이 출고되지 않게 잠근다 |
| ② 취소 확정 | 지갑·주문·상품 처리가 끝난 뒤 (흐름 9번) | 잠금을 풀고 취소를 확정한다 |

**예약 풀기 API는 필요 없다.** 판매자는 승인 뒤 거절할 수 없고, 환불은 "처리 중"으로 바꾼 뒤에 예약하므로 예약을 무를 일이 없다.

## 약속 (환불이 기대하는 동작)

### ① 취소 예약

```
POST /internal/v1/delivery/cancel-reservations
{ "refundId": 7, "orderItemId": 101, "quantity": 1 }
```

- 예약이 걸린 동안 그 배송 건은 **송장을 등록할 수 없다.** (지금 `CANCELLATION_RESERVED` 검사와 같은 동작)
- 송장 등록과 예약이 동시에 와도 **둘 중 하나만 성공**해야 한다.
- 같은 `refundId`로 다시 오면 수량을 더하지 않고 성공으로 답한다. 내용이 다르면 409.
- `shipmentId`는 넘기지 않는다. `shipment_item.order_item_id`가 유니크라 `orderItemId`로 찾을 수 있다.

| 응답 | 경우 | 환불이 하는 일 |
| --- | --- | --- |
| 200 | 예약됨 (또는 같은 예약이 이미 있음) | 다음 단계 진행 |
| 409 `INVALID_SHIPMENT_STATE` | 이미 송장 등록됨 | 승인 불가, 구매자에게 반품 안내 |
| 409 `CANCEL_QUANTITY_EXCEEDED` | 남은 수량보다 많음 | 승인 불가 |
| 404 (새 코드 제안) | 주문 상품의 배송 건이 아직 없음 | "요청됨"으로 되돌리고 "잠시 후 다시" |
| 409 (새 코드 제안) | 같은 `refundId`로 내용이 다른 요청 | 환불 쪽 버그로 봄 |

환불은 409 두 가지를 응답 본문의 에러 코드로 구분한다. 이미 출고면 반품 안내, 수량 초과면 다른 안내를 하기 때문이다.

### ② 취소 확정 (잠금 해제)

```
POST /internal/v1/delivery/cancel-reservations/{refundId}/confirm
```

- 예약한 수량을 취소 확정 수량으로 옮긴다. 예약이 사라지므로 남은 상품은 다시 출고할 수 있다.
- 그 배송 건의 상품이 **모두 취소되면 배송도 취소**(`CANCELLED`)한다.
- 이미 확정됐으면 아무것도 바꾸지 않고 성공으로 답한다.

| 응답 | 경우 |
| --- | --- |
| 200 | 확정됨 (또는 이미 확정됨) |
| 404 (새 코드 제안) | 해당 `refundId`의 예약 기록 없음 |

### 예시

같은 배송 건에 양말 3개와 모자 1개가 있을 때

| 순서 | 일어난 일 | 예약 / 취소 확정 수량 (양말) | 배송 건 상태 | 송장 등록 |
| --- | --- | --- | --- | --- |
| 처음 | — | 0 / 0 | PREPARING | 가능 |
| ① | 양말 1개 예약 | 1 / 0 | PREPARING | **막힘** |
| ② | 양말 1개 확정 | 0 / 1 | PREPARING | 가능 (양말 2개, 모자 출고) |
| ①② | 나머지 양말 2개, 모자 1개도 예약·확정 | 0 / 3 (모자 0 / 1) | **CANCELLED** | — |

## 자세한 배경

### 지금 코드 상태

| 있는 것 | 위치 |
| --- | --- |
| `Shipment.reserveCancel(orderItemId, quantity)` — `PREPARING`에서만 예약 | `Shipment.java:239` |
| 예약이 있으면 송장 등록 거절 (`CANCELLATION_RESERVED`) | `Shipment.java:221` |
| 송장 등록은 shipment 행 잠금 아래에서 처리 | `ShipmentService.java:105` |
| 모든 항목이 전량 취소일 때만 배송 취소 | `Shipment.java:282` |

| 없는 것 |
| --- |
| `reserveCancel`을 부르는 서비스·API |
| 예약 수량을 취소 확정 수량으로 옮기는 메서드 |
| 같은 요청이 두 번 와도 한 번만 처리하는 장치 (`reserveCancel`은 수량을 더하기만 함) |

### 참고 (설계를 점검하면서 발견한 것)

- **`ShipmentItem.cancel(int)`은 예약 수량을 줄이지 않는다** (`ShipmentItem.java:120`). 확정에 그대로 쓰면 예약이 남아 송장 등록이 계속 막히고, 같은 개수가 예약과 확정에 두 번 세어진다.
- **잠금 조회를 첫 쿼리로 해야 한다.** `ShipmentRepository.findByIdForUpdate`의 주석(23~26줄)대로, 잠금 전에 일반 조회를 하면 REPEATABLE READ 스냅샷이 고정된다. 예를 들어 양말 확정과 모자 확정이 거의 동시에 오면, 늦게 잠금을 얻은 쪽이 잠금 전 시점으로 양말을 "취소 0개"로 읽는다. 그러면 전부 취소인데도 배송 건이 PREPARING에 남고, 예약도 0이라 빈 배송에 송장을 등록할 수 있다. 첫 쿼리를 잠금 조회로 하거나, 지갑 결제(`BuyerWalletService.java:98-101`)처럼 READ COMMITTED로 실행하면 피할 수 있다.
- **배송 취소 때 대기 중인 배송지 변경 요청.** 송장 등록 때는 자동 거절하지만(`ShipmentService.java:111-112`), 배송 취소 때는 그런 처리가 없다. 남겨 두면 판매자가 승인할 때 `INVALID_SHIPMENT_STATE`로 실패한다.
- **(제안)** `Shipment.dispatch()`에 "전량 취소된 배송 건은 출고 불가" 확인을 넣으면, 어떤 이유로 전부 취소된 배송 건이 PREPARING에 남아도 빈 배송이 나가지 않는다.
- **(제안)** `ShipmentItem.reserveCancel`의 Javadoc(131줄)은 "취소 확정 **이벤트**를 받을 때 옮긴다"고 되어 있다. 확정이 HTTP API로 오므로 표현을 맞추면 좋겠다.

### 테스트로 확인하면 좋은 것

- 같은 `refundId`로 예약·확정을 두 번 보내도 수량은 한 번만 바뀐다.
- 확정 뒤 남은 상품은 송장 등록이 된다.
- 모든 항목이 전량 취소되면 `CANCELLED`가 되고 대기 중 배송지 변경 요청이 거절된다.
- 같은 배송 건의 서로 다른 항목 확정 두 건이 동시에 와도 `CANCELLED`가 된다.
- 송장 등록과 예약이 동시에 와도 하나만 성공한다 (기존 `ShipmentDispatchConcurrencyIntegrationTest`를 실제 서비스로).
