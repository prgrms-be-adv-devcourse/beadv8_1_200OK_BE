## 요청 요약

배송 잠금이 걸린 뒤(흐름 6번) 환불 모듈이 지갑에 **구매자 예치금 반환**을 요청한다. 이를 받을 내부 API 하나를 요청한다.

---

## 약속 (환불이 기대하는 동작)

```
POST /internal/v1/wallets/refunds
{ "refundId": 7, "orderId": 10, "buyerId": 1, "sellerId": 5, "amount": 13000 }
```

- 구매자 지갑에 `amount`만큼 돌려준다. **금액은 환불이 계산해서 넘긴다.** (`BuyerWallet.java:76`의 "돌려줄 금액이 맞는지는 호출하는 쪽에서 확인한다"와 같음)
- **근거 키는 `REFUND:{환불ID}`로 부탁한다.**
- 같은 `refundId`로 다시 오면 또 넣지 않고 성공으로 답한다. 같은 근거 키인데 금액이 다르면 409.
- 출고 전 취소라 **판매자 지갑은 건드리지 않는다.** 구매자가 낸 돈은 정산 전까지 시스템이 갖고 있기 때문이다.

| 값 | 쓰는 곳 |
| --- | --- |
| `refundId` | 근거 키 `REFUND:{refundId}` |
| `orderId` | 이용 내역에 어느 주문의 환불인지 표시, 결제 금액 확인(제안) |
| `buyerId` | 돌려줄 구매자 지갑 |
| `sellerId` | 기록용. 1단계에서는 판매자 지갑을 쓰지 않음 |
| `amount` | 상품 금액. 판매자 묶음이 전부 취소되면 배송비와 추가 운임 포함 |

| 응답 | 경우 |
| --- | --- |
| 204 | 반환됨 (또는 이미 같은 환불을 처리함) |
| 409 | 같은 근거 키로 금액이 다름 |
| 422 | 금액이 0 이하 |

### 근거 키를 `REFUND:{환불ID}`로 하는 이유

`BuyerWallet.refund` 주석에는 "취소 건 ID 또는 주문 상품 ID"로 되어 있다. 그런데 같은 주문 상품을 여러 번 나눠 취소할 수 있어서, 주문 상품 ID를 키로 쓰면 두 번째 환불이 막힌다.

```
양말 3개 중 1개 취소 (환불 7) → REFUND:7 ✅
나중에 1개 더 취소 (환불 8)  → REFUND:8 ✅

(주문 상품 ID를 키로 쓰면)
첫 번째 → REFUND:101 ✅
두 번째 → REFUND:101 → 이미 쓴 키라 막힘 ✗
```

## 자세한 배경

### #34 계획과 달라진 점

| #34 원래 계획 | 바뀐 내용 | 이유 |
| --- | --- | --- |
| "주문 취소 이벤트"를 받아 반환 | 환불 모듈이 HTTP API로 요청 | 모듈 간 통신을 HTTP(동기)로 하기로 함, 요청 주체는 환불 모듈 |
| 주문 단위 반환 | 주문 상품·개수 단위 (한 주문에 여러 번 가능) | 부분 취소를 지원함 |
| 같은 주문 중복 반환 방지 | 같은 환불ID 중복 반환 방지 | 한 주문에 환불이 여러 번 있을 수 있음 |

### 참고 (설계를 점검하면서 발견한 것)

- **중복 확인은 결제 방식(READ COMMITTED)을 추천한다.** 충전(`BuyerWalletService.java:61`)처럼 기본 격리 수준으로 확인하면, 같은 요청이 동시에 두 번 올 때 둘 다 "아직 없음"으로 통과하고 두 번째가 근거 키 유니크 제약에 걸려 500이 난다. 결제(`payForOrder`, `BuyerWalletService.java:98-101`)는 READ COMMITTED로 이 문제를 피한다.
- **(제안) 이용 내역에 환불 보여 주기.** 지금 이용 내역은 충전과 결제만 보인다(`WalletLedgerService.java:30`). 잔액은 늘었는데 이유가 안 보인다. `REFUND`와 주문 번호를 함께 보여 주길 제안한다. 지금 주문 번호는 근거 키 `PAYMENT:{주문ID}`에서 꺼내는데 환불 키에는 주문 번호가 없어서, 받은 `orderId`를 따로 저장해야 한다.

  ```
  10/21  결제  주문 10  -33,000
  10/22  환불  주문 10  +13,000
  ```

- **(제안) 결제 금액을 넘는 환불 막기.** `WalletOrderPayment`(주문 ID, 구매자, 금액)로 이 주문을 결제한 구매자가 맞는지, 돌려준 합이 결제 금액을 넘지 않는지 확인할 수 있다. 넣는다면 성공한 결제(`isPaid()`)만 기준으로 해야 한다. 잔액 부족으로 실패한 결제도 금액을 가진 채 남기 때문이다(`WalletOrderPayment.java:56-58`). 또 위의 주문 ID 저장이 먼저 있어야 "이 주문에서 돌려준 합"을 구할 수 있다.
- **(확인 필요) 보유 한도.** `refund()`는 보유 한도(`MAX_BALANCE`)를 확인하지 않는다. 결제 뒤 충전을 많이 해서 환불로 한도를 넘게 되는 경우를 어떻게 할지 정해 주면 좋겠다. 막으면 환불이 실패하므로, 환불은 한도와 관계없이 받는 쪽을 제안한다.

### 테스트로 확인하면 좋은 것

- 같은 `refundId`로 두 번 보내도 잔액은 한 번만 늘어난다.
- 같은 `refundId`가 동시에 두 번 와도 한 번만 반영되고 둘 다 성공으로 답한다.
- 같은 근거 키로 금액이 다르면 409가 난다.
- 같은 주문에 서로 다른 `refundId`로 두 번 환불하면 둘 다 반영된다.
