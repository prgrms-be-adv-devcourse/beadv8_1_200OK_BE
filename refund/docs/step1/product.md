# 상품 팀 요청: 환불 재고 일부 해제

> 환불 1단계(#323) 요청서 중 상품 팀 부분이다. 전체 흐름과 공통 부탁은 [README.md](README.md)를 본다.
> 의견은 해당 줄에 리뷰 댓글로 남겨 주세요.

## 요청 요약

출고 전 취소가 끝나면(흐름 8번) 취소한 개수만큼 재고를 되돌린다. 주문의 **옵션 하나에서 N개만** 되돌리는 내부 API를 요청한다.

---

## 약속 (환불이 기대하는 동작)

```
POST /internal/v1/products/stock-allocations/{orderId}/partial-release
{ "refundId": 7, "productOptionId": 55, "quantity": 1 }
```

- 주문 10의 옵션 55에서 **1개만** 재고를 되돌린다. 묶인 수량이 줄어 다른 사람이 살 수 있게 된다.
- 같은 `refundId`로 다시 오면 또 풀지 않고 성공으로 답한다. 내용이 다르면 409.
- 상품은 재고를 "주문 + 옵션" 단위로 기억하고 주문 상품 번호를 모르므로, 환불이 주문에서 받은 옵션 ID를 넘긴다.

| 응답 | 경우 |
| --- | --- |
| 204 | 해제됨 (또는 같은 `refundId`로 이미 해제함) |
| 404 (새 코드 제안) | 주문 + 옵션의 배정 기록 없음 |
| 409 (새 코드 제안) | 배정 수량보다 많이 풀려고 함, 또는 같은 `refundId`로 내용이 다름 |

### 예시

| 일어난 일 | 옵션 55 총 재고 / 묶인 수량 | 살 수 있는 수량 |
| --- | --- | --- |
| 처음 (주문 10이 양말 3개 배정) | 10 / 3 | 7 |
| 양말 1개 취소, 일부 해제 | 10 / 2 | 8 |
| 같은 요청이 다시 옴 | 10 / 2 (그대로) | 8 |

## 자세한 배경

### 지금 코드로는 안 되는 이유

`ProductStockService.release(orderId)`(`ProductStockService.java:81`)는 **주문 전체** 재고를 한꺼번에 풀고, 한 번 푼 주문은 다시 쓸 수 없다(`allocate`가 `ALLOCATION_ALREADY_RELEASED`로 거절). 양말 1개만 취소해도 이걸 부르면 아직 배송할 다른 상품 재고까지 풀려 다른 사람이 살 수 있게 된다.

같은 주문에서 같은 옵션을 여러 줄 사면 배정 기록 하나로 합쳐진다(`ProductStockService.java:51-55`). 그래서 일부 해제도 "주문 + 옵션"의 배정 기록에서 수량을 줄이는 방식이 자연스럽다.

### 참고 (설계를 점검하면서 발견한 것)

- **배정 기록은 조건부 UPDATE로만 바뀐다.** 상태가 `updatable = false`이고 "ALLOCATED → RELEASED 전이는 조건부 UPDATE 쿼리로만 한다"는 주석이 있다(`ProductStockAllocation.java:31-33`). 수량도 바꾸는 메서드가 없다. 예를 들어 `UPDATE ... SET quantity = quantity - :n WHERE id = :id AND status = 'ALLOCATED' AND quantity >= :n` 형태로 하고, 0행이면 409로 답하면 같은 옵션 두 줄이 동시에 풀려도 수량이 맞다.
- **`productOptionRepository.release`도 조건이 맞지 않으면 예외 없이 0을 돌려준다.** 반환값 확인이 필요하다.
- **일부 해제로 배정 수량이 0이 될 때 `RELEASED`로 바꾸면 `allocate()`가 오판한다.** "이 주문에 RELEASED 기록이 하나라도 있으면 이미 해제한 주문"으로 판단하기 때문이다(`ProductStockService.java:44`). 0이 된 기록은 상태를 바꾸지 않거나 별도로 구분하길 제안한다.
- **기존 `release(orderId)`와 겹칠 때.** `release`는 조건부 UPDATE 전에 읽은 수량으로 재고를 되돌린다(`ProductStockService.java:84-87`). 일부 해제와 겹치면 더 풀 수 있다. 다만 결제가 끝난 주문에는 `release`가 불리지 않아 위험은 작다.

### 테스트로 확인하면 좋은 것

- 같은 `refundId`로 두 번 보내도 묶인 수량이 한 번만 줄어든다.
- 일부 해제 뒤 기존 `release(orderId)`를 부르면 남은 수량만 풀린다.
- 같은 주문에 서로 다른 `refundId`로 두 번 일부 해제하면 각각 반영된다.
- 같은 옵션 두 줄을 동시에 일부 해제해도 수량이 맞다.
- 일부 해제로 0이 된 주문에 같은 주문 ID로 `allocate`를 다시 보내도 "이미 해제한 주문"으로 오판하지 않는다.
