## 환불 1단계 흐름

```
1. 구매자: 주문 상세에서 환불 요청 (주문, 주문 상품, 개수)
2. 환불 → 주문: 환불용 조회 → "요청됨" 저장
3. 판매자: 승인 대기 목록 조회
4. 판매자 승인 → "처리 중"으로 바꾸고 돌려줄 금액 계산·저장
5. 환불 → 배송: 취소 예약 (잠금)        ← 이미 출고면 "승인 불가", 반품 안내
6. 환불 → 지갑: 예치금 반환
7. 환불 → 주문: 취소 수량 반영
8. 환불 → 상품: 재고 일부 해제
9. 환불 → 배송: 취소 확정 (잠금 해제)
10. "완료"
```

- 판매자가 거절하면 "거절"로 끝난다. 구매자는 판매자 승인 전까지 철회할 수 있다.
- **배송 잠금이 처음, 잠금 해제가 마지막이다.** 돈을 돌려준 뒤 상품이 나가면 구매자가 돈과 상품을 둘 다 받는다. 주문이 취소 수량을 기록하기 전에 남은 상품이 나가 구매확정되면 정산 금액이 더 나간다. 잠겨 있는 동안에는 출고·구매확정·정산이 일어나지 않아 안전하다.
- 1~3번(요청됨)에서는 주문·배송·지갑·상품 모두 아무것도 바뀌지 않는다.
- 승인된 뒤에는 되돌리지 않는다. 중간에 실패하면 환불 쪽에 "처리 중"으로 남기고 다시 처리한다.

## 모든 팀에 공통으로 부탁하는 것

- 내부 HTTP API(`/internal/v1/...`)로 부른다. 1차 구현은 동기 호출이고, 통신은 성공한다고 본다(자동 재시도는 나중).
- **같은 `refundId`로 두 번 와도 한 번만 처리하고 성공으로 답한다.** 응답이 사라져 환불이 같은 요청을 다시 보낼 수 있다. 같은 `refundId`인데 내용(수량·금액)이 다르면 409로 막는다.
- 같은 요청이 **동시에** 두 번 와서 유니크 제약에 걸려도 500이 아니라 성공으로 답해 주길 부탁한다.

## 용어

| 용어 | 뜻 |
| --- | --- |
| 환불 ID (`refundId`) | 환불 요청 한 건의 번호. 중복 처리를 막는 기준 |
| 배송 잠금 | 배송의 취소 예약. 잠기면 송장을 등록할 수 없어 상품이 나가지 않음 |
| 잠금 해제 | 배송의 취소 확정. 예약 수량을 취소 수량으로 옮겨 남은 상품을 다시 출고할 수 있게 함 |
| 판매자 묶음 | 한 주문 안에서 같은 판매자의 상품들. 배송 한 건과 배송비·추가 운임을 공유함 |
