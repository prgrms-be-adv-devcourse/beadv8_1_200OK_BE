# 주문 팀 요청: 환불용 조회·취소 수량 반영 (#28 관련)

> 환불 1단계(#323) 요청서 중 주문 팀 부분이다. 전체 흐름과 공통 부탁은 [README.md](README.md)를 본다.
> #28(환불 상태 반영)의 계획을 1단계 설계에 맞춰 구체화했다. 달라진 점은 아래 표에 있다.
> 의견은 해당 줄에 리뷰 댓글로 남겨 주세요.

## 요청 요약

| 요청 | 언제 부르나 | 하는 일 |
| --- | --- | --- |
| ① 환불용 조회 | 구매자가 요청할 때(흐름 2번), 판매자가 승인할 때(흐름 4번) | 환불이 확인·금액 계산에 쓸 주문 정보를 준다 |
| ② 취소 수량 반영 | 지갑 반환이 끝난 뒤(흐름 7번) | 취소된 개수를 기록한다 |
| ③ 구매확정 금액 조정 | (주문 내부) | 구매확정 이벤트 금액에서 취소된 개수를 뺀다 |

주문은 **취소가 끝났을 때 한 번만** 알림(②)을 받는다. 요청 단계에서는 주문을 건드리지 않는다.

## 약속 (환불이 기대하는 동작)

### ① 환불용 조회

```
GET /internal/v1/orders/{orderId}/items/{orderItemId}
```

```json
{
  "orderId": 10, "orderItemId": 101,
  "buyerId": 1, "sellerId": 5,
  "productOptionId": 55,
  "productName": "양말", "optionName": "흰색",
  "status": "PREPARING",
  "unitPrice": 10000, "quantity": 3, "refundedQuantity": 1,
  "sellerGroup": {
    "shippingFee": 3000,
    "remoteAreaFee": 3000,
    "items": [
      { "orderItemId": 101, "quantity": 3 },
      { "orderItemId": 102, "quantity": 1 }
    ]
  }
}
```

| 값 | 환불이 쓰는 곳 |
| --- | --- |
| `buyerId` | 로그인한 구매자의 주문인지 확인 (그래서 이 API는 구매자를 따지지 않아도 됨) |
| `sellerId` | 판매자 승인 목록에 보여 줄 판매자 |
| `productOptionId` | 상품 재고 되돌리기 (상품 모듈은 옵션 단위로 기억함) |
| `productName`, `optionName` | 환불 목록에 표시 |
| `status` | 출고 전인지 1차 확인 |
| `unitPrice`, `quantity`, `refundedQuantity` | 돌려줄 금액, 취소 가능 개수 |
| `sellerGroup.shippingFee`, `sellerGroup.remoteAreaFee` | 판매자 묶음이 전부 취소되면 함께 돌려줄 배송비와 추가 운임 |
| `sellerGroup.items[].quantity` | 같은 묶음의 상품별 주문 수량. "묶음 전부 취소"인지 판단할 때 씀 |

- 응답: 200, 404 주문이 없거나 주문 안에 그 주문 상품이 없음.

### ② 취소 수량 반영

```
POST /internal/v1/orders/items/{orderItemId}/refunds
{ "refundId": 7, "quantity": 1 }
```

- `refundedQuantity`에 수량을 더한다. 주문 수량이 모두 취소되면 그 주문 상품은 `REFUNDED`가 된다.
- 같은 `refundId`로 다시 오면 더하지 않고 성공으로 답한다. 수량이 다르면 409.
- 응답: 성공, 404 주문 상품 없음, 409 취소 수량 합계가 주문 수량 초과, 409 같은 `refundId`로 수량이 다름.

### ③ 구매확정 금액 조정

구매확정 이벤트 금액에서 취소된 개수를 빼 주길 요청한다.

```
보낼 금액 = 단가 × (수량 − refundedQuantity) = 10,000 × (3 − 1) = 20,000
```

- 배송비는 지금처럼 묶음 배송비를 그대로 보낸다. 일부 취소에서는 배송비를 구매자에게 돌려주지 않으므로, 남은 상품이 구매확정되면 배송비는 판매자 몫이다.
- 전부 취소된 상품은 `REFUNDED`라 구매확정 대상이 아니다(지금 `confirmPurchase`는 `DELIVERED`일 때만 확정).

### 데이터 변경 (제안)

| 변경 | 내용 |
| --- | --- |
| `order_item.refunded_quantity` | 취소가 끝난 개수, NOT NULL 기본 0 |
| 반영 기록 테이블 | `refund_id`(UNIQUE), `order_item_id`, `quantity` — 같은 요청을 두 번 반영하지 않으려고 둠 |

## 자세한 배경

### #28 계획과 달라진 점

| #28 원래 계획 | 바뀐 내용 | 이유 |
| --- | --- | --- |
| 환불 진행 수량 + 환불 완료 수량 | 완료 수량(`refundedQuantity`)만 | 판매자가 승인하면 배송이 잠겨 출고되지 않는다. 출고가 안 되면 배송 완료도, 구매확정도 될 수 없으므로 처리 중인 동안 따로 막을 필요가 없다 |
| "환불 진행", "환불 완료" 이벤트 | ② 한 번 | 위와 같은 이유. 1차 구현은 HTTP |
| 주문이 "환불 가능 수량" 계산 | 값만 주고 환불이 계산 | 처리 중인 요청 수는 환불만 안다. 주문이 계산하면 처리 중인 요청을 빼지 못한다 |
| (없음) | 요청 단계에서는 주문 상태를 바꾸지 않음 | 아래 참고 |

### 요청 단계에서 주문 상태를 바꾸지 않는 이유

판매자는 취소 요청을 무시하고 그냥 출고할 수 있다(이미 포장한 경우 등). 이때 요청 단계에서 주문 상품을 `CANCEL_REQUESTED`로 바꿔 두었다면 이렇게 된다.

```
구매자 취소 요청 → 주문: 양말 CANCEL_REQUESTED
판매자가 무시하고 송장 등록 → 배송: SHIPPING
주문: 배송 시작 알림을 받지만 PREPARING이 아니라서 건너뜀 (OrderItem.java:92)
주문: 배송 완료도 PREPARING/SHIPPING이 아니라서 건너뜀 (OrderItem.java:101-103)
→ 양말은 배송 중인데 주문은 CANCEL_REQUESTED에 멈추고 구매확정도 안 됨
```

요청 단계에서 주문을 건드리지 않으면 판매자가 무시하고 출고해도 주문은 평소대로 흘러간다.

### 참고

- `CANCEL_REQUESTED`는 쓰이지 않게 된다. 남길지 지울지는 주문 팀 판단이다.
- 모든 상품이 `REFUNDED`가 된 주문을 주문 단위 `CANCELED`로 바꿀지도 주문 팀 판단이다.
- 주문의 배송비는 지금 항상 0이다(`OrderSellerGroup.java:49-50` TODO). 배송비 계산이 붙어야 배송비 환불이 실제 금액을 갖는다. 추가 운임(`remoteAreaFee`)은 지금도 실제 값이 들어간다.
- 같은 요청이 동시에 두 번 와서 반영 기록 유니크 제약에 걸리면 500이 아니라 성공으로 답해 주면 좋겠다.

### 테스트로 확인하면 좋은 것

- 같은 `refundId`로 ②를 두 번 보내도 `refundedQuantity`는 한 번만 늘어난다.
- 3개 중 1개 취소 후 남은 2개는 평소대로 배송 중 → 배송 완료 → 구매확정된다.
- 3개 모두 취소하면 `REFUNDED`가 되고 구매확정되지 않는다.
- 1개 취소 뒤 구매확정하면 2개 금액(20,000)이 이벤트로 나간다.

### 범위 밖

반품(2단계), 구매확정 뒤 환불(3단계), 주문 상세 화면에 취소 상태 표시(프론트와 따로 정함).
