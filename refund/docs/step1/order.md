# 주문 팀 요청: 환불용 조회·환불 끝남 알림 (#28 관련)

> 환불 1단계(#323) 요청서 중 주문 팀 부분이다. 전체 흐름과 공통 부탁은 [README.md](README.md)를 본다.
> #28(환불 상태 반영)의 계획을 1단계 설계에 맞춰 구체화했다. 달라진 점은 아래 표에 있다.
> 의견은 해당 줄에 리뷰 댓글로 남겨 주세요.

## 요청 요약

| 요청 | 언제 부르나 | 하는 일 |
| --- | --- | --- |
| ① 환불용 조회 | 구매자가 요청할 때(흐름 2번) | 환불이 확인·금액 계산에 쓸 주문 정보를 준다 |
| ② 환불 끝남 알림 | 환불이 끝날 때. 성공(흐름 7번), 거절·철회(흐름 4번), 승인 불가(흐름 5번) | 결과를 받는다. 성공이면 취소된 개수를 기록한다 |
| ③ 구매확정 금액 조정 | (주문 내부) | 구매확정 이벤트 금액에서 취소된 개수를 뺀다 |

주문은 ① 조회를 받을 때 주문 상품 상태를 바꿀 수 있다(어떤 상태로 바꿀지는 주문 팀이 정함). 환불은 어떻게 끝나든 **환불 하나당 한 번** ② 알림을 보내므로, 요청 때 바꾼 상태는 이 알림으로 풀 수 있다.

## 약속 (환불이 기대하는 동작)

### ① 환불용 조회

```
GET /internal/v1/orders/{orderId}/items/{orderItemId}
```

```json
{
  "orderId": 10, "orderItemId": 101,
  "buyerId": 1, "sellerId": 5,
  "productOptionId": 55,
  "productName": "양말", "optionName": "흰색",
  "status": "PREPARING",
  "unitPrice": 10000, "quantity": 3, "refundedQuantity": 1,
  "sellerGroup": {
    "shippingFee": 3000,
    "remoteAreaFee": 3000,
    "baseShippingFee": 3000,
    "freeShippingThreshold": 50000,
    "items": [
      { "orderItemId": 101, "unitPrice": 10000, "quantity": 3 },
      { "orderItemId": 102, "unitPrice": 5000, "quantity": 1 }
    ]
  }
}
```

| 값 | 환불이 쓰는 곳 |
| --- | --- |
| `buyerId` | 로그인한 구매자의 주문인지 확인 (그래서 이 API는 구매자를 따지지 않아도 됨) |
| `sellerId` | 판매자 승인 목록에 보여 줄 판매자 |
| `productOptionId` | 상품 재고 되돌리기 (상품 모듈은 옵션 단위로 기억함) |
| `productName`, `optionName` | 환불 목록에 표시 |
| `status` | 출고 전인지 1차 확인 |
| `unitPrice`, `quantity`, `refundedQuantity` | 돌려줄 금액, 취소 가능 개수 |
| `sellerGroup.shippingFee`, `sellerGroup.remoteAreaFee` | 판매자 묶음이 전부 취소되면 함께 돌려줄 배송비와 추가 운임 |
| `sellerGroup.items[].quantity` | 같은 묶음의 상품별 주문 수량. "묶음 전부 취소"인지 판단할 때 씀 |
| `sellerGroup.baseShippingFee`, `sellerGroup.freeShippingThreshold` | 주문 시점의 기본 배송비와 무료배송 기준 금액(#342). 일부 취소 뒤 무료배송 기준이 깨지는지 판단 ([아래](#일부-취소로-무료배송-기준이-깨질-때)) |
| `sellerGroup.items[].unitPrice` | 같은 묶음의 상품별 단가. 취소 뒤 남은 묶음 금액을 구할 때 씀 |

- 응답: 200, 404 주문이 없거나 주문 안에 그 주문 상품이 없음.

### ② 환불 끝남 알림

```
POST /internal/v1/orders/items/{orderItemId}/refunds

{ "refundId": 7,  "result": "COMPLETED", "quantity": 1, "deductedShippingFee": 3000 }  ← 환불 성공
{ "refundId": 8,  "result": "REJECTED" }                                              ← 판매자 거절
{ "refundId": 9,  "result": "WITHDRAWN" }                                             ← 구매자 철회 (승인 전)
{ "refundId": 10, "result": "NOT_APPROVABLE" }                                        ← 승인했지만 이미 출고돼 승인 불가
```

| `result` | 언제 | 주문이 하는 일 |
| --- | --- | --- |
| `COMPLETED` | 지갑 반환이 끝난 뒤(흐름 7번) | `refundedQuantity`에 수량을 더한다. 상태는 주문 팀이 정한다(예: 모두 취소되면 `REFUNDED`) |
| `REJECTED` | 판매자가 거절함 | 수량은 그대로. 요청 때 바꾼 상태가 있으면 되돌린다 |
| `WITHDRAWN` | 구매자가 승인 전에 철회함 | 위와 같음 |
| `NOT_APPROVABLE` | 판매자가 승인했지만 배송 잠금에서 이미 출고로 확인됨 | 위와 같음 |

- `quantity`, `deductedShippingFee`는 `COMPLETED`일 때만 온다.
- `deductedShippingFee`는 이 취소로 환불 금액에서 뺀 배송비다. 빼지 않았으면 0이다. 주문은 이 값을 기록해 두었다가 ③에서 판매자 몫 배송비로 보낸다.
- 환불 하나는 위 넷 중 하나로 한 번만 끝난다. 같은 `refundId`로 다시 오면 반영하지 않고 성공으로 답한다. 같은 `refundId`인데 결과나 수량이 다르면 409.
- 응답: 성공, 404 주문 상품 없음, 409 취소 수량 합계가 주문 수량 초과, 409 같은 `refundId`로 내용이 다름.

### ③ 구매확정 금액 조정

구매확정 이벤트 금액에서 취소된 개수를 빼 주길 요청한다.

```
보낼 금액 = 단가 × (수량 − refundedQuantity) = 10,000 × (3 − 1) = 20,000
```

- 배송비는 묶음 배송비에 ②로 받은 `deductedShippingFee` 합계를 더해서 보낸다. 환불에서 뺀 배송비는 남은 상품을 보내는 판매자 몫이기 때문이다.

```
주문 시점 배송비 0(무료배송) + 환불에서 뺀 배송비 3,000 = 3,000
```

- 환불만 배송비를 뺐는지 안다. 주문이 같은 계산을 다시 하면 두 곳 결과가 어긋날 수 있어서, 환불이 뺀 금액을 ②로 알려 준다.
- 전부 취소된 상품은 `REFUNDED`라 구매확정 대상이 아니다(지금 `confirmPurchase`는 `DELIVERED`일 때만 확정).

### 데이터 변경 (제안)

| 변경 | 내용 |
| --- | --- |
| `order_item.refunded_quantity` | 취소가 끝난 개수, NOT NULL 기본 0 |
| 반영 기록 테이블 | `refund_id`(UNIQUE), `order_item_id`, `quantity`, `deducted_shipping_fee` — 같은 요청을 두 번 반영하지 않으려고 둠. 뺀 배송비는 ③에서 씀 |

## 자세한 배경

### 일부 취소로 무료배송 기준이 깨질 때

무료배송이던 묶음에서 일부만 취소하면 남은 묶음 금액이 무료배송 기준 아래로 내려갈 수 있다. 이때 환불은 아래처럼 처리한다. 기준은 배송 모듈의 배송비 규칙(`ShippingFeePolicy`)과 같고, 값은 주문 시점 값(①의 `baseShippingFee`, `freeShippingThreshold`)을 쓴다.

- 취소 뒤 남은 묶음 금액이 무료배송 기준 아래면, 환불 금액에서 기본 배송비를 뺀다.
- 환불 금액이 기본 배송비보다 작으면 부분 취소를 받지 않는다(전체 취소만 가능).
- 그 뒤 남은 상품까지 모두 취소해 묶음이 전부 취소되면, 앞에서 뺀 배송비도 마지막 환불 때 함께 돌려준다. 상자가 나가지 않으니 배송비를 받을 근거가 없다. 이때 묶음이 모두 `REFUNDED`라 구매확정이 없으므로, 주문에 기록된 `deductedShippingFee`는 쓰이지 않는다.

예시 (기본 배송비 3,000원, 5만 원 이상 무료배송)

```
A 30,000 + B 30,000 = 60,000원 주문(배송비 0) → B 취소 → 남은 30,000원, 기준 아래
→ 환불 30,000 − 3,000 = 27,000원, ②에 deductedShippingFee 3,000
→ A 구매확정 때 배송비 3,000을 판매자 몫으로 보냄(③)

A 49,500 + B 1,000 = 50,500원 주문(배송비 0) → B 취소 → 남은 49,500원, 기준 아래
→ 1,000 < 3,000 → 부분 취소 불가

첫 예시에서 이어서 A도 취소 → 묶음 전부 취소
→ 환불 30,000 + 앞에서 뺀 3,000 = 33,000원 (구매자는 60,000원을 모두 돌려받음)
```

### #28 계획과 달라진 점

| #28 원래 계획 | 바뀐 내용 | 이유 |
| --- | --- | --- |
| 환불 진행 수량 + 환불 완료 수량 | 완료 수량(`refundedQuantity`)만 | 판매자가 승인하면 배송이 잠겨 출고되지 않는다. 출고가 안 되면 배송 완료도, 구매확정도 될 수 없으므로 처리 중인 동안 따로 막을 필요가 없다 |
| "환불 진행", "환불 완료" 이벤트 | ② 끝남 알림 한 번 (결과 4가지) | 진행은 ① 조회 때 주문이 직접 알 수 있고, 끝은 ②로 알린다. 1차 구현은 HTTP |
| 주문이 "환불 가능 수량" 계산 | 값만 주고 환불이 계산 | 처리 중인 요청 수는 환불만 안다. 주문이 계산하면 처리 중인 요청을 빼지 못한다 |
| (없음) | 요청 때 주문이 상태를 바꿀 수 있음 | 주문 팀 의견(PR #415). 아래 참고 |

### 요청 때 주문 상태를 바꾸는 경우

주문 팀은 ① 조회를 받을 때 주문 상품 상태를 바꿔(예: 대기) 후속 처리를 막기로 했다. 환불은 어떻게 끝나든 ②를 한 번 보내므로, 주문은 그 알림을 받고 상태를 되돌리거나 다음 상태로 바꾸면 된다.

```
구매자 요청   → ① 조회 → 주문: 양말 "대기"(주문 팀이 정함)
판매자 거절   → ② REJECTED       → 주문: 원래대로
구매자 철회   → ② WITHDRAWN      → 주문: 원래대로
이미 출고     → ② NOT_APPROVABLE → 주문: 원래대로
환불 성공     → ② COMPLETED      → 주문: 취소 수량 기록, 상태 변경
```

다만 아래 두 경우는 ②가 가지 않는다. 주문 팀이 알고 정해 주면 좋겠다.

- **① 조회 뒤 환불 저장이 실패한 경우.** 환불은 조회한 뒤 요청을 저장한다. 같은 상품에 진행 중인 요청이 있어 409로 끝나면 환불 요청이 없으므로 ②도 없다. 조회 때 바꾼 상태가 풀리지 않는다.
- **판매자가 거절하지 않고 출고한 경우.** 판매자는 요청을 무시하고 송장을 등록할 수 있다(이미 포장한 경우 등). 이때 주문 상품이 `PREPARING`이 아니면 배송 시작·완료 알림을 건너뛰어(`OrderItem.java:92`, `101-103`) 상태가 멈출 수 있다. 환불 요청은 "요청됨"에 남아 있다가, 판매자가 나중에 승인하면 `NOT_APPROVABLE`로 끝나 그때 ②가 간다.

### 참고

- 모든 상품이 `REFUNDED`가 된 주문을 주문 단위 `CANCELED`로 바꿀지는 주문 팀 판단이다.
- 주문의 배송비는 #342(PR #349)에서 실제 값이 들어가게 된다. 그 전까지는 0이라 배송비 환불·차감이 실제 금액을 갖지 않는다. 추가 운임(`remoteAreaFee`)은 지금도 실제 값이 들어간다.
- 같은 요청이 동시에 두 번 와서 반영 기록 유니크 제약에 걸리면 500이 아니라 성공으로 답해 주면 좋겠다.

### 테스트로 확인하면 좋은 것

- 같은 `refundId`로 ②를 두 번 보내도 `refundedQuantity`는 한 번만 늘어난다.
- 3개 중 1개 취소 후 남은 2개는 평소대로 배송 중 → 배송 완료 → 구매확정된다.
- 3개 모두 취소하면 `REFUNDED`가 되고 구매확정되지 않는다.
- 1개 취소 뒤 구매확정하면 2개 금액(20,000)이 이벤트로 나간다.
- ②에 `deductedShippingFee` 3,000이 온 묶음은 구매확정 때 배송비가 주문 시점 배송비 + 3,000으로 나간다.
- ② `REJECTED`, `WITHDRAWN`, `NOT_APPROVABLE`이 오면 `refundedQuantity`는 그대로고, 요청 때 바꾼 상태가 되돌아간다.
- 같은 `refundId`로 결과가 다른 ②가 오면 409가 난다.
