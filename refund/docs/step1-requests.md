# 환불 1단계 팀별 요청서 (의견 요청)

> 의견을 받기 위한 Draft PR용 파일이다. 머지하지 않는다.
> 환불 1단계(#323, 에픽 #322)에서 환불 모듈이 부를 API를 각 팀에 요청한다.
> 아래는 환불이 기대하는 **동작(약속)**이다. 내부 구현(테이블, 잠금 방법 등)과 URL·에러 코드 이름은 각 팀이 정하면 된다.
> 의견은 해당 줄에 리뷰 댓글로 남겨 주세요.

## 환불 1단계 흐름

```
1. 구매자: 주문 상세에서 환불 요청 (주문, 주문 상품, 개수)
2. 환불 → 주문: 환불용 조회 → "요청됨" 저장
3. 판매자: 승인 대기 목록 조회
4. 판매자 승인 → "처리 중"
5. 환불 → 배송: 취소 예약 (잠금)        ← 이미 출고면 "승인 불가"
6. 환불 → 지갑: 예치금 반환
7. 환불 → 주문: 취소 수량 반영
8. 환불 → 상품: 재고 일부 해제
9. 환불 → 배송: 취소 확정 (잠금 해제)
10. "완료"
```

**모든 API에 공통으로 부탁하는 것**

- 내부 HTTP API(`/internal/v1/...`)로 부른다.
- **같은 `refundId`로 두 번 와도 한 번만 처리하고 성공으로 답한다.** 응답이 사라져 다시 보내는 경우가 있다. 같은 `refundId`인데 내용(수량·금액)이 다르면 409로 막는다.

## 1. 배송: 취소 예약·확정 (#184 B9-3)

**① 취소 예약**

```
POST /internal/v1/delivery/cancel-reservations
{ "refundId": 7, "orderItemId": 101, "quantity": 1 }
```

- 예약이 걸린 동안 그 배송 건은 **송장을 등록할 수 없다**(지금 `CANCELLATION_RESERVED` 검사와 같은 동작).
- 송장 등록과 예약이 동시에 와도 **둘 중 하나만 성공**해야 한다.

| 응답 | 경우 | 환불이 하는 일 |
| --- | --- | --- |
| 200 | 예약됨 (또는 같은 예약이 이미 있음) | 다음 단계 진행 |
| 409 `INVALID_SHIPMENT_STATE` | 이미 송장 등록됨 | 승인 불가, 반품 안내 |
| 409 `CANCEL_QUANTITY_EXCEEDED` | 남은 수량보다 많음 | 승인 불가 |
| 404 | 주문 상품의 배송 건이 아직 없음 | "잠시 후 다시" |

**② 취소 확정 (잠금 해제)**

```
POST /internal/v1/delivery/cancel-reservations/{refundId}/confirm
```

- 예약한 수량을 취소 확정 수량으로 옮겨, 남은 상품은 다시 출고할 수 있게 한다.
- 그 배송 건의 상품이 **모두 취소되면 배송도 취소**(`CANCELLED`)한다.
- 응답: 200 확정됨(또는 이미 확정됨), 404 예약 기록 없음.

**예약 풀기 API는 필요 없다.** 판매자는 승인 뒤 거절할 수 없고, 환불은 "처리 중"으로 바꾼 뒤에 예약한다.

> **참고 (점검하면서 발견한 것)**
> - `ShipmentItem.cancel(int)`은 확정 수량만 늘리고 예약 수량은 줄이지 않는다. 확정에 그대로 쓰면 예약이 남아 송장 등록이 계속 막힌다.
> - `ShipmentRepository.findByIdForUpdate` 주석대로 잠금 조회를 첫 쿼리로 하지 않으면, 서로 다른 상품 확정이 동시에 올 때 "전부 취소"를 놓쳐 배송이 취소되지 않을 수 있다.
> - 배송이 취소될 때 대기 중인 배송지 변경 요청이 남으면, 판매자가 승인할 때 오류가 난다(송장 등록 때는 자동 거절함).

## 2. 상품: 재고 일부 해제

```
POST /internal/v1/products/stock-allocations/{orderId}/partial-release
{ "refundId": 7, "productOptionId": 55, "quantity": 1 }
```

- 주문 10의 옵션 55에서 **1개만** 재고를 되돌린다. 지금 `release(orderId)`는 주문 전체를 풀어서 쓸 수 없다.
- 응답: 204 해제됨(또는 이미 해제함), 404 배정 기록 없음, 409 배정 수량보다 많음.

> **참고 (점검하면서 발견한 것)**
> - 배정 기록의 상태는 조건부 UPDATE로만 바꾸게 되어 있다(`ProductStockAllocation.java:31`).
> - 일부 해제로 배정 수량이 0이 될 때 `RELEASED`로 바꾸면, `allocate()`가 "이미 해제한 주문"으로 판단한다(`ProductStockService.java:44`).

## 3. 주문: 환불용 조회·취소 수량 반영 (#28 관련)

**① 환불용 조회**

```
GET /internal/v1/orders/{orderId}/items/{orderItemId}
```

```json
{
  "orderId": 10, "orderItemId": 101,
  "buyerId": 1, "sellerId": 5,
  "productOptionId": 55,
  "productName": "양말", "optionName": "흰색",
  "status": "PREPARING",
  "unitPrice": 10000, "quantity": 3, "refundedQuantity": 1,
  "sellerGroup": {
    "shippingFee": 3000,
    "remoteAreaFee": 3000,
    "items": [
      { "orderItemId": 101, "quantity": 3 },
      { "orderItemId": 102, "quantity": 1 }
    ]
  }
}
```

- `sellerGroup`은 판매자 묶음이 전부 취소될 때 배송비와 추가 운임도 돌려주기 위해 필요하다.
- 응답: 200, 404 주문 또는 주문 상품 없음. 구매자 확인은 환불이 한다.

**② 취소 수량 반영**

```
POST /internal/v1/orders/items/{orderItemId}/refunds
{ "refundId": 7, "quantity": 1 }
```

- 취소된 수량을 기록한다. 주문 수량이 모두 취소되면 그 주문 상품은 `REFUNDED`가 된다.
- 응답: 성공, 404 주문 상품 없음, 409 취소 수량 합계가 주문 수량 초과.

**③ 구매확정 금액 조정**

- 구매확정 이벤트 금액에서 취소된 수량을 빼 주길 요청한다(`OrderService.java:205`의 TODO). 예: 3개 중 1개 취소 → 2개 금액 20,000원.

**#28 계획과 달라진 점**

| #28 원래 계획 | 바뀐 내용 | 이유 |
| --- | --- | --- |
| 환불 진행 수량 + 완료 수량 | 완료 수량만 | 승인 뒤에는 배송이 잠겨 처리 중에 구매확정될 일이 없음 |
| "환불 진행", "환불 완료" 이벤트 | ② 한 번 | 위와 같음. 지금은 HTTP |
| 주문이 "환불 가능 수량" 계산 | 값만 주고 환불이 계산 | 처리 중인 요청 수는 환불만 앎 |
| — | 요청 단계에서는 주문 상태를 바꾸지 않음 | 판매자가 요청을 무시하고 출고하면 `CANCEL_REQUESTED`가 배송 반영을 건너뛰어 멈춤 |

> **참고**
> - `CANCEL_REQUESTED`는 쓰이지 않게 된다. 남길지는 주문 팀 판단.
> - 주문 배송비는 지금 항상 0이다(`OrderSellerGroup.java:50` TODO). 배송비 계산이 붙어야 배송비 환불이 실제 금액을 갖는다.

## 4. 지갑: 예치금 반환 (#34 관련)

```
POST /internal/v1/wallets/refunds
{ "refundId": 7, "orderId": 10, "buyerId": 1, "sellerId": 5, "amount": 13000 }
```

- 구매자 지갑에 `amount`만큼 돌려준다. 금액은 환불이 계산해서 넘긴다.
- **근거 키는 `REFUND:{환불ID}`로 부탁한다.** 같은 상품을 여러 번 나눠 취소할 수 있어서, 주문 상품 ID를 키로 쓰면 두 번째 환불이 막힌다.
- 출고 전 취소라 판매자 지갑은 건드리지 않는다. `sellerId`는 기록용이다.
- 응답: 204 반환됨(또는 이미 반환함), 409 같은 근거 키로 금액이 다름, 422 금액 0 이하.

**#34 계획과 달라진 점**: "주문 취소 이벤트" 대신 환불 모듈이 HTTP로 요청하고, 주문 단위가 아니라 주문 상품·개수 단위로 여러 번 반환될 수 있다.

> **참고 (점검하면서 발견한 것)**
> - 충전 방식(기본 격리 수준)으로 중복을 확인하면, 같은 요청이 동시에 두 번 올 때 둘 다 통과하고 두 번째가 500이 된다. 결제(`payForOrder`)는 READ COMMITTED로 이 문제를 피한다.
> - 제안: 이용 내역에 환불도 보여 주기(지금은 숨김, `WalletLedgerService.java:30`), 결제 금액을 넘는 환불 막기(성공한 결제만 기준).
