# 설계 결정 기록(ADR) 작성

이슈 하나를 처리한 세션에서 "무엇을 왜 그렇게 정했는지"를 `docs/decisions/`에 남긴다. 다음에 같은 기능을 고칠 때 `session-context` 스킬로 불러와 AI에게 그 당시 맥락을 준다. 위치, 기록 기준, 머리말 필드, 작성 규칙의 기준은 `docs/decisions/README.md`이고 이 스킬은 절차만 다룬다.

## 먼저 알아둘 것

- **결정의 이유는 대화에만 있다.** 코드와 diff에는 없다. `/clear`나 `/compact`를 한 뒤에는 이유가 사라지므로, 결정이 오간 같은 세션에서 PR을 올리기 전이나 직후에 실행한다. 세션이 이미 비워졌다면 git 기록으로 알 수 있는 것만 쓰고 그 사실을 문서에 적는다.
- 이 스킬은 모든 PR에 쓰는 것이 아니다. README의 "무엇을 남기나" 기준에 해당하는 결정이 없으면 쓰지 말고 이유를 알린다.
- 문서는 작업 브랜치의 PR과 함께 리뷰된다. PR이 아직 없어도 쓸 수 있다.

## 절차

1. **작업 정보를 정한다.**
   ```bash
   git branch --show-current
   ```
   - 브랜치가 `main`이나 `dev`이거나 `<유형>/<이슈번호>` 형식이 아니면 멈추고 알린다. 이슈 번호는 이 이름에서 얻는다.
   - PR 번호는 인수로 받거나 `env -u GITHUB_TOKEN gh pr view --json number,title,baseRefName,url`로 찾는다. 기준 브랜치를 정하는 데만 쓰고 문서에는 적지 않는다.
   - 기준 브랜치는 PR이 있으면 `baseRefName`, 없으면 `dev`다. 먼저 `git fetch origin <기준 브랜치>`로 최신을 받는다(읽기만 하는 동작이다).
   - PR이 없는데 이 브랜치가 다른 작업 브랜치 위에 쌓인 경우(`git log --oneline origin/dev..HEAD`에 이 이슈가 아닌 커밋이 보인다)에는 부모 브랜치를 기준으로 쓸지 사용자에게 묻는다. 그대로 두면 부모의 변경이 이 문서의 근거에 섞인다.
2. **모듈을 정한다.**
   ```bash
   git diff --stat origin/<기준 브랜치>...HEAD
   ```
   - 변경 경로의 최상위 폴더 중 `settings.gradle.kts`의 모듈명과 같은 것이 후보다. 하나면 `module`이다.
   - 여러 개면 결정을 주도한 모듈 하나를 사용자에게 묻는다(`AskUserQuestion`). 나머지 모듈은 따로 적지 않는다. 질문할 수 없으면(`claude -p`) 변경이 가장 큰 모듈을 고르고 그렇게 골랐다고 알린다.
   - 모듈에 속하지 않는 구조·규칙·공통 결정은 `common`, 인프라·배포는 `infra`다.
3. **같은 이슈의 문서가 있는지 본다.**
   ```bash
   find docs/decisions -name '<이슈번호>-*.md'    # 없으면 아무것도 출력하지 않는다
   git cat-file -e origin/dev:docs/decisions/<모듈>/<파일> 2>/dev/null && echo "머지됨"
   ```
   - 없으면 새로 쓴다.
   - 있고 `origin/dev`에 없으면(이 PR에서 쓴 문서) 사용자에게 묻고 고친다.
   - `origin/dev`에 이미 있으면(머지된 문서) 고치지 않는다. 끝에 `## 후속 (YYYY-MM-DD)` 절만 덧붙인다.
4. **근거를 모은다.**
   ```bash
   git log origin/<기준 브랜치>..HEAD --format='%h %s'
   git diff --stat origin/<기준 브랜치>...HEAD
   ```
   "왜"는 이 대화에서 가져온다. 사용자가 정한 결정, 검토한 대안과 버린 이유, 고칠 때 다시 깨지기 쉬운 전제다. 남은 작업, 테스트 결과, 구현 중 겪은 일은 문서에 쓰지 않는다(README 참고).
5. **템플릿으로 쓴다.** `docs/decisions/TEMPLATE.md`를 복사해 채운다.
   - 머리말 필드의 형식과 상태 값, 작성 규칙(`(미확인)` 표시, 중복 금지, 100줄)은 `docs/decisions/README.md`가 기준이다. 여기서는 값만 정한다. `date`는 오늘이고, `paths`는 실제로 있는 경로인지 `ls`로 확인한다.
   - 이 대화에서 읽거나 돌려 본 것만 "확인했다"고 쓴다.
   - 템플릿의 주석은 지운다.
6. **저장한다.** `docs/decisions/<모듈>/<이슈번호>-<slug>.md`에 쓴다(모듈 폴더가 없으면 만든다). `slug`는 영문 소문자·숫자·하이픈 2~4단어다(예: `delivery-hexagonal`). 색인 파일은 만들지 않는다. 색인은 읽는 쪽이 `build-index.sh`로 그때그때 출력한다.
7. **민감정보를 점검한다.** Write·Edit로 쓸 때는 `.claude/hooks/scan-adr-before-write.sh` 훅이 쓰기 전에 한 번 검사해 걸리면 막는다. 이 단계는 훅이 못 보는 경우(Bash로 쓴 문서)와 저장된 파일 전체를 확인하려고 유지한다.
   ```bash
   bash .claude/skills/session-summary/scan-sensitive.sh docs/decisions/<모듈>/<이슈번호>-<slug>.md
   ```
   종료 코드가 1이면 줄 번호와 종류가 출력된다. 그 줄을 지우거나 일반화하고(파일 경로와 이름으로 가리키고 값은 옮기지 않는다) 통과할 때까지 다시 돌린다. 스크립트가 못 잡는 것(개인정보, 내부 시스템의 구체적인 이름)은 직접 읽어 확인한다.
8. **사용자에게 확인받는다.** 저장한 파일 경로, `(미확인)` 항목 목록, 민감정보 점검 결과, 코드 저장소 이력에 남는다는 점을 보여주고 커밋해도 되는지 **명시적 승인**을 받는다. 승인 전에는 커밋하지 않는다. 이 결정이 앞으로 모든 작업에 적용되는지(규칙으로 올릴 후보인지)도 한 줄로 알린다. 올리려면 `docs/CONVENTION.md` 원문을 먼저 고쳐야 하고, 이 스킬은 규칙 파일을 고치지 않는다.
9. **승인 후 커밋한다.** 현재 작업 브랜치에 문서 파일만 커밋한다. 형식은 `commit` 스킬을 따른다.
   ```bash
   git add docs/decisions/<모듈>/<이슈번호>-<slug>.md
   git commit -m "Docs: <제목> 결정 기록 추가" -m "- <이 문서가 담은 결정과 이유 한두 줄>" -m "Ref: #<이슈번호>"
   ```
   - 파일을 이름으로 지정해 `git add`한다(`git add -A` 금지). 커밋 메시지는 한글이고 AI 표기를 넣지 않는다.
   - push와 PR 생성은 하지 않는다. 사용자가 요청하면 `pr` 스킬 절차를 따른다.
10. **마무리한다.** PR 본문의 `💬 참고 사항`에 넣을 ADR 줄을 알려준다.
    ```
    - 설계 기록(ADR): `docs/decisions/<모듈>/<이슈번호>-<slug>.md`
    ```
    저장소 경로만 쓰고 브랜치 기준 GitHub 주소는 쓰지 않는다. 머지 후 브랜치를 지우면 그 주소가 열리지 않는다(`docs/decisions/README.md`의 "PR에서 연결하기"). PR 본문은 사용자가 요청하기 전에는 고치지 않는다.
## 쓰지 않는 것

- 작성자, 머지 커밋, 기능 태그, 파일 목록은 머리말에 넣지 않는다. 리팩터링으로 바뀌거나 작성 시점에 알 수 없다.
- 머지된 문서를 고치지 않는다. 틀린 내용은 `## 후속`으로 정정한다. 결정이 통째로 바뀌면 이전 문서의 `status`만 `대체됨(이슈번호)`로 바꾸고 새 문서를 쓴다.
