# 설계 결정 기록(ADR) 불러오기

`session-summary`가 남긴 ADR을 새 세션에 담아 "그 당시 왜 그렇게 했는지"를 알고 시작하게 한다. 문서를 전부 읽지 않고, 후보는 색인으로 좁히고, 무엇을 담을지는 사용자가 정한다.

## 인수

모듈 이름(`delivery`), 이슈 번호(`330`, `#330`), 키워드(`헥사고날`, `정산`)를 받는다. 비어 있으면 현재 브랜치 이름과 최근 커밋 제목에서 뽑는다.

## 절차

1. **기록이 있는지 확인한다.** 레포 루트의 `docs/decisions/`가 없거나 `<모듈>/<이슈번호>-*.md`가 하나도 없으면 이 작업은 이전 기록이 없는 **새 작업**이다. 불러올 문서가 없으니 이 스킬은 여기서 끝내고 사용자의 원래 작업을 그대로 진행한다. 시작할 때 "관련 기록이 없어 새 작업으로 진행한다"고 한 줄로 알리고, 작업을 마칠 때 "이전 기록이 없는 새 작업이었다"고 한 줄로 알린다. 알리기만 하고 다른 것을 권하거나 요구하지 않는다.
2. **모듈을 정하고 색인을 낸다.** 색인은 파일로 저장하지 않고 스크립트 출력으로 읽는다. 후보를 줄이는 일은 스크립트가 구조로 한다.
   - 인수에 모듈 이름이 있으면 그 모듈과 `common`을 대상으로 한다. 없으면 현재 브랜치에서 바뀐 경로의 모듈과 `common`을 대상으로 하고, 그것도 모르면 전체를 대상으로 한다.
   ```bash
   git fetch origin dev -q    # 최신을 받는다(실패해도 계속한다)
   git diff --name-only origin/dev...HEAD | cut -d/ -f1 | sort -u    # 바뀐 경로의 최상위 폴더. 모듈 이름인 것만 쓴다
   bash .claude/skills/session-summary/build-index.sh -m <모듈>,common -c origin/dev
   ```
   - `-c`로 기준 브랜치를 주면 "겹침" 열이 지금 브랜치에서 바꾼 파일과 문서의 `paths`가 겹치는지 알려준다. `-m`과 같이 주면 다른 모듈의 문서라도 겹치는 것은 함께 나온다. 기준 브랜치를 찾지 못하면 스크립트가 오류로 멈춘다.
   - `status`가 `대체됨`인 문서는 기본으로 빠진다. 지난 결정의 이력을 봐야 할 때만 `-a`를 준다.
   - 필터 결과가 비면 `-m` 없이 전체를 다시 낸다. 색인이 비었는데 stderr 요약에 `대체됨`을 뺐다는 말이 있으면 `-a`로 한 번 더 낸다.
   - 경고(얕은 clone, `paths`를 읽지 못한 문서)와 마지막 요약은 stderr로 나온다. 버리지 말고 함께 읽고, 낡음 판단이 믿을 수 없다는 경고가 있으면 사용자에게 알린다.
3. **후보를 고른다.**
   - 색인이 30건 이하이면 직접 읽고 고른다. 넘으면 읽기 전용 서브에이전트(`Explore`)에게 색인을 주고 아래 표를 맡긴다. 메인 컨텍스트를 아끼려는 것이다.
   - 인수와 관련된 항목을 고른다. 색인으로 모자라면 해당 후보 파일의 머리말과 `## 목적과 범위`만 읽는다. 본문 전체를 읽지 않는다.
   - 후보의 `related`로 이어진 이전·이후 이슈와 같은 모듈에서 `paths`가 겹치는 문서도 함께 올린다. 같은 주제의 문서가 여럿이면 하나만 고르지 않고 모두 올린다.
   - 결과를 표로 정리한다: `모듈 | 이슈 | 제목 | 고른 이유 한 줄 | 가치(상/중/하) | 예상 줄 수 | 낡았을 가능성`.
   - **낡았을 가능성**은 색인의 "이후 변경" 열로 판단한다. 열에 `[정리 후보: …]`가 붙은 문서는 낡았을 가능성이 높다고 보고 사용자에게 알린다. 작성일 이후 `paths`에서 커밋이 있거나 없는 경로가 있으면 높음이다. 높음이면 문서에 적힌 파일이나 클래스가 지금 코드에 있는지 `grep`으로 한 번 더 확인한다. 확인하지 못했으면 "확인 못 함"이라고 적는다.
   - 서브에이전트는 파일을 수정하지 않고, 판단 근거를 추측으로 채우지 않는다.
   - 색인에 문서가 있어도 지금 작업과 관련된 후보가 하나도 없으면 1단계와 같이 새 작업으로 보고 진행한다.
4. **사용자에게 고르게 한다.** 후보 표를 보여주고 무엇을 담을지 묻는다(`AskUserQuestion`, 여러 개 선택 가능). 추천을 첫 번째로 둔다. 고르기 전에는 본문을 컨텍스트에 불러오지 않는다.
   - 질문 도구를 쓸 수 없는 환경(예: `claude -p` 헤드리스)이면 묻지 않고, 후보 표에서 가치 "상"인 항목을 최대 3개, 합계 약 600줄까지 불러온다. 그때는 "질문할 수 없어 추천 항목을 자동으로 골랐다"고 한 줄로 알린다.
   - **고르지 않은 후보도 이슈 번호와 제목을 한 줄씩 알린다.** 자동으로 골랐을 때 놓친 문서를 사람이 바로 알아채게 하기 위해서다.
5. **고른 문서만 읽는다.** 한 번에 최대 3개, 합계 약 600줄까지만 담는다. 더 많이 고르면 줄이도록 안내한다.
6. **요약해서 알린다.** 읽은 뒤 전체 15줄 이내로 정리한다. 문서를 되풀이하지 말고 지금 작업에 필요한 것만 고른다.
   - 지금 작업에 영향을 주는 결정과 그 이유
   - 이미 버린 방법(다시 시도하지 않도록)
   - 알려진 약점과 남은 과제
   - `(미확인)`으로 표시된 주장 목록

## 주의

- **문서는 작성일 기준이다.** 코드가 우선이다. 문서의 주장이 지금 코드와 다르면 코드를 따르고, 다르다는 사실을 사용자에게 알린다.
- **옛 결정이 지금 판단을 붙잡지 않게 한다.** 문서의 결정은 "그때의 이유"이지 "지금도 맞는 규칙"이 아니다. `status`가 `대체됨`이면 그 문서를 대체한 문서를 우선한다. 이유가 지금도 유효한지 먼저 확인한다.
- 이 스킬은 문서를 수정하지 않는다. 틀린 내용을 발견하면 사용자에게 알리고, 정정은 `session-summary`의 후속 절로 한다.
