# 사람 정답 매기기 지침

분류 기준은 [`criteria/criteria.json`](../criteria/criteria.json)이다. 모델에 주는 질문과 같은 문서를 보고 매긴다. 이 지침에는 입력 방법과 절차만 쓴다.

## 지켜야 할 것

- **모델 결과를 보기 전에 매긴다.** 평가용 300개는 정답을 다 매긴 뒤에 모델에 돌린다.
- 두 명이 매기면 서로의 시트를 보지 않는다. 다른 칸만 나중에 논의한다.
- 생성 데이터의 태그(`data/reviews.jsonl`의 `tags`, `hardCase`)를 보지 않는다. 의도된 답에 끌려간다.
- 별점은 없다. 본문만 보고 판단한다.

## 입력 코드

| 코드 | 뜻 | 쓰는 칸 |
|---|---|---|
| `p` | 긍정 | 전체, 항목 |
| `n` | 부정 | 전체, 항목 |
| `o` | 중립 | 전체, 항목 |
| `m` | 혼합 | 전체, 항목 |
| `-` | 언급 없음 | 항목만 |
| `?` | 판단 불가 | 전체, 항목 |

- 판단 불가는 언급은 있는데 감성을 정할 수 없을 때만 쓴다. 언급이 없으면 `-`다. 모델 선택지에는 없고, 품질 지표에서 빼고 개수만 보고한다.
- 헷갈린 칸은 `note`에 이유를 짧게 적는다. 명세를 다듬을 때 이 메모를 본다.
- 스프레드시트에서 `-`가 수식으로 바뀌면 `'-`로 입력한다.

## 판정 요약표 (분류 기준 v0.2)

매길 때 옆에 둔다. 원본은 `criteria.json`이고, 기준이 바뀌면 이 표도 함께 고친다.

**어느 항목인가**

| 리뷰 표현 | 매기는 항목 | 매기지 않는 항목 |
|---|---|---|
| 무름, 곰팡이, 시듦, 쉰내, 짓물러 즙이 흐름 | 신선도 | 상품 상태 |
| 멍, 찍힘, 터짐, 깨짐 | 상품 상태 | 신선도 |
| "물러서 터졌어요" (변질과 손상이 둘 다 쓰임) | 신선도, 상품 상태 | |
| 크기, 양, 외관, 사진과 다름 | 상품 상태 | 가격 (가격을 함께 말할 때만 가격도) |
| 당도, 식감, 향, 푸석함, 속이 마름 | 맛 | 신선도 |
| 박스 찌그러짐, 완충재, 밀봉 | 포장 | 배송 |
| 손상의 원인이 포장이라고 쓰임 | 포장, 상품 상태 | |
| 원인 없이 "멍들었어요" | 상품 상태 | 포장 |
| 늦게 와서 상함 | 배송, 신선도 | |
| 배송 속도, 일정, 배송 기사 응대 | 배송 | |
| 가공품 유통기한 | 신선도 | |
| 판매자 응대, 손편지·서비스 동봉 | 전체 감성에만 | 여섯 항목 모두 |
| 맛·품질 칭찬 | 맛 (품질은 전체 감성에만) | 상품 상태 |

**어떤 감성인가**

| 상황 | 판정 |
|---|---|
| 결론(재구매, 추천, 비추천, "재구매는 안 할 것 같아요")이 있음 | 결론을 따른다. 항목 안의 결론도 같다("비싸지만 아깝지 않아요"는 가격 긍정) |
| 결론 없이 상품 자체와 배송·포장 평가가 갈림 | 상품 자체를 따른다("맛 최고인데 배송 늦음"은 전체 긍정) |
| 결론 없이 상품 자체에 좋은 말과 나쁜 말이 함께 | 혼합 |
| "나쁘지 않아요", "괜찮은 편" | 긍정 |
| "그냥 그래요", "무난해요", "보통이에요" | 중립 |
| 사실만 적음("배송 3일 걸림", "색이 진한 편") | 중립 |
| 평가를 미룸("아직 안 먹어봄") | 전체 중립 |
| "물렁물렁해요"처럼 잘 익음과 무름이 구분 안 됨 | 불만 표현("너무", "상한 듯")이 있을 때만 신선도 부정, 없으면 중립 |
| 반어("배송 참 빠르네요^^ 일주일 걸림") | 부정 |

## 순서

1. `node dataset/make-sheets.ts <이름>`으로 시트를 만든다(`data/labels/<이름>/tuning.csv`, `eval.csv`).
2. **조정용 100개**를 먼저 매긴다.
3. 조정용으로 명세를 점검한다. `node dataset/probe-prompt.ts`로 질문지를 만들어 회사가 다른 고급 모델 두 개에 넣고, 답을 `data/probe/<모델>.jsonl`로 저장한 뒤 `node dataset/probe-compare.ts`로 사람 답과 다른 칸을 모은다. 두 모델이 함께 다르게 고른 칸부터 보고, 명세가 애매했던 곳은 `criteria.json`을 고치고 버전을 올린다. 바꾼 이유는 `criteria/CHANGELOG.md`에 적는다. 모델은 정답을 정하는 데 쓰지 않는다.
4. 명세를 고친 뒤 **평가용 300개**를 매긴다. 위 판정 요약표를 옆에 둔다. 평가용을 매기기 시작한 뒤에는 명세를 고치지 않는다. 고치면 이미 매긴 정답과 기준이 어긋난다. 다 매긴 뒤 처음 30개쯤을 다시 훑어, 매기는 동안 기준이 흔들리지 않았는지 본다.
5. `node dataset/check-sheet.ts data/labels/<이름>/eval.csv`로 빈칸과 잘못된 코드를 찾는다.
6. 일치도를 낸다.
   - 두 명: `node dataset/agreement.ts data/labels/<A>/eval.csv data/labels/<B>/eval.csv eval`
   - 혼자: 1주 뒤 `node dataset/make-sheets.ts <이름>-recheck`로 50개 시트를 만들어 다시 매기고(이전 시트를 보지 않는다) `node dataset/agreement.ts data/labels/<이름>/eval.csv data/labels/<이름>-recheck/eval.csv eval-self`
7. 정답 파일을 만든다.
   - 두 명: `-disagreements.csv`의 다른 칸을 논의해 `-gold-draft.csv`의 `a|b` 칸을 고친다. `check-sheet.ts`를 통과하면 `data/labels/gold-eval.csv`로 저장한다. agreement를 다시 돌려도 고친 초안은 덮어쓰지 않는다(`--force`를 줄 때만 덮어쓴다).
   - 혼자: 처음 매긴 `data/labels/<이름>/eval.csv` 300행 전체가 정답이다. 다시 매긴 50개는 κ를 내는 데만 쓴다. 그대로 `data/labels/gold-eval.csv`로 복사한다.
8. κ는 항목마다 둘로 나온다. 언급 여부 κ(언급 없음 대 나머지)와, 두 사람이 모두 언급한 칸의 감성 κ다. 둘 중 하나라도 0.6 미만이면 그 항목의 명세를 먼저 고치고 다시 매긴다. 언급 없음까지 한꺼번에 섞어 κ를 내면 감성 판단이 엇갈려도 높게 나와서 나눠 본다. 감성 κ 옆의 n이 작으면(예: 20 미만) 몇 칸에 크게 흔들리므로 숫자와 함께 n을 보고한다.
9. κ를 보고 채택 기준 숫자를 한 번만 조정해 고정한다. 모델 결과를 보기 전에 한다.

## 다시 매길 50개

`-recheck` 시트에는 반복 실행용으로 미리 고른 평가용 50개(`repeatRun: true`)가 들어간다. 세트를 나눌 때 시드로 골랐다.
